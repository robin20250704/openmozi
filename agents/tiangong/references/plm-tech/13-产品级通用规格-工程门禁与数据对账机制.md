# 13 · 产品级通用规格：工程门禁与数据对账机制

> **来源**：批次 G（REQ-2026-0844/0845/0772）实战沉淀 + 用户口径逐条裁定（2026-09-12：「①建议存在性对账而不是硬 FK ②建立 CI 机制 ③去除陈旧断言」）。原始证据见 `.creature/tasks/plm-self87-req/report-batch-g-0844-0845-0772.md` 及其附录 A。
> **定位**：把"如何证明产品是好的、如何证明数据是好的"从**个人习惯**提升为**产品级机制**——CI 分层门禁是"每次改动都必须过机器判据"的纪律，存在性对账是"数据与契约之间必须有对账机制"的纪律。
> **分层关系**：12 号文（评审机制与列表范式）描述**功能语义层**的产品级规格（G-REV/G-LST/G-API）；本文描述**工程机制层**的产品级规格（G-CI/G-REC）。
> 语义冲突时以本文（含用户口径）为准；实现细节以 `ipd/deploy/wsl/plm-app/` 与 `.creature/kb/contracts.md` 为准。
> **贯穿全文的一条元纪律**：**「没跑」不等于「通过」；「检查执行失败」不等于「检查通过」；「断言恒真」等于「没有断言」。** 三条都属于同一类失败——**假绿**，比"没有断言"更危险，因为它训练人忽略门控输出。

## 1. 抽取判据与编号

一条内容进入本文，须至少命中其一：

| 判据 | 例证 |
|---|---|
| **语义级**：用户口径确认的工程纪律，不依赖具体模块 | 「没跑 ≠ 通过」（MISSING 与 FAIL 分列）、「对账为主而非硬 FK」、「例外必须点名并会自动催清理」 |
| **结构级**：可在任意模块/任意域原样复用的机制 | 分层 CI 入口、断言特征串自校验、迁移编号巡检、逻辑引用登记表与对账器 |
| **缺陷级**：跨批重复出现的缺陷模式，须机械化堵住 | 断言引用源码中不存在的文案（0466 长期假 FAIL）、按占位符判据造成的假失败（分页上限）、UI 走查互相打断、恒真断言导致失败点漂移、按列名猜引用关系 |

编号：**G-CI-***（工程门禁）/ **G-REC-***（数据对账）/ **G-DATA-***（存量数据处置）。每条规格含：规格正文、依据、**验收断言**（新域/新批次接入照抄断言，不允许"参照实现即可"）。

## 2. 工程门禁通用规格（G-CI）

### G-CI-1 分层 CI 入口（唯一入口，按依赖分层）

**规格**：产品必须有**唯一的** CI 入口脚本，并按"**依赖什么**"分层——不是按"重要程度"分层。

| 层 | 内容 | 依赖 | 何时必须跑 |
|---|---|---|---|
| **T1 静态** | 后端编译 ＋ 前端类型检查 ＋ **断言特征串自校验**（G-CI-3）＋ 迁移编号巡检（G-CI-4） | 无（任何机器/托管 runner） | 每次提交 |
| **T2 单测** | 后端全量 JUnit（严格模式先重建测试库） | docker（plm-pg） | 每次提交 |
| **T3 运行态** | 端到端聚合验收 ＋ 真浏览器 UI 走查 | **已部署**且健康的服务 ＋ Windows Chrome | 每次部署后 / 发布前 |
| **T4 巡检** | 数据不变量 ＋ 库口径对账 ＋ 逻辑引用对账（G-REC）＋ 覆盖率 | 已部署服务 | 每次部署后 / 每日 |

**四条纪律**：

1. **「没跑」必须显式显示为未跑**（`MISSING`），与 `FAIL` **分开计数**；汇总行机器可读：`CI_RESULT=PASS|PARTIAL|FAIL`（`PARTIAL` = 有层未跑）。
2. **不得为跑不了的层伪造"通过"**：托管 runner 不具备 T3/T4 环境时，工作流只声明跑 T1/T2，报告里 T3/T4 显示为未跑（本产品 `.github/workflows/ipd-plm-ci.yml` 即此口径）。
3. **层内子项判据一律取"子项自己打印的 `PASS=n FAIL=n`"**，不取退出码——退出码只说"有没有失败"，说不出"验了多少条"，而"验了 0 条"与"验了 28 条"必须能区分。
4. **门控脚本之间不得互相干扰**：脚本若使用全局互斥资源（浏览器实例、固定端口、单实例服务），必须**隔离资源**（各用各的端口/实例）或**加原子锁并在拿不到锁时显式失败**（退出码非 0），**不得"抢不到就凑合跑"**（否则产出随机假失败，见 §5 缺陷 3）。

**依据**：批次 G 的 240+ 个 PLM 脚本此前**无统一入口、无分层**——"跑哪些、跑多深"全靠人记；只跑编译则改动没被任何断言覆盖也全绿；全跑运行态则换台机器就跑不起来（无法进流水线）。

**验收断言**：
- A1 `CI_RESULT` 取值与所选层一致：未选层出现在"未跑"清单而非"通过"清单；
- A2 任一层失败时汇总行 `CI_RESULT=FAIL`，且明细里逐项给出失败子项的 `PASS/FAIL` 数字；
- A3 在**没有部署服务**的机器上跑 T1/T2 可全绿，且 T3/T4 显示为 `MISSING`（不是 FAIL、更不是 OK）。

### G-CI-2 质量门三层（构建态 / 一致性 / 运行态）

**规格**：任何一条需求的验收证据必须覆盖三层，**三层缺一不可**：

| 层 | 含义 | 判据形态 |
|---|---|---|
| **构建态** | 代码能编译、类型正确、单测全绿、迁移可执行 | `MVN_COMPILE_EXIT=0`、`TSC_EXIT=0`、`Tests run: N, Failures: 0, Errors: 0` |
| **一致性** | 契约/元数据/权限/审计在各处口径一致 | 审计链自校验、权限一致性启动校验、枚举值域与库同源、迁移终态版本一致 |
| **运行态** | **部署到位**后的端到端断言（用户路径） | 端到端脚本 `PASS/FAIL` 数字 ＋ 真浏览器 UI 走查 |

**纪律**：
- **"代码能编译"不构成交付**：需求现场若是"界面/接口对外表现不对"，则运行态断言是交付判据的必要组成。
- **回归必须整体跑**：新增判据要**注册进聚合台**，否则"新增的断言"不影响交付结论（本产品聚合台：`plm-batch-e-accept.sh` 及各批次聚合脚本）。
- **每条"应当为 0 / 应当为 N"的判据必须配负向对照**：先证明"该检查能发现违规"，再声明"当前为 0"。没有负向对照的判据可能因 SQL/选择器写错而**空转通过**（G-REC-3 的自检即此纪律的实例化）。

### G-CI-3 断言特征串自校验（防「假 FAIL」，必须门控）

**规格**：凡断言以"**界面/接口文案**"为特征（"只有新功能存在时才会出现的串"），该特征串**必须**由机器核对"它确实存在于被检产物中"，且该校验**必须进 T1 门控**。

**四条纪律**：

1. **核对清单必须从断言脚本自动抽取**，禁止"另抄一份硬编码数组"——两份清单必然漂移，且抄的那份通常只覆盖一部分（本产品实测：硬编码清单列 16 条、断言脚本实际 28 条 ⇒ **漏掉的 12 条从未被校验**，其中两条长期假 FAIL）。
2. **抽取数 = 0 必须判失败**（抽取逻辑失效比缺文案更危险：全绿但什么都没校验）。
3. 报错要**区分两种失败**：`MISSING-SRC`（源码根本没有这条文案 ⇒ 断言写错或功能未接线）与 `MISSING-IMG`（源码有、运行中的镜像没有 ⇒ 产物/镜像陈旧）。二者处置完全不同。
4. 若断言的本意是"某段**实现语义**存在"（如"只提交改动字段"这类**代码注释里的设计措辞**），则**不得**拿它当界面文案断言——必须换成**真正由该功能产生的用户可见文案**（本产品实例：用「没有检测到改动」这一"无改动即不发请求"的提示，作为 PATCH 语义的直接证据）。

**依据**：0466 的两条断言长期报红，根因是**断言引用了只存在于代码注释里的措辞**；而"长期报红"直接导致门控可信度下降（"狼来了"），是**假绿的前置条件**。

**验收断言**：
- A1 T1 层输出 `NEEDLE_CHECK PASS=n FAIL=0`，且 `n` 等于断言脚本中 `check '<串>' '<标签>'` 形态的条数（抽取不漏不多）；
- A2 人为把某条特征串改成源码中不存在的文案 ⇒ T1 立即 FAIL 并指明是哪一条与它的标签；
- A3 断言脚本新增一条文案断言时**不需要**改动校验脚本（自动抽取生效）。

### G-CI-4 迁移编号巡检（启动期才暴露的问题必须提前拦）

**规格**：Flyway 的编号类问题（重复版本、非法命名、版本段非数字）**在服务启动时才报**，等价于生产不可用；因此必须由 T1 静态层提前拦截：

1. 命名形态必须是 `V<数字>__<描述>.sql`；
2. 版本号**不得重复**（重复会在启动期抛 duplicate version）；
3. 版本段必须可解析为整数；
4. **磁盘最大版本 必须等于 `flyway_schema_history` 最大成功版本**——不一致的两种含义都要报警并给处置方向：
   - 磁盘更大 ⇒ 迁移写了但**没在目标库执行**（部署未跟上代码）；
   - 库更大 ⇒ **库里有磁盘上已不存在的迁移**（不可回滚，必须查明来源）。

**依据**：本产品每批都在新增迁移（当前 104 个脚本 / V108），"写了迁移没跑"与"库里多出未知迁移"都属于**静默漂移**。

## 3. 数据对账通用规格（G-REC）

### G-REC-0 总则：数据与契约之间必须有对账机制

**规格**：凡"**契约（规格/元数据/枚举/引用关系）**"与"**库中数据**"之间存在一致性的要求，就必须有一条**机器可跑的对账判据**。只修代码、不加对账的后果是：同类漂移下一次依旧只能靠**用户报障**发现。

**依据（批次 G 三类问题的共同点）**：
- REQ-2026-0844：`REQ.sourceType` 登记值域 5 值，而库里有 **42 行越界值**（写入侧从不校验）；
- REQ-2026-0845：**75 行业务计划书的 `project_id` 全部为 NULL**（写入侧不填归属）；
- REQ-2026-0772：`t_req_trace` 的唯一键曾因"删后插"的执行序被绕过。

三者**都不是"代码写错"**，而是"**没有对账**"。

**对账的三种形态（按成本从低到高选用）**：

| 形态 | 载体 | 适用 |
|---|---|---|
| 白名单断言 | 单测（跑在测试库/全新库上） | 少量关键列/关键表的结构性不变量（枚举越界、未绑定、唯一键重复、审计链、迁移终态） |
| 登记表驱动对账 | 独立脚本（跑在部署库上） | 全库、跨表的引用完整性（G-REC-1）；**默认选它** |
| 启动期自校验 | 应用启动时（如权限一致性 `PERM_CONSISTENCY`） | 违反即"不该服务"的硬约束，启动失败优于带病运行 |

### G-REC-1 逻辑引用登记表 + 全库对账（**不是**硬外键）

**规格**：本产品**不为业务引用新增数据库外键**（用户 2026-09-12 裁定；与 ADR-6「不设双权威」同源）。业务引用一律由 **登记表 + 对账器** 守护：

1. **登记表是唯一权威**：每一列"逻辑引用"（`*_id` 形态但无 DB FK）必须逐条登记，声明**目标表.列**，或**显式声明"不判"并给出理由与实测证据**（多态引用 / 外部系统 id / WORM 台账 / 聚合编码）。
2. **对账器**从登记表生成检查并输出**悬空报告**；**禁止按列名猜目标表**（见 §5 缺陷 1）。
3. **覆盖率自查**：把"登记表"与"库中实际存在的无 FK `*_id` 列"求差集——**差集不为 0 即失败**（有列没被登记 = 对账漏网）。新增任何此类列**必须同时登记**。
4. **类型安全比较**：跨类型比较（`text` ↔ `bigint`、`text` ↔ `uuid`）一律"**先正则过滤再转换**"，禁止裸 `::bigint`/`::uuid`（PG 不保证求值顺序，脏值会直接抛错，见 ADR/C-072）。
5. **SQL 执行失败一律判 FAIL**，绝不当作"零悬空"（否则一次类型/拼接错误就变成假绿——本产品实测在一条 union 上连栽四次，全靠这条判据拦住）。

**为什么不用硬 FK（必须写清，避免后人"顺手加个约束"）**：

| 维度 | 事实 | 结论 |
|---|---|---|
| 故障源 | 悬空引用的成因是**绕开应用直删数据 / 脚本清理**（应用侧根本没有删该对象的通道） | FK 拦不住设想的那个故障 |
| `ON DELETE RESTRICT` | 清理会被 DB 挡住 ⇒ 问题从"待处理"变成"无法处理"，运维会再 `DROP CONSTRAINT` 绕过 | 把可管理的问题变成不可管理 |
| `ON DELETE SET NULL` | 被引用对象删除时绑定被抹成 NULL ⇒ **"曾绑定哪一次 X"的历史证据消失** | 与 WORM / 可追溯直接冲突 |
| 覆盖面 | 本产品有 **60 个**无 FK 的逻辑引用列 | 加一列只治一列 |
| 架构 | ADR-6 已确立"不设双权威" | 加 FK 属背向既有 ADR |

**验收断言**：
- A1 对账输出 `REF_INTEGRITY=PASS`，且报告里同时给出"可判条数 / 显式不判条数 / 悬空条数 / 未登记条数"；
- A2 覆盖率自查 `REF_COVERAGE=PASS`（登记条数 = 库中无 FK 引用列条数）；
- A3 **自检有效**：注入一条"必然悬空"的映射后对账**必须报出悬空**（证明判据非空转），此为 PASS 的前置条件；
- A4 临时新增一个无 FK 的 `*_id` 列而未登记 ⇒ 覆盖率自查 FAIL。

### G-REC-2 已知例外基线（点名放行，且会自动催清理）

**规格**：对账一旦发现**已知且已被确认**的悬空，**不得**把该列改成"不判"（那是永久失明），而必须进**例外基线**：

1. 基线条目 = `表 列 + 理由 + 处置结论`；对账时打印为 `[基线内·已知]`，不计失败；
2. **基线之外**的悬空一律 FAIL（新问题不得被掩盖）；
3. **基线里的项不再悬空**同样 FAIL ⇒ 逼人清理例外，防止"临时豁免"变成永久豁免。

**依据**：例外必须有生命周期。与"登记表写 `-`（不判）"的区别：**不判 = 永久失明；基线 = 点名放行 + 自动催清理**。

### G-REC-3 防空转：负向对照 / 自检是判据的一部分

**规格**：任何"应当为 0 / 应当为 N"的对账与不变量判据，**必须**包含以下之一，否则不得作为门控：

| 手段 | 做法 | 反例（本产品实际踩过） |
|---|---|---|
| **负向对照** | 在同一判据内先插入一条违规数据，断言"计数 +1"，再删除并断言回到原值 | `INV-1` 枚举越界检查：先插一条越界行证明"检查能发现它" |
| **自检入口** | 提供 `--selftest`，用"必然悬空"的映射跑**同一套生成逻辑**，要求报出悬空 | `plm-ref-integrity.sh --selftest`（交叉比对一个不可能命中的列） |
| **参照集反证** | 过滤类断言需证明"参照集里存在违反该条件的行"（否则判据无区分度） | 静默参数排查：分页上限使两侧条数相同造成 4 条假失败 |

**纪律**：判据若无法区分"通过"与"数据恰好干净/参数恰好相同"，必须在输出里**显式标注"本判据无区分度"或"SKIP（数据缺失，非放行）"**，不得静默计入 PASS。

### G-REC-4 列入对账的对象（用登记的"不判"清单反推）

**规格**：以下类别**必须**被显式登记（可选择"不判"，但理由与证据必须落地）：

| 类别 | 例 | 判据 |
|---|---|---|
| 跨域业务引用 | 计划书版本 ↔ DCP 评审、任务书 ↔ 项目、需求 ↔ 项目 | 判悬空 |
| 质量链引用 | CAPA ↔ 投诉/召回/变更、注册 ↔ 资料卷 | 判悬空 |
| 多态引用 | `obj_id`/`target_id`/`ref_id`（按 `obj_type` 指向不同表） | **不判**（需按类型分支，未实现前必须写明） |
| 外部系统 id | `pms_project_id`、`op_version_id`、`decide_wf_id` | 不判（非本库表） |
| 弱引用/WORM 台账 | `t_audit_log.object_id`（指向已删对象的**审计历史**是设计要求）、`t_event.aggregate_id`（聚合编码）、搜索索引 | 不判 |
| 列名相似但**无引用关系** | `t_inbox.event_id`(uuid) 与 `t_event.id`(bigint) 完全不同 id 空间 | **不判，且必须写明"实测反例"**（见 §5 缺陷 1） |

## 4. 存量数据处置通用规格（G-DATA）

### G-DATA-1 存量归一：走应用侧（保留 WORM 审计），不走迁移脚本裸 SQL

**规格**：修改**受控记录**的字段值时：

1. **逐行写审计**（`before` / `after` / `原因` / `actor=system:legacy-repair`）——受控记录的字段变更必须能回答"原值是什么"；
2. **不得在 Flyway 迁移里手写审计哈希链**：`t_audit_log` 是 WORM 哈希链，手写极易产出**断裂的链**（那一刻起自校验恒为 false），必须走既有 `AuditService.record`；
3. 归一目标值必须**先确认为合法值**（否则归一后的行自己会被写入侧拒绝）；
4. **一次性修复必须可重复执行（幂等）**，并**用第二次执行 NOOP 作为幂等自证**。

**依据**：REQ-2026-0844 的 14 行越界值归一，第一次执行归一 14 行、第二次输出 `[LEGACY-REPAIR/0844] NOOP`。

### G-DATA-2 删除类操作：删前备份 + 逐行安全前置 + 实际删除数作为断言

**规格**：删除存量数据（清理、归并、去重）必须同时满足四条：

1. **删前落盘备份**（可回灌的 INSERT 脚本），并在交付物中给出路径；
2. **逐行安全前置校验**：任一"仍被引用"命中即**跳过并告警**，保留而不误删；
3. **"存在引用"必须区分真实引用与悬空引用**：`col IS NOT NULL` **不构成**"在用"的证据——必须用 `EXISTS (SELECT 1 FROM 目标表 …)` 判定（本产品实测：首版判据把 28 行的**悬空** `bound_review_id` 当成"仍在用"，导致"清理 0 行、跳过 28 行"且脚本退出 0）；
4. **把"实际删除数"作为断言**：脚本必须打印"清理 N 行 / 跳过 M 行"，且 **N=0 而 M>0 需人工复核判据**——否则删除任务会"看起来成功、实际零产出"。

**补充**：被删对象的 WORM 事件**保留**（"曾经存在过"这一事实不可抹除）；删除动作本身**逐行审计**。

### G-DATA-3 存量数据问题的报告纪律

**规格**：对账工具**首次**发现的存量数据问题：

1. **不得擅自清理**（删除是破坏性动作，需业务确认"该批数据是否承认"）；
2. 必须**先取证归因**（谁建的、什么时候、字段组合对应哪条业务流程、是否与已知夹具残留同源）；
3. 结论要么进**例外基线**（G-REC-2，点名 + 处置计划），要么进需求/整改项，**不得只留在聊天记录里**。

### G-DATA-4 受控订正通道：生效/受控记录只增不改，订正走新条目

**规格**：凡进入「生效/受控」状态的记录（需求、文档版本、评审结论、已批准的变更……），**一律不得原地改写**；
需要订正时**新建一条订正条目并通过显式取代关系指向被订正条目**。落地实例：REQ-2026-0784（V104）。

**五条纪律**：

| # | 纪律 | 内容 |
|---|---|---|
| 1 | **不可改** | 被订正条目**保持原样**（内容一字不改、只追加取代关系）——这是记录控制（CSV/Part 11）对"已完成记录"的要求，也是审计链能自证的前提 |
| 2 | **显式关系** | 取代关系落库（`t_req_trace` 语义的 `supersedes` 关系 + `supersededBy` 反向查询），**不得**用标题里写"（作废）"之类的隐式约定代替 |
| 3 | **三条守卫** | ①不得订正自己（`SUPERSEDE_SELF`）；②被订正条目不存在 → `SUPERSEDE_TARGET_NOT_FOUND`；③**不得成环**（`SUPERSEDE_CYCLE`）——A 取代 B、B 再取代 A 会让"哪条有效"无法判定 |
| 4 | **双向可见，且只读** | 被订正条显示**警示横幅**（取代者单号可点 + 一句「本条内容保持原样不可修改，请以订正条目为准」+ 被订正条目自身状态）；订正条目显示**信息条**（指向被取代条目）。**只做单向**会出现"两条看起来都像有效的"；横幅是关系投影、**不是编辑位**，不得提供"原地解除取代关系" |
| 5 | **状态可见** | 被订正条目处于 `OBSOLETE` 等终态时，其**不可编辑**必须与"流程中锁定"区分呈现（G-API-1 的错误码也要能区分：`*_LOCKED` 与 `*_NOT_FOUND` 都映射 400，但码不同） |

**为什么必须是产品级规格**（而不是需求域的私有实现）：①可追溯性是**跨域**要求（BR-04/17/19：任何受控记录都要能回答"当时是什么、谁改的、改成什么"）；
②若各域各写一套订正方式，则"被订正条目还能不能被改"这个问题**每个域答案不同**，审计无法给出统一保证；
③"原地改"是最容易被实现者顺手做出来的动作（改一条字段最省事），因此需要**明文禁止 + 机器判据**。

**验收断言**（任何实现了"生效后不可改"的域照抄）：
- A1 对被订正条目执行更新 → 4xx，且**其内容字段一字未变**（改前后做全字段比对，不是只看状态）；
- A2 订正自己 → `SUPERSEDE_SELF`；目标不存在 → `SUPERSEDE_TARGET_NOT_FOUND`；构造 A→B→A 环 → `SUPERSEDE_CYCLE`；
- A3 两端界面：被订正条显示警示横幅且横幅上的单号可跳转；订正条显示信息条；**两条同时可见时不产生"两条都有效"的歧义**；
- A4 订正关系**不新增第三条记录**（不得靠"复制一份再改"实现订正）。
