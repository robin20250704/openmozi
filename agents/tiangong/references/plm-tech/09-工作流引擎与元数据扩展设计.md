## 1. 工作流引擎

### 1.1 问题

状态机硬编码散落在各域 Service 的 Java 常量和前端常量中，改流程需改代码+编译+部署，各域重复实现。

### 1.2 方案：YAML 定义 + 通用引擎 + 前端 Hook

```
┌──────────────────────────────────────────────────────────────┐
│  resources/flows/*.yaml  （流程定义，配置即数据）              │
│         ↓ 启动时加载                                           │
│  FlowEngine（平台服务，@PostConstruct 扫描 classpath:flows/）  │
│         ↓ 查询 API                                             │
│  GET /api/v1/_platform/flows/{flowId}  （下发流程定义）        │
│         ↓ HTTP                                                 │
│  useFlow(flowId)  （前端 Hook，驱动 UI）                       │
│         ↓                                                      │
│  各域页面（状态下拉 / 流转按钮 / 可编辑性 / 状态色彩）          │
└──────────────────────────────────────────────────────────────┘
```

### 1.3 YAML 格式

```yaml
flow: requirement              # 流程标识（全局唯一，各域 Service 用此 ID 查询）
label: 需求审批流               # 显示名
states:                        # 状态集合（有序，key = 状态值）
  PROPOSED:
    label: "提案"              # 显示名
    color: "primary"           # 语义色（对应前端设计令牌，见 08-前端实现规格 §1.1）
  ANALYZED:
    label: "分析"
    color: "warn"
  APPROVED:
    label: "批准"
    color: "ok"
  # ...
transitions:                   # 迁移边集合
  - { from: PROPOSED, to: ANALYZED, label: "分析" }
  - { from: ANALYZED, to: APPROVED, label: "批准" }
  - { from: ANALYZED, to: PROPOSED, label: "回退", rework: true }   # rework=true 需填原因
  # ...
editableStatuses: [PROPOSED, ANALYZED]   # 可编辑内容的状态集合（批准后锁定，改动走 ECO）
```

**字段说明**：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `flow` | string | ✅ | 流程标识，全局唯一 |
| `label` | string | | 显示名（缺省取 `flow`） |
| `states` | map&lt;string, StateDef&gt; | ✅ | 状态集合，key 为状态值 |
| `states.*.label` | string | | 状态显示名（缺省取 key） |
| `states.*.color` | string | | 语义色令牌名（`primary`/`warn`/`ok`/`err`/`med`/`muted`/`info`/`ai`） |
| `transitions` | list&lt;TransitionDef&gt; | ✅ | 迁移边集合 |
| `transitions[].from` | string | ✅ | 起始状态 |
| `transitions[].to` | string | ✅ | 目标状态 |
| `transitions[].label` | string | | 按钮显示名（缺省取 `to`） |
| `transitions[].rework` | boolean | | 是否为回退边（`true` 时前端弹出原因输入框，后端校验非空） |
| `transitions[].guards` | list&lt;string&gt; | | **（B2，GAP-14）守卫声明**（如 `dcp:DCP1`）——引擎解析并下发给前端做按钮预判，后端域服务权威执行（`ProjectService.transition → assertStageGuard`，见 §1.8.2） |
| `transitions[].signers` | list&lt;string&gt; | | **（B2）签署方声明**（该迁移须哪些签署方完成，如 `["host","design","quality","reg"]`） |
| `transitions[].join` | string | | **（B2）并行汇聚**（多前驱迁移的 join 节点标记，为 B4~B6 流程级编排预留） |
| `transitions[].countersign` | boolean | | **（B2）会签标记**（会签语义现由 SignatureService 哈希链承接 BR-04，此字段为流程级声明预留） |
| `transitions[].requires` | list&lt;FieldReq&gt; | | **（2026-09-09）推进前置条件**：声明"目标字段必须已填写"才允许执行该迁移。`FieldReq = { field: 实体字段码, label: 展示名 }`。引擎负责**声明与下发**，**域服务权威执行**（对齐 `guards` 模式，见 §1.11） |
| `transitions[].requireReason` | boolean | | **（V115 / REQ-2026-1075）强制理由**：非退回边也要求填迁移理由（如作废边 `reason: true`）。此前 YAML 里写 `reason: true` 被解析器静默忽略（L-286"声明了却没有消费者"），V115 起补进解析器"声明即生效"；`rework` 边沿用既有硬编码 |
| `transitions[].ownerOnly` | boolean | | **（REQ-2026-1001，用户裁定 2026-09-17）作者边**：只有文档责任人/编制人（`t_document.owner`，空则回落 `created_by`）可执行。声明化后随 `GET /_platform/flows/doc` 暴露，不藏在代码 if 里 |
| `transitions[].gate` | string | | **（批2，裁定 D-IMODEL-7）DCP 门约束**：该边受哪一道 DCP 门约束（如 `DCP_ES`）。**声明在边上而非查 `t_gate_map`**（那张表是项目阶段轴映射，产品轴有同名状态会撞名）；`null`/空/`gate: none` = 无门（显式语义，非"未配置所以放行"）。判据唯一：`ReviewService.hasApprovedDcp(主项目, gateCode)` |
| `editableStatuses` | list&lt;string&gt; | | 可编辑内容的状态集合 |

> **兼容性（GAP-14 已验证）**：`TransitionDef` 由 4 字段扩为 **14 组件**记录（roles/guards/signers/join/countersign/task/requires/**requireReason**/**ownerOnly**/**gate**），保留 **8 参兼容构造器**（GAP-14，roles/task/requires 等缺省）及 V115 追加的 12/13 参兼容构造——**既有全部 21 个 flow YAML 零改动照常加载**。可选字段未写时解析为 null/空，引擎行为与 v1 完全一致。

### 1.4 后端组件

#### 1.4.1 FlowDefinition（数据模型）

```java
public record FlowDefinition(
    String flow,
    String label,
    Map<String, StateDef> states,
    List<TransitionDef> transitions,
    List<String> editableStatuses
) {
    public record StateDef(String label, String color) {}
    // 迁移边（14 组件）：roles=边级角色门；task=待办任务分派；requires=推进前置条件；
    // guards/signers/join/countersign = B2 会签预留；requireReason/ownerOnly/gate = V115/REQ-2026-1001/D-IMODEL-7
    public record TransitionDef(String from, String to, String label, boolean rework,
                                List<String> roles, List<String> guards, List<String> signers,
                                String join, int countersign, TaskDef task, List<FieldReq> requires,
                                boolean requireReason, boolean ownerOnly, String gate) {
        // GAP-14 兼容构造（8 参 = roles/task/requires/requireReason/ownerOnly/gate 缺省，旧 YAML 零改动）
        public TransitionDef(String from, String to, String label, boolean rework,
                             List<String> guards, List<String> signers, String join, int countersign) {
            this(from, to, label, rework, null, guards, signers, join, countersign, null, null, false, false, null);
        }
        // V115 兼容构造（13 参 = gate 缺省 null；12 参 = ownerOnly/gate 缺省）
        public boolean hasCountersign() { return countersign > 0; }
        public boolean hasGate() { return gate != null && !gate.isBlank(); }
        public boolean needsReason() { return rework || requireReason; }   // 该边是否须填理由
        public boolean roleAllowed(Set<String> userRoles) { ... }  // 边未配 roles → 域级 RBAC 兜底(true)
    }
    public record TaskDef(String mode, String assigneeFrom, String candidateRole, Integer dueDays) {}
    // （2026-09-09）推进前置条件：field=实体字段码，label=展示名（错误提示与前端 tooltip 用）
    public record FieldReq(String field, String label) {}

    public boolean canTransition(String from, String to, Set<String> userRoles) { ... }  // L1 边级角色门
    public List<TransitionDef> transitionsFrom(String state) { ... }
    public boolean isRework(String from, String to) { ... }
    public boolean isEditable(String state) { ... }
    public List<String> signersFor(String from, String to) { ... }   // B2：该迁移的签署方（空=无要求）
    public List<FieldReq> requiredFields(String from, String to) { ... }   // 推进前置条件（空=无要求）
}
```

> 注：`TaskDef.mode` = `ASSIGNED`（assigneeFrom 解析指定人）/ `CANDIDATE`（candidateRole 候选池认领）；`dueDays` 折算 `due_date`。

#### 1.4.4 各域 Service 接入

改造前（硬编码）：
```java
private static final Map<String, List<String>> TRANSITIONS = Map.of(
    "PROPOSED", List.of("ANALYZED"), ...);
private static final Set<String> REWORK_EDGES = Set.of("ANALYZED:PROPOSED", ...);

public ReqResp transition(Long id, String to, String reason) {
    List<String> allowed = TRANSITIONS.getOrDefault(from, List.of());
    if (!allowed.contains(to)) throw new BizException("非法迁移");
    if (REWORK_EDGES.contains(from + ":" + to)) { /* 校验 reason */ }
}
```

改造后（FlowEngine 驱动）：
```java
private final FlowEngine flowEngine;  // 构造注入

public ReqResp transition(Long id, String to, String reason) {
    var allowed = flowEngine.transitionsFrom("requirement", from);
    if (allowed.stream().noneMatch(t -> t.to().equals(to))) throw new BizException("非法迁移");
    if (flowEngine.isRework("requirement", from, to)) { /* 校验 reason */ }
}
```

#### 1.4.5 任务分派组件（FlowTaskService，L2）

`t_flow_task` 为**跨域通用**任务实例表（任务 = 待执行的迁移实例；状态机仍是唯一事实源，可从对象状态重建，无冗余）。接口：

| 方法 | 签名 | 职责 |
|---|---|---|
| `onEnterState` | `void (flowId, objType, objectId, state)` | 对象进入状态时按 YAML 出边 `task` 配置生成待办任务 |
| `onTransitioned` | `void (flowId, objType, objectId, from, to, actor)` | 迁移后任务 DONE(执行人)/CANCELLED(同状态其余) + 生成下一状态任务 |
| `assertCanExecute` | `void (objType, objectId, from, to, login, isAdmin)` | ASSIGNED 任务仅 assignee/claimed_by/admin 可执行 |
| `claim` / `release` | `void (taskId)` | CANDIDATE 认领（candidate_role ∈ 我的角色）/释放 |
| `myTasks` | `List<Map> myTasks()` | 我的跨域待办（工作台数据源；角色隔离 + overdue 标记） |

**REST**：`GET /_platform/tasks/my`、`POST /_platform/tasks/{id}/claim`、`POST /_platform/tasks/{id}/release`。

#### 1.4.6 当前处理人（派生，无冗余列）

"当前处理人"**不建独立列**，由 `t_flow_task` 实时派生——`claimed_by ?? assignee`（CANDIDATE 已认领→认领人；ASSIGNED→指定人；CANDIDATE 待认领→空="待认领"）。

| 方法 | 签名 | 职责 |
|---|---|---|
| `currentAssignee` | `String (objType, objectId)` | 单对象当前处理人（create/transition/update 的详情响应用） |
| `currentAssignees` | `Map<Long,String> (objType, List<Long>)` | 批量派生（列表页避免 N+1） |
| `matchingIds` | `List<Long> (objType, assignee)` | 指定处理人的对象 id 集（按处理人筛选） |

**按处理人筛选**：`list()` 先 `matchingIds` 预求 id 集 → 空则直接空页 → 非空走 `repo.searchByAssignee(..., r.id IN :assigneeIds)`（拆分两个 @Query 方法，规避 Hibernate 6 对 collection 参数 `IS NULL` 的不支持）。默认筛选条件 = 当前登录用户（前端 `assignee` 初始 = `currentUser()`）。

> **跨域复用**：`FlowTaskService` / `t_flow_task` / `currentAssignee` 与域无关——项目/文档/物料/产品域只需在各自流程 YAML 配 `task` + `roles`，其待办与"当前处理人"即自动出现在工作台与业务页。

#### 1.4.7 认证与身份链（AuthContext 双模式，全平台底座）

任务分派（claim/release/assertCanExecute）、当前处理人派生、审计 actor、域级 RBAC（`@PreAuthorize`）**全部消费同一个 `AuthContext`**——身份链正确性是流程引擎与全平台的前置底座（V-019：身份来自认证载体而非调用参数，禁止从前端参数取）。

**双模式**（`PLM_AUTH_MODE`，`SecurityConfig` 二选一）：

| | dev 模式（默认） | oidc 模式（生产） |
|---|---|---|
| 认证 filter | DevAuthFilter（security chain 内） | oauth2ResourceServer + JwtContextFilter |
| 身份来源 | `X-PLM-User` header（缺省 seedUser） | JWT `preferred_username`（`sub` 是 UUID，仅兜底） |
| 角色来源 | `t_user_role`（DB） | Keycloak realm roles（`realm_access.roles`，过滤 default-roles-* 等杂角色） |
| 管理员判定 | login=seedUser → admin | roles 含 `admin` |
| 未认证请求 | 回落 seedUser（宽松，仅限开发） | **401**（fail-closed） |

**实现红线**（L-098 三缺陷——任何一处违反，症状都是"所有真实登录身份都变成 admin"）：

1. **DevAuthFilter 必须按 mode 跳过**：`@Component OncePerRequestFilter` 会被 Spring Boot 自动注册为**容器级 filter**（order 最低、排在 security chain **之后**）——即使 SecurityConfig 没注册它也会执行。若 oidc 下不 `shouldNotFilter` 跳过，它会在 JwtContextFilter 写入正确身份后**用 seedUser 覆盖 AuthContext**。
2. **login 不得把 `sub` 作首选**：Keycloak `sub` 是 UUID；`preferred_username` 才是与 `t_user.login`/`created_by`/`claimed_by` 对齐的业务身份，必须优先取用。
3. **JwtContextFilter 必须注册在认证之后**：用 `addFilterBefore(AuthorizationFilter.class)`（全部认证 filter 之后、授权之前）。注册到 `UsernamePasswordAuthenticationFilter` 之前会跑在 `BearerTokenAuthenticationFilter` 之前，读不到 Jwt → roles 恒空。

**跨域语义**：新域零身份代码——transition 的 actor、任务的 claimed_by、currentAssignee、审计流水全部自动继承 AuthContext；域内不需要（也不允许）自行解析身份。

### 1.5 前端组件

#### 1.5.1 useFlow Hook

```typescript
export function useFlow(flowId: string, myRoles: string[] = []) {
  // 从 /api/v1/_platform/flows/{flowId} 拉取流程定义（模块级 Promise 缓存：在途去重、失败不缓存可重试，批次56/58）
  return {
    flow,              // FlowDefinition | null（含 attachmentStatuses / ownerTransferStatuses，批次46）
    states,            // string[]（状态值数组，驱动状态下拉）
    transitionsFrom,   // (state) => TransitionDef[]（该状态全部出边）
    visibleTransitions,// (state) => TransitionDef[]（L1 边级角色门：未配 roles 的边恒显示；配了则与 myRoles 有交集，admin 全显）
    isRework,          // (from, to) => boolean
    requiresReason,    // (from, to) => boolean（V115/批次46：requireReason || rework，驱动原因输入框）
    editableStatuses,  // string[]（驱动详情面板可编辑性）
    attachmentStatuses,// string[]（批次46：附件可上传状态，未声明回落 editableStatuses）
    ownerTransferStatuses, // string[]（批次46 #41：所属人可转移状态，未声明回落 editableStatuses）
    stateLabel,        // (state) => string（状态显示名；useCallback 稳定身份，P3-5）
    stateColor,        // (state) => string（语义色令牌名）
  };
}
```

#### 1.8.2 守卫接线（单点）

```java
// ProjectService.transition（唯一入口）
var allowed = flowEngine.transitionsFrom("project", from);
if (allowed.stream().noneMatch(t -> t.to().equals(to))) throw new BizException("非法状态迁移");
reviewService.assertStageGuard(id, from, to);   // B2：查 t_gate_map.stage_from/stage_to，未映射流转零拦截
```

- 守卫的**数据源是 t_gate_map 种子**（11 门点：旧门映射/阶段端点/TR 阻断指向）——改映射 = UPDATE 种子数据，不改代码（配置即数据，与 flow YAML 同哲学）。
- **门点执行序（V185，2026-09-28 用户裁定）**：`seq` 是**门点执行序号**（不再是"阶段轮次编号"）——`DCP0=0, TR1=1, TR2=2, DCP1=3, TR3=4, DCP2=5, TR4=6, DCP_ES=7, TR5=8, TR6=9, DCP3=10`，**严格全序**且与 `sort_key` **同序**；每道 TR 的 `seq` 小于其 `blocks_dcp` 的门（TR 先于它所阻断的 DCP）。三列口径已落 **列注释**（口径成为数据，不只在代码注释里），迁移 `V185__gate-map-seq-align.sql` 并把全序性做成结构约束 `UNIQUE(t_gate_map_seq_uk)`。
- **机器守卫（防再漂移）**：`GateMapService.load()`（`@PostConstruct`）按与 V185 同一组判据自检三条——①`seq` 严格全序（无并列）；②`sort_key` 升序 ≡ `seq` 升序；③每道 TR 的 `seq` < 其 `blocks_dcp` 的 `seq`；任一不成立抛 `GATE_MAP_INCONSISTENT` **拒绝启动**。理由：门序自相矛盾时不报错，而是**同一个界面说"该先做 TR3"、一次发起却被告知"该先做 DCP2"**——比不可用更坏。
- 前端 `advance()` 目前取 `transitionsFrom(...)[0]` 直接 POST，**不做守卫预判**（§1.10 缺陷 6）——演进：按钮渲染前调 `GET /reviews/precheck?projectId&gateCode=` 干跑，把"过不了、缺什么"内联展示在推进按钮旁。

**门序守卫与门序检查项（V185 / 2026-09-28 用户裁定：两个读面同源）**

判据、文案、硬拒绝的**唯一实现** = `com.plm.domain.review.GateOrderGuard`（判据 `missingPriorGates`、文案 `missingDetail`、硬拒绝 `assertSatisfied`）；两个读面只消费它，不各写一份：

| 读面 | 行为 |
|---|---|
| 发起口 `POST /api/v1/reviews/request` | 前序门未定论 ⇒ **400 `GATE_ORDER_VIOLATION`**，消息逐条列出缺失门（条目形态 `[TR1] TR1 需求/方案评审：该门尚无已定论评审，须先完成`，多条用「；」分隔，并给出"按 seq 从小到大依次做完再重试"的下一步） |
| 只读口 `GET /api/v1/reviews/precheck` | 新增检查项 **`GATE_ORDER`**（严重度 **BLOCKING**，`passed` 只由"有无缺失门"决定）：与发起口**同一实现**——此前"预检全绿、发起必被拒"的两套读数由此消除（发起按钮按 `precheck.passed` 启用，旧口径下会在"必被拒"状态下显示为可用）。执行序首门 `DCP0`（seq=0）前序门为空集 ⇒ 如实自述 **N/A**（不是"已核查且无欠账"） |

- V185 之前为绕开 `seq`/`sort_key` 矛盾而在判据里写的**特例（"排除本门自己阻断的门"）已删除**：数据对齐后判据只剩一条规则——seq 小的先做（详见 §1.8.2 与 V185 迁移注释）。
- **执行位置**：**先于机器预检**。门序错误使"这道门现在能不能开"本身不成立，先报"缺 3 份证据"会把调用方引去补与真因无关的材料。
- **与并行守卫的关系**：`ReviewService.assertGateOrder`（REQ-2026-1278：TR 不得在其阻断的 DCP 已放行后补开；可带 `lateRequestReason` ≥8 字显式 override 并写审计 `review.late_request_override`）**保持不变**，且**晚于**门序守卫执行——两条判据不同、都要跑；只有前序门均已定论之后，"技术评审补做"这条 override 才言之有物。

### 1.9 工作流引擎 vs 评审编排（引擎边界，B2 权威口径）

**结论：DCP/TR 评审不走 flow YAML，由 ReviewService 显式编排；FlowEngine 继续只管"对象状态机"。**

| 维度 | FlowEngine（状态机） | 评审编排（ReviewService） |
|---|---|---|
| 建模对象 | 对象**状态**（项目/文档/变更…23 个 flow，§1.6 台账） | 多角色**过程**（申请→预审→逐项判定→结论签署→遗留闭环） |
| 驱动方式 | YAML 声明式，启动加载 | 服务层显式编排（强类型、可单测） |
| 步骤语义 | 状态间迁移边 | 预审检查项（每检带 SQL 判据；V185 起含门序 `GATE_ORDER`）/ COND 生成遗留问题 / 签署哈希链（BR-04）/ 双写幂等 |
| 守卫关系 | `TransitionDef.guards` 声明（B2 起） | 守卫的**被调方**：`assertStageGuard` / `precheck` 是引擎声明的执行者 |
| 配置化程度 | 全配置（改 YAML 重启生效） | 清单可配置（t_checklist_template 模板拆分）；编排逻辑代码承载 |

**为什么不把评审做成 YAML 状态机**：评审步骤携带丰富业务语义（逐项判定×模板、COND→问题对象、签署链、双写幂等），通用状态机 DSL 表达力不足且失去类型安全；清单模板已把"可配置"该下沉的部分下沉了。**B2 扩展 TransitionDef 四字段的意义**：为 B4~B6 流程级编排（并行/join/会签声明）预留兼容语法，评审编排若未来需要按产品线差异化配置，优先扩 t_checklist_template/规则表而非 flow 化。

> **通用化（2026-09-10）**：评审容器模型（清单＋责任人＋结论＋签署＋否决＋遗留，定论 WORM）与"评审是流程守卫输入、非流程节点"已抽取为产品级通用规格 **G-REV-1 / G-REV-6**，见 `12-产品级通用规格-评审机制与列表范式.md` §2——新业务域接入评审按该规格执行，不重造编排。

### 1.9.1 评审门按管理类别裁剪（2026-11-11 用户裁定 D63-8 / D63-9）

**需求原文**：「项目管理类别如果选 III 类项目/NA，评审环节简化：仅保留 DCP0、TR1、DCP1、DCP2、TR6、DCP3。」

**先纠正一个前提**：原设想里两个备选方案（A 流程引擎加条件分支、B 按管理类别切换不同流程）

⇒ 本节的实现落点是 **`t_gate_map` 的作用域过滤**，与 §1.9 「优先扩 t_checklist_template/规则表而非 flow 化」
的既有裁定一致。

**分类口径（D63-10，探针实测 68 个项目：空 55 / II 11 / NA 1 / I 1）**：
`I` / `II` / **空** 走完整 11 门；`III` / `NA` 走 6 门。
**空值归入完整档是刻意的**——空 = 未登记 = 未表达偏好，不应静默给存量项目减掉 5 道门。
若判据写成「未知走最严」，同样要**在文档和错误提示里写明**，不能让它成为隐式默认。

**本节的读侧一致性义务（2026-11-12 批次65 / D65-1，用户实测报缺）**：
后端读侧一直是现算的——`ProjectService.flowOverview` 首行即
`gateMap.orderedFor(normalizeMedClass(p.getMedClass()))`，**每次请求都按项目当前 `med_class` 重算门集，无任何缓存**。
所以"改类别后门集不变"**不可能**是本节的判据或表数据问题；实测根因在前端：`ProjectsPage.saveProject`
保存成功后只做 `setSelected` + `patchRow`（就地补行），**从不重跑 `loadFlow`**，于是时间线、项目统计卡、
ctx-bar 门进度这一组派生读数一起停在旧门集上，用户必须刷页面才看到变化。

⇒ 由本节推广出的通则（**不只对 `medClass` 生效**）：凡是**改变门集或检查项解析结果**的字段，
保存成功后前端必须**当场重取** `flow-overview`，把该字段的读侧刷新当作交付的一部分，
不能以"接口那边已经是新的"就算完。凡涉及 `skip_med_classes` / `product_kind` 的字段都按此条处理。

**必须同步改的一处（否则 DCP3 永远不可达）**：
`GateOrderGuard.missingPriorGates` 现行判据是「同项目所有 `seq` 更小的门都已 DECIDED」。
丢弃 5 门后不调它，TR6(seq 9) 与 DCP3(seq 10) 永远凑不齐前序门 ⇒ 直接 400 `GATE_ORDER_VIOLATION`。
⇒ 判据改为「**本项目适用门集 ∩ `seq < seq(G)`**」。
已核验：裁剪后保留集的 `seq` 仍严格递增，且每道保留 TR 的 `seq < blocks_dcp.seq` 仍成立
（TR1=1<5、TR6=9<10）⇒ §1.8.2 的三条启动自检**无需豁免**。

**阶段轴显示纪律（2026-11-13 批次66 需求③）**：III/NA 类的阶段轴与 I/II **同源同序**
（`project-flow.yaml` 11 阶段，阶段**不按类别裁剪**，只有门集按 `skip_med_classes` 减）——
PRJ-2026-0906 实测：III 类完成 DCP0（守卫 `DCP0：立项→概念`）后由用户手动推进，库值已到 `概念`，
系统并未多推一步。用户所见「界面显示推进到计划」的真身是**统计卡「推进阶段」格的动作目标态**
（「推进 → 计划」= 概念的唯一出边），不是当前阶段读数。展示纪律：该格必须**并列**渲染
`当前阶段 {库值}` 与 `推进 → {下一目标}`，且推进按钮接 `flow.stageGuards` 守卫态——
守卫不满足（如 DCP1 尚无评审行）时按钮禁用并显示「须 {gateCode} 结论 GO/GO_WITH_RISK」，
不得渲染一个点了必被后端 `STAGE_GUARD_BLOCKED` 拒绝的按钮。

**`DCP_ES` 被丢弃的后果（D63-9，用户原话：「III类项目是为了支持试产等这些非商业项目。
没有销售决策是合理的」）**：`ReviewService.assertStageGuard` 的语义是
「`dcpForTransition(from,to)` 找不到映射则**放行**」，所以 III 类/NA 项目的**开发→验证**流转
**无守卫直接放行**。这是**裁定的结果，不是缺陷**——但必须在用户手册里显式写明，
否则用户看到"别的项目要门、这个项目不要"会当成系统漏拦。

**分母口径**：门进度是 `x/N`，N 由后端 `totalGateCount` 下发（前端不写死），
所以 N 从 11 变 6 **沿用同一条通道**，无前端硬编码改动。

**字典边界（裁剪的是"本项目适用集"，不是"门点词表"）**：
本节最易出的错，是把"按类别裁剪"一路扩散到**字典类**读面上。三处**刻意保持全量**，已逐一核过：

| 调用点 | 口径 | 为什么不该裁剪 |
|---|---|---|
| `MilestoneController` 里程碑「关联门码」下拉 | 全量字典（只校验码在词表内） | 里程碑是**计划性记录**，可关联的门码是词表事实；裁掉 TR2 后，一个已存在的里程碑会突然指向一个"本项目不存在"的门 |
| `PlatformController` `GET /_platform/gates` | 全量 `t_gate_map` | 它是**平台级门点字典**（含 `oldGateCode` 双写映射），供下拉、导入校验、报表用；按当前用户的项目类别裁剪会让同一个端点在不同上下文里返回不同词表 |
| `PcoGateImpactService` 输出排序 | `ordered()` 全量排序，**集合**另用 `allFor(medClass)` | 排序不裁剪（顺序只依赖 `seq`）；裁剪只作用在"影响了哪些门"的集合上 |

⇒ 一句话口径：**「某个项目当前适用哪些门」走 `*For(medClass)`；
「门点有哪些 / 按什么顺序」走全量。** 反过来就会得到"下拉里选得到、点了报
`GATE_NOT_APPLICABLE_FOR_MED_CLASS`"的割裂。

**可复用先例**：`ChecklistTemplateService.resolve(gateCode, medClass, market, productKind)`
的降级链（精确 → 逐维降级 → 通用层）与并集合并规则。库内**已存在 1 条 `med_class='III'` 实例**
（`DCP_ES` 的降级清单）——「按 III 类差异化」这条数据通道**已经在跑**，
且恰好落在本节要丢弃的那道门上。

### 1.11 推进前置条件（requires）——声明 / 下发 / 权威执行三层契约（2026-09-09）

**问题**：状态机允许"批准 → 实现"这类迁移，但业务上要求**先补齐某字段**（如"方案制定中"状态必须填写方案内容才能进入实现）。此前引擎只有 `guards`（业务规则守卫，域内自定义），缺少**通用字段完备性**声明能力。

**三层契约**（对齐 `guards` 的"引擎声明 + 域执行"边界，§1.9）：

| 层 | 职责 | 实现 |
|---|---|---|
| 声明 | 在 flow YAML 迁移边写 `requires: [ { field, label } ]` | `TransitionDef.requires` |
| 下发 | 流程定义端点把 `requires` 随迁移边下发给前端；前端据此**禁用按钮 + tooltip 提示**（预判，非权威） | `FlowEngine.requiredFields()` / `GET /_platform/flows/{flowId}` |
| 权威执行 | 域服务在 `transition()` 校验链中读取 `requiredFields(from,to)`，逐项检查实体字段（空串/纯空白视为未填）；不满足 → `400 FIELD_REQUIRED`，message 含 `label` | 各域 Service（如 `RequirementService.transition`） |

**为什么引擎不读实体**：引擎不认识各域实体结构（§1.9 边界）——它只声明"字段码 + 展示名"，字段取值由域服务提供（实体/DTO 在手，校验零额外查询）。

**需求流实例**（V45 起边级 roles 为两级角色口径——组织角色/项目角色，详见 `10-流程角色与任务分派设计.md` §6）：

```yaml
- { from: SOLUTION_DEFINING, to: IMPLEMENTED, label: "确定方案",
    roles: [prj_sa, prj_dev, admin],                       # prj_* 为项目角色（t_project_member）
    requires: [ { field: solution, label: "方案内容" } ],
    task: { mode: CANDIDATE, candidateRole: prj_dev, dueDays: 5 } }
```

未填方案内容时推进 → `400 FIELD_REQUIRED / 请先填写方案内容后再推进到实现`；前端"确定方案"按钮禁用并提示。

**录入模版由元数据定义**：方案内容字段的录入骨架存 `t_attr_template.sample_value`（`kind=JSONB` → 前端 `longtext/textarea`），经 `GET /_platform/metadata/detail-fields?objType=REQ` 下发为 `placeholder`——**改模版 = 改元数据一行，零发布**（§2.4/§2.8）。

**兼容性**：`requires` 为可选字段，既有 21 个 flow YAML 零改动照常加载（与 B2 的 TransitionDef 扩字段同法）。

### 2.6 与 JSONB 存储的闭环（ADR-1）

```
主干字段（reqCode/title/status/...）    → t_requirement 真实列 + 真实外键
差异字段（verifyMethod/stdClause/...）  → t_requirement.attrs JSONB
                                         → t_attr_template 定义属性元数据
                                         → 前端据 columnDefs() 动态生成列
                                         → 写入时 validateAttr() 校验
```

**红线**：关联字段（一切 `xxx_id`）必须是真实列+真实外键；JSONB 只放属性、不放关系。

### 2.7 属性转正机制

JSONB 属性查询频率超阈值时，管理员一键提升为生成列并建索引：

```sql
ALTER TABLE t_requirement ADD COLUMN verify_method TEXT
    GENERATED ALWAYS AS ((attrs->>'verifyMethod')) STORED;
CREATE INDEX idx_verify_method ON t_requirement(verify_method);
```

灵活性归灵活性，性能按使用量自适应优化。

### 2.9 风险控制引擎（法规/内部管理规则校验 + 软提醒，B39）

> 需求：对**法规规则**（R-REG-*）与**内部管理规则**（R-INT-*）做风险校验；**只做 UI 柔性提醒（分等级）**，后端**记录风险项**（检测内容/等级/关联对象/字段/检测时间/唯一ID），**更新/追加去重 + 可追溯历史**；**不做强制校验**（业务写入不阻断）。

#### 2.9.1 原则（软校验 = 提醒不阻断）
- 风险引擎**不阻断写入**，只产出风险项供 UI 按等级提醒（HIGH=红、MED=琥珀、LOW=蓝）。硬校验仍按既有 BR（如 BR-07 子件须 RELEASED）在各域 Service 权威执行——两者解耦。
- **规则 = 配置文件（YAML/JSON，B40 起）**：规则源在 `classpath:rules/risk-rules.yaml`（+.json），与 `classpath:flows/*.yaml`（流程引擎）同理——**改文件 + 重启即生效，无需 UI/DB，零部署**（`t_attr_template` 同属「配置即数据」）。`t_risk_rule` 表(V14)已清空，保留为预留 schema（未来如需 DB 驱动规则可复用）。
- **条件 DSL 必须为 MAP**：单条件 `{field,op,value}`；多条件用 `and/or/not` 组合（**勿用顶层数组**，Jackson 无法反序列化为 Map，L-109）。`op ∈ {empty,present,eq,ne,in,lenLt}`；求值上下文 = 对象核心字段 + `attrs`（09 §2.8）。

#### 2.9.2 数据库（V14）
```
t_risk_rule   : id, rule_code UK, rule_name, obj_type, field, severity[LOW/MED/HIGH],
                condition JSONB(条件DSL), message_template, enabled, version, created_by, created_at
t_risk_item   : id, risk_uid UK(=objType:objId:ruleCode), rule_code, obj_type, obj_id, field, severity,
                content, context JSONB(评估时对象字段快照), occurrence_count, first_detected_at,
                last_detected_at, resolved, resolved_at, version, created_by
t_risk_item_event : id, risk_uid, event[DETECTED/UPDATED/RESOLVED/RESURRECTED], detail, actor, occurred_at
```

#### 2.9.3 条件 DSL（JSONB，递归求值）
```jsonc
{"field":"medClass","op":"eq","value":"III"}          // 字段=值
{"field":"intendedUse","op":"empty"}                   // 字段为空/空白
{"field":"title","op":"lenLt","value":5}               // 长度 < N
{"and":[{"field":"medClass","op":"eq","value":"III"},  // 组合：and / or / not
        {"field":"intendedUse","op":"empty"}]}
```
求值上下文 = 对象核心字段 + `attrs`（09 §2.8 元数据字段并入），`op ∈ {empty,present,eq,ne,in,lenLt}`。

#### 2.9.4 更新/追加去重 + 追溯（核心机制）
- **唯一键 `risk_uid = objType:objId:ruleCode`** → 同一规则+对象 **只会有一行** `t_risk_item`，杜绝大量重复。
- 每次评估 `RiskEngine.evaluate(objType,objId)`：
  - **首次命中** → INSERT 风险项（occurrence_count=1, first=last=now, resolved=false）+ `DETECTED` 事件；
  - **持续命中** → 仅 UPDATE `occurrence_count++`、`last_detected_at`、`context`（**不写事件**，避免事件日志爆炸；计数/首末时间保留完整时间线）；
  - **条件满足（风险解除）** → UPDATE `resolved=true` + `resolved_at` + `RESOLVED` 事件；
  - **复发** → UPDATE `resolved=false` + `occurrence_count++` + `RESURRECTED` 事件。
- **追溯**：`t_risk_item` 的 first/last/occurrence_count + `t_risk_item_event` 的 DETECTED/RESOLVED/RESURRECTED 时间线，构成风险生命周期。
