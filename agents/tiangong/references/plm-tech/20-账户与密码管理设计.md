> **用户裁定（2026-09-19，批次37 D5）**：管理员重置 = **一次性临时密码 + 强制首次登录改密**，在治理台**一次性展示**（不走邮件/短信）。

## 1. 边界：凭据的唯一事实源

| 事实源 | 持有内容 | 说明 |
| --- | --- | --- |
| **Keycloak**（realm `plm`） | **口令（credential）**、会话、登录策略（爆破防护/密码策略）、required actions | **唯一**能读写口令的地方；PLM 库中**不存在**口令列（现状核对：`t_user` 只有 `login/display_name/is_active`） |
| PLM 库 | `t_user`（业务属性：显示名/启用态）、`t_user_role`（角色分配）、审计链 | 业务身份与授权；**永不同步口令** |
| 两库一致性 | `login` 为唯一关联键 | 漂移检测纳入既有对账口径（见 §9 A4） |

**硬约束（本设计的第一条不变量）**：
- **PLM 后端在任何路径上都不得持久化口令**（不写库、不写审计、不写日志、不进异常报文）。
- 口令的**校验由 Keycloak 完成**，PLM 只做"转发 + 授权判定 + 留痕"。
- 不允许出现"PLM 自建口令体系"（那会产生第二事实源，与 INV-1/INV-2 冲突，且无法复用 Keycloak 的爆破防护与密码策略）。

| 能力 | 现状 | 差距 |
| --- | --- | --- |
| 建立用户 | `POST /_admin/users`（写 `t_user` + 角色）；Keycloak 侧由 `plm-migrate-users.sh` 一次性迁移（**同一口令（迁移期统一口令；实际取值见部署包 agents/tiangong/.env 的 PLM_PASSWORD，不随文档分发）**） | 新建用户**不会**在 Keycloak 建账号 → 无法登录；无口令下发路径 |

| 我的信息 | 顶栏只有 `user-chip`（头像首字母 + 登录名 + dev 身份下拉 + 登出） | 本设计 §6 |

> 用户无法自助修改（安全意识上不可接受），管理员也无法在有人离职/口令泄露时立即重置。
> 这正是 §7 接入检查表里"不引入任何默认口令"的既有欠账在账户域的体现。

## 4. C1 管理员重置：一次性临时密码 + 强制首登改密

### 4.1 机制（Keycloak 原生能力，不发明轮子）

1. PLM 生成**一次性临时密码**（§4.2），调用 Keycloak Admin API：
   `PUT /admin/realms/plm/users/{id}/reset-password`，body `{"type":"password","value":"<临时密码>","temporary":true}`；
2. 同时确保该用户带 `UPDATE_PASSWORD` required action：
   `PUT /admin/realms/plm/users/{id}`，body `{"requiredActions":["UPDATE_PASSWORD"]}`（**幂等**：已含则不重复加）；
3. Keycloak 在用户**下次登录成功后强制跳转改密**（`temporary=true` 本身即语义，required action 是双保险，
   也保证"改了但没登录"的窗口里状态一致）；
4. PLM 侧**只回显一次**临时密码（响应体里返回 + 前端一次性展示 + 复制按钮），**不落库、不落审计正文**；
5. 审计只记录**事实**：`admin.user.credential.reset`（对象 = login、操作者 = 当前身份、时间、结果），
   **不含口令**（§9 A2 有专门断言）。

### 4.2 临时密码生成规则

| 规则 | 取值 | 理由 |
| --- | --- | --- |
| 长度 | **16** | Keycloak 策略 `length(12)` 已是最低下限；16 留余量，且远高于策略（策略变化不会让生成器失效） |
| 字符集 | 大写 + 小写 + 数字 + 符号（各至少 1） | 满足"看起来不像可猜口令"的最基本要求 |
| 生成位置 | **服务端**（`SecureRandom`） | 前端生成等于把"口令强度"交给不可信环境 |
| 禁用项 | 不含登录名、不含 `plm`、不含连号/重复模式 | 与 `notUsername`/`notEmail` 策略同向 |
| 传输 | 仅在该次响应中返回（HTTPS/内网） | 一次性 |
| 有效期 | 由 `temporary=true` + required action 保证"用一次即必须改" | 不需要自建过期字段 |

### 4.3 交互（按 `08 §6.1` 全程无弹窗）

```
系统设置 › 用户管理 › 右侧用户详情卡
│ 用户：robin（张明）  [启用] ─────────────────────────────┐
│ 登录名  robin            角色 [组织: ...] [项目: ...]      │
│ 姓（lastName）*  [____]  名（firstName）*  [____]         │
│ 邮箱 *          [robin@example.com]                        │
│ 身份齐备  齐备（可创建凭据账号）/ 缺失（补齐后才能创建）    │
│ 口令  ⓘ 由 Keycloak 管理（本系统不存储口令）              │
│ ┌ [重置密码（生成一次性临时密码）] ─────────────────────┐ │
│ │ ⚠ 重置后该用户下次登录必须修改密码。                   │ │
│ └──────────────────────────────────────────────────────┘ │
│ 一次性凭证（仅本次显示，离开后不可再取）：                 │
│   Kf7#mQ2x-Rt9pLw4   [复制]  ⏱ 请通过可信渠道转告本人      │
└──────────────────────────────────────────────────────────┘
```

> **批次37 补**（§5.6.1 用户裁定）：详情卡同时是**身份字段的补录入入口**（存量账号在库里没有
> `email/firstName/lastName`，补齐后"身份齐备"，才能创建凭据账号）。缺值用橙色边框 + 「⚠ 待补」显式标出，
> **不留空**——留空会被读成"这列没数据"，而实际含义是"这个账号现在登不上"。

| 元素 | 规格 |
| --- | --- |
| 按钮文案 | 「重置密码（生成一次性临时密码）」——**说清结果是"临时"**，不用含糊的"重置" |
| 前置说明 | 常驻一句风险提示（重置后必须改密）；不需要二次确认（可恢复动作，且不可逆性低） |
| 一次性展示区 | 生成后才出现；`data-testid="user-temp-password"`；**复制按钮** + 「关闭后无法再次查看」说明 |
| 关闭即失效 | 面板切换/关闭后前端状态清空；**后端无"取回"端点**（可判定：再请求不返回旧口令） |
| 失败语义 | Keycloak 不可达 → 502 + 明确文案「凭据服务不可用，口令未变更（未发生部分生效）」；用户不存在 → 404；无权限 → 403 |
| 幂等性 | 重复点击 = 生成**新**临时密码（旧临时密码立即失效）——这是**期望**语义，不是幂等：口令类操作天然不可重放（响应里给出"本次生成时间"） |

### 4.5 首登强制改密的**端到端**验证（W31，2026-09-19 补；回应"这个功能真的验过吗"）

**先说结论**：功能**可用**，且已在部署态被真浏览器端到端驱动验证（`W31 = 20/0`）。
但需要如实记录：本批**最初并没有验**这一段——当时的证据只有"配置侧"（`requiredActions` 含
`UPDATE_PASSWORD`、临时口令 ROPC 取不到 token），而"用户真的被拦下来并改成功"从未被驱动过。
用户追问后才发现这个缺口，补了本门禁。

**判据落在用户能看到的页面上**（`ipd/deploy/wsl/plm-app/plm-b37-first-login.cjs`）：

| 步骤 | 断言 | 实测读数 |
| --- | --- | --- |
| 管理员重置 → 一次性临时口令 | F4 | 16 位，响应含 `expiresHint="首次登录必须修改（Keycloak UPDATE_PASSWORD）"`、`loginReadiness=ok` |
| 临时口令直接换 token | A1 | `400 invalid_grant`（门是关着的：临时态不给 token） |
| 登出后点「登录（SSO）」 | B1 | 跳到 `…/protocol/openid-connect/auth?client_id=plm-web&response_type=code&code_challenge=…`（PKCE） |
| 用临时口令提交登录 | **B2/B3** | **被拦在** `…/login-actions/required-action?execution=UPDATE_PASSWORD`，且页面确实是改密页（`#password-new` 在场）；`.topbar` 未渲染 |
| 此时应用侧身份 | B4 | `localStorage.plm_user = null`（**未建立任何应用会话**） |
| 填新口令 + 确认并提交 | C1/C2 | 自动跳回 `http://localhost:5174/?…&code=…`，`.topbar` 渲染（**进入系统**） |
| 应用侧身份 | C3 | `plm_user = bf37fl…`（就是该夹具用户，不是别人的会话） |
| 新口令可用 | D1 | ROPC **200** |
| 临时口令失效 | D2 | ROPC `400 invalid_grant: Invalid user credentials`（**一次性：用过即废**） |
| 不再反复逼改 | D3/D4 | `requiredActions=[]`；凭据转非临时 |
| 夹具回收 | C9/C10 | Keycloak 204 + PLM 200（另有 psql 兜底）；残留 **0** |

**驱动这段流程的两个坑（都写进套件注释与 lessons，避免下次重踩）**：
1. ~~本 SPA **不会**自动跳 Keycloak：它先渲染自己的登录落地页（「请通过统一身份认证（Keycloak OIDC）登录」/「登录（SSO）」），
   必须**点击 SSO 按钮**才发起 OIDC 重定向；~~
   **2026-09-20 批次39 改动（用户裁定 D39-1）**：未登录落地**自动**进统一认证（零点击，见 §4.6）；
   应用自己的登录页降级为**兜底页**。驱动脚本因此不能假设"必须点按钮"——`plm-harness` 已改为
   「有兜底卡才点、没有就等 `#username`」，两态都覆盖；
2. **只清 `localStorage` 不够**：浏览器里还留着上一段登录的 **Keycloak SSO 会话 cookie**，
   于是下次发起授权会直接带 `code` 302 回应用（**以上一个身份静默登录**）——首跑就是这样"通过"了
   若干条本不该通过的断言。必须先真正登出 Keycloak（访问 `…/protocol/openid-connect/logout` 并确认登出页），
   否则整段验证会在**错误的身份**上做，结论不可信。（批次39 追加：清理应用的 local/session storage
   必须用 CDP `Storage.clearDataForOrigin` **按 origin** 清——`DOMStorage.clearDataForOrigin` 返回成功
   却**一个键都没清**，会让应用静默登录，把"未登录落地"的用例整组带偏。）

### 4.4 与 `t_user` / Keycloak 的建号闭环（本设计顺带补的缺口）

`POST /_admin/users` 现状只建 PLM 行。本设计要求：**建号时同时（可选地）建 Keycloak 账号**，
从而"新建用户 ⇒ 能登录"成立。口径：
- **建号必须采集全部必要身份字段**（`email` / `firstName` / `lastName`，见 §5.6.1 的用户裁定与 V138）：
  它们既是凭据服务声明式档案的必填项，也是**人的真实信息**，只能由管理员提供，系统不得合成；
- 建号成功后**不自动下发口令**；由管理员按 §4 生成临时密码（两步，避免"建号即产生未知口令"）；
- 若 Keycloak 账号缺失而管理员点了重置 → 返回 **409 + 文案「该用户在凭据服务中不存在（login=X）：请先同步/创建凭据账号」**，
  并在响应里给出可执行的下一步；**不得**静默创建（静默创建会让"授权范围"与"账号集合"分叉）。
- 该补口同时进入 §9 A4 的两库漂移对账。

### 4.6 未登录落地即进统一身份认证（批次39 · 用户裁定 D39-1）

**需求原话**：「访问首页，在没有登录的情况，直接显示 用户名/密码 登录页面，无需再点击 登录(SSO)按钮」。

**裁定**：方案 A —— 未登录访问**自动跳转**到凭据服务的登录页（零点击），而不是在应用内自建用户名/密码表单。
被否的两条候选与理由（避免后来者重新发明）：

| 候选 | 致命问题 |
| --- | --- |
| **B 应用自建用户名/密码表单**（前端走 `grant_type=password`） | ① 需在 UAT 重新打开 `plm-web` 的 password 授权，与批次38 前刚落地的加固（SF-U07）相反；② **必然打断本设计 §4 的「首登强制改密」**——Keycloak 对存在待办动作的账号拒发令牌（本仓取证：`plm-b37-first-login.cjs` A1、批次38 UAT 门禁实测 `Account is not fully set up`）；③ 口令进入 SPA 内存 |
| **C 应用页放输入框 + `login_hint` 预填后跳转** | 点击次数仍是 2 次，不满足"零点击" |

**实现口径**（判据表见 `08 §6.9`；纯函数 `frontend/src/auth/autoLogin.ts`）：

- 分支顺序：已有 token → dev 入口显式打开 → 回调中（code+state）→ 凭据服务报错（`error`）→
  **历史回退**（`back_forward` / bfcache `pageshow.persisted`）→ 否则跳转；
- **防循环**用"本次导航是不是历史回退"，而不是"30s 内跳过就不再跳"：后者会误伤正常路径
  （从凭据服务登出回来时"上次跳转"就在几秒前 ⇒ 本该零点击的场景退化成要点按钮）；
- **失败必须可见**：`signinRedirect()` 的 reject（发现文档取不到等）落到兜底页的 `role=alert` 文案；
  旧写法 `.catch(() => {})` 会让用户看到一个"点了没反应"的按钮；
- **深链还原**：跳转前暂存目标路径（剔除 OIDC 协议参数、只收站内路径），回调后回跳——
  零点击跳转如果顺手把用户的目标丢在门外，是**本批引入**的新缺陷。

**门禁**：`W32-未登录落地即进统一认证`（真浏览器，22 条断言）覆盖：零点击到达、首屏不是应用登录卡
（挂住发现文档后采样，判据不靠抢时机）、页面自己发起 OIDC 的网络证据、深链还原、按「返回」不被弹回、
错误可见、dev 入口语义保留、登出后零点击回登录页。

## 5. C2 用户自助修改口令（须验旧口令）

### 5.1 三条候选路径（选型记录）

| 路径 | 旧口令校验方 | 需要的能力 | 优点 | 致命问题 |
| --- | --- | --- | --- | --- |
| **P1 前端直连 Keycloak Account API**（浏览器带自己的 token 调 `/realms/plm/account/credentials/password`） | Keycloak | `plm-web` 客户端 CORS + 用户持 `manage-account` | 口令不经 PLM 后端 | 新增浏览器→Keycloak 跨域面；错误语义/审计散落两处；PLM 侧无法统一留痕 |
| **P2 后端 + ROPC 校验旧口令**（后端用 `grant_type=password` 验旧口令，再用服务账号改） | Keycloak（ROPC） | 后端持有服务账号 `manage-users` | 实现最直白 | **依赖 ROPC**——而 `19 §8-1` 已把"生产关闭 ROPC"列为计划动作 ⇒ 本路径有**确定的失效日期**；且后端要同时握有管理权限与用户明文 |
| **P3 后端代理 Account API**（后端用用户自己的 Bearer token 转发到 Keycloak `account/credentials/password`） | Keycloak（Account API 内部校验旧口令） | 用户 token 含 `manage-account` | ① 旧口令只到 Keycloak；② 审计单点；③ 无浏览器跨域面；④ 不依赖 ROPC | **本环境不可用（PoC 实测）**：KC 26 已不挂载旧 Account REST API（见 §5.5 结果） |
| **P2′（采纳）后端 + 专用机密客户端的 ROPC 校验 + 服务账号改密** | Keycloak（ROPC） | 后端服务账号 `manage-users` + **仅该机密客户端**开启 `directAccessGrantsEnabled` | ① 旧口令校验由 Keycloak 完成（复用其爆破防护与策略）；② 审计与错误语义在 PLM 单点；③ 无浏览器跨域面；④ 验证的登录名**取自 token 主体**（不是请求参数）⇒ 不构成"任意用户的口令预言机"；⑤ ROPC 面被**收敛到一个内部机密客户端**（可在不影响公开客户端 `plm-web` 的前提下单独关闭） | 仍依赖 ROPC（但范围最小、可单独关闭、且现状 `plm-web` 本身已开 ROPC 供 CI 套件使用） |

**结论（2026-09-19 修订）**：采用 **P2′**。
- P3 原为首选，但 PoC 证明其在 KC 26 **不存在**（设计不能建立在"我以为有的接口"上）；
- P1（浏览器直连 Account API）同因不可用；
- P2′ 的已知代价（ROPC 依赖）被收敛为"一个内部机密客户端 + 一个只能验证调用者本人的端点"，并写进 `19 §4` 的敞口清单（实现期同批更新）。


### 5.2 端点语义

`POST /api/v1/_me/password`（body：`oldPassword`、`newPassword`、`confirmPassword`）

> **旧口令的校验方式（P2′）**：后端用机密客户端 `plm-backend-admin`（`directAccessGrantsEnabled=true`）对
> **token 主体的登录名**（不是请求参数）发起一次 `grant_type=password`；成功 ⇒ 证明调用者持有旧口令；
> 随后用服务账号 `reset-password(temporary=false)` 写入新口令。Keycloak 的 `bruteForceProtected` 对这次校验同样生效。

| 场景 | 结果 | 语义 |
| --- | --- | --- |
| 正常 | 204 + 前端提示「密码已修改，请使用新密码」 | 成功后**当前会话是否失效**：Keycloak 默认保留当前会话；本设计**保持会话**（避免"改密即被踢出"的体验坑），但在面板提示「其他设备上的登录会在 N 分钟后过期」 |
| 旧口令错误 | **400** + 「当前密码不正确」 | 计数由 Keycloak 爆破防护负责（`bruteForceProtected=true`）——**不在 PLM 自建计数器**（自建=第二套策略，易被绕过） |
| 新口令不合策略 | **400** + 策略原文（来自 Keycloak 错误响应，例如 `invalid_password` → 「密码长度不足（至少 12 位）」） | 前端**先做**同口径预校验（§5.4），后端仍是权威 |
| 新旧相同 | **400** + 「新密码不能与当前密码相同」 | 后端比对前先行拒绝（否则 Keycloak 可能直接接受，形成"改了个等于没改"） |
| 两次输入不一致 | 前端即时拦截（不发请求） | 前端校验不得替代后端校验 |
| 未认证 | 401 | — |
| 目标非本人 | **不存在该参数**（服务端以 token 主体为准） | 结构上杜绝"改别人密码"（§9 A3） |
| dev 模式 | **409** + 明确文案（§8） | 不静默成功、不静默 500 |

### 5.3 为什么"验旧口令"是必须的（不可省略的判据）

- 防"会话劫持后改密夺号"：只凭 token 就能改密 = 拿到 token 即永久占有账号；
- 与 §4 的管理员重置形成**两条不同强度**的路径：管理员**不需要**旧口令（处置场景），用户**必须**提供（自助场景）；
- 因此断言里必须有反例：**不带/带错旧口令一律 400，且口令未变更**（§10 B2）。

### 5.4 口令策略的单一事实源

- 策略定义在 **Keycloak realm**（`length(12) and notEmail and notUsername`，`plm-keycloak-security-policy.py` 为落地脚本）；
- 后端**不复制**策略常量：前端预校验用**保守同值**（长度 ≥12、非邮箱、非用户名）仅用于"即时提示"，**最终以 Keycloak 返回为准**；
- 策略变更只改 Keycloak + 前端的提示文案（提示文案里注明"以服务端为准"）；
- 断言：把策略设为 `length(16)` 后提交 12 位新口令 → **必须 400 且口令未变更**（证明后端没有把策略写死成 12）。

### 5.6 实现期实测事故：档案不全的账号"建得成、登不上"（**已修**）

**发现方式**：门禁 T3-16 的 B 组"建号后真登录一次"（而不是只看建号返回码）。

**现象与证据**（同一脚本三种建号体，实测对照）：

| 建号时写入的档案 | `POST /users` | 重置口令 | ROPC 登录 |
| --- | --- | --- | --- |
| `username` + `firstName`（**原实现**） | **201** | **204** | ❌ `invalid_grant: Account is not fully set up` |
| `+ lastName` | 201 | 400 | ❌ 同上 |
| `+ email`（`{login}@plm.local`，`emailVerified=true`） | 201 | 204 | ✅ **200** |

**根因**：realm 的**声明式用户档案**（`GET /admin/realms/plm/users/profile` 可查）把
`email` / `firstName` / `lastName` 标为 `required: {roles:["user"]}`。缺任一项 ⇒ Keycloak 拒绝签发令牌。
即：**两个成功码之后跟着一个永远登不上的账号**——调用方（管理员）看到的全是成功。

**修法（已实现，含一轮用户裁定后的返工）**：
1. `KeycloakAdminClient.ensureUser` 写全三件必填档案 + 建号后**读回校验**（`profileGaps`），
   缺项则**显式报错**（把"静默不可登录的账号"变成一次响亮的失败）；
2. `adminReset` 对**既有**账号同样先校验档案，并把 `loginReadiness` / `loginReadinessDetail` 写进响应与审计
   （口令照旧下发——管理员可能要先占住口令——但界面会明确告诉他"对方现在还登不上，缺 X"）；
3. 门禁增加 **B7/B10**（档案齐备 + 建号后可登录）与 **C4b**（`loginReadiness=ok`）。

> **口径升级（建议进 `19 §7` 新域检查表）**：凡"在外部身份源里创建/变更账号"的能力，判据必须包含
> **一次真实登录**（建号返回码与设口令返回码都不足以证明账号可用）。

#### 5.6.1 用户裁定：**不许合成身份字段**（本节 ⑤ 的返工，2026-09-19）

第一版修法为了"满足必填约束"，在**后端合成**了 `email={login}@plm.local`、`lastName='PLM'`
（沿用 `plm-keycloak-setup.sh` 的既有约定）。用户裁定否决：

> "创建用户时 UI 界面要支持用户输入所有必要字段。"

**理由（为什么合成是错的）**：合成值满足约束，却往身份源里写入了**看起来像邮箱、实际不可达**的数据。
将来任何基于 email 的能力（通知、口令找回、按邮箱匹配账号）都会**静默失效**——缺陷不会在写入时报出来，
而会等到某个下游功能上线才暴露。这与 §5.6 的原始事故是同一族（"看起来成功、实际不可用"）。

**返工实现**：
1. **数据模型补齐**（迁移 **V138**）：`t_user` 增加 `email` / `first_name` / `last_name`
   （**不加 NOT NULL**：存量 48 个账号没有这些值，硬加要么迁移失败要么逼出一次伪造回填；
   改为**在写路径上强制**，并把缺口显式暴露给管理员）。`email` 建**部分唯一索引**（`lower(email)`，NULL 不参与）。
2. **建号 API 强制必填**：`POST /_admin/users` 要求 `email`（含格式与唯一性校验）+ `firstName` + `lastName`，
   缺任一项返回 **400 并说明"凭据服务档案要求必填，缺它的账号无法登录"**；`displayName` 缺省由 姓+名 组合。
3. **建凭据账号不再兜底**：`CredentialService.ensureCredentialAccount` 从 `t_user` 取**真值**；
   缺字段时返回 **400 + 可执行下一步**（"请先在用户详情中补齐这几项"），**不合成**。
   已存在的账号则把 PLM 侧真值**同步**到 Keycloak（存量账号的占位值由此被订正）。
4. **界面采集全部必要字段**：建号表单 = 登录名 / 姓(lastName) / 名(firstName) / 邮箱（皆必填、前端即时校验）
   + 显示名（选填）；界面写明**为什么必填**；用户详情面板可对存量账号**补录/订正**；
   **用户信息 DataGrid 直接显示 `名(firstName)` / `姓(lastName)` / `邮箱` 三列 + `身份齐备` 判列**，
   缺值以「⚠ 待补」显式标出（不留空、不静默）。
5. **门禁**（防回归，正反成对）：
   - T3-16 **B2/B2b/B2c**：缺身份字段建凭据账号 → 400；**反证**不得出现合成邮箱；负向路径无副作用；
     **B5b/B5c**：建号 API 缺 email → 400、格式非法 → 400；
     **B8**：身份源里的 email **必须等于管理员录入的真值**；
   - W30 **N1–N6**：建号表单六个锚点齐备、界面写明必填理由、**DataGrid 含三个身份列**、
     缺值显示「⚠ 待补」、缺邮箱提交就地报错且**未创建任何账号**；**F4**：身份源 email == 录入真值。

> **口径（与 `21` 的治理口径一致）**：系统**不替用户编造事实**。必填约束由**采集**满足，
> 不可满足时**显式拒绝并指出下一步**，且缺口必须在界面上可见——"静默填充一个看起来合理的值"是最坏选项。

### 5.7 权限点归属的实测确认（`admin` + `pdt_manager`）

### 5.8 存量账号身份字段的一次性补齐（2026-09-19，用户指令）

**为什么需要**：V138 之前建的 48 个账号在 `t_user` 里没有 `email/first_name/last_name`
（其中 44 个完全为空）⇒ 它们是"身份不齐备"的账号：在凭据服务侧登录会被拒，
界面上也会显示「⚠ 待补」。用户指令：

> "已经创建的用户，按照其显示名，一次性补齐 firstname、lastname、email（名字拼音@plm.local）"

**规则（不是新发明，是把库里既有的先例覆盖到全部行）**：
库里原本已有 3 行进这个口径——`zhangming 张工 → fn=明 ln=张`、`clin1 秦淑珍 → fn=淑珍 ln=秦 email=qingshuzhen@plm.local`。

| 类别 | 判定 | 姓 / 名 | 邮箱 |
| --- | --- | --- | --- |
| 中文人名（去括号注解后 2–4 汉字） | `PERSON-CN`，39 例 | 姓=首字，名=其余（如 `孙志刚 → 孙/志刚`） | 姓名拼音 `sunzhigang@plm.local` |
| 英文人名（去注解后 ≥2 个 ASCII 词） | `PERSON-EN`，2 例 | 名=首词，姓=末词（`min zhang → min/zhang`） | `minzhang@plm.local` |
| 非人名（角色/技术账号：系统管理员、质量工程师、SE1、PDM Integration…） | `ROLE`，7 例 | 名=显示名，姓=login | `{login}@plm.local` |

**两条裁定**：
1. **以显示名为准**——例如 `zhangming` 的显示名是「张工」⇒ 取 `张/工/zhanggong@plm.local`
   （凭据服务里此前的「明」被覆盖，这是选定的口径：显示名是本系统的业务事实源）；
2. **保护真实邮箱**——身份源里已是**可路由**地址的账号保留原地址，不替换成拼音地址。
   实测命中 2 例：`zhang@qq.com`、`27621344@qq.com`（`robinzeng`）。
   **判定细节（易错）**：`.local` 是保留给 mDNS 的不可路由顶级名、`example.com/org/net` 是 RFC 2606 保留示例域
   ⇒ 二者都算**占位**、不算真实。首版规则只排除了 `plm.local/example.com`，于是把
   `pdm-integration@kefu.local`、`pm-ipd@ipd.local` 误判为"真实邮箱"而保留下来（已在试算阶段修掉）。

**执行与结果**（脚本 `ipd/deploy/wsl/plm-app/plm-b37-identity-backfill.py`，默认试算、`--apply` 才写）：

| 项 | 结果 |
| --- | --- |
| 写入 | PLM **48/48**、凭据服务 **48/48**（两边一致） |
| 自检 | 仍缺身份字段的账号 = **无**；`email` 库侧唯一 = **唯一**；身份齐备 **48/48** |
| 真邮箱保护 | `zhang@qq.com`（PLM=IdP=zhang@qq.com）、`27621344@qq.com` 均保留 |

> **教训（已进 `lessons.md` L-474）**：脚本要在 WSL 里同时写 PLM 与凭据服务；首版把 API 基址写成
> `127.0.0.1:5173` —— **端口写错**（5173 此处并未提供服务），于是出现"凭据服务 48/48 成功、PLM 0/48 失败"的
> **半途状态**（两边不一致）。
> **订正后的准确事实**：PLM 后端在 **8081**，且 **WSL 内可直达**（实测 `curl localhost:8081` → 401 = 服务在场）；
> 前端同源代理 `http://localhost:5174/api/v1` 亦可（浏览器走的就是它）。
> 处置：脚本基址改为**直连 8081**（少一跳），复跑后两边齐平；并把"多存储写入前先探测各端点可达性、
> 且**不要把'端口不通'误当成'服务不可达'**"写入规程。

> ⚠ **本补齐是一次性数据订正，不是长期机制**：**新增账号**的身份字段由界面采集（§5.6.1），
> 系统不合成；若再有存量缺口，界面已能一眼看出（「身份齐备=缺失」+「⚠ 待补」）并可逐条补录。

| 焦点 | 打开后焦点进入面板（第一个可交互元素），`Esc` 关闭后焦点回到 `user-chip`（键盘可达，`08 §7`） |
| 锚点 | `data-testid`：`my-profile-panel`、`mp-login`、`mp-display-name`、`mp-roles`、`mp-auth-mode`、`mp-pwd-old`、`mp-pwd-new`、`mp-pwd-confirm`、`mp-pwd-submit`、`mp-pwd-msg` |

| 只读字段口径 | 事实源 |
| --- | --- |
| 登录名/显示名/角色 | PLM `t_user` + `t_user_role`（与 `/_admin` 同一读口径，但**只读自己**） |

## 7. 后端契约

### 7.1 端点表

| 端点 | 方法 | 权限 | 请求 | 响应 | 审计事件 |
| --- | --- | --- | --- | --- | --- |
| `/_admin/users/{id}/credential/reset` | POST | `@permissionService.can('_admin','user.credential.reset')` | 空 | `{login, temporaryPassword, expiresHint:"首次登录必须修改", generatedAt}` | `admin.user.credential.reset`（**不含口令**） |
| `/_me` | GET | 已认证（仅自己） | — | `{login, displayName, roles[], authMode, credentialTemporary, passwordChangedAt}` | 不记（只读） |
| `/_me/password` | POST | 已认证（仅自己） | `{oldPassword, newPassword, confirmPassword}` | 204 | `me.credential.change`（成功/失败都记，**不含口令**） |
| `/_admin/users` | POST | 既有 `_admin.user_role.assign` | 既有 + 可选 `createCredential: true` | 既有 + `credentialCreated` | 既有 + `admin.user.credential.create` |

> 命名与既有风格一致（`/_admin` 治理面、`/_me` 自助面）；`/_me` 前缀为**本设计新增的约定**，用于"只能操作自己"的一族端点（后续"我的待办/我的通知"可归入，避免再发明第二个前缀）。

### 7.2 权限点登记（`t_permission_rule` 口径）

| 域 | 动作 | 角色 | 说明 |
| --- | --- | --- | --- |
| `_admin` | `user.credential.reset` | `admin`, `pdt_manager` | 与既有 `_admin.manage`/`user_role.assign` **分开**：重置口令是"应急处置"权限，不应随"能配角色"自动获得 |
| `_admin` | `user.credential.create` | `admin`, `pdt_manager` | 建号时同步建凭据 |
| `_me` | `read` / `write` | 所有已认证角色 | 仅自己；`PermissionService` 无需参与（主体即最小范围），但**必须**进 `PermissionConsistencyCheck` 的登记表以免成为"未登记的口子" |

### 7.3 配置项（不引入默认口令/默认密钥 — INV-2）

```yaml
plm:
  keycloak:
    admin:
      base-url: ${PLM_KEYCLOAK_ADMIN_URL:http://plm-keycloak:8090}   # 无默认口令
      realm: ${PLM_KEYCLOAK_REALM:plm}
      client-id: ${PLM_KEYCLOAK_ADMIN_CLIENT_ID:}                    # 未配置 ⇒ 端点返回 503（显式不可用）
      client-secret: ${PLM_KEYCLOAK_ADMIN_CLIENT_SECRET:}            # 未配置 ⇒ 同上；**不得**有 `:-admin` 之类兜底
      # 自助改密的旧口令校验（P2′）：复用同一机密客户端（需 directAccessGrantsEnabled=true）
      # 其公开客户端 plm-web 的 ROPC 与它无关，可各自独立关闭
```
- 未配置即**拒绝服务该能力**（503 + 文案「凭据服务未配置」），而不是退回某种"开发默认"；
- 密钥来源：compose 的 env（生产改密钥托管，随 `19 §8-1` 那批一起做）；**不入库、不入日志**；
- `19 §5` 要求：改安全配置同批更新 `19 §4` 与 KB。

## 8. dev / oidc 双模式口径（**不得静默**）

| 模式 | C1 管理员重置 | C2 自助改密 | C3 我的信息 |
| --- | --- | --- | --- |
| `oidc` | 正常 | 正常 | `authMode: OIDC`；凭据状态可读 |
| `dev`（`X-PLM-User`，无凭据体系） | **409** + 「当前为 dev 认证模式：口令由凭据服务（Keycloak）管理，dev 身份没有口令可重置」 | **409** + 「dev 认证模式下没有口令；请切换到 OIDC 登录后修改」 | 面板照常显示 `authMode: dev`，**改密区整体禁用**（灰按钮 + **可见原因**，遵循 `08 §9` 陷阱 28 同族的"禁用必须给理由"） |

口径来源：`19 INV-3`（旁路显式、可关闭、不可隐式开启）——dev 模式本身是"显式旁路"，
因此"在 dev 下密码功能不可用"必须**说出来**，而不是返回 200 什么也没做（那会制造"我改了密码其实没改"的假象）。

## 9. 安全与合规断言（本设计的判据主体）

| ID | 断言（可判定） | 反例（必须同时成立） |
| --- | --- | --- |
| **A1** | 管理员重置后，用**临时密码**可登录，且登录后被要求改密（`UPDATE_PASSWORD`） | 改密前用原密码登录 → 失败 |
| **A2** | 口令**不落任何持久化**：审计行、应用日志、响应缓存中 `grep` 不到临时密码/新口令明文 | 反例：审计正文含口令 → 判红（用"注入可识别口令串 + 全库/日志扫描"实现） |
| **A3** | `/_me/password` **只能**改自己：以 A 的 token 请求、body 里带 B 的用户名 → 仍只可能改 A（结构上无该参数）；响应无 B 的任何信息 | 反例：任何"能改他人"的路径存在 ⇒ 判红 |
| **A4** | 两库一致：`t_user.login` 与 Keycloak 用户集合的差集被**显式报告**（`/_admin/users/credential-consistency`），且 CI 对账为 0 缺口 | 反例：`t_user` 有、Keycloak 无 ⇒ 必须出现于报告（否则"看不见"= 静默） |
| **A5** | 服务账号为**最小授权**：只有 `manage-users` + `view-users`；用它调 `DELETE /admin/realms/plm` 之类 → 403 | 反例：能改 realm 设置 ⇒ 判红 |
| **A6** | 旧口令错误 **400 且口令未变更**（用新口令登录失败、旧口令仍可登录） | — |
| **A7** | 未认证/无权限：`/_admin/users/{id}/credential/reset` 无 token → 401；非 `admin/pdt_manager` 身份 → 403（**正反成对**，`19 §7`） | — |
| **A8** | 一次性：重置响应里的临时密码**不可二次获取**（无取回端点；再调 = 生成新的一次性密码，旧值失效） | — |
| **A9** | 爆破防护仍生效：对同一用户名连续 5 次错误旧口令 → 该账号被锁（Keycloak 策略），PLM 侧错误码保持 400/423 语义一致 | 反例：PLM 自建计数器把 Keycloak 策略遮蔽 ⇒ 判红 |

**测试隔离纪律（硬性）**：口令类断言**必须**用**专用一次性测试账号**（如 `t_pwdchk_<runid>`），
自建自清（用完删除 Keycloak 账号 + `t_user` 行），**禁止**改任何既有测试账号（`robin`/`zhangming`/`se1`/…) 的口令——

### 10.1 部署环境门禁（批次38 增补 —— 本能力曾"只在 dev 可用"）

**事故**：本能力（C1 重置口令 / C2 自助改密）在 dev 正常，但 **UAT 上所有口令端点返回 503
「凭据服务未配置：本能力需要 PLM_KEYCLOAK_ADMIN_CLIENT_ID/SECRET（不在代码里放默认口令）」**。

**根因（单点、可复现）**：`ipd/deploy/uat/docker-compose.uat.yml` 的 `plm-service.environment`
里**没有** `PLM_KEYCLOAK_ADMIN_*` 三项，`/opt/plm-uat/compose/.env` 里也没有 ⇒ 容器内
`plm.keycloak.admin.client-id` 为空 ⇒ `KeycloakAdminClient.configured()==false` ⇒ `requireConfigured()`
抛 503。dev 之所以正常，是因为 `release-plm-app.sh` 显式加载 `.plm-keycloak-credential.env` 注入。

**关键证伪**：现象**不是**"第一次能用、后来坏了"——UAT 边缘日志显示对 `users/1`、`users/58`、
`users/101` 的三次 `credential/reset` **全部** 503（`2026-09-20T00:24–00:27Z`），
与"哪个用户/第几次"无关；容器自 `2026-09-19T21:57Z` 起从未重启，环境变量自始至终为空。

**修法（三层，缺一层都还会复发）**：

| 层 | 产物 | 判据 |
| --- | --- | --- |
| 编排 | `docker-compose.uat.yml` 补三项（**仍不给默认值**，保持"未配置=显式 503"） | `docker compose config` 解析出非空 |
| 注入/密钥 | `provision-uat-credential.sh` + `remote/credential-client-payload.sh`：幂等校正客户端与最小授权，**密钥以本环境 Keycloak 库为准**写回 `.env` | 服务账号 token → 读用户 200 / 改 realm 403 / ROPC 错口令 400 |
| 门禁 | `smoke-uat.sh` I-2（容器视角配置断言）+ `verify-uat-credential.sh`（29 条端到端行为断言） | 末尾 503 反向断言 + 夹具残留 0 |

**密钥归属口径（SF-U08）**：UAT 的 `plm-backend-admin` 目前与 dev **同一把 secret**（同源库快照带来），
经裁定本批**先复用**；风险是"从 UAT 快照还原 dev 会覆盖 dev 密钥"⇒ 两侧 provision 脚本均须可幂等重跑。
后续项：UAT 独立密钥轮换。

**工程口径（两条，写入 lessons）**：
① **"dev 全绿"不等于"部署环境可用"**——凡"依赖外部服务凭据的能力"，其门禁必须**每个部署环境各有一条**，
且断言要落在**该环境的注入面**（容器 env / compose 解析结果），不能只测应用逻辑；
② **断言不得依赖机密值的内容**——首版门禁写 `grep 'SECRET: "?plm'`（假定开发密钥以 `plm` 开头），
而真实密钥是随机串 ⇒ 配置正确也报"为空"。断言只依赖结构与长度。
