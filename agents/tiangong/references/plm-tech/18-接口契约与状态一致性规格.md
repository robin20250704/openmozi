# 18 · 产品级通用规格：接口契约与状态一致性

> **本文回答什么问题**：同一件事在系统里有几种说法？哪些"看起来成功"的操作其实没写进去？
> 本文是**长期有效**的产品级规格（不随批次失效）；批次证据留在任务目录与电容器里。
> 来源：批次28（PRJ-2026-0087 于 2026-09-18 提交的 6 条 PROPOSED 需求）——其中 5 条是同一族缺陷的不同侧面。

## 1. 错误契约（E-1~E-5）

| # | 条款 | 判据 / 现状证据 |
| --- | --- | --- |
| **E-1** | **任何 4xx/5xx，无论由 MVC 层还是 Servlet 过滤链产生，都返回同一形状 `{code, message, ts}`**。两个出口共用同一份序列化（`GlobalExceptionHandler` 负责 MVC，`ApiResponses` 组件负责过滤链，**两者都用容器里的同一个 `ObjectMapper`**），**不得**各写一套 | 批次28 实测：带 token 的 400 有结构化体，**不带 token 的 401 体为空**——调用方必须写两套解析，空体在自动化里还会被读成"服务端没响应"而不是"你没带凭据"。修法：`SecurityConfig.exceptionHandling(authenticationEntryPoint / accessDeniedHandler)` |
| **E-1b** | **中文错误体必须按"UTF-8 字节数"设 `Content-Length` 并显式 flush**。禁止 `mapper.writeValue(response.getWriter(), …)`：容器会按**字符数**算长度，中文一字 3 字节 ⇒ 响应被截断成半个 JSON | 批次28 实测（**修法首版就是错的**）：`Content-Length: 216`，客户端只收到 136 个字符（正好断在 `realm=plm)` 后），`JSON.parse` 报 `Expected ':' after property name at position 136`。现口径：`writeValueAsBytes` → `setContentLength(bytes.length)` → 写 OutputStream → `flush()` |
| **E-1c** | **容器错误派发路径 `/error` 必须在过滤链上放开**（否则 `sendError` 派发被 `anyRequest().authenticated()` 拦下 → 二次 `AccessDeniedException` 发生在**响应已提交之后** → 连接被中断，客户端看到 `socket hang up` 而不是可读错误） | 批次28 实测：`Content-Type: text/plain` 请求返回 socket hang up，服务端日志 `Unable to handle the Spring Security Exception because the response is already committed` |
| **E-2** | **状态码承担语义**：客户端据此做不同决策的情形必须给不同码。已定口径：`401` 未认证 / `403` 已认证但无权限 / `404` 路径寻址资源不存在 / `405` 方法不支持 / `413` 实体过大 / `415` 媒体类型不支持 / `416` 区间不可满足 / `400` 入参或业务规则不满足 | 批次28 实测：`Content-Type: text/plain` 与**不带 Content-Type**（被判为 `application/octet-stream`）都返回 `400 SERVER_ERROR: Content-Type … is not supported`——调用方只会怀疑服务端，而真实处置是"改用 application/json" |
| **E-3** | **枚举/受控值域的拒绝文案必须附合法值清单**，且清单**从元数据读**（不是代码里的常量副本） | `MetadataService.validateAttrWithValues`（REQ-2026-0844 起）；批次28 把 `source_channel` 的清单也改成从 `t_attr_template` 读 |
| **E-4** | **文案指向的动作必须真的可行**（`C-099`）：拒绝时给的三条出路都要能走通，否则等于把合法工作流堵死 | 反例：需求曾报"请走变更 ECO"，而需求域根本没有 ECO 通道；批次28 的"评审期退回"也差点造出同型路障（见 §4） |
| **E-5** | 技术细节（堆栈/类名）**不进对外文案**，只进服务端日志；兜底出口用类型化文案 | `GlobalExceptionHandler.generic`（REQ-2026-0909） |

## 2. 请求级记忆的写后失效（M-1~M-4）

`RequestCache` 是**请求级**记忆（同请求内同一事实只查一次；请求结束即失效）。它带来一个必须成对遵守的纪律：

| # | 条款 | 判据 / 现状证据 |
| --- | --- | --- |
| **M-1** | **写路径必须失效**：本请求内先读、后写同一张表时，写完必须 `invalidatePrefix` / `invalidateAll`。表清单与既有调用点：AdminController（角色/ABAC/用户角色）、GovernanceService（角色到期）、ProjectService（建项目落 PM 成员）、PermissionService（权限点种子） | 类注释原文即此纪律 |
| **M-2** | **纪律要落到"唯一出口"而不是"记得加一行"**：写某张表的函数应合成一个入口（如 `ReviewService.signerWrite(reviewId, sql, args…)`），入口内完成"写 + 失效" | 批次28 REQ-2026-2050：合并签署**插了签署行**，同请求内 `chairSigned` 又命中写前记住的**空表** ⇒ `400 SIGNER_REQUIRED` 并把签署行与留痕审计**一起回滚**（现场只剩一句"签署后方可判定"，无法反推）。两步路径（两个 HTTP 请求）因此不受影响——**只有"同请求内先读"的用例能测出来** |
| **M-3** | **失效要覆盖 INSERT 与 UPDATE**：状态翻转（作废/撤回/释放）改的是同一张表 | 同一批把否决/撤回/意见/作废签署 6 条写路径统一收口 |
| **M-4** | 新增这类记忆前先问：**本请求内会不会写它**？会写就别记（或必须记就配失效） | 批次27 引入记忆是为消除读放大（列表 263 次全表扫），收益真实；但**收益不能靠放宽正确性换** |

## 3. 内容写必须留痕（V-1~V-4）

| # | 条款 | 判据 / 现状证据 |
| --- | --- | --- |
| **V-1** | **每一次"内容写"都必须推进可观察的版本面**：`updated_at` 前进 +（有版本列者）`version` 递增。二者是"改前/改后能否区分"的最小事实 | 批次28 REQ-2026-2111：`PUT /requirements/{id}` 改完标题，`version` 与 `updated_at` **都不动**（列声明 `updatable=false`，而库侧**无触发器**——实测 `pg_trigger` 为空）⇒ 列表「最近更新」列与 `updatedFrom/To` 筛选失真；同域的 `transition()`/`backfillSolution()` 本来就推进 version，`update()` 是**遗漏**而非设计 |
| **V-2** | **不要假设"数据库会自动维护时间戳"**：本项目没有 `updated_at` 触发器；要么服务层显式写，要么有迁移明确建触发器。发现注释与现实不符时，**以 `pg_trigger` / 列定义实测为准**并订正注释 | `V11__attrs-updated.sql` 注释写"updated_at 列已存在，DB 自动维护"——实测不成立（本条约定的由来） |
| **V-3** | **时间戳精度口径要写明**：PG `timestamptz` 为**微秒**精度，Java `Instant` 为纳秒 ⇒ 库内值必然被截断，**逐位相等不成立**；跨层比较用"同一时刻 + 容差窗口"表达 | 批次28 用例先按逐位相等写，实测假红（`…058374Z` vs `…058374440Z`）；改为"响应 ∈ [库内值, 库内值+1s]" |
| **V-4** | **字段级审计**：主数据/治理字段的变更要记 `before → after`（键级差异，不记整体哈希）；审计不可用"history 查不到"冒充"没人改过" | `REQ-2026-1084`（项目域）、批次28 给 `clinicalPath` 补上与 `medClass/targetMarkets` 同口径的字段级审计 |

## 4. 业务流/工作流变更的三条判据（W-1~W-3）

| # | 条款 | 判据 / 现状证据 |
| --- | --- | --- |
| **W-1** | **加边之前先问"这条边上去，路是不是通的"**：新状态/新边必须检查它在**其它守卫**下是否可达（同门唯一性、对象状态白名单、可编辑性集合） | 批次28 REQ-2026-2051 差点造出"给了路、路上有门"：任务书处于 `DCP0_REVIEW` 时**必然**存在一条 `IN_REVIEW` 的 DCP0 评审，而 `POST /reviews/request` 的守卫是"同任务书不得有 IN_REVIEW 的 DCP0 评审"，且 **`t_review.status` 只有 PLANNED/IN_REVIEW/DECIDED 三值、无"作废"值、也无作废在飞评审的入口** ⇒ 退回后重新提交必被拦 |

| **W-3** | **状态域变更（加状态值）必须单独审批**：`t_review.status` 之类的值域是"状态机"的一部分，扩值 = 改模型，需用户裁定 + 迁移 + 各读取面（待办预检/唯一性守卫/驾驶舱/门线）同步处置 | 同上（本批**没有**扩值域，正因为口径被否） |

## 5b. 可选关系字段的读写契约（R-1~R-3；批次54B 立，源自需求「所属产品」）

> 需求「所属产品」（`t_requirement.product_id`）是本仓**第一个"可空关系字段 + 服务端推断"**的字段。
> 实测出的三条坑对**所有**同类字段都成立（项目归属、父需求、归属产品、后续任何"从上级推断"的字段），故立为契约。

| # | 条款 | 判据 / 现状证据 |
| --- | --- | --- |
| **R-1** | **可空关系字段有且只有三种态，且三态必须在界面上可区分**：① **未归属**（id 为空，**正常态**，不是"加载中"也不是异常）；② **已归属**（id + **业务键**，对外不得给内部 id，见 C-135）；③ **悬空**（id 有值但业务键取不到 ⇒ 显示 `#id` 并标注，**不得**显示成"未归属"） | 批次54B `ReqProductAssignBatch54Test#danglingReferenceIsDistinguishable`：物理删除产品后 `productId` 仍在而 `productCode=null`——若把两者都读成空，一条"指向不存在产品"的需求会被静默读成"还没填"，永远不会有人去修。界面侧：网格列三态各有其词（编号 / 编号（推断）/ 未归属），W91 P6b |
| **R-2** | **部分提交不得清空未提交的字段**：可空关系字段的 `null` 语义必须是**"本次没改"**，显式清空要走**独立开关**（如 `clearProduct:true`）；"既给值又要求清空"是**歧义请求，400 拒绝**，不猜 | 批次54B B6/B7/B5。这是本仓**最容易静默做错、且做错没有任何报错**的一类：面板是"只提交改动字段"的形态，若把 `null` 当清空，任何一次只改标题的保存都会把归属抹掉，用户看到的只是"值不见了" |
| **R-3** | **系统推断出来的值必须与用户填写的值可区分**（只读投影如 `productInferred`），且**推断只在写入时发生、不静默回填存量**；不推断的后果（存量行为空）必须在界面空态里**如实写出条数** | 批次54B `resolveProduct` 规则 ①~④（设计 15 号文 §8.4）+ W91 P3a/P4d。反例代价（4 号文同族）：`t_project.product_id` 的"镜像列 vs 权威列"之争——把推断结果当用户填写上屏，用户会以为系统记下了他的选择。**本批实测：505 条存量需求可从项目推断却不回填**，故 54C 的视图初期会偏空 ⇒ 空态必须自披露口径 |
| **R-4** | **统计面（图表/词云）的下钻必须在服务端过滤，且过滤条件必须在落地页可见**。前端过滤 + 服务端分页 = 口径打架（"第 1 页 3 条、第 2 页 2 条、总数是全量"）；而"带参数跳过去但落地页不读参数"更坏——用户以为"我点的那个词没有相关需求" | 批次54C：买点视图点维度/词 ⇒ `/requirements?productId=&appealsDim=`/`&buyPointTerm=`。落地页（需求清单）改造三件：① 读 URL 初值（入口语义，不做双向同步）；② **可见筛选条**逐条可清除（本仓对"看不见的筛选"的既有定性：用户会以为数据丢了）；③「清空全部筛选」必须一并清掉它们。服务端两个新筛选复用**既有 id 求交机制**（与处理人/基线同一段代码），不新拼一套 SQL（V-186） |
| **R-5** | **可点即须可达**：画布/图表里的可点元素（词云、自定义图形）必须另有**键盘可达的等价形态**，且该形态同时是走查的**确定性锚点**——否则"点得中吗"只能靠猜坐标，判据会假红或假绿 | 批次54C 词云（ECharts `custom` 系列自绘）：设计稿只写了画布。落地时补一行真按钮的"词表条"——① canvas 对键盘用户等于不可用；② 走查若靠猜画布坐标命中"第一个词"，"没命中"会被读成产品缺陷（L-891 同族：判据缺陷伪装成产品缺陷） |

## 5c. 项目主数据字段的可写窗口契约（K-1~K-4；批次64 立）

> 批次64 的两条诉求落在这里：**创建时应当能选产品种类**（此前全站无入口），**DCP0 之后管理类别应当锁死**。
> 二者的共同结构是「同一个字段在不同时点归谁写」——本仓此前把 `product_kind` 做成"永久只读＋建后走治理变更"，
> 把 `med_class` 做成"永久可写"，两头都缺了**窗口**这个概念。

| # | 条款 | 判据 / 现状证据 |
| --- | --- | --- |
| **K-1** | **字段写权必须按窗口声明，不能按字段一刀切**：每个项目主数据字段只能是「创建时写（建后只读）」/「全程可写」/「建后 N 时点锁死」三者之一，必须在接口契约里明写，并与界面一致（只读就渲染只读、可写就给控件） | 本批实测：`ProjectsPage.tsx:961` 把 `productKind` 声明成 `kind:'text', readonly:true`，而 `productKind` 在整个前端**只出现在 `ProjectsPage` 与 PCO 差异展示**，没有任何创建入口能设置它 ⇒ 用户在创建表单看到的是一个永远为空的只读文本框。库上 **6 条产品主档 5 条 `product_kind` 为空、71 个项目 70 个未分类** ⇒ 该维度事实上从未被使用 |
