# 26 · 项目目标与达成率设计

> 定位：把**散落在 `t_project.attrs` 自由 JSONB 与立项书自由 JSON 里的项目目标**，收敛为**项目的一等子对象**（带版本管理、可受控变更、可算达成率）。
> 依据：用户裁定 **D-P1~D-P9**（见 §1），以及 2026-10 实测摸底（§2，带查询与实测值）。
> 上游：`docs/plm-design/ipd-extension/02-IPD信息架构扩展设计.md` §2.2/§2.6（T_BIZ_PLAN / T_PROJECT 修正）、`docs/plm-tech/23-变更域三单据与工作台设计.md`（D-18「转变更单必须由人点」纪律）、`docs/plm-design/06-权限模型设计.md` §5（敏感字段名单）、`docs/plm-tech/21-治理台与权限治理设计.md`（`t_sensitive_field` 登记表）。
> 下游：`27-项目变更单设计.md`（PCO 变更目标）、`28-资金对象与币种换算设计.md`（金额类型）、`ipd/plm-app/backend`（`domain/project` 新增目标/达成子域、迁移 V200+）、`frontend/src/pages/ProjectsPage.tsx` / `ProjectObjectivesPanel.tsx`。
> 断言：`ProjectObjectiveIntegrationTest`（14 例）+ 受影响面定向回归 11 个测试类 78 例，见 **§12.4**。

## 0. 一句话结论

**项目目标从"自由 JSONB 里的一堆键"变成 `t_prj_obj_dim` + `t_prj_objective` + `t_prj_objective_rev` 三张表承载的一等子对象**；`t_biz_plan_rev`（立项书）**由"目标的权威来源"降为"初始目标的权威来源"**——它提供**第一版**目标，之后每次变更由 `t_prj_objective_rev` 版本承接；达成情况独立成第四张表。

**兑现时点有两个，但不是两套机制**（`D-P10`/`D-P13`/`D-P14`）：

| 承诺类型 | 兑现时点 | 冻结触发 |
| --- | --- | --- |
| **研发承诺**（投入三科目 / BOM 成本 / 上市时间） | 上市当天 | `上市 → 维护` 流转**同事务**结账，**零新端点** |
| **经营承诺**（售价 / 耗材毛利率 / 首年销量） | 上市后 180 / 365 天 | `t_open_issue` 的 `due_date` 驱动，**到期未结账红标**（复用仓内已落地的 OVERDUE 机制） |

**但本轮最重要的结论来自实测（§2）：60 个项目里只有 3 个有目标数据、只有 1 个有 `targetBomCost`、里程碑与任务合计 18 条且多为测试垃圾数据、`t_capacity` 与 `t_fin_model` 均 0 行。** ⇒ **本轮不做看板/驾驶舱徽标/资源负荷**，只把结构与计算能力做对；把"看起来很完整但没数据"的仪表盘推迟，是本设计最大的克制。

## 2. 实测摸底基线（Q1，2026-10）

> 数据源：dev 环境 `plm-pg`（`docker exec -i plm-pg psql -U plm -d plm`）。查询与实测值如实登记，**不凭设计文档推断**。

### 2.1 项目与阶段分布

```sql
SELECT status, count(*) FROM t_project GROUP BY status ORDER BY 2 DESC;
--  概念 | 51   已终止 | 5   立项 | 3   开发 | 1     （合计 60）
```

**★ 关键事实：51/60（85%）在「概念」阶段、仅 1 个在「开发」。** `project-flow.yaml` 的 `editableStatuses: [立项, 概念, 计划]` ⇒ **绝大多数项目当前仍可直接编辑**。这意味着 PCO 的"计划阶段后须走变更"锁**现阶段几乎不生效**，其价值要等项目真正推进后才显现（这本身是合理的：未立项完成的项目当然可自由调整承诺）。

### 2.2 门线实况

```sql
SELECT review_type, gate_code, status, count(*) FROM t_review GROUP BY 1,2,3 ORDER BY 2,3;
--  DCP | DCP0   | DECIDED   | 78      DCP | DCP0   | IN_REVIEW | 1
--  DCP | DCP1   | DECIDED   |  4      DCP | DCP1   | IN_REVIEW | 2
--  DCP | DCP2   | DECIDED   |  1
--  TR  | TR1    | DECIDED   | 10      TR  | TR1    | IN_REVIEW | 1
--  TR  | TR2    | DECIDED   |  8
--  TR  | TR3    | DECIDED   |  1
--  （DCP_ES / DCP3 / TR4 / TR5 / TR6 = 0 条）
```

- 57 个项目有 `DECIDED` 评审，但**绝大多数只到 DCP0**。
- **只有 3 个项目真正走到 DCP1/DCP2**：`298`（DCP1×2 + DCP2）、`1238`（DCP1）、`1244`（DCP1）。
- **DCP1 的 4 条 DECIDED 结论全部是 `GO_WITH_RISK`**（无一条纯 `GO`）。
- **`DCP_ES` / `DCP3` / `TR4` / `TR5` / `TR6` 完全空白** ⇒ 阶段门体系在真实数据上只跑到"开发决策"。

**⇒ 对门禁影响评估的直接约束**（详见 `27 号文` §5）：L1 候选门点表里 `DCP_ES/DCP3/TR4~TR6` 的映射**当前无对象可影响**；L2 预检项的实用面在 `DCP1 / DCP2 / TR1~TR3`。**不为不存在的门点写代码。**

### 2.4 `attrs` 目标键实况（"分散字段"的活标本）

## 3. 目标维度体系

### 3.1 `t_prj_obj_dim` —— 维度定义（**科目可配置**的落点）

```sql
CREATE TABLE t_prj_obj_dim (
  dim_code      TEXT PRIMARY KEY,
  dim_label     TEXT NOT NULL,
  category      TEXT NOT NULL CHECK (category IN ('PROJECT_COST','PRODUCT_COST','MARKET','SCHEDULE','QUALITY')),
  value_kind    TEXT NOT NULL CHECK (value_kind IN ('MONEY','QTY','RATE','DATE')),
  unit          TEXT,                       -- 展示单位（'万元' / '台' / '天' / '%'）
  currency      TEXT,                       -- MONEY 必填；合法值读 common.Currencies
  direction     TEXT NOT NULL CHECK (direction IN ('LOWER_BETTER','HIGHER_BETTER')),
  actual_source TEXT NOT NULL DEFAULT 'NONE' CHECK (actual_source IN ('AUTO','MANUAL','NONE')),
  eval_offset_days INT NOT NULL DEFAULT 0,   -- D-P14：相对「上市日」的承诺兑现期限（天）；0=研发承诺（上市即结账）
  source_attr   TEXT,                       -- 从 attrs 迁来的原键（可追溯，勿删）
  active        BOOLEAN NOT NULL DEFAULT TRUE,
  sort_no       INT NOT NULL DEFAULT 0,
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**为什么是表而不是 CHECK 枚举**：`D-P2` 明确"具体分哪几个科目后续可能需要根据不同企业特点调整"。做成表 ⇒ 新增「差旅费」「工装摊销」「临床费」是**加一行 + 前端自动出列**（与 `t_attr_template` 驱动列同一范式，`columnDefs(objType)`），**不改代码、不改表结构**。

**单位必声明**（`V81` 教训原文："实测跨对象口径冲突的根源之一就是单位未声明，缺单位时数字无法比较"；§2.4 的 `budget` 1800 vs 200 即活证据）。金额类统一走 `28 号文` 的资金对象，`unit` 只作**展示单位**（`MONEY` 的 `unit` 固定为 `10000` 分之一之类的换算因子声明，见 `28 号文` §3）。

### 3.2 ★ `D-P2a`：项目成本 vs 产品 BOM 成本是两个概念

| 概念 | 是什么 | 维度 | 目标值来源 | 实际值来源 | 变更审批 |
| --- | --- | --- | --- | --- | --- |
| **项目投入成本** | 研发花了多少 | `LABOR` 人力 / `MATERIAL` 物料 / `EXPENSE` 费用（**科目可增**） | **金额**（`D-P7`：人数仅参考） | **MANUAL**（工时/费用系统在本仓外） | `BUDGET` → **IPMT 主任** |
| **产品 BOM 成本** | 制造一台的料工费 | `BOM_COST` | `attrs.targetBomCost` 回填 | **AUTO**：`ItemService.costCompare().bomCost` | `GOAL` → **IPMT 主任** |
| **产品目标售价** | 卖一台多少钱 | `PRICE` | `attrs.targetPrice` 回填 | `MANUAL` | `GOAL` → **IPMT 主任** |
| **耗材毛利率** | 耗材业务毛利 | `CONSUMABLE_GM` | `attrs.consumableGrossMargin`（`D-P8`） | `MANUAL` | `GOAL` |
| **耗材复购周期** | 客户复购间隔 | `CONSUMABLE_RPT_MONTHS` | `attrs.consumableRepurchaseMonths`（`D-P8`） | `MANUAL` | `GOAL` |
| **上市时间** | 承诺哪天上市 | `LAUNCH_DATE` | **立项书 / 里程碑派生**（`D-P9`） | `AUTO`：`t_milestone.actual_date` | `GOAL` → **IPMT 主任** |
| **首年销量** | 商业承诺 | `YEAR1_VOLUME` | `attrs.year1Volume` | `MANUAL`（ERP/销售域） | `GOAL` → **IPMT 主任** |

> **曾经的口径错误（本设计显式纠正）**：讨论初稿把 `TARGET_COST` 的目标值接 `attrs.targetBomCost`、实际值接 `costCompare().bomCost` —— **这两个都是产品侧**，被当成"项目成本"。合并成一个维度会把"研发投入"与"制造成本"两个**责任人不同、达成方向不同、变更动因不同**的口径搅在一起。这正是 `attrs` 里 `targetBomCost` 的原罪，也是仓内已付出代价的地方：`V103` 记录了"项目 520 / 产品 40 / 任务书 905"三方不一致，`V81` 记录了"销量 charter 1.5 万台 vs 计划 3 万"冲突。

**`devHeadcount`（人数）不作为目标维度**（`D-P7`）：它是**参考信息**，不是可承诺的金额目标。处置见 §8（留在 `attrs` 并登记元数据）。

**`eval_offset_days`（`D-P14`）：承诺兑现期限 = 相对「上市日」的天数。** 上表逐维度取值：

| `eval_offset_days` | 维度 | 语义 |
| --- | --- | --- |
| **`0`** | `LABOR` / `MATERIAL` / `EXPENSE` / `BOM_COST` / `LAUNCH_DATE` | **研发承诺** —— `上市 → 维护` 流转时同事务结账 |
| `180` | `PRICE` / `CONSUMABLE_GM` | 上市后半年结账 |
| `365` | `YEAR1_VOLUME`（**首年销量本就该一年后结算**）· `CONSUMABLE_RPT_MONTHS` | 上市后一年结账 |

**期限是维度属性、不写死在代码里**（与"科目可配置"同一范式）；到期未结账由 `t_open_issue` 的 `OVERDUE` 机制呈现为红标欠账（见 §7.2）。**登记与评价是两件事**：两类都要登记、都要受 PCO 管控（`GOAL` → IPMT 主任），只是**兑现时点**不同。这与 `D-P8` 不冲突。

## 4. 数据模型

### 4.1 `t_prj_objective` —— 目标当前值（每项目每维度一行）

```sql
CREATE TABLE t_prj_objective (
  id           BIGSERIAL PRIMARY KEY,
  project_id   BIGINT NOT NULL REFERENCES t_project(id),
  dim_code     TEXT NOT NULL REFERENCES t_prj_obj_dim(dim_code),
  target_value NUMERIC(18,4),
  currency     TEXT,                       -- MONEY 维度冗余币种（与 dim.currency 一致，快照用）
  target_date  DATE,                       -- DATE 维度用
  current_rev  INT NOT NULL DEFAULT 1,     -- 指向 t_prj_objective_rev.rev
  source_kind  TEXT NOT NULL DEFAULT 'MANUAL'
               CHECK (source_kind IN ('BIZ_PLAN','ATTR','MANUAL')),
  source_ref   TEXT,                       -- 'BPL-2026-0130/1.0' 或 'attrs.targetBomCost' 或 't_milestone/DCP3'
  created_by   TEXT NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  version      INT NOT NULL DEFAULT 1,     -- V196 乐观锁范式
  CONSTRAINT uq_prj_objective UNIQUE (project_id, dim_code)
);
```

### 4.2 `t_prj_objective_rev` —— 目标基线版本（**只增不改**快照）

```sql
CREATE TABLE t_prj_objective_rev (
  id            BIGSERIAL PRIMARY KEY,
  project_id    BIGINT NOT NULL REFERENCES t_project(id),
  rev           INT NOT NULL,
  status        TEXT NOT NULL CHECK (status IN ('BASELINED','SUPERSEDED')),
  snapshot      JSONB NOT NULL,            -- {dim_code: {target_value, currency, target_date}} 全量
  change_pco_id BIGINT,                    -- 哪个 PCO 把它推到这一版（首个基线为 NULL）
  approved_by   TEXT NOT NULL,             -- 冗余留痕：记 pco 决策人，可独立复核
  approved_on   TIMESTAMPTZ NOT NULL,
  content_hash  TEXT NOT NULL,             -- 照 IpdModelService:1207 口径
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT uq_prj_obj_rev UNIQUE (project_id, rev)
);
```

**为什么不把版本塞进主表**：`t_biz_plan_rev` 已验证"哈希冻结的版本快照"这套做法是对的（`contentHash` 使"当时批的是哪一版"可独立复核）。目标同样要能回答**"当初承诺的到底是多少"**。同时 `T_PROJECT` 已有的 `version`（V196）是**并发**版本（每次 UPDATE +1），**语义完全不同**——两者不可混为一谈。

## 5. 立项书作为**初始**目标的权威来源（`D-P1` + `D-P5`）

### 5.1 两条链要分清

| 关系 | 语义 | 基数 | 谁写 |
| --- | --- | --- | --- |
| `t_prj_objective.source_kind='BIZ_PLAN'` + `source_ref='BPL-2026-0130/1.0'` | **初始来源**（哪一版立项书定的） | N 目标 → 1 立项书版本 | 回填时写一次，之后不改 |
| `t_prj_objective_rev.change_pco_id` | **后续变更**（哪张 PCO 推的） | N 版本 → 1 PCO | PCO 批准时写 |

**立项书一旦 `APPROVED` 就不可改写**（`IpdModelService:750-754`；要改必须 `createRev` 升版 → 新 WIP → IPMT 重批）。这与"滚动更新的实际值"是**两种节奏** ⇒ 见 §5.3。

### 5.2 为什么目标不能并进 `t_biz_plan_rev`

| 约束 | `t_biz_plan_rev` | `t_prj_objective` | 结论 |
| --- | --- | --- | --- |
| 写入频次 | 每道 DCP 前后（低频） | 实际值持续刷新（高频） | 语义不同 |
| 不可变性 | `APPROVED` 后哈希冻结（`contentHash` 覆盖 `finance` 全文） | 当前值可改，历史在 `_rev` | 不可混存 |
| 内容形态 | 自由 JSONB + 散文（`market`/`finance`/`roadmap_fit`/`risk`/`exec_summary`） | 结构化列 | 达成率需按维度聚合，JSONB 不可稳定聚合 |

**若把实际值塞进 `finance` JSONB**，等于让一份哈希冻结的商业论证承载滚动数据 —— 既违反该表的 WORM 语义，也让 `contentHash` 失去意义（**批的时候算进去的数和三个月后不是同一批数**）。

### 5.3 ★ `D-P5`：立项书 JSON 自由文本 → **引用**一等对象

**问题**：`t_biz_plan_rev.finance` 实测含 `targetCost` / `销量万台` / `毛利率` / `T0投入` / `年支出`（`CharterPage.tsx:122-129`），`market` 含 `Y3目标`。这些是目标却**藏在自由 JSONB 里**，与 `t_prj_objective` 形成**第四套数字**。

**做法（不复制、不双写）**：

```jsonc
// t_biz_plan_rev.finance 中，抽取后的目标键改为引用式
{
  "targetCost":  { "$ref": "OBJ", "dim": "BOM_COST", "objectiveRev": 3 },   // 不再是裸数字
  "销量万台":     { "$ref": "OBJ", "dim": "YEAR1_VOLUME", "objectiveRev": 3 },
  "毛利率":      { "$ref": "OBJ", "dim": "CONSUMABLE_GM", "objectiveRev": 3 }
  // 其余非目标键（三年现金流 / IRR / 敏感性…）保持原样，它们是**测算**不是**目标**
}
```

| 规则 | 说明 |
| --- | --- |
| **引用是单向的** | 目标 → 立项书版本（`source_ref`）；**立项书不反写目标** |
| **可读面统一** | 读到 `{"$ref":...}` 时**必须解析到 `t_prj_objective` 当前值**并随响应给出 `resolvedValue` + `resolvedFrom`（照 `costCompare().costBasis.sources[]` "每个数字带出处"的既有范式） |
| **不得双重计入** | 达成率计算**只认 `t_prj_objective`**；`finance` 里的引用**不参与求和** |
| **对账只报不拦** | 目标值 ≠ 立项书解析值时，走 `FinModelService.consistencyCheck:198-239` 同款"只报不拦"告警（口径差异可能合理） |
| **旧数据渐进** | 存量 68 份立项书**不批量改写**（`APPROVED` 的不可改写）；只对**新 WIP/REVIEW 版本**启用引用式编辑 |

> **注意**：`RETRACTED` 状态不在 `flows/bizplan-flow.yaml` 中（V116 新增的终态），`SUPERSEDED` 版本不可撤回（`IpdModelService:1059-1062`）。"抽取"操作只对 `WIP`/`REVIEW` 版本开放。

## 6. 达成率计算

### 6.1 实际值取数（每维度显式声明来源）

| 维度 | `actual_source` | 取数实现 | 复用 |
| --- | --- | --- | --- |
| `BOM_COST` | **AUTO** | `ItemService.costCompare(productId, bomView, substitutionPolicy)` 的 `bomCost` | ★ **仓内唯一实现，禁止重算**。响应必须同时给出 `substitutionPolicy` / `structurePublished` / `missingCostLines` / `costBasis.sources[]` |
| `LAUNCH_DATE` | **AUTO** | `t_milestone.actual_date`（`gate_code` 指向上市门） | 见 §7.3 的码表对齐 |
| `LABOR` / `MATERIAL` / `EXPENSE` | **MANUAL** | 人工登记（工时与费用系统在本仓外） | 界面必须显"人工登记"+登记人+时间 |
| `PRICE` / `YEAR1_VOLUME` / `CONSUMABLE_GM` / `CONSUMABLE_RPT_MONTHS` | **MANUAL** | 人工登记（ERP/销售域） | 同上 |
| （预置但无源） | **NONE** | 进度类、资源负荷类（`C2`：`t_capacity` 0 行） | 界面显"暂无数据源"，**不写 0** |

### 6.2 归一化达成率（避免"越高越好/越低越好"各算各的）

```
direction = LOWER_BETTER  →  rate = target / actual
direction = HIGHER_BETTER →  rate = actual / target
```

| 边界 | 处理 |
| --- | --- |
| `actual IS NULL` 或 `actual = 0` | `rate = NULL` + `rate_note='实际值缺失/为零，无法计算'`；**界面显"无法计算"，绝不写 0**（0 达成率会误导成"彻底没达成"） |
| 目标值 `NULL` | 该维度**不算入**汇总，`rate_note='未设目标'` |
| 成本类结构未发布 | 照 `costCompare` 的 `structurePublished` 披露，**不作数** |
| 汇总口径 | 跨维度**不做单一总达成率**（成本类与销量类不同量纲，加权平均无业务含义）；只做**分类目小计**（`PROJECT_COST` 小计可加总，因同量纲同币种） |

### 6.3 密级（`Q4` 裁定：单开修复）

- 成本/售价类目标**必须走 `FinanceFieldAccess.canReadFinance(projectId)`**（`platform/governance`），无权用户一律 `***`。
- `t_sensitive_field` 登记表**新增行**登记 `PRJ_OBJECTIVE.BOM_COST` / `PRICE` 等，**基线角色与 `FinanceFieldAccess.FINANCE_ROLES` 同源**（`V193` 已建立"判定与影响面预览读同一列"的结构性保证）。
- **先决**：`FinanceFieldAccess.FIELD_KEY` 当前**只有 `"CHARTER.fin_estimate"` 一个键**（`FinanceFieldAccess.java:39`），而 `IpdModelService.getBizPlan()` 读取 `t_biz_plan_rev.finance` 时**不走脱敏** ⇒ 同一份 SECRET 数据已从第三个入口泄漏（该类注释 `:15-23` 恰好预言过上一次同类事故）。**本设计不新建漏口**；`Q4` 裁定单开修复，**B1 之前必须合入**。

> **`FinanceFieldAccess` 必须从"单键"改为"按字段键判定"**（B1 落地时一并做，理由见 §6.3.1）。

#### 6.3.1 为什么"再加一个判据"就是重演上一次事故

`FinanceFieldAccess` 的类注释（`:15-23`）把上一次事故写得很清楚：判定只写在 `CharterService.redact` 里，而 `ItemService.costBasis` 直接从 `t_charter` 取 `fin_estimate` 拼进响应 ⇒ **一个入口生效、另一个入口漏**。修复方式是把判定抽成共享组件、两边共用。

**同一个病灶现在换了个位置**：`FIELD_KEY` 是**一个硬编码常量**，所以"新增一个财务字段"只有两条路——① 改这个常量（于是**所有**字段的授权判定被一次性改掉，`t_field_grant` 里按旧键授的名单对不上）；② 新写一个判据（于是有了第二份实现，正是该类注释里预言的事）。

⇒ 本次把 `FIELD_KEY` 升级为**按字段键判定的多键形态**（`canReadFinance(projectId, fieldKey)`），基线角色仍从 `t_sensitive_field` 读，`FIELD_KEY` 保留为 `CHARTER.fin_estimate` 的**默认键**（既有调用点零改动）。**新增财务字段 = 往登记表加一行 + 调用点传对键**，不碰判定逻辑。

## 7. 冻结机制（`D-P4`）

### 7.1 为什么不能只用一个时点结账

不同承诺的"实际值出现时点"差异极大：DCP3 之前**没有销量**、**没有上市实绩**；BOM 成本随时可测；投入成本按月累计。

若**所有维度统一在 `上市 → 维护` 结账**，上市后经营类目标（销量/售价/毛利率）会被判为"无实绩"，而它们**本来就该在上市后半年/一年才结算**；若反过来**按每个维度自定门点**，又要引入 `assess_window` + `freeze_gate` 两列并依赖可能有零实例的 DCP 门（实测 `DCP3` 一条评审都没有）。

⇒ 取**第三个口径**：兑现期限是**相对上市日的偏移天数**（`D-P14`），研发类为 `0`（挂在既有流转上），经营类为 `180`/`365`（挂在已实现的逾期机制上）。**两个时点、两套现成机制，都不自造。**

### 7.2 ★ `D-P10` + `D-P13` + `D-P14`：**达成率按承诺兑现时点计算**（原 `assess_window` 与 `eval_at_closeout` 布尔两个设计均已作废）

**裁定（两条）**：

| 编号 | 裁定 |
| --- | --- |
| **D-P10** | 所有维度的达成率**统一在项目结项时计算并冻结**，不做"分维度分评价期" |
| **D-P13** | **"结项"映射到既有的 `上市 → 维护` 阶段流转**（`flows/project-flow.yaml:66` 的"推进"边，`roles: [pdt_manager, PM, product_manager, admin]`）——**不新增 closeout 动作** |

原设计（`assess_window = PRE_LAUNCH/POST_LAUNCH` + 每维度 `freeze_gate`）**整体作废**，理由有二：

| 原设计的动机 | 为什么不需要了 |
| --- | --- |
| "一刀切冻结会冻掉一半数据"（DCP3 冻结会冻死销量/售价） | 冻结点推到**结项**之后（§7.3 另有处理） |
| "DCP3 当前无实例，退化路径需要再确认" | 不依赖任何 DCP 门，**该悬而未决的问题直接消失** |

**收益**：`t_prj_obj_dim` 少两个列（`assess_window` / `freeze_gate`），冻结判据**唯一且简单**（一次既有状态流转），不需要空集/退化分支，**且不新增任何端点或状态**。

#### 冻结判据（`D-P13`）

| 项 | 内容 |
| --- | --- |
| 触发 | `t_project.status` 由 `上市` → `维护` 的状态流转（`project-flow.yaml:66`，"推进"边） |
| 落点 | 挂在 **`ProjectService.transition`** 的既有守卫之后，**同一事务内**完成：① 按结项时数据计算全部维度达成率 ② 全部置 `FROZEN` ③ 写 `frozen_at`（= 流转时刻）/`frozen_by`（= 触发流转的人）/`frozen_reason` ④ 记审计 + 事件 `PRJ_CLOSEOUT` |
| `frozen_by` 的取证 | **直接取该次流转的操作人**（`transition` 端点已有 actor），不新增字段、不另建结项人 |
| 结项之后 | 刷新接口 **400 `PRJ_ACHIEVEMENT_FROZEN`**；文案写明"由谁在何时因「上市→维护」冻结"（**无 override 通道**，见 §7.4） |

> **"结项"在系统里的既有依据**：`project-flow.yaml` 的 `上市 → 维护`（`:66-67`）是 11 条推进边中**唯一一条"研发承诺期结束、转入产品运营期"**的边 —— `上市` 的上一段是「设计转换」，`维护` 的下一段是「退市」。把它当结项点，业务语义成立：**"转维护"= 这个项目的研发承诺已兑现或未兑现，要结账了**。

**顺带解决的三件旧账**（此前由 `PROJECT_CLOSED` 事件承担、从未实现）：`GAP-28` 🔴（项目关闭后 PDT 权限回收，`ipd-extension/02-差距分析.md:54`）· `IBR-09`（项目角色权限随项目关闭回收）· `01A:70`（PDT 团队随项目关闭解散）。**建议在同一次流转里一并触发**（权限 `expire` + 团队 `disbanded_on`），因为它们与达成率快照是同一个"结账时刻"的下游动作。

#### ★ `D-P14`：经营类目标用「承诺兑现期限 + 到期红标」，不做布尔排除

**问题的本质**不是"实绩为空"，而是**经营类目标没有评价时点**——被登记、被 PCO 管控，但永远不会被结算，等于"登记了但不做"。

**做法**：用**相对上市日的偏移天数**取代布尔开关，并**直接复用仓内已完整落地的 `t_open_issue` OVERDUE 机制**。

##### 复用的先例（不是新发明）

| 能力 | 实现位置 |
| --- | --- |
| 逾期日扫升格 | `OpenIssueService.java:562-571`：`status IN ('OPEN','VERIFYING') AND due_date < today → 'OVERDUE'` |
| 升级事件 | `events.record("ISSUE_OVERDUE", ...)`（同方法内） |
| 工作台"逾期优先"排序 | `FlowTaskService.java:786/844/866`、`WorkbenchDashboardService.java:62/130` |
| 到期日在工作台呈现 | 同上（`overdue` 计数与 `onTimeRate` 口径） |
| **"不能一出生就逾期"的守卫** | `OpenIssueService.java:115-126`：拒绝 `dueDate` 早于当日，缺省 `今天+14` 天 |

它的语义正是这里需要的：**"该在某个时点结的事，到点了没结 → 变成红标欠账，而不是悄悄记成空值"**（沿用 `GateOrderGuard:52-54` 的"欠账要可见"纪律）。

##### 数据模型改动（一列）

```sql
-- t_prj_obj_dim：eval_at_closeout BOOLEAN  →  eval_offset_days INT NOT NULL DEFAULT 0
eval_offset_days INT NOT NULL DEFAULT 0   -- 相对「上市日」的兑现期限偏移（天）
```

| `eval_offset_days` | 维度 | 兑现时点 |
| --- | --- | --- |
| **`0`** | `LABOR` / `MATERIAL` / `EXPENSE` / `BOM_COST` / `LAUNCH_DATE` | **研发承诺** —— 挂 `上市 → 维护` 同事务结账（不变，**零新端点**） |
| `180` | `PRICE` / `CONSUMABLE_GM` | 上市后半年 |
| `365` | `YEAR1_VOLUME`（**首年销量，本就该一年后结算**）· `CONSUMABLE_RPT_MONTHS` | 上市后一年 |

**期限是维度的属性，不写死在代码里** —— 换企业、换产品线时改配置即可（与"科目可配置"同一范式）。

##### 复用而非新建：同事务写一条 `t_open_issue`

给每个 `eval_offset_days > 0` 的目标行建单时，**同事务**写一条：

```java
openIssueService.create(projectId,
    /* bindGateCode = */ null,                 // ★ 不绑门：目标逾期不得阻断 DCP/TR
    /* description  = */ "目标结账：首年销量（承诺 10000 台）",
    ownerLogin,                               // 目标责任人
    LocalDate.of(launchDate).plusDays(180),   // due_date
    /* sourceConditionNo = */ "OBJ/" + dimCode);
```

于是**免费获得**：逾期日扫 · 升级事件 · 工作台待办与红标 · 逾期优先排序 · "不能一出生就逾期"的守卫。

> **已核实不会误伤门线**：`PrecheckService:459` 与 `ProjectService:1078` 均按 `bind_gate_code = 本门` 匹配，**传 `NULL` 不匹配任何门** ⇒ 目标逾期**不会**触发 `OPEN_ISSUES` 门线判据（那超出本需求范围）。

##### 三态（取代 Boolean）

| 态 | 判据 | 界面 |
| --- | --- | --- |
| **待评价** | `今天 < 上市日 + eval_offset_days` | "N 天后结账" |
| **到期未结账** | `今天 >= 期限` 且 `status='OPEN'` | 🔴 红标欠账（由 `t_open_issue` 的 `OVERDUE` 呈现） |
| **已结账** | 已写入终值并 `FROZEN` | 终值 |

##### 效果对比

| | 原方案（Boolean 排除） | **本方案** |
| --- | --- | --- |
| 经营类目标 | 登记了，**永远不结算** | **有评价时点、有责任人、逾期可见** |
| 研发类结账 | `上市 → 维护` 同事务 | **不变**（零新端点） |
| 实际值来自 ERP、PLM 拿不到 | 结项时才发现没数 → 写 NULL | **到期前就在待办里提醒录入** |
| 新增机制 | — | **0（复用 `t_open_issue`）** |
| 结项报告形态 | 一张表 | 「研发承诺结账」+「经营承诺跟踪」两段（**本来就是两个时间尺度**） |

> **与 `D-P8` 不冲突**：耗材毛利率/复购周期**是**项目目标，**要登记、要受 PCO 管控、都由 IPMT 批**；只是**评价时点**不同。登记与评价是两件事。

#### 时序

```
项目进行中（开发/验证/注册申报/设计转换/上市）
  →  t_prj_achievement 可刷新（UPSERT 当前行，写 measured_on/by）
  →  offset>0 的维度：同事务已建 t_open_issue（due = 上市日 + offset）

[上市 → 维护]  ← 研发承诺结账点，同一事务内
  ├─ 计算全部 eval_offset_days=0 维度的达成率（NULL 的写 NULL + rate_note）
  ├─ 全部置 FROZEN，写 frozen_at/frozen_by/frozen_reason
  ├─ 记审计 + 事件 PRJ_CLOSEOUT
  └─ （建议同事务）PDT 权限回收 + 团队解散

结项之后
  →  offset=0 维度：刷新接口 400 PRJ_ACHIEVEMENT_FROZEN
  →  offset>0 维度：仍可录入实际值；到期未录 → 由 t_open_issue 升为 OVERDUE 红标
  →  录入终值并结账 → 置 FROZEN，t_open_issue 关闭
```

**目标在结项前被 PCO 改过怎么办？** 旧目标基线下的达成记录**保留**（`objective_rev_id` 不同），结项报告可同时给出"按最新承诺"与"按各次承诺"两套达成率 —— 这正是版本化的价值：**事后能回答"当初承诺的是多少、实际是多少"**。

### 7.3 ★ `D-P9`：上市时间在目标，里程碑**受它约束**

| 对象 | 存什么 | 谁可写 |
| --- | --- | --- |
| `t_prj_objective`(`LAUNCH_DATE`) | **承诺**的上市日 | **仅 PCO**（计划阶段后可写） |
| `t_milestone`（上市里程碑） | 执行排期 `planned_date` + 实绩 `actual_date` | `planned_date` **受目标约束**；`actual_date` 任何人可登记 |

**约束的实现（"一处一事实"的正确形态）**：

1. `t_milestone.planned_date` **不得超过** `t_prj_objective(LAUNCH_DATE).target_date`（服务端守卫，超出即 400 `MILESTONE_BEYOND_LAUNCH_TARGET`）。
2. 目标变更（PCO 批准）时：若新目标**早于**现有里程碑计划日 ⇒ 服务端在**同一事务内**下调该里程碑 `planned_date`（并记审计），避免"承诺与排期脱节"；若新目标**晚于**里程碑 ⇒ **只提示不自动改**（里程碑提前是执行方的有利安排，不是错误）。
3. `actual_date` 达成判定 = 实际 ≤ 目标。

> **⚠ 摸底发现的数据缺陷（须在 B1 修）**：`t_milestone.gate_code` 实测存的是**旧码**（`'G1/DCP1 概念批准'`、`'G2/DCP2 计划批准'`，`V20` 建表于门码迁移之前），而 `t_gate_map.new_gate_code` 是 `DCP1/DCP2` ⇒ **里程碑与门点当前无法 JOIN**。`t_gate_map` 已有 `old_gate_code` 列可做映射（`V24:10`），迁移须用 `COALESCE(new_gate_code, old_gate_code)` 反查并回填，**否则"里程碑↔门↔目标"三向关联全断**。

### 7.4 冻结的语义

- 冻结后刷新接口 **400 `PRJ_ACHIEVEMENT_FROZEN`**，文案写明"由谁在何时以何理由冻结"。
- **不设 override 通道** —— 沿用 `GateOrderGuard:52-54` 的"**前序门是欠账不是补做**"纪律：要改评价口径就改 `t_prj_obj_dim`（配置变更，走治理台留痕），而不是解锁单条数据。
- 冻结动作留审计 + 事件（`audit.record` + `events.record`）。

### 8.1 `targetVaveCost` 为什么"不设"（`D-P11` 的取证）

**你的问题："VAVE 降本目标，是降什么本？"** —— 实测后的答案是：**在本仓内它没有确定含义，而且与 `targetBomCost` 存在真实混淆。**

```sql
SELECT prj_code, attrs->>'targetBomCost' bom, attrs->>'targetVaveCost' vave, attrs->>'targetPrice' price
FROM t_project WHERE attrs ? 'targetVaveCost' OR attrs ? 'targetBomCost';
--  PRJ-2026-0245 | 呼吸机 R3 增强型 |  (空) | 520 | 1999
--  PRJ-2026-0538 |              | 140  | (空)|  (空)
```

| 发现 | 证据 |
| --- | --- |
| **两个值从不在同一个项目上共存** | `targetBomCost` 只在 PRJ-2026-0538，`targetVaveCost` 只在 PRJ-2026-0245 |
| **登记注释与实测矛盾** | `V154:81` 写"值样例：520（**与 targetBomCost=140 并列** ⇒ VAVE 降本目标）"——但 520 与 140 **根本不在同一个项目**，"并列"是错的 |
| **同一个 520 曾被当作目标 BOM 成本** | `V103:25` 记"实测产品 5 的基线由 40 → 项目 **PRJ-2026-0245 的 520**"——而这个 520 现在挂在 `targetVaveCost` 上。**同一业务事实被两个字段名承载过** |
| "VAVE"（Value Analysis / Value Engineering）在设计文档中**零出现** | 全仓 grep 无定义 |

**结论与处置**：

1. **不设 `VAVE` 维度、不建目标行**（`D-P11`：不明确就不要此字段）——你判断正确：若 VAVE 降的就是 BOM 成本，那 `BOM_COST` 一个就够；若降的是别的（本、包装、渠道），那是另一个**尚未存在**的维度，不能靠猜。
2. **`attrs.targetVaveCost` 原值保持不动**（不删、不迁、不改权限），但**不作为任何计算或达成率的输入**。
3. **登记为待业务定义**：`V154` 的标签「VAVE 目标成本（元）」与注释「与 targetBomCost 并列」**建议订正**（改动属设计/迁移内容，**需另行裁定，本轮不动**）。

## 8.2 ★ 界面侧收敛：删掉「扩展属性」分组（2026-11-11 需求批次 63，用户裁定 D63-5）

> §8 讲的是**数据侧**收敛（键迁到哪、值留不留）。本节讲**界面侧**：
> 用户看到的是「**项目目标与达成**」和「**扩展属性**」两处内容重叠，要求删分组。
> 结论是 **删分组，不删数据**——两件事必须分开写，否则会被误读成"这些字段没了"。

### 8.2.1 三个真相（与用户原判断的偏差，如实登记）

1. **「扩展属性」是一个 catch-all 分组，不是一组有定义的字段。**
   `ProjectsPage.buildPrjDetailSectionSpecs` 里它写作 `codes: [], dynamic: true`，
   含义是"把不在任何已知分组里的扩展键全塞进来"。所以**删掉它 = 删掉一个兜底桶**，
   不是删掉十个字段。删桶之后，原来落在桶里的键必须有地方去，否则就是**静默消失**。
2. **`目标市场` 之前是"两处并存、且只有一处有消费者"。**
   核心列 `t_project.target_markets`（`V1:113`）有 **10 个后端消费者**
   （预检、交付物模板、PCO 词表、PMS 对接、OpenAPI…），**但界面上没有任何输入框**；
   `attrs.marketSeg` 反过来——**有界面、无任何业务消费者**（纯文本域，无人读）。
   ⇒ 用户"看起来重叠"的感觉来自后者，**但要接的是前者**：用户裁定改用核心列、
   `attrs.marketSeg` 退役（数据保留）。这是**首次让核心列露出界面**，不是搬家。
3. **`预算` 的语义冲突未解**：`attrs.budget` 是**单值**（实测 1800 / 200），
   26 号文 §3 的 `LABOR`/`MATERIAL`/`EXPENSE` 是**三科目**。
   两者量纲都无单位声明。本轮**两个都不动**（`budget` 仍留 `attrs`），
   等同 §8.1 对 `targetVaveCost` 的处理：不明确就不要动，但要登记。

| --- | --- | --- | --- |

| `devHeadcount` | 扩展属性 | **主数据** | 移位（`D-P7` 人数仅参考，不设维度） |

**「目标市场」放哪里，为什么不是一条目标行**：26 号文 §3.1 的 `t_prj_obj_dim` 是

### 8.2.3 ⚠ `is_grid_col=FALSE` 的键：本轮显式裁定（否则删桶会静默改可见性）

`GET /metadata/columns` **只返回 `is_grid_col=TRUE` 的键**，
而项目页从不调 `/metadata/detail-fields` ⇒
凡 `is_grid_col=FALSE` 的扩展键，**今天就已经在界面上不可见**。

本轮删掉 catch-all 桶后必须回答"它们是否恢复可见"，逐键裁定如下：

| 键 | 裁定 | 理由 |
| --- | --- | --- |
| `criticalPath`（关键路径） | **保持不可见**，登记为待业务定义 | 与里程碑/计划任务功能重叠，露出来会和里程碑打架；无人定义其口径 |
| `registrationPath`（注册路径） | **保持不可见** | 同上（与注册申报子流程重叠） |
| `charterCode`（立项书编号） | **保持不可见** | 权威在 `t_biz_plan`，此处是冗余镜像 |
| `targetBomCost` | **保持不可见** | 已迁 `BOM_COST` 目标行（§8），露出双份会诱发两处编辑 |

**判词**："不露出来"不等于"删掉"。这四个键的 `attrs` 原值**一律保留**，
若日后业务给出定义，走 `t_attr_template` 正常登记即可（与 §8.1 同一处理原则）。

### 8.2.4 「项目简介」：新增，且**必须**声明为长文控件（登记值是 `JSONB`，不是 `longtext`）

新增项目扩展键 `intro`（标签「项目简介」），落在**主数据**分组。
⚠ **不做这一步会得到一个单行输入框**：`ProjectsPage` 的 `kindMap` 把
`t_attr_template.kind='STRING'` 一律映射成 `text`（单行 `<input>`），
只有映射到 `longtext` 的 kind 才渲染 8 行的 `<textarea>`。

**订正（本轮实现后回写）**：本节初稿写的是「元数据里显式声明 `kind='longtext'`」——
**`longtext` 根本不是合法的库侧 kind**。`t_attr_template_kind_check` 的值域是
`STRING | NUMBER | BOOLEAN | ENUM | DATE | JSONB | REF`，
照初稿写会直接被 CHECK 拒掉。**本库登记"长文属性"用的就是 `JSONB`**：
`09-工作流引擎与元数据扩展设计.md:615` 的 kind→控件映射表写着
`| JSONB | Map | longtext | textarea |`（同 `:533`；`V39:5`、`V42:6,9` 注释同款），
`ProjectsPage.tsx` 的 `kindMap` 又把 `JSONB → 'longtext'`
⇒ **库里 `JSONB` = 界面长文文本域**，且 `ProductCorrectionService` 的
`to_jsonb(?::text)` 分支让纯文本原样往返。
`DetailField` 无 `maxLength` 字段，长文本高度由前端常量 `LONG_TEXT_ROWS=8` 决定，
**不必也不应**在库里自造长度限制。
`is_grid_col` 有意置 `FALSE`（项目简介是面板里的长文，不该在列表网格里占一列），
面板侧由「主数据」分组显式声明承载（与核心字段同一处声明）。

### 8.2.5 「目标市场」块：控件清单与形状纪律（D63-6 源 = 核心列）

「目标与达成」页签里，科目分组之上另立一个**平级区块**（理由见 §8.2.2 末段）。
判据用的具体控件（`frontend/src/components/ProjectMarketsBlock.tsx`）：

| 控件 | testid | 读数用途 |
| --- | --- | --- |
| 区块容器 | `prj-markets` | 块真的渲染出来了 |
| 复选框组 | `prj-markets-pick` | — |
| 单个市场复选框 | `prj-market-<CODE>` | 勾选态 == 库里真值 |
| 清单外代码（只读） | `prj-market-extra-<CODE>` | 清单外的码**逐字保留、不吞不猜** |
| 无目标市场 | `prj-markets-empty` | 空集与未登记不混淆 |
| 老形状提示 | `prj-markets-legacy` | 库里存的不是 `{"markets":[…]}` 时出现 |
| 保存按钮 | `prj-markets-save` | 无改动时 `disabled` |
| 成功 / 失败提示 | `prj-markets-msg` / `prj-markets-err` | 反馈可见 |

> **反馈存活规则（D63-14 同批实测，属通用纪律）**：`ProjectMarketsBlock` 保存成功后把返回的新对象
> 交回父组件刷新 ⇒ `sig` 随之变化 ⇒ 若 `[project.id, sig]` 的 effect 无条件清提示，
> **成功横幅会被自己擦掉**：数据确实落库，用户却看不到任何反馈，与失败不可区分。
> 口径：**消息的失效条件只能挂在实体 id 变化（换项目）或下一次用户编辑上，
> 绝不能挂在派生值（如由 props 算出的签名）上**。

**形状纪律（三条都是实测踩出来的）**：

1. **规范写形状只有一种**：`{"markets": ["NMPA","CE"]}`。
   库里历史上存在过**另两种形状**——`{"NMPA": true}`（键即码）与裸数组。
   `ProjectService.markets(...)` 是**唯一**读侧归一入口（`Map` 带 `markets` 键时该键胜出），
   界面读数一律先经 `targetMarketsOf(raw)` 归一，**并对老形状显示提示**，
   提示里写明"下次保存会被收敛成规范形状"——不静默改写用户的既有数据形状。
2. **清空必须发 `{"markets": []}`，发 `null` 无效**：
   `ProjectService.update` 的写入分支是 `if (in.targetMarkets() != null)`，
   `null` 会被**整段跳过** ⇒ 界面看着清了、库里没动。这是"清空按钮无效"类缺陷的标准成因。
3. **清单是"可勾选白名单"，不是"取值约束"**（D63-14，裁定于审计）：勾选清单取前端
   `MARKET_CODES` 六项 `NMPA / FDA / CE / UKCA / PMDA / MHRA`；退役的
   `attrs.marketSeg` 枚举只有四项（`V13:13`、`V154:135-142` 的 `NMPA/CE/FDA/MHRA`），
   **是清单的真子集** ⇒ 任何历史值都还勾得上，不会出现"库里有、界面够不着"。
   但库里确实存在**清单外**代码（如 `电商`，来自既往人工录入），
   这类码**必须原样保留并渲染成不可编辑标签**（`prj-market-extra-<CODE>`）：
   白名单管的是"能勾什么"，不是"允许存什么"。因此**不要**给该列加 CHECK 约束，
   也不要在保存时丢弃清单外码（那会造成一次普通保存就吃掉别人的市场）。
   判据配对：`M2c`（不存在的假项）↔ `M2`（真实码仍是勾选态）。

> 附带裁定（D63-7）：目标市场**不建成 `t_prj_obj_dim` 目标行、不算达成率、不冻结**。
> 详见 `decisions.md` D63-7 与本文件 §3.1 的口径说明。

### 12.2 ★ 实施中发现的 5 处设计与现状不符（已改设计口径，**不掩盖**）

| # | 设计原文 | 现状 | 处置 |
| --- | --- | --- | --- |
| 1 | §7.2 `source_condition_no = 'OBJ/' + dimCode` | 该列是 **`INTEGER`**（V71，"结论级第 N 条"），且 V121 用它建了 `(source_review_id, source_condition_no)` 幂等唯一索引。塞字符串会**毁掉该索引语义**（那不是序号） | 新增 `t_open_issue.source_condition_key TEXT`（纯增量，存量行 NULL，既有读写与索引零影响）。**两列职责不同，不复用** |
| 2 | 结账时关闭 `t_open_issue` | `OpenIssueService.close` 强制"关闭证据必须能解析为一个**真实存在的受控对象编号**"（REQ-2026-1018/1162）。目标结账的证据**就是那条达成记录本身**——它若没有编号，就只能拿项目号/文档号凑证据，那是"证据与结论不对应" | 给 `t_prj_achievement` 发业务编号 `OBJA-YYYY-NNNN`（`SequenceService.next`），并登记进 `EVIDENCE_PREFIXES`（与 REQ-2026-1207 补 `RA` 同一理由） |
| 3 | §6.2 对所有维度套 `target/actual` 比率 | `LAUNCH_DATE` 的实绩是**日期**，装不进 `NUMERIC(18,4)`。塞成 `20260501` 是"格式对了、语义错了"，日后必然有人把它当金额求和 | 另立 `actual_date DATE` 列；**日期类不参与比率**，改用**提前/延迟天数**写进 `rate_note`（达成判定 = 实际 ≤ 目标，§7.3 口径不变） |
| 4 | §6.1 `LAUNCH_DATE` 实绩 = 上市门里程碑 | `t_gate_map` 里**没有** `stage_to='维护'` 的门（`上市→维护` 不挂 DCP）。按不存在的值去 JOIN 会**恒定取不到数**，而"取不到就当没有实绩"是静默失效 | 改用 `stage_to='上市'`（DCP3，"进入上市阶段的那道门"）。**门码仍不写死**，从元数据读（V-185） |
