## 1. 抽取判据与编号

| 判据 | 例证 |
|---|---|
| **语义级**：与具体模块无关的产品级要求 | 「发布完成 = 三处产物指纹一致」、「主业务对象选择一律用检索面板」 |

## 2. 交付与部署完整性（G-DEP）

### G-DEP-1 产物指纹门：「完成」的判据是产物一致，不是命令返回 0

**规格**：前后端都是**两级缓存**（宿主构建产物 → 镜像 → 运行容器），任一级漏做都会出现
「代码改了、跑的仍是旧产物」而**毫无报错**——这被称为**假部署**。因此发布完成的判据是：

**宿主产物指纹（jar `sha256` / dist 目录树指纹） → 镜像内 → 运行容器内，三处必须一致。**
不一致时自动 `--force-recreate` 并**复检**；复检仍不一致 → 发布失败。

**四条纪律**：

| # | 纪律 | 理由 |
|---|---|---|
| 1 | **一律使用一键发布脚本**，禁止手工分步构建后宣称已发布 | 分步构建是"漏做 Level 2/3"的温床（`Dockerfile` 只 `COPY` 预构建产物；web 是 runtime-only 镜像） |
| 2 | **`RUN rm -rf <目标目录>/*` 再 `COPY`** | `COPY` 是**合并语义**：基础镜像自带文件（如 nginx 的 `50x.html`）会让目录树指纹**恒不相等**，制造永久误报 |
| 3 | **构建前强制刷新属性缓存**（WSL 9P 场景） | Windows 侧编辑后在 WSL 内构建，可能读到旧内容而产物 hash 却变了——"产物看起来是新的"是最危险的假绿 |
| 4 | **发布清单落盘** | 每次发布写入 `release-<ts>.json`（含 git commit、各级指纹、认证模式），否则"发布了哪个版本"事后无法复核 |

**依据**：2026-09-12 的 PLM 一键发布脚本（`ipd/deploy/wsl/plm-app/release-plm-app.sh`，6 步全绿才 PASS，
输出 `RELEASE_RESULT=PASS|FAIL` 与退出码）＋ 前端 `Dockerfile` 的 `rm -rf` 修复
（原实现因 nginx 自带 `50x.html` 而**恒报"漏做镜像重建"**——误报会让门控失去信用）。

**验收断言**：
- A1 发布脚本输出 `RELEASE_RESULT=PASS`，且**清单文件存在**并能读出 git commit 与三处指纹；
- A2 人为制造"只重建前端 dist 不重建镜像" ⇒ 脚本必须**报失败**（不得静默通过）；
- A3 改动一行前端文案后重跑：**容器内产物**确实包含该文案（用 `docker exec … grep` 复核，不是看宿主 dist）。

### G-DEP-2 CI 与本地必须调用同一发布入口

**规格**：CI 流水线与本地发布**必须调用同一个脚本**，不得在 CI 里另写一份部署步骤。

**理由**：CI 另写一份必然绕过本地脚本里注入的关键参数（**认证模式**、token、指纹校验），
于是"CI 绿了但线上配置不同"——部署配置漂移比代码漂移更难发现。

**落地**：`ipd/deploy/ci/plm-app-release.yml`（build-and-verify / deploy-dev）调用 `release-plm-app.sh`。

### G-DEP-3 交付判据的层级（与 G-CI-2 连接）

**规格**：一次交付的完成判据按**由内到外**四级，逐级都必须有可复核证据：

| 级 | 判据 | 证据形态 |
|---|---|---|
| L1 代码 | 编译 / 类型检查 / 单测 | 退出码 + `Tests run: N, Failures: 0` |
| L2 构建 | 宿主产物已生成**且为最新** | 产物时间/指纹 + 关键文案在产物中可 `grep` |
| L3 部署 | 三处指纹一致（G-DEP-1） | `RELEASE_RESULT=PASS` + 清单落盘 |
| L4 用户路径 | 端到端断言 / 真浏览器走查 | `PASS=n FAIL=0`（"没跑"记为未跑，见 G-CI-1） |

**纪律**：**L2/L3 不通过时，L4 的结论无效**（在旧产物上验收 = 测的不是本次代码）。
本产品实测过一次真实事故形态：`PLM_AUTH_MODE=dev` 下做的 UI 断言结论**不能代表 oidc 生产形态**，
故认证模式必须进发布清单并在验收报告里标明。

## 3. 通用 UI 纪律（G-UI）

### G-UI-1 主业务对象选择一律用检索选择面板（禁止简单下拉/自由文本 ID）

**规格**：凡**选择主业务对象实例**（项目、物料、需求、文档、变更……），必须使用
**服务端检索 + 分页的选择面板**（`SearchPick`，落点 `components/SearchPick.tsx` + 数据层 `lib/lookup.ts`），
**不得**退化为 `<select>` 或自由文本 ID 输入。

**理由（实测缺陷）**：`GET /xxx?pageSize=100` 预加载当全量 + 本地过滤 ⇒ 单页上限 100、
部分域又按 `createdAt` 升序 ⇒ **静默丢掉的恰好是最新数据**（用户实测：101+1=101 选项、缺的正是最旧两条）。
这是"看起来能用、数据悄悄不全"的典型形态，**必须靠构件级约定堵死**，不能靠每个页面自觉。

**纪律**：①候选完整性**必须显式**（「共 N 条 · 已加载 M 条」），不得让用户以为看到的是全部；
②检索走服务端（`/_platform/lookup/search` 型端点）；③字段接入统一走详情面板的 `kind:'lookup'`，
不得为某页另写一套选择器。

### G-UI-2 详情面板是统一构件（含 PATCH 语义与乐观写）

**规格**：对象详情/编辑**一律用统一详情面板构件**（`components/DetailPanel.tsx`），按 `kind` 渲染控件
（`text` / `textarea` / `select` / `date` / `lookup` / `json`），并统一承载：

- **仅提交发生改变的字段**（PATCH 语义）——"无改动"时**不发请求**并就地提示（这也是 13 号文 G-CI-3 里
  `没有检测到改动` 能作为 PATCH 语义证据的原因）；
- 草稿态（`_isNew`）的「创建」路径与失败回滚/草稿保留；
- 只读态与锁定态的**区分呈现**（配合 G-DATA-4 的受控记录横幅）。

**纪律**：新增对象域**不得自建详情面板**；如需新控件类型，**扩展 `kind`** 而不是另起一套表单（否则 PATCH 语义、
错误处理、只读呈现会在各页分叉）。

#### G-UI-2b 复杂字段在详情面板里**独占整行**（批次34 新增，按类型自动判定）

**规格**：详情面板中**复杂字段**（`kind ∈ {longtext, json, jsonread, kv, multi}` —— 长文本、JSON 结构化区、
键值区、多选）在**全屏两列网格**（`.dp.expanded .dp-body`）下必须**独占整行**（`.dp-row.wide`，
即 `grid-column: 1 / -1`）；判据由字段的 `kind` **自动**给出，可用 `DetailField.wide: true/false` 显式覆盖
（例如并排的两个短备注）。渲染时必须输出 `data-field="<code>"` 锚点，使"布局是否真的生效"可被机器断言。

**为什么**：全屏下两列布局把复杂字段与短字段并排，复杂字段撑十几行 ⇒ 同行另一字段纵向大片留空
（用户原话："导致同行的另一字段纵向上下过空"）。
**规则必须写在共用构件里**（`DetailPanel` 的 `isWideField`），不得逐页面手工标记——
否则只修了一个页面，下一个域加长文本字段时同样问题会重犯（与 G-UI-2 的"扩展 kind 而不是另起一套"同源）。

**判据（可复跑的机器断言）**：全屏后复杂字段宽度 ≥ 容器宽 90% 且相邻复杂字段 `top` 严格递增；
**反例**：普通短字段仍为半栏（证明没有把整面板退化成单列）。参考 `W28-批次34三条反馈UI` 的 L2/L3/L3b/L4/L5。

#### G-UI-2c 详情面板的**附加区块（`extra`）**在全屏两列下一律**独占整行**（批次53 新增）

**规格**：详情面板展开态下字段区是两列网格（`.dp.expanded .dp-body`），而 `extra` 槽位
（流程条 / 订正取代 / RTM 追溯 / 流转动作 / 处理记录）承载的都是**整宽区块**，必须 `grid-column: 1 / -1`。

**为什么**（批次53 真浏览器几何实测，需求详情面板）：`extra` 若按普通网格项自动排版，会落进**最后一行的右半栏**
（w=692 / 整行 1353 = **51%**），并把同行字段行撑到 **418px**（该字段自身内容只有 30px）——
左侧输入框孤零零居中（用户原话"很空"），右侧四类控件在 51% 宽度里一路换行（用户原话"纵向空间很长"）。

**纪律**：与 G-UI-2b 同源——**规则必须写在共用构件里**（`DetailPanel` 把 `extra` 包进 `.dp-extra`，
规则在 `styles.css` 一条），页面**不得**自行给 `extra` 写内联 `gridColumn`
（批次53 已把 CBB 资产库页此前那处内联同义写法上收删除，避免"同一规则两处维护、只改一处"）。

**判据（可复跑的机器断言）**：`W44-批次53详情面板附加区块独立整行UI`——附加区块宽 ≥ 0.9× 字段区整行宽、
与任何字段行纵向不相交、位于最后一个字段行之下、区块内四类控件各自独立占一行且各占满整行宽、
字段行行高 ≤ 1.6× 自身最高子元素；**反例**：字段区仍是两列。规则全文与量值基线见
`docs/plm-tech/frontend/03-detail-panel.md` §5.8 与 `frontend/01-design-tokens-shell-layout.md` §3.6（G-UI-7-8）。

### G-UI-3 处理记录（变更历史）是统一构件

**规格**：任何对象的「处理记录」必须**复用**统一构件与统一端点：
`GET /{domain}/{id}/history` → `[{ts, actor, action, diff}]`，前端由 `components/HistorySection.tsx`
渲染为「**旧 → 新**」；各域共用 `AuditService.findByObject`（一处修改全平台生效）。

**纪律**：①**不得**各域另写历史端点（载荷口径会分叉）；②界面不得只显示"谁改的"而不显示"改了什么"
（用户明确要求"改了什么"可见）；③`_isNew` 草稿行**不得**触发历史查询（否则会清空/报错）。

### G-UI-4 后端原文不得直出界面；脱敏值不得当真实值

**规格**：两条界面纪律（均为当日实测缺陷的机械化堵口）：

1. **错误文案归一化**：后端框架原文（Java 异常、类型转换、SQL 原文）**一律经** `lib/apiError.ts` 的
   `humanizeApiError(e, fallback)` 处理——业务文案透传、框架原文降级为通用兜底，**不得**由拦截器 toast
   与页面 `setMsg` **双路直出**（双路 = 两处都要改，必然漏一处）。
2. **脱敏值必须视为"无值"**：脱敏（`***` 或契约字段 `*Masked`）是 **truthy 字符串**，若当真实值处理会：
   被 `JSON.stringify` 当对象展示、被编辑清空写成 `{}`（**数据破坏**）、让"无权限提示"永远不可达。
   脱敏态一律**只读渲染 + 明确"无权限/已脱敏"提示**，且**任何情况下不回写**。

**上游一致性**：接口侧不泄露库结构/约束名/写入语句，见 12 号文 **G-API-1.1** 与 13 号文对写入异常脱敏的要求；
界面侧不得把后端意外吐出的技术细节渲染给使用者。

### G-UI-8 枚举/词表一律服务端下发，前端不承载业务词表（2026-10-02 新增）

**规格**（与 13 号文 G-CI/G-REC 的反假绿纪律同源，UI 场景的具体化）：

| # | 纪律 | 实测反例 |
|---|---|---|
| 1 | **必须禁用缓存**后再验（`Network.setCacheDisabled` + `ignoreCache`） | 缓存旧 `index.html` → 引用旧 chunk，页面行为像旧版本 |
| 2 | **必须等待条件，不得等待时间**（`until(条件)` 而非固定 `sleep`） | 请求式搜索 + 固定 4s ⇒ 负载高时目标行未出现，脚本走兜底路径，失败点漂移到下游断言 |
| 3 | **兜底路径必须记为证据**（如 `fallbackUsed`）；断言不得恒真 | `check(..., rowClicked \|\| true)` 恒真 ⇒ 主路径"点行联动详情"实际未被验证 |
| 4 | **走查脚本的互斥资源必须隔离或加锁**（浏览器实例/固定端口） | 两个走查脚本共用同一 CDP 端口且无条件 kill ⇒ 互相打断，症状是"单独重跑全绿、一起跑同时红" |
| 5 | **不得用 X-PLM-User 头伪造身份**，必须走真实 SSO | 走查要验证的是**用户路径**，伪造身份会把权限/登录问题掩盖掉 |

### G-UI-6 详情面板必须覆盖对象的**关联/归属**字段（哪怕不可编辑）（批次41 新增）

**规格**：详情面板（G-UI-2）的字段集必须**从对象主数据推**（"这个对象有哪些属性/关联"），
**不是**从"我打算让用户改什么"推。凡对象**存在**的关联与归属字段（关联产品、所属项目、责任人、来源、
所属层级/父对象、外部引用……），详情面板**必须可见**：可改的用检索选择面板承载（G-UI-1），
不可改的以**只读**呈现，且呈现口径遵守 G-REF 4.1（`/_platform/lookup/resolve` 批量取号，
显示「编号 · 名称」，**不得**把"尚未解析"（`#id`）与"归属为空"（如「未关联」）混为一谈）。

**判据（可机械核对的入口）**：**"列表有该列 / 工具栏能按它筛选 ⇒ 详情面板必须也有"**。
走查要有一条断言直接问："打开这一条，能不能回答它属于哪个产品（项目/父对象）？"

**实测反例（批次41 回炉，用户 2026-09-20 报障）**：风险台账 `t_risk_item_ledger.product_id` 是**必填**归属
（本环境 8/8 条都指向 `P-2026-0101`），工具栏**能**按产品筛选、列表**有**「产品」列，而详情面板里**查不到**——
用户打开一条风险无法回答"这属于哪个产品"。修法即上面两条：只读字段 + 「编号 · 名称」口径。

**与 G-UI-2 的关系**：这不是"另起一套字段"，而是提醒"统一构件只解决**形态**，
字段**覆盖度**仍要靠对象主数据对账"——`DetailField[]` 清单应对着对象 DTO 逐字段过一遍。

**只读是"接口不能写"的诚实表达，不是实现偷懒的借口（2026-09-20 追加，用户第三轮裁定）**：
用户看完只读归属后问"能不能改选？"（原话：「在新建风险的详情面板中，产品、项目都要可以通过相应的对象选择控件，
选择/改选，而不是不可编辑」；随后裁定"已有条目也要能改选"）。结论：
① 只要**写路径支持**该字段（PATCH DTO 里有它、有校验与留痕），界面就该给**可编辑**形态（G-UI-1 检索选择面板），
**新建草稿与既有对象一视同仁**——"新建能改、打开已存的就不能改"是最容易让人觉得系统半成品的形态；
② 只读形态留给"接口层确实不能写"的字段，且要在**报告里写明"为什么不给改"**（本次是 `UpdateRiskReq` 缺字段，
于是补了字段 + 校验 + 审计，而不是把只读当结论）；
③ 若该字段是**派生判定的输入**（如"风险→关联产品"决定按谁的可接受准则阈值判定），改它必须**连带重算派生判定**
并留痕（合同 C-133），否则"能改了"反而制造出错的结论；
④ 可清空的字段要有**显式的清空语义**（`clearXxx`），"空值就跳过"在 PATCH 语义下等于静默无效（教训 L-521）。

### G-UI-8 枚举/词表一律服务端下发，前端不承载业务词表（2026-10-02 新增）

**规格**：任何一个"界面下拉/标签用的枚举值域"，**权威只在服务端**，并且**值域与显示词同批下发**
（值域 = 列表；显示词 = `code → label` 映射）。前端**只做取数与渲染**，一律走 `src/domain/*` 取数口：

| 类别 | 权威源 | 前端取数口 |
|---|---|---|
| 流程状态（可流转态 + 中文词） | `flows/*.yaml` → `GET /_platform/flows/{flow}` | `hooks/useFlow(flowId, myRoles)` / `hooks/useFlowStateLabel(flowId)` |
| 评审门结论 | 后端 `GateConclusionVocabulary` → `GET /projects/gate-conclusions` | `domain/gateConclusions.ts` |
| 上市后监督（投诉/CAPA/召回） | `PvDtos` → `GET /pv/enums` | `domain/pvEnums.ts` |
| 业务风险台账（等级/阶段/层级/验证态/来源 + S×P 等级矩阵） | `RiskLedgerDtos` + `RiskLevelMatrix` → `GET /risk-ledger/enums`、`/risk-ledger/level-matrix` | `domain/riskEnums.ts` |

**纪律**：
① **`api/client.ts` 不承载业务词表**——它只放 HTTP 客户端与接口类型；词表放进去就等于又造了一份权威：
   服务端加一个值 → 界面下拉选不到（该值的数据在界面上**建不出来**）；界面若有服务端没有的值 → 提交必被服务端拒。
② **显示词也要一起下发**：只下发值域、把中文留在前端，只是把"第二份权威"从值域搬到显示词，缺陷形态不变
   （`CRITICAL` 到货了、"严重"没到货，界面只能裸显码值）。
③ **取不到就退化，不回落写死的旧常量**——回落写死等于把刚消灭的第二份权威放回来。
   退化口径：下拉**选项为空**、标签**回落原码**、**判定类**（如 S×P→等级）**不给结论**（宁可"不知道"，不猜结论）。
④ **预览口径必须查权威**：界面上任何"当帧预览"（如 S×P→等级、门计数）都要用服务端下发的矩阵/读数，
   不得在前端复述阈值——阈值一改，预览就会与保存后的结果不一致，而**提示文本是最容易被漏改的副本**。
⑤ 异步到货的词表**必须写进 memo/useMemo 依赖数组**（L-715 家族）：漏写会让显示词锁死在首帧的码值上。

**反例（本条的来源，均实测）**：`PostMarketPage` 从 `api/client.ts` 导入六份自持值域、在 **24 处**消费，
而后端 `/pv/enums`（注释写着"前端下拉与文档共用同一来源"）**从来没人调用**；
`RiskLedgerPage` 同样自持五份，还抄了一份 S×P 阈值表，而 `/risk-ledger/level-matrix` 的 javadoc
明确写着"由唯一权威计算生成，不写死 25 个格子"——**端点建好了，没人用**（13 号报告 S5 / 14 号报告 S5 同一条根因）。

## 5. 缺陷档案（本文各条规格对应的当日实测缺陷）

| # | 缺陷 | 症状 | 规格 |
|---|---|---|---|
| 1 | **假部署** | 改了代码但行为没变：宿主 dist 更新了、plm-web 镜像未重建（runtime-only 镜像）⇒ nginx 一直服务旧 bundle | G-DEP-1 |
| 2 | **指纹恒不相等（误报）** | nginx 基础镜像自带 `50x.html` + `COPY` 合并语义 ⇒ web 目录树指纹永远对不上，门控**永久误报** | G-DEP-1.2 |
| 3 | **WSL 9P 缓存致"新产物旧内容"** | Windows 编辑后 WSL 内构建仍读旧内容，产物 hash 却变了（最危险的假绿） | G-DEP-1.3 |
| 4 | **预加载单页当全量** | 对象选择器 `pageSize:100` + 本地过滤 ⇒ 静默丢掉最新数据（101 vs 112 选项） | G-UI-1 / G-REF 4.1 |
| 5 | **框架原文直出界面** | Java 异常/类型转换/SQL 原文经拦截器与页面双路吐给用户 | G-UI-4.1（＋12 号文 G-API-1.1） |
| 6 | **脱敏值当真实值** | `***` 是 truthy：被当对象序列化、被编辑清空写成 `{}`（数据破坏）、"无权限"提示永不可达 | G-UI-4.2 |
| 7 | **UI 走查假绿/假红** | 缓存旧 chunk、固定 sleep 等不到目标行、恒真断言让失败点漂移、两脚本抢同一 CDP 端口互相打断 | G-UI-5（＋13 号文 G-CI-1.4） |
| 8 | **认证模式混入结论** | `AUTH_MODE=dev` 下做的 UI 断言被当成生产结论，须在 oidc 下重验 | G-DEP-3（认证模式必须进发布清单与报告） |
| 9 | **关联关系在详情面不可见** | 对象**有**归属字段（风险→关联产品）、列表有该列、工具栏能按它筛选，唯独详情面板查不到 ⇒ 用户打开一条记录无法回答"这属于谁"（批次41 用户报障） | G-UI-6 |
