# 10 · 流程角色与任务分派设计

> **定位**：回答"流程各阶段由什么角色处理、具体单据由哪个人处理"两个问题的设计与实现规格。补齐 `09-工作流引擎与元数据扩展设计.md` 中流程引擎缺失的**任务分派/会签时限**能力（对齐 `04-应用架构 §4`：流程引擎 = 状态机执行 + 任务分派 + 会签/或签 + 时限与升级）。
> **落地**：M1（边级角色门）+ M2（任务实例 + 工作台待办）已实现并验证；M3（会签/升级）预留。
> **版本**：v1（2026-09-05）。

## 1. 问题拆解

"不同角色 × 具体需求单 × 具体处理人员"是**两个正交问题**：

| 层 | 问题 | 约束性质 | 承载 |
|---|---|---|---|
| **岗位层** | 这类迁移**允许哪些角色**执行？ | 制度约束（RBAC 细化） | YAML 边级 `roles` |
| **人员层** | 这一单**具体该谁**处理？ | 工作分派（任务编排） | `t_flow_task` 任务实例 |

**改造前缺口**（实现证据）：

- YAML 只有 states/transitions/editableStatuses，**无边级角色**；
- `transition()` 只调域级 RBAC——`requirement.transition` 允许 PM/PDT/RA/QA/SE/admin 6 角色在**任何状态、任何边**一视同仁（system_engineer 能批准需求、product_manager 能验证需求）；
- V-040⑦ 刻意排除对象级 ABAC（为让 IPMT/PDT 批非本人需求），但**没有任何人员分派机制**；
- 无待办中心（侧栏"工作台"导航实际挂需求管理页）。

**可借鉴的系统内先例**：评审域 `t_review_item.judge_role/judge_by`（角色声明→实际执行人）、ECO 域 `EcoTaskEntity(assignee, dueDate)`、遗留问题 OVERDUE 自动升级。

**人员解析的两级角色体系**：

| 层级 | 表 | 解析语义 | 优先级 |
|---|---|---|---|
| 项目实例级角色 | `t_project_member(project_id, login, role_code)` SPONSOR/PM/SE/QA/RA | "本项目"的 PM 是张三 | 高 |
| 全局功能角色 | `t_user_role` + `t_role` | 全公司的 RA 是李四/王五 | 兜底 |

## 2. L1 边级角色门（M1 已实现）

### 2.1 YAML 格式

```yaml
transitions:
  - { from: ANALYZED, to: APPROVED, label: 批准,
      roles: [product_manager, pdt_manager, admin] }        # 边级角色门
  - { from: ANALYZED, to: PROPOSED, label: 回退, rework: true }  # 无 roles → 回落域级 RBAC
```

### 2.2 运行时校验链

```
transition() 请求
  → ① 域级 RBAC：permission.authorize(domain, "transition")      （现有，不动）
  → ② 迁移合法性：flowEngine.transitionsFrom(flowId, from) 含 to   （现有，不动）
  → ③ 边级角色门（新增）：flowEngine.canTransition(flowId, from, to, actor.roles)
       边无 roles → true（回落域级 RBAC，兼容存量）
       边有 roles → actor.roles ∩ roles ≠ ∅（admin 全通）
```

### 2.3 前端过滤

`useFlow` 返回的 `transitionsFrom` 携带 `roles`；页面拉取 `GET /_platform/permission/me` 取当前用户角色，**无权边不渲染按钮**（admin 全显）。

### 2.4 与 V-040⑦ 的关系（不冲突论证）

V-040⑦ 排除的是**对象实例级 ABAC**（数据访问控制：IPMT 必须能批非本人需求）；边级角色门是**流程编排语义**（这个动作该由哪个岗位执行）——限制的是岗位类别而非对象归属，正交且方向一致。

## 3. L2 任务实例与工作分派（M2 已实现）

### 3.1 语义：任务 = 待执行的迁移实例

对象进入状态 S 时，按 S 出边的 `task` 配置生成任务行——待办即"你有一单需求待批准"。**状态机仍是唯一事实源**（对象表 status 列），任务表可随时从对象状态重建（对齐 04-§4"无状态引擎，状态存库"）。

### 3.2 t_flow_task 表（V38）

```sql
CREATE TABLE t_flow_task (
    id             BIGSERIAL PRIMARY KEY,
    flow_id        TEXT NOT NULL,               -- requirement / project / ...
    object_type    TEXT NOT NULL,               -- REQ / PRJ / ...
    object_id      BIGINT NOT NULL,
    from_state     TEXT NOT NULL,               -- 当前状态
    to_state       TEXT NOT NULL,               -- 任务目标 = 完成此迁移
    label          TEXT,                        -- 待办动作名（如"批准"）
    mode           TEXT NOT NULL CHECK (mode IN ('ASSIGNED','CANDIDATE')),
    assignee       TEXT,                        -- ASSIGNED：指定人
    candidate_role TEXT,                        -- CANDIDATE：候选人角色
    claimed_by     TEXT,                        -- 认领人
    status         TEXT NOT NULL DEFAULT 'OPEN'
                   CHECK (status IN ('OPEN','CLAIMED','DONE','CANCELLED')),
    due_date       DATE,                        -- dueDays 折算
    done_by        TEXT, done_on TIMESTAMPTZ,
    created_on     TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_ftask_my ON t_flow_task(assignee, status);
CREATE INDEX idx_ftask_obj ON t_flow_task(object_type, object_id);
```

**生命周期**：

```
进入状态 S ──→ 按出边 task 配置生成任务（OPEN）
CANDIDATE 认领 ──→ CLAIMED（claimed_by=me，可 release 回 OPEN）
执行迁移成功 ──→ 本次迁移对应任务 DONE（done_by=执行人）
              ──→ 同对象同 from_state 其余任务 CANCELLED
              ──→ onEnterState(to) 生成下一状态任务
对象回退      ──→ 同样：CANCEL 旧任务 + 生成回退后状态的任务
```

### 3.3 人员解析链（assigneeFrom）

YAML 声明，按序取第一个命中：

| assigneeFrom | 解析 | 适用 |
|---|---|---|
| `creator` | `t_requirement.created_by`（各域 created_by 列） | 起草人自行推进 |
| `owner` | 对象 owner 字段（有则用） | 有 owner 的域 |
| `pm` | `t_project_member WHERE role_code='PM' AND project_id=对象.project_id` | 项目内分派 |
| （缺省→CANDIDATE） | `candidateRole` 全局角色池 | 无确定负责人 |

### 3.4 YAML task 配置

```yaml
transitions:
  - { from: PROPOSED, to: ANALYZED, label: 分析,
      roles: [system_engineer, product_manager, pdt_manager, admin],
      task: { mode: ASSIGNED, assigneeFrom: creator, dueDays: 3 } }   # 起草人推进
  - { from: ANALYZED, to: APPROVED, label: 批准,
      roles: [product_manager, pdt_manager, admin],
      task: { mode: CANDIDATE, candidateRole: product_manager, dueDays: 3 } }  # PM 池认领
```

### 3.5 执行约束

- **ASSIGNED 任务**：迁移执行人必须 = `assignee` 或 `claimed_by` 或 admin（任务分派的实质约束）。
- **CANDIDATE 任务**：M1 角色门已保证执行人属候选角色；认领人优先，未认领不强制。
- 迁移成功后任务 DONE/CANCELLED + 审计链记录（`t_audit_log` 复用）。

### 3.6 REST 端点

```
GET  /api/v1/_platform/tasks/my          → 我的跨域待办（联对象表取编号/标题，附 overdue；含 canAssign）
POST /api/v1/_platform/tasks/{id}/claim  → CANDIDATE 认领（candidate_role ∈ myRoles）
POST /api/v1/_platform/tasks/{id}/release→ 释放认领（CLAIMED → OPEN）
GET  /api/v1/_platform/tasks/{id}/assignees → 可指派候选人（项目成员优先，回退 candidateRole 组织角色用户）
POST /api/v1/_platform/tasks/{id}/assign → 指派处理人 {assignee}（2026-09-09 新增，需求 4）
```

`myTasks` 判定：ASSIGNED → `assignee=me OR claimed_by=me`；CANDIDATE → `candidate_role ∈ myRoles`（OPEN）或 `claimed_by=me`；admin 全见。
`canAssign` 判定（同一套逻辑，避免前端重复实现）：admin ∨ `pdt_manager` ∨ 对象所属项目的项目角色 `PM`（`t_project_member.role_code='PM' AND login=me`）。指派语义：`assignee=目标人`、`mode='ASSIGNED'`、`status='OPEN'`、`claimed_by=NULL`（指派后回到待执行），写审计 `task.assign`。

### 3.7 当前处理人（派生 + 按处理人筛选）

**建模**：`currentAssignee` **不建独立列**，由 `t_flow_task` 实时派生（任务表可从对象状态重建，无冗余、零不同步）：

```
currentAssignee = claimed_by ?? assignee
    CANDIDATE + CLAIMED → 认领人
    ASSIGNED            → 指定人（assigneeFrom 解析）
    CANDIDATE + OPEN    → 空（"待认领"）
```

#### 3.7.1 FlowTaskService 派生/筛选 API

| 方法 | 签名 | 职责 |
|---|---|---|
| `currentAssignee` | `String (objType, objectId)` | 单对象处理人（create/transition/update 的详情响应 `toResp`） |
| `currentAssignees` | `Map<Long,String> (objType, List<Long>)` | 批量派生（列表页 `list()` 避免 N+1） |
| `matchingIds` | `List<Long> (objType, assignee)` | 指定处理人的对象 id 集（按处理人筛选） |

#### 3.7.2 后端查询：按处理人筛选

`RequirementService.list()` 流程：

```
assignee 提供? → matchingIds("REQ", assignee) → 空集? → 直接空页
               → 非空 → repo.searchByAssignee(..., r.id IN :assigneeIds)   ← 拆分 @Query
assignee 未提供? → repo.search(...)                                     ← 原查询（无过滤，[] 参数分散寻址）
```

> **关键**：`r.id IN :assigneeIds` 独立成 `@Query` 方法（`searchByAssignee`），而不是在公共查询加 `:list IS NULL OR ...`——Hibernate 6 对 **collection 参数不支持 `IS NULL` 判断**（会抛类型绑定错误），拆两个方法最稳。

#### 3.7.3 前端模式

- **toolbar 筛选**："当前处理人"下拉（`GET /users/lookup` 用户库选项），**默认 = 当前登录用户**（`assignee` state 初始 `currentUser()`）。
- **表格列**：`{ field: 'currentAssignee', headerName: '当前处理人', width: 110, filter: false, valueFormatter: p => p.value ? p.value : '待认领' }`（关联派生值，`filter: false`——筛选走 toolbar 下拉而非列过滤器）。
- **详情字段**：`{ code: 'currentAssignee', label: '当前处理人', kind: 'tel', readonly: true }`（只读展示）。
- **流转后保留对象**：`transition()`/`doRework()` 成功后 `setSelected(r.data)`（transition API 返回更新后 `ReqResp`）——**保留显示原对象**并同步刷新版本/状态/处理人；禁止 `setSelected(null)`（会清空详情面板）。

### 3.8 任务分派的身份来源（dev / OIDC 双模式）

claim / release / 执行约束（`assertCanExecute`）/ 当前处理人写入的 login **一律取 `AuthContext`（认证载体），禁止从前端参数取**（V-019）。双模式下同一套业务代码，身份由平台认证链（09 §1.4.7）注入：

| 任务分派语义 | dev 模式（X-PLM-User） | oidc 模式（Bearer JWT） |
|---|---|---|
| 认领人 `claimed_by` | header 用户 | token `preferred_username` |
| 角色池判定 `candidateRole ∈ myRoles` | `t_user_role`（DB） | **`t_user_role`（DB，2026-09-09 起）** |
| ASSIGNED 执行人约束 | assignee=header 用户 | assignee=`preferred_username` |
| 当前处理人派生 | `claimed_by ?? assignee`（同构） | 同构 |

**身份与角色分离（2026-09-09 权威口径，用户确认）**：**登录身份来自认证载体**（oidc: JWT `preferred_username`；dev: `X-PLM-User`，仅开发），**角色一律以系统设置（DB `t_user_role` / `t_project_member`）为唯一事实源**——`JwtContextFilter` 在 oidc 模式下按 login 查 DB 取角色，**不再消费 Keycloak `realm_access.roles`**。收益：①系统设置改角色立即生效；②dev/oidc 授权语义一致；③消除"前端恒发 X-PLM-User 导致身份被 DB 角色覆盖"的隐性双轨（该系统设置创建角色 403 的根因）。Keycloak 仍负责账号与认证，其 realm roles 仅作 IdP 侧组织用途。

**角色对齐要求（已由上述改造消解）**：历史口径要求"Keycloak realm role 名必须与 `t_role.code` 同名词"；改造后该要求不再影响授权判定，但**建议保持同名**以便 IdP 侧审计对照。

**系统设置写权限**：`_admin.manage` = {admin, pdt_manager}（V40）；无权限用户创建角色返回 403 + 可行动提示（前端不静默失败）。

**OIDC 模式验收**（`plm-oidc-backend-verify.sh` 10 条 + `plm-oidc-sso-verify.cjs` 7 条，全绿）：

| # | 断言 | 结果 |
|---|---|---|

| B3 | Bearer token → 200；pm1 `permission/me` roles=product_manager（**历史口径**：当时取自 realm roles；2026-09-09 改造后取自 DB，见 B7） | PASS |

| S1 | 真实 Keycloak SSO 登录（登录页→PKCE 回调）→ topbar 显示 `pm1` | PASS |

## 4. 工作台承接（待办汇聚）

**每个业务对象的待处理事项以面板方式汇聚到一张工作台**（`/` 路由，侧栏"工作台"）：

```
┌─ 工作台 ────────────────────────────────────────────────┐
│ page-head：工作台 + 当前用户角色徽章                        │
│ ┌─ 需求待办面板 ─────────────┐ ┌─ 项目待办 ────────────┐ │
│ │ [批准] 📎REQ-2026-0184 ... │ │ 暂无待办              │ │
│ │ [实施] 📎REQ-2026-0183 ... │ ├─ 文档待办 ────────────┤ │
│ │ [认领]（CANDIDATE+OPEN）    │ │ 暂无待办              │ │
│ └───────────────────────────┘ └──────────────────────┘ │
│ ┌─ 物料待办 ──────────┐ ┌─ 产品待办 ──────────────────┐ │
│ └─────────────────────┘ └────────────────────────────┘ │
└─────────────────────────────────────────────────────────┘
```

**交互原则**（2026-09-09 修订）：面板呈现待办清单 + **轻量动作行内完成**——`认领`（CANDIDATE 接单）、`指派`（项目经理派单，行内下拉无弹窗）、`推进`（处理人直接流转，**无需修改对象内容**，满足"处理人可直接在待办推进流程状态"）；**涉及内容编辑的操作仍跳转业务页**（详情面板统一保存）。行内按钮一律 `stopPropagation()`。

- 数据源：`GET /_platform/tasks/my` 按 `object_type` 分组渲染面板——**新域接入流程引擎后其待办自动出现在工作台**（`OBJ_LABEL` 注册即点亮，未知类型归入"其他"面板）。
- 面板行：待办动作 pill（目标状态色）/ 📎 编号 / 标题 / 时限（逾期红标）/ `认领` 按钮 / `xx 处理中`（CLAIMED）/ `指派:xx`（ASSIGNED）/ **`指派` 按钮**（`canAssign`）/ **`推进` 按钮**（`task.label`；迁移边 `requires` 未满足时禁用 + tooltip 提示，后端 `FIELD_REQUIRED` 权威兜底）。
- 逾期：`due_date < today AND status ∈ (OPEN, CLAIMED)` → 红标 + 排序置顶。

## 5. L3 会签/或签 + L4 升级（M3 预留，未实现）

### 5.1 会签/或签

```yaml
transitions:
  - { from: ANALYZED, to: APPROVED, label: 批准,
      sign: { mode: ALL, nodes: [ { label: PM批准, roles: [product_manager] },
                                   { label: RA会签, roles: [ra] } ] } }
```

- 建模：一条迁移生成多条任务（同 sign_group），**ALL = 全部 DONE 才放行**（BR-05 RA 会签、BR-14 SQE 会签），ANY = 任一完成。
- 最后一个 DONE 人触发 transition；部分完成的签节点保留 DONE 记录（审计）。

### 5.2 时限升级

- M2 已有 `due_date` + 工作台逾期红标。
- M3：定时扫描 OPEN/CLAIMED 逾期任务 → 通知 assignee/candidateRole → 逐级升级（对齐 `t_open_issue` OVERDUE 先例：逾期升级 + 绑定门点阻断）。

## 6. 需求流配置实例（requirement-flow.yaml 现行内容）

> 2026-09-09 更新①：新增"方案制定中"状态（SOLUTION_DEFINING）与推进前置条件；原 `APPROVED→IMPLEMENTED` 直达边**移除**（实现必经方案制定）。
> 2026-09-09 更新②（角色对齐，用户定义落地）：新增**已验收**状态（ACCEPTED）；主链各节点按"组织角色/项目角色"重新分派——提出=组织任何人、分析=需求分析师、批准=产品经理（**批准前必须已指定承接项目**）、方案=项目角色 prj_sa、实现=prj_dev、测试=prj_qa、验收回到需求分析师。

| 边 | roles（角色门） | task（任务分派） | requires（推进前置条件） |
|---|---|---|---|
| PROPOSED→ANALYZED 分析 | requirement_analyst/pdt/admin | CANDIDATE requirement_analyst 3d | — |
| ANALYZED→APPROVED 批准 | product_manager/admin | CANDIDATE product_manager 3d | （承接项目必填，服务端 400 PROJECT_REQUIRED） |
| ANALYZED→PROPOSED 回退 | （域级 RBAC） | 无（回退即时动作） | — |
| APPROVED→SOLUTION_DEFINING **方案制定** | prj_sa/pdt/admin | CANDIDATE prj_sa 3d | — |
| SOLUTION_DEFINING→IMPLEMENTED **确定方案** | prj_sa/prj_dev/admin | CANDIDATE prj_dev 5d | **solution（方案内容）** |
| SOLUTION_DEFINING→APPROVED 回退 | （域级 RBAC） | 无 | — |
| APPROVED→ANALYZED 回退 | （域级 RBAC） | 无 | — |
| IMPLEMENTED→VERIFIED **测试** | prj_qa/admin | CANDIDATE prj_qa 5d | — |
| IMPLEMENTED→APPROVED 回退 | （域级 RBAC） | 无 | — |
| VERIFIED→ACCEPTED **验收** | requirement_analyst/admin | CANDIDATE requirement_analyst 3d | — |
| ACCEPTED→CLOSED 关闭 | requirement_analyst/pdt/admin | 无（低风险即时动作） | — |

- **节点角色定义（需求 2 落地口径，V45/V46）**：
- **两级角色体系参与门禁**：有效角色 = 组织角色（`t_user_role`）∪ **项目角色**（`t_project_member`，按对象所属项目圈定）——批准后主链（方案/实现/测试）由"对应项目的角色"处理；边级角色门（`TransitionDef.roleAllowed`）、域级 RBAC（`permission.can(domain,action,roles)` 显式角色集重载）、任务候选池（`myTasks` 的 prjRoleBranch）与认领（`claim`）四处同口径。

#### 6.2.3 签署/否决模型（t_review_signer，V46 新表）

| 评审类型 | 必需签署（`signer_role=CHAIR`，一票生效） | 否决权 | 权限点 |
|---|---|---|---|

| TR（技术评审） | `tr_chair`（或 admin） | `quality` / `pdt_quality` | 同上 |

- **表结构**：`signer_role ∈ {CHAIR,MEMBER,QA}` × `action ∈ {SIGN,VETO,ABSTAIN}` × `status ∈ {ACTIVE,RELEASED}`；`on_behalf_of` 代理签署双留痕（GAP-31）；`sign_hash` 复用 SignatureService；同一评审同人同角色同动作仅一条 ACTIVE（`uq_review_signer_active`，否决解除后可重提）。
- **decide 前置校验链**：无 CHAIR 签署 → 400 `SIGNER_REQUIRED`（LEGACY 双写记录豁免）；存在 ACTIVE 否决票 → 400 `VETO_PENDING`（解除 release-veto 置 RELEASED 后可判）；结论 GO_WITH_RISK/COND 必填 `condition_note` → 400 `COND_NOTE_REQUIRED`；强制项未全判 → `MANDATORY_ITEMS_PENDING`（TERMINATE/REDIRECT 止损豁免）。
- **COND 两级条件意见**：项级 `judgeItem` COND 必填 `note`（条件意见）+ 可选 owner/due → 生成 `t_open_issue`；结论级落 `t_review.condition_note/condition_owner/condition_due` 并**同事务**生成一条 `t_open_issue`（绑定门点：DCP→下一道 DCP；TR→其 `blocks_dcp`）。
- **旧门四方签署退役（BR-04）**：`openGate` 不再要求 host/design/quality/reg 四方齐备，`signGateParty` 端点保留但只读归档（`t_sign_rec` 历史保留）；开门新判据 = 强制项全 PASS + 遗留清零 + **该门映射的 DCP/TR 评审结论已满足**（DCP ∈ {GO, GO_WITH_RISK}，TR ∈ {PASS, COND}；该门尚无评审记录时放行以兼容双跑——开门动作本身会经 `recordLegacyDecision` 生成 LEGACY 评审）。**2026-09-10 补齐同源残留**：门卡片 `GateResp.canOpen/blockReason` 同步对齐——去掉"会议签署未齐"签署条件，改判「GATE_REVIEW_NOT_PASSED：<gate> 评审未通过（须 DCP 结论 GO/GO_WITH_RISK 或 TR 结论 PASS/COND）——请先在评审工作台完成判定」（与 openGate 同源判据 hasReviewRecord/gateSatisfied）；后端集成测试 8 条失配同步对齐（`projectGate_br04` 改写为退役守卫 + 评审判据，不保留旧断言），见 acceptance §7.10。

#### 6.2.7 两级意见 + 一次签署成结论（V50，2026-09-10 用户实测反馈）

**缺陷链**（用户以 PRJ-2026-0003 实测暴露）：PM/IPMT 主任走完「发起 DCP0 评审 → 项级判定 → 记否决 → 记录评审结论」后，选 REDIRECT 被 400「否决/有条件决策必须记录理由」拦下，而 UI **根本没有理由输入框**；同时"记录评审结论"是什么、专业评审与综合评审的关系、签署与结论的先后均无定义。

**口径（用户确认）**：

1. **两级意见，范围不同，允许差异化**
   - **项级（专业评估）**：责任角色（`judge_role`）对本领域检查项判 PASS/COND/FAIL + 条件意见 → 写入 `t_review_item.conclusion/note`；
   - **结论级（综合评估）**：主席（DCP=IPMT 主任 / TR=技术评审主席）对投资·技术·资源·风险做综合权衡 → 写入 `t_review.opinion`（V50 新增列）。
   - 专业评估与综合评估**范围不同**，故主席的结论级意见**可以不同于**项级汇总（例如项级全 PASS 但主席因组合风险给 GO_WITH_RISK）。
2. **系统给候选、用户可改**：`suggest(review, items)` 按项级结果生成候选——
   - 存在 FAIL → 候选 REDIRECT/FAIL；存在 COND → 候选 GO_WITH_RISK/COND；全 PASS → 候选 GO/PASS；
   - 候选意见 = `【项级专业意见汇总】`（逐项：项号 检查项：结论 [责任角色] 条件意见）+ `【综合评估】` 空段待主席填写；
   - `GET /reviews/{id}` 返回 `suggestedConclusion`/`suggestedOpinion`，前端预填到综合意见框并提供「采纳系统建议」按钮（可改）。
3. **签署 = 形成合议结论**（用户明确否定"先签署再给意见"的两步模型）：主操作是**「签署并记录结论」**，一次原子完成——
   - `POST /reviews/{id}/decide` 带 `sign=true` 时，在写入结论前校验主席身份，写 CHAIR SIGN 记录（`reason='签署并记录结论：<结论>'`），`sign_hash` = SHA-256(`RVW|reviewCode|conclusion|opinion|conditionNote`)，签名与"结论 + 综合意见"绑定；审计 `review.sign_decide`；
   - 保留独立 `POST /sign`（仅签署）作为会签/会上先签的次要路径；已签署后按钮变「记录结论」；
   - 判定前置链不变：`SIGNER_REQUIRED`（未签署且未走合并路径）/`VETO_PENDING`（存在 ACTIVE 否决）/`MANDATORY_ITEMS_PENDING`（TERMINATE/REDIRECT 豁免）/COND 必填条件意见。
4. **结论理由按决策矩阵渲染**：`GET /reviews/decision-rules?reviewType=` 返回 `[{decision, allowedRoles, reasonRequired}]`，前端据此渲染"结论理由（必填）"输入框（REDIRECT/TERMINATE/NO_GO/REJECT/FAIL/COND 为 t；COND 类由条件意见承担理由）——消除"后端要理由、前端无输入框"的契约错配（根因见 L-147/N-025）。
5. **判定资格显式化**：`GET /reviews/{id}` 的每个评审项返回 `allowedRoles`（资格角色）、`assignee`/`claimedBy`（处理人）、`taskId`、`canJudge`、`canJudgeOverride`（admin 代判）。前端按 `canJudge` 显隐 PASS/COND/FAIL 按钮（无权显示「无判定资格」），后端始终权威兜底。

### 6.3 权限一致性自动校验（V57，2026-09-10——同一缺陷模式出现 4 次后的机械化堵漏）

**动机**：「域级权限点 ⊇ 其细粒度资格并集」被违反已发生 4 次（V41 需求流 → V49 项目流转 → V52 `review.opinion` → V54 `project.gate.judge`），每次都是"合格的人被域级拦死、系统不报错、靠人工核对才发现"。改为**机器检查**：`com.plm.platform.permission.PermissionConsistencyCheck`。

**校验项**（每次启动执行；`GET /api/v1/_admin/permission/consistency` 可随时查询同一份报告）：

| 违规码 | 判据 | 对应历史缺陷 |
|---|---|---|
| `JUDGE_ROLE_UNKNOWN` | `t_checklist_item` / `t_gate_check` 的 `judge_role` 必须是 `JudgeRoleMatrix` 的键 | 清单写 `pdt_manager` 而矩阵缺键 → 该项无人可判且无候选待办（静默） |
| **`DOMAIN_UNION_MISSING`** | **域级权限点 ⊇ 细粒度资格并集**：`review.opinion` ⊇ JudgeRoleMatrix 值并集；`project.gate.judge` ⊇ 同；`review.decide` ⊇ `t_gov_decision_rule.allowed_roles` 并集；`project.transition` ⊇ **project-flow** 全部边级 roles 并集 | V41/V49/V52/V54 |
| `ROLE_UNDEFINED` | 权限点/决策矩阵/流程边引用的角色码必须在 `t_role` 定义 | V46 决策矩阵引用 `IPMT/TR_LEAD` 等未定义码 → 实际仅 admin 可决策 |
| `RULES_DB_DRIFT` | `PermissionService.RULES` 与 `t_permission_rule` 对同一 (domain, action) 必须一致 | V46/V52 改动 DB 后忘记同步 RULES |
| `ABAC_LEAST_PRIVILEGE`（告警） | 某 obj_type 的 write 角色集中，部分角色有 `t_role_abac` 规则、部分没有 → 同时持有两类角色的用户可能被 least-privilege 误拒 | V55→V56 放开 PM 后被对象级 ABAC 拒 |

**策略**：`plm.permission.consistency.strict=true`（默认）→ 启动发现违规即抛 `IllegalStateException` **终止启动**（容器进入重启循环、healthcheck 不通过），把"能启动但合格用户 403"的静默缺陷变成**交付前可见的失败**；紧急放行用 `PLM_PERMISSION_CONSISTENCY_STRICT=false` 或 `PLM_PERMISSION_CONSISTENCY_EXEMPT=<违规码>`（须登记理由）。

**边界（为什么取"按流程"取并集）**：边级 roles 的并集必须**按流程**取——需求流边里有 `prj_sa/prj_dev/prj_qa/requirement_analyst`，与 `project.transition` 无关；按"全部流程"取会产生假阳性（本校验实现时即被自身抓到一次）。

**连带修复（V57 校验发现）**：
1. **`t_permission_rule` 从未生效**：`canRoles` 用 `om.convertValue(PGobject, List<String>)` 解析 jsonb，pgjdbc 读回的是 `PGobject` → 抛异常被 `catch(Exception ignored)` 吞掉 → **永远回退 RULES**。即"元数据矩阵优先（表胜）"是假的，V46/V49/V52/V54/V55 对 `t_permission_rule` 的修改在运行时全部未生效。修复：统一 `parseRoles()`（List / 反射取 `getValue()` / JSON 字符串三态容差）。
2. **`assertJudgeRole` 粗粒度集合漏掉项级资格角色**：只认 `DCP_JUDGES`/`TR_JUDGES`（IPMT/PDT 治理侧），而 DCP 清单的责任角色含 `ra`/`quality`/`dcc`/`hardware`… → 这些责任人过了项级矩阵也会被前置门 403。修复：判定权 = **本评审任一评审项的资格角色 ∪ 评审类型治理角色**。

### 6.4 签署 / 否决 / 结论的语义边界（V58，2026-09-10 用户口径确认）

> **产品级规格回链**：本节的签署=定论（WORM）、否决靶子="推进"而非评议结论、"修改决策=再次发起新评审"等语义已抽取为 **G-REV-5**（`12-产品级通用规格-评审机制与列表范式.md` §2.5，含守卫族统一错误码与 UI 断言 A4"界面语义明示"）——新域评审的签署/否决/结论 UI 与守卫按该规格接入，本节为项目域实例与语义出处。

**用户口径（原文要点）**：签署处应显示**最终形成的综合评议结论**；IPMT 主任有否决权，**可在签署前**提交否决（签署前可撤回）；界面须明确**否决否决的是"项目继续往下推进"，而不是否定前面形成的集体评议结论**；**签署后决策形成定论，项目流程按意见推进**；要改决策只能**再次发起一次新的决策评审**。

| 动作 | 谁做 | 语义 | 系统效果 | 时间窗 |
|---|---|---|---|---|
| 项级专业意见 PASS/COND/FAIL | 各评审项资格角色（JudgeRoleMatrix） | 专业评估（**输入**） | 写 `t_review_item`；COND → 遗留问题 | 评审中 |
| **否决 VETO** | IPMT 成员/主任（TR=质量/PDT 质量代表） | **阻止项目继续往下推进**（不放行下一阶段），**不是**否定集体评议结论 | `t_review_signer(MEMBER|QA, VETO)`；存在 ACTIVE 否决 → 签署/形成结论被拒（`VETO_PENDING`） | **仅签署前**（签署后 `SIGNED_NO_VETO`）；签署前可由本人或 admin **撤回**（RELEASED 留痕） |
| **主席签署** | IPMT 主任（TR=技术评审主席） | **代表 IPMT 形成合议结论并生效（定论）** | 写 `CHAIR/SIGN` + 签名哈希（绑定「结论 + 综合意见」） | 一次；不可重复、不可撤销 |
| **结论** | 主席随签署选定 | 决议的**内容**：GO / GO_WITH_RISK / REDIRECT / TERMINATE（TR: PASS/COND/FAIL） | 写 `t_review.conclusion`；**仅 GO / GO_WITH_RISK 解锁阶段流转** | 与签署同一原子操作 |

**关键澄清**：
1. **签署 ≠ 通过**。签署是"决议生效"的程序动作，结论才是"通过与否"。`REDIRECT`/`TERMINATE` 同样是"已签署形成结论"，但项目不往前走。
2. **签署 = 定论**。签署后不再接受否决（否决窗口关闭）、不可改判；要改只能**再次发起新的决策评审**（旧评审保持 WORM 只读）。界面在定论后提示"如需修改决策，请再次发起评审"。
3. **否决的靶子**是"往下推进"而不是"集体评议结论"——项级专业意见与综合意见继续有效并留档，只是本决策点不放行。
4. 兼容路径：`POST /reviews/{id}/sign`（仅签署、不带结论）保留用于**历史数据/会签**（如 RVW-2026-0160 即为该状态）；界面默认只提供「签署并形成结论（定论）」一步完成，历史"已签署未记录结论"的评审显示「记录结论（补齐历史签署）」。

**实现要点**：
- `ReviewService.veto`：`DECIDED` → 拒；存在 `CHAIR/SIGN ACTIVE` → `SIGNED_NO_VETO`；理由必填。
- `ReviewService.sign`：新增 `VETO_PENDING` 前置（存在未撤回否决 → 无法签署形成结论）；保留原 DECIDED / 主席身份 / 不可重复校验。
- 前端「IPMT 决策与签署」区：顶部即显示**最终形成的综合评议结论**（结论 + 综合意见 + 条件意见；未签署时标注"拟形成，未生效"）；主席签署行（签署人/时间/代签/签名绑定内容）；否决行（身份标注 + "否决的是推进而不是评议结论"说明 + 撤回）；定论后显示"再次发起决策评审"指引。**陈旧显示修正（2026-11-13 批次66 需求②）**：此前"签署+定论"合并 POST 的响应会陈旧显示「拟形成…（尚未签署，未生效）」——现 `ReviewService` 每次写经 `headWrite()` 使 `rvw:head|` 请求级记忆失效，且 decide 物化条件台账行后调 `forgetCondsMemo()` 清 `rvw:conds|` 记忆，合并响应即带最终结论与 DECIDED 状态。
- **项目阶段显示修正（2026-11-13 批次66 需求③）**：项目统计格显示**真实当前阶段**（`t_project.status` 库值），不再把"下一可达阶段"误标为当前阶段；「推进」按钮由 `flow.stageGuards` 门控——守卫不满足时禁用并提示"须 {dcp} 结论 GO/GO_WITH_RISK"。未引入自动推进；III/NA 类项目阶段轴与 I/II 同源，仅门集裁剪，同一显示纪律适用。

> 本节语义（签署=定论 / 否决=阻推进非否决议案 / 改判=再次发起评审）已连同评审容器、责任人管理、强制检查项抽取为产品级通用规格 **G-REV-1~6**，见 `12-产品级通用规格-评审机制与列表范式.md` §2。

### 6.5 认证模式：身份生效是权限结论的前提（V58 附带，L-179）

**现象**：某次回归发现"所有用户的 `/me` 都返回 `[pdt_manager, admin]`"、签署记录 actor 全是 `admin`——即 **`PLM_AUTH_MODE` 退回 `dev`**（`X-PLM-User` 模拟，缺失时回退 seed user）。此时任何权限断言/否决断言都会假绿。

**根因**：`docker-compose.plm-app.yml` 用 `${PLM_AUTH_MODE:-dev}` 兜底，而 `deploy-plm-app.sh` 才 `export PLM_AUTH_MODE=oidc`。**绕过部署脚本直接 `docker compose up -d plm-service`** → 容器静默进入 dev 模式。

**堵漏**：① `SecurityConfig` 启动即播报 `AUTH_MODE mode=…`，dev 模式打 **WARN** 并说明后果与正确部署方式；② e2e 增加**认证模式守卫断言**（不同 token 必须得到不同角色集，否则直接 FAIL 并提示 `PLM_AUTH_MODE=dev`）；③ 部署一律走 `deploy-plm-app.sh`（不要直接 compose up）。

### 6.6 需求基线流配置实例（req-baseline-flow.yaml，2026-11-11 用户裁定 D63-1~D63-4）

**为什么单列一节**：需求基线是 §6 那条「两级角色四处同口径」不变量**唯一的违反者**，
且违反方式很隐蔽——不是报错，是**按钮静默消失**。这类缺陷必须写进规格，否则下一次
"照 §6.1 checklist 复制"会把错误一起复制到下一个域。

**状态机（三态，2026-11-11 去掉 `ARCHIVED`）**

```
DRAFT ──批准──→ APPROVED ──作废──→ OBSOLETE
  └────────────────作废──────────────→  OBSOLETE
```

| 边 | roles（角色门） | task（任务分派） | reason |
|---|---|---|---|
| DRAFT→APPROVED 批准 | pdt_manager / admin | **CANDIDATE pdt_manager 3d**（原无） | **必填**（原无） |
| APPROVED→OBSOLETE 作废 | **pdt_manager / admin**（原含 requirement_analyst） | 无 | 必填（原就是） |
| DRAFT→OBSOLETE 作废 | **pdt_manager / admin**（原含 requirement_analyst） | 无 | 必填 |

**`ARCHIVED` 态为什么删**：它与 `OBSOLETE` 的唯一实质差别，是 `RequirementBaselineService`
的活跃口径 `status <> 'OBSOLETE'` ——**归档态仍算「当前基线」**，也就是归档根本做不到
"让老基线退出当前依据"，它只表达"暂停使用但仍占位"。用户裁定"新基线发布，老基线作废"时，
归档承担不了这件事。探针实测库内 `ARCHIVED` **0 条** ⇒ 零存量迁移。
⇒ 迁移须替换 `V150__req-version-and-baseline.sql:72` 的
`CHECK (status IN ('DRAFT','APPROVED','ARCHIVED','OBSOLETE'))`。

**批准新基线不自动作废旧基线**（用户裁定 D63-3，手动作废）：同项目可并存多条基线；
"一条需求可多次纳入不同基线"本就是既有语义（`UNIQUE(baseline_id, req_version_id)` 只在单条基线内去重）。
随归档态一并退役的权限点：`archive`、`unarchive`；`obsolete` 保留。

**批准必填的范围**（用户裁定 D63-4）：**只有需求与需求基线两个域**。
后端执行点本来就存在（`RequirementService` / `RequirementBaselineService` 的 `REASON_REQUIRED`），
本批补的是**声明**（YAML `reason: true`）与**前端输入框**。
⚠ `docs/plm-user-guide/附录C:51` 登记的「交付物批准无审批意见」偏差**本批不修**（范围外），
该条目继续留在附录 C，不要被后人误读为已修。

**理由字段即交接说明**：全平台**只有一个** `reason` 字段承载
"交接说明 / 回退原因 / 作废依据 / 批准意见"，落 `t_audit_log` 的 `diff.reason`，**库里没有专列**。
`TransitionDef.needsReason() = rework || requireReason` 是唯一判定点，
前端 `useFlow.requiresReason(from,to)` 已按它取数——所以边一旦加 `reason: true`，输入框自动出现。
⚠ 前端**不得**再硬编码"只有作废才要理由"（`RequirementsBaselinesPage.tsx:211` 现正是这么写的），
否则声明改了、界面不跟，就出现"后端 400、界面上找不到该填的框"。

**⚠ 重构红线：T4-6 对账是字符串扫描**
`deploy/wsl/plm-app/plm-edge-role-integrity.sh:36-40` 靠扫描
「声明域 → 执行类」映射来核验边级角色门，**不是运行时调用**。
把 `edge.roleAllowed` 挪进平台层会让扫描失读并触发假红（历史上已发生过一次，
`kb/health.2026-09.012.md` 有记录）。
⇒ 角色判定仍留在 `RequirementBaselineService` 内显式调用，只把**角色集合**换成两级口径。
