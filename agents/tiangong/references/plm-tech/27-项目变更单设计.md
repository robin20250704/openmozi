## 0. 一句话结论

**项目变更单 PCO 是独立对象，不是 ECO 的一个字段**——因为它的**批准人（IPMT 主任 / PDT 经理，不是 CCB 五维签署人）**、**门禁后果（影响 DCP/TR 门线，不是影响物料版本）**、**生命周期（比 ECO 轻得多）**三者全不同；而**前端承载完全复用** `/changes` 工作台，扩为"**一页四对象、一线四单据**"。

**最重要的一条纪律**：`t_project` 现有的 `project:update` 权限点**含 `PM`**（`PermissionService.java:151-163`），即**项目经理今天就能直接改项目的 `plan_start/plan_end/attrs`**。若不封这条路，PCO 只是一条"可绕过的可选流程" ⇒ **锁定 `ProjectService.update` 是 PCO 落地的前提，不是附属工作**（§9）。

## 2. 为什么独立于 ECO（5 条判据）

| # | 判据 | 事实（可核） | 合进 `t_eco` 会怎样 |
| --- | --- | --- | --- |
| **① 批准主体不同** | ECO 走 **CCB 五维签署**（技术/法规/风险/V&V/制造）+ CCB 决议（`ChangeService` 五维 JSONB + `ccbResult`）；PCO 走 **IPMT 主任 / PDT 经理单签** | — | 一个 `t_eco` 要同时表达两套签署链，字段大面积互斥 |
| **② 生命周期不同** | ECO 9 态（含五维评估、CCB 评审、任务包、验证），`editableStatuses:[DRAFT]`；"进度挪两周"要走 8 步 | `flows/eco-flow.yaml` | 状态机分叉，`flows/` 的唯一事实源被污染 |
| **③ 门禁后果不同** | ECO 的后果是"已发布对象被授权改动"（`ChangeService.assertChangeWindow` 是 **BR-01 的唯一实现**）；PCO 的后果是"某道 DCP/TR 的决策依据可能失效" | `ChangeService.java:1138-1188` | ★ **最严重**：项目级变更混入后，`assertChangeWindow` 的判据输入变了，**污染 BR-01 的授权面** |
| **④ 数据模型不兼容** | `t_eco` **无 `project_id`**；`t_eco_affected.obj_type` 的 CHECK 只允许 `ITEM_REV/DOC_REV/BOM/REG/SOFTWARE` | `V7__item-bom-change.sql:110/142` | 要加 CHECK 值，等于允许"ECO 授权一个项目对象被改"，而 BR-01 的授权面本就是技术对象 |
| **⑤ 边级角色门未接** | `ChangeService` **从不调用 `edge.roleAllowed()`**，变更域整体不在 `EdgeGateEnforcement.CALL_SITES` 注册表内 | `ChangeService.transitionEco:570-617` | 要实现两级审批，得先把整个 ECO 域接进边级角色门——**改造面远大于新建 PCO** |

**载体形态三选一的裁定（Q1）**：

| 选项 | 复用度 | 问题 |
| --- | --- | --- |
| A1 复用 `t_eco` + `change_scope` | 最高 | 上述 5 条，尤其 ③ 污染 BR-01 |
| **A2 独立 PCO，前端并入工作台（选定）** | 通道全复用，对象不复用 | 需登记新对象类型（§10） |
| A3 不建单据，只在项目上加记录 | 低 | 无审批、无留痕闭环 |

## 3. 数据模型

```sql
CREATE TABLE t_pco (
  id                BIGSERIAL PRIMARY KEY,
  pco_code          TEXT NOT NULL UNIQUE,                 -- PCO-YYYY-NNNN，seq.next("PCO")
  project_id        BIGINT NOT NULL REFERENCES t_project(id),
  pco_class         TEXT NOT NULL
                    CHECK (pco_class IN ('GOAL','SCOPE','SCHEDULE','RESOURCE','BUDGET')),
  title             TEXT NOT NULL,
  reason            TEXT NOT NULL,                        -- 变更事由（必填）
  before_json       JSONB,                                -- 变更前（按类取键）
  after_json        JSONB,                                -- 变更后
  impact_gate_codes TEXT2],                               -- L1 评估出的受影响门点
  impact_note       TEXT,                                 -- 门禁影响说明（人可补充/修正）
  impact_assessed   BOOLEAN NOT NULL DEFAULT FALSE,       -- 是否已完成 L1 评估（进 SUBMITTED 前必须 TRUE）
  status            TEXT NOT NULL DEFAULT 'DRAFT'
                    CHECK (status IN ('DRAFT','SUBMITTED','APPROVED','REJECTED',
                                      'IMPLEMENTING','CLOSED','CANCELLED')),
  approve_role      TEXT,                                 -- ipmt_chair | pdt_manager | admin
  approve_by        TEXT, approve_on TIMESTAMPTZ,
  reject_reason     TEXT,
  linked_eco_id     BIGINT REFERENCES t_eco(id),          -- 范围变更引发技术变更时挂 ECO
  created_by        TEXT NOT NULL,
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  version           INT NOT NULL DEFAULT 1                -- V196 乐观锁范式
);
CREATE INDEX idx_pco_project ON t_pco(project_id, status);
CREATE INDEX idx_pco_class   ON t_pco(pco_class, status);

-- 门禁影响（可查询"本门是否被未关闭的 PCO 影响"）
CREATE TABLE t_pco_gate_impact (
  id        BIGSERIAL PRIMARY KEY,
  pco_id    BIGINT NOT NULL REFERENCES t_pco(id) ON DELETE CASCADE,
  gate_code TEXT NOT NULL,
  auto_hit  BOOLEAN NOT NULL DEFAULT TRUE,   -- true=规则算出；false=人工追加
  reason    TEXT,
  UNIQUE (pco_id, gate_code)
);
```

**刻意不建的表**（复用既有，避免第二套）：

| 不建 | 用什么 | 理由 |
| --- | --- | --- |
| `t_pco_task` 实施任务 | `t_project_task` | 项目变更的实施动作就是项目任务 |
| `t_pco_affected` 受影响对象 | `t_eco_affected`（挂 `linked_eco_id`） | 受影响的**技术**对象走 ECO；受影响的**项目**对象在本单 `before/after_json` |
| `t_pco_eval` 评估 | 无 | PCO **不要**五维评估（`D-C1` 语境：比 ECO 轻得多） |

## 4. 状态机与两级审批

### 4.1 `flows/pco-flow.yaml`

```yaml
flow: pco
label: 项目变更单(PCO)
states:
  DRAFT:        { label: "草稿",        color: "primary" }
  SUBMITTED:    { label: "待审批",      color: "warn" }
  APPROVED:     { label: "已批准",      color: "ok" }
  REJECTED:     { label: "已驳回",      color: "err" }
  IMPLEMENTING: { label: "实施中",      color: "primary-dark" }
  CLOSED:       { label: "已关闭",      color: "muted" }
  CANCELLED:    { label: "已取消",      color: "muted" }
transitions:
  - { from: DRAFT,     to: SUBMITTED,    label: "提交审批" }
  - { from: DRAFT,     to: CANCELLED,    label: "取消", rework: true }
  # ★ 两条同名目标边，按 pco_class 条件放行（服务端只放行其中一条）
  - { from: SUBMITTED, to: APPROVED,     label: "批准（IPMT主任）",
      roles: [ipmt_chair, admin], cond: "pco_class in (GOAL,SCOPE,BUDGET)" }
  - { from: SUBMITTED, to: APPROVED,     label: "批准（PDT经理）",
      roles: [pdt_manager, admin], cond: "pco_class in (SCHEDULE,RESOURCE)" }
  - { from: SUBMITTED, to: REJECTED,     label: "驳回", roles: [ipmt_chair, pdt_manager, admin], rework: true }
  - { from: APPROVED,  to: IMPLEMENTING, label: "开始实施" }
  - { from: IMPLEMENTING, to: CLOSED,    label: "实施完成→关闭" }
editableStatuses: [DRAFT]
```

### 4.2 ★ `D-C6` 两级审批的落法

| `pco_class` | 批准人 | 对应边 |
| --- | --- | --- |
| `GOAL` 目标 | **IPMT 主任** `ipmt_chair` | `批准（IPMT主任）` |
| `SCOPE` 范围 | **IPMT 主任** `ipmt_chair` | 同上 |
| `BUDGET` 预算 | **IPMT 主任** `ipmt_chair` | 同上 |
| `SCHEDULE` 进度 | **PDT 经理** `pdt_manager` | `批准（PDT经理）` |
| `RESOURCE` 资源 | **PDT 经理** `pdt_manager` | 同上 —— ⚠ **词表保留但本轮不实现**（`D-C9`，§5.3）；服务端对 `RESOURCE` 暂返 400 `PCO_CLASS_NOT_IMPLEMENTED` |
| **PM `PM`** | ❌ **不在任何一条边的 `roles` 里** | — |

**实现要点（三条，缺一条就等于没实现两级审批）**：

1. **边级角色门必须真接线**。`ChangeService` 不调 `edge.roleAllowed()` 是变更域的历史欠账；**PCO 必须调**，且要把 `pco` 加进 `EdgeGateEnforcement.CALL_SITES` 注册表，让 CI 盯住"声明了 `roles` 但没执行"（`GET /_platform/flows/pco` 的 `edgeGates` 会如实报 `DECLARED_NOT_ENFORCED`）。
2. **`cond` 是新能力**。`FlowEngine.TransitionDef` 当前解析的字段是 `from/to/label/rework/roles/guards/signers/join/countersign/task/requires/reason/ownerOnly/gate`（`FlowEngine.java:79-99`），**没有 `cond`**。两条选择：
   - (a) **在 YAML 扩展 `cond` 表达式**（引擎改造，通用能力，其它域也能用）
   - (b) **不给两条边，给一条 `roles: [ipmt_chair, pdt_manager, admin]`**，由服务端按 `pco_class` 二次判"这个人此刻够不够格"
   - ★ **建议 (b) 做首版**：`TransitionDef.roles` 保持"谁能按这条边走"（域级判据），`pco_class` 的分流是**本域的业务判据**，放服务端更符合仓内既有分层（`ChangeService.transitionEco` 的 `allDimsSigned` / `ccbResult` 守卫就是本域判据）。`cond` 留待有第二处需求时再进引擎。
3. **`admin` override（`D-C4`）**：`admin` 同时在两条边的 `roles` 里。但要在审计里**如实记 `approve_role`**（区分 `ipmt_chair` / `ADMIN_OVERRIDE`），照 `recordIpmtDecision:1200-1203` 的 `role` 归一口径——否则"谁批的"事后不可辨。

### 4.3 进入 `SUBMITTED` 的前置

| 前置 | 判据 | 理由 |
| --- | --- | --- |
| `impact_assessed = true` | L1 门禁影响评估已完成 | 不评估就提交 ⇒ 审批人无从判断影响面 |
| `impact_gate_codes` 非空 | 至少评估出 1 个门点 | 空集自述（照 `checkGateOrder:1098-1105` 的 `NOT_APPLICABLE` 范式） |
| `after_json` 完整 | 该类必填键齐 | 照 `FlowEngine` 的 `requires` 字段前置机制 |

### 5.3 ★ RESOURCE 类：实测证明它**没有落点**（`D-C9`，本轮不实现）

原始设想的落法是"RESOURCE 类 PCO 记录**项目名册的专职投入承诺变更**"（`before/after_json` = 关键岗位 + 承诺投入工时）。**2026-10 实测推翻了它**：

```sql
SELECT count(*) members, count(DISTINCT project_id) prj FROM t_project_member;   -- 86 / 60
SELECT count(*) FROM t_capacity;                                              -- 0
SELECT count(*) FROM t_project_task WHERE planned_hours IS NOT NULL;           -- 6
-- t_project_member 样例：capacity_hours_per_week / part_time_factor **全为 NULL**
```

| 三类"资源"数据 | 实际内容 | 是不是"项目承诺"？ |
| --- | --- | --- |
| `t_project_member`（86 行 / 60 项目） | 只有 `login` + `role_code`（谁参与、什么角色） | ❌ **人事名册**，不是投入承诺 |
| `t_project_member.capacity_hours_per_week` / `part_time_factor` | **全为 NULL**（V167 加的列从未填过） | ❌ 字段存在但**零数据** |
| `t_capacity` | **0 行** | ❌ 是**企业产能事实**（个人每周能工作多少小时），不是项目承诺 |
| `t_project_task.planned_hours` | 仅 **6 行**有值 | 是**任务级明细**，粒度太细 |

**结论**：**"专职投入承诺"这个字段是我凭空发明的**——它既不在你提的需求里，仓里也没有对应物。把它设计进 PCO，等于为一个**零数据、且无人提出**的功能设计数据结构。

**处置（`D-C9`）**：

| 项 | 处置 |
| --- | --- |
| `pco_class` 的 `RESOURCE` 值 | **保留在 CHECK 里**（词表一次定好，避免将来加值要改 CHECK）；但**本轮不实现**其影响面映射、界面入口与审批路由 |
| `t_prj_objective` 的资源类目标 | 同 26 号文 §9 取舍：**本轮不做** |

## 7. ★ 收编 `changeProductKind`（现成先例，及其缺陷）

`ProjectService.changeProductKind:891-933` 已完整实现了"变更 + 门禁影响评估"形态：

- ✅ **绕过 `editableStatuses` 锁定**（注释 ② 原文："种类恰恰最需要在项目跑起来之后被修正……建项目时选错/未选，用户此前**没有任何合法途径**改对，只能改库"）
- ✅ 强制理由 + 审计 before/after
- ✅ 返回 `affectedGates` / `affectedReviewGates`
- ✅ 明确"**在途不变、后续重解析**"的生效口径
- ✅ 复用 `project.update` 权限点，不新造

**但它的影响面判据是坏的** —— 这是必须收编的真正理由：

| 缺陷 | 证据 | 后果 |
| --- | --- | --- |
| `affectedGates` 查**已退役**的旧门表 | `ProjectService.java:922-923` 查 `t_gate` + `t_gate_check`；这两张表自 `V92`（REQ-2026-0700）起**恒空**（`judge/openGate/signGateParty` 现在全抛 `STAGE_GATE_RETIRED`） | **该数组恒为空** |
| `affectedReviewGates` **无任何过滤** | `:926-927` 查 `t_gate_map` 全表，循环里只有 `if (!affectedReviews.contains(m))` 去重 | 等于"**所有评审门都受影响**" ⇒ 实质是个恒为真的断言 |

**⇒ 它是"模式存在、判据未实现"的半成品。** 若不收编，结果是同一件事有两个口子：一个判据坏的（`product_kind`）、一个判据好的（PCO），且**用户仍可绕过 PCO 改种类**。

**收编方案**：`POST /projects/{id}/product-kind` 端点**保留做薄封装**，内部改为"起草 PCO(SCOPE) 并预填 `after_json.productKind`"；影响面改由 `PcoGateImpactService` 给出。**原 `ChangeKindResp` 保留一个版本的兼容期**（返回 `pcoCode` 替代 `affectedGates`），随后删除。

> **2026-11-13 批次66 用户裁定（D66-2）废止本节收编**：产品种类的可写窗口对齐管理类别的
> D64-3 纪律——DCP0 发起前 `POST /projects/{id}/product-kind` **直接写库生效**（reason 留痕），
> DCP0 发起后锁死（`PRODUCT_KIND_LOCKED_AFTER_DCP0`）。「kind → PCO(SCOPE) 起草」路线不再接新单
> （直接写+审计已满足可追溯，且在 DCP0 后锁死的口径下 PCO 路由失去存在意义）；
> `PcoService.applyApprovedChange` 的 kind 分支保留为存量已批 PCO 的兼容执行口。

## 9. ★ 锁定 `ProjectService.update`（`D-C5` + `D-C8`，**PCO 落地的前提**）

### 13.2 实施中发现的设计偏差（5 处，均已改口径）

1. **迁移号 V201 已被占** → 改 **V203**（Flyway 拒绝重号，硬失败）。
2. **`FlowEngine` 不解析 `cond`**（`FlowEngine.java:79-99`）⇒ §4.2 的"按类别分流"**不能**写成两条边。实施取选项 (b)：一条边 + 服务端 `assertApprover` 分流。**不造第三处"声明了却没有消费者"**（仓内已踩 `roles:` 与 `reason:` 两次）。
3. **必填键改成"至少 N 个"**。原定「SCOPE 必须同时给 `name` + `productId`」——落第一版就撞上：**只改产品种类**是完全合法的范围变更，却被逼着重填既有值。逼用户重填 = 教会用户无脑填，而 `after_json` 是审批人判断"改了什么"的唯一依据。改为：键必须在 `WRITABLE_KEYS` 里（挡越权）+ 至少 1 个（挡空单）。
4. **`auto_hit` 语义修正**：它是"**规则**是否算出这一项"，不是"有没有人碰过它"。初版把人工追加写成 `DO UPDATE SET auto_hit=FALSE`，导致"规则命中且人工也加"的行被标成人工项 ⇒ `removeGateCodes` 删不掉它。
5. **批准那一刻才落地**（`SUBMITTED → APPROVED` 同事务写主数据/目标/里程碑）。理由：PCO 的全部意义是"承诺变更经签字后**在项目记录上生效**"；若拖到 `IMPLEMENTING`，"已批准"与"已生效"之间有一段可无限期悬空的窗口，项目记录会停在一个**没人守却还有效**的旧承诺上。`IMPLEMENTING`/`CLOSED` 跟踪的是下游动作。

#### 13.3.1 ★ 为什么 #5 能在"全绿的定向回归"下溜过去（这一节比 bug 本身重要）

**根因不是粗心，是验收脚本在说谎。**

`plm-pco-accept.sh` 的回归步骤原本这样写：

```bash
mvn test -Dtest='PcoIntegrationTest,ProjectObjectiveIntegrationTest,ChangeKindBackwardCompatTest,\
ProjectDomainIntegrationTest,ItemStructureScopeTest,ProductKindIntegrationTest,\
EdgeRoleIntegrityTest,MetadataConsistencyTest' -DfailIfNoSpecifiedTests=false
```

那 4 个类名（`ChangeKindBackwardCompatTest` / `ProjectDomainIntegrationTest` /
`EdgeRoleIntegrityTest` / `MetadataConsistencyTest`）是**凭印象写的，仓里根本不存在**。
surefire 对"点名但找不到"的类是**静默跳过**的（`failIfNoSpecifiedTests=false` 关掉的正是这个报错），
而脚本只统计 `Tests run` 计数、不核对"点名了几类 / 实际跑了几类" ⇒
**它报 "60/60 PASS"，实际只跑了 8 个点名类里的 4 个**，且这 4 个里没有任何一条碰过预检链。

**两条教训，写在这里而不是提交记录里：**

1. **"判据看起来是绿的"不等于"跑过了"。** 验收脚本的第一职责不是"跑测试"，
   而是**证明它真的跑了它声称要跑的东西**。计数正确 ≠ 覆盖正确。
2. **`-DfailIfNoSpecifiedTests=false` 在定向回归里等于自废武功。**
   它的正当用途只有"允许某几个类被删掉"，代价是**拼错类名与类被删变得完全同形**。
   定向回归应当**不加**这个开关。

**已落地两道守卫**（写在 `plm-pco-accept.sh` 里，不靠人记得）：

| 守卫 | 做什么 | 防的是 |
| --- | --- | --- |
| `check_classes_exist` | 跑之前核对每个点名类在 `src/test/java/com/plm/` 里有对应 `.java`，**缺一个就硬失败** | 拼错/类被删 ⇒ 静默跳过 |
| 报告核对 | 跑完按 `target/surefire-reports/TEST-*.xml` 数"实际执行类数"，少于点名数即失败；**跑前先清空报告目录**（否则旧报告会冒充本轮） | 静默跳过、上一轮残留 |
| 单类运行去掉 `-DfailIfNoSpecifiedTests=false` | 类名写错直接失败 | 同上 |

> 守卫自身也踩了两次坑，一并记下：① `ls TEST-$c.xml` 漏了包前缀（实际是 `TEST-com.plm.$c.xml`），
> 8 个全"缺报告"，差点把一次全绿回归误判成失败；② 第一版用 `grep` 数日志里的 `-- in X` 行，
> 而 surefire 的类汇总行会因类名长度换行，计数少 1 ⇒ 误报"7/8"。
> **两次都是同一个毛病：用一个不可靠的代理量去证明"跑了"，而手边就有硬证据（报告文件）。**

#### 13.3.2 #5 暴露的第二个 bug：`PRJ_CHANGE` 的严重度是 BLOCKING

补上 L2 测试后立刻又挂一条：`expected: <ADVISORY> but was: <BLOCKING>`。

`PrecheckItem.ofCounted(...)` 的**第 5 参是 `applicability`（适用性），严重度被硬编码成 `BLOCKING`**
（`ReviewDtos.java:434`）。我按"看起来像"把 `ADVISORY` 传进了那个槽位——**类型对、编译过、语义错**。

这与 `V200` 的"占位符数量对了不代表对齐对了"是**同一类缺陷**：
一个位置只放一个**位置正确**的值，语义照样错，而且**不报错**。
若不补这条断言，`PRJ_CHANGE` 会以 BLOCKING 上线 ⇒ 未关闭的变更单直接拦住发评审，
而变更单本身要靠发评审才推进 ⇒ **流程死锁**——恰好是我在注释里声称要避免的那个结果。

修法：新增 `PrecheckItem.ofCountedAdvisory(...)`（**改名不重载**，理由见该方法注释——
前缀类型序列相同时，调用点读起来一模一样，意图不自述）。

### 13.6 前端四个缺陷：加第 4 个对象时，"漏分支"这一形态的完整一次

后端 25/25 绿、`vite build` 绿、验收脚本判 PASS，而**界面上 PCO 完全不可用**。
两条是用户报上来的，另外两条是同一形态下被顺藤摸到的。四个都属**同一根因**：

> **三元链 + `Record<string, …>` 查表加第 N 个对象时，漏写分支不会让 `tsc` 报错**，
> 缺陷要到运行期才炸，而且炸在**整页**而不是局部。

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| A | 点「项目变更单」页签 ⇒ `Cannot read properties of undefined (reading 'noun')`，**整页白屏** | `ChangeDetailPage.tsx` 的 `LIST_META` 是 `Record<string,…>` 且只有 ECR/ECO/ECN 三项。`scopeRef.current = { noun: LIST_META[obj].noun … }` 位于**每次渲染无条件执行**的赋值里，`obj='PCO'` 时取到 `undefined` 再取属性 ⇒ 崩的不是 PCO 那一块，是**整页** | 补 PCO 三项文案，**并把键类型收紧成 `Record<ObjType, …>`** |
| B | 项目详情面板**无法发起**项目变更 | 两层同时缺：① `ProjectsPage.TABS` 7 项里**没有**「项目变更单」页签 ⇒ 无入口；② `PcoPanel` 唯一挂载点（`ChangeDetailPage:1320`）**不传** `projectId`，而 `PcoService.create:82` 对 null 必抛 `VALIDATION_ERROR "必须指定项目"` ⇒ **即使从 `/changes?obj=PCO` 点"新建"也 100% 失败**，全系统无一条能创建 PCO 的界面路径 | ① `ProjectsPage` 追加第 8 个页签挂 `<PcoPanel projectId={selected.id} />`；② `PcoPanel` 在无 `projectId` 时用 `SearchPick objType="PRJ"` 让用户选项目 |
| C | 在 PCO 页签下，标题/面包屑显示的是**上一条 ECO 的编号与标题** | `:1231` 面包屑与 `:1234` `<h1>` 的三元链最后一档默认落 ECO ⇒ PCO 无分支就回落 ECO | 两处各补 `obj === 'PCO'` 分支 |
| D | PCO 下**每一次操作失败都没有任何提示**，界面像没反应 | `OpFeedbackBar` 整体被包在 `{obj !== 'PCO' && …}` 里，而 `PcoPanel` 的失败经 `onError → setErr` 写的是**同一份** `err` ⇒ 守卫把**回执的渲染出口一起屏蔽了** | 把 `OpFeedbackBar` 移到守卫**之外**（守卫只该屏蔽筛选器与分页，不该屏蔽回执） |

**顺带修掉的两处同型缺陷**

- `PcoPanel.tsx:190` 的「（本轮不实现）」标注写在 `<option>` 的 map 体内，却判的是 `disabled`
  —— 而 `disabled` 是**当前所选类别**的派生值（`notImplementedClasses.includes(form.pcoClass)`）。
  ⇒ 结果是"选中任一未实现类别时**全部**选项都打上该标注、而 `RESOURCE` 自己反而不带标注"，
  用户在 `RESOURCE` 上**看不到任何"本轮不实现"的提示**（旁边的说明段落 `:195` 又是对的，只覆盖所选项）。
  改判 `c`（该项自身）。**这是"查表判据写错键"的第四种变体。**
- `routes.ts` 的 `OBJ_LABEL` 未登记 `PCO` ⇒ 工作台/对象引用会把 `PCO#12` 原样打给用户
  （与 `ISS`/`TASK`/`BPL` 当初缺登记时的症状同族）。

**关于 A 的修法为什么不只是"补一条文案"**

补 PCO 能修好这一次，但下一个对象加进来时同样的坑会原样再踩一遍。故把键类型从
`Record<string, …>` 收紧成 `Record<ObjType, …>`，让"加对象必须补文案"由**编译器**保证。
已按此验证（临时把 `ObjType` 加上第 5 个成员 `ZZZ`，预期 `tsc` 硬失败）：

```
error TS2741: Property 'ZZZ' is missing in type '{ ECR: string; ECO: string; ECN: string; PCO: string; }'
              but required in type 'Record<ObjType, string>'.                    ← OBJ_LABEL
error TS2741: Property 'ZZZ' is missing in type '{ ECR: {…}; ECO: {…}; ECN: {…}; PCO: {…}; }'
              but required in type 'Record<ObjType, { noun: string; emptyHead: string; emptyReason: string; }>'.  ← LIST_META
```

顺带一提：修完立刻有回报——`共 {objTotal} 条{LIST_META[obj].noun}` 里我一度加了 `obj === 'PCO'` 分支，
`tsc` 直接报 `TS2367: 与 '"PCO"' 无重叠`（那行已在 `obj !== 'PCO'` 守卫内，是死分支）。
**这类"编译器发现不了的漏分支"与"编译器能发现却被宽类型放过的漏分支"是两类，前者要靠人工核对，后者该用类型堵死。**
`tsconfig.json` 里 `noUnusedLocals: false` / `noUnusedParameters: false`（死代码不会被告警）
+ `Record<string,…>` 查表（本批四处缺陷的载体）＝**前端最大的静默失效面**。

**页面结构上的一处收敛**：PCO 在 `ChangeDetailPage` 里是整块替换网格（`obj === 'PCO' ? <PcoPanel/> : <div className="dual">…`），
所以状态筛选/日期/搜索/分页对它一律无意义，`LIST_META` 的 PCO 条目**只为**让那个无条件解引用不崩。
真正的 PCO 列表在 `ProjectsPage` 的新页签里，`projectId` 天然确定、无需再选项目。

危害不是"占地方"，而是**看起来像权威表**——改它没有任何效果，而查"对象名怎么写"的人正好会查到这里。
已删除，并在原位留注释指向唯一实现 `lib/routes.ts`。

**为什么 `tsc` 没拦住**：`tsconfig.json` 里 `noUnusedLocals: false` ⇒ **死变量编译器不管**。
而 §13.6 那套"`Record<ObjType,…>` 收紧键类型"的手段在这里**同样无效**——
它只保证"**已登记**的键是全的"，对"这张表根本没人用"零约束。
**两道防线都不覆盖"死代码"这一类**，只能靠"源码 grep 不到引用 + 产物 grep 不到字面量"两头对证。

**顺带纠正一条容易互相套用的经验**（已写进 `routes.ts:61-74` 的注释）：
不是所有"对象名表"都该收紧键类型。

- **封闭键域**的表（键 ⊆ `ObjType`，且漏一条就整页崩）⇒ 收紧成 `Record<ObjType, …>`，让编译器兜底。
  本批的 `ChangeDetailPage.LIST_META` 属此类。
- **开放键域**的表（`routes.ts.OBJ_LABEL` 故意同时收待办侧 `ITM`、交付物侧 `ITEM`、
  以及 `REQ/DOC/REG/CHT/RVW/BPL/RA` 这些不进变更流程的对象）⇒ **收紧会把合法键编译判错**，
  逼人去改对的东西。改用**兜底函数**：`objLabel()` 对未登记的码回落原码（不猜语义），
  漏登记的症状退化为"显示 `PCO#12` 这种不可读行标题"，而不是崩页。

> `CODE_ROUTE` 至今**未登记 PCO**（§13.7），因为 `/changes?obj=PCO&code=` 还没有落地处理逻辑；
> `OBJ_LABEL` 则**已登记**（上面这条），两者不冲突：前者管"点了跳哪"，后者管"怎么称呼"。
