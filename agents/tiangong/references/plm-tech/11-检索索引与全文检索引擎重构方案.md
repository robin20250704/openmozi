## ② 预处理与索引：设计

### 2.1 为什么必须预索引
**现状（批次46 重构后口径）**：`DedupService` 已**读 `t_search_index`**——候选池由 `exact_key` 等值、`norm_text` 的 pg_trgm 词法 top-k、`embedding` 向量 cosine top-k 三路预筛（各 k=24）合并，再对候选集逐对评分；原"在内存 `sources(objType)` 全量 + 逐对评分（O(N²)，聚类尤其）"的记述**已被批次46 推翻**（`sources()` 现仅作只读列表接口，内部同样走索引）。**但设计前提不变**：关键词/SimHash/向量三层都必须**物化到索引表**，查询只走索引——否则 PLM 真实物料/文档数量级下不可扩展。

### 2.2 派生索引表 `t_search_index`（放 plm-pg）
```sql
CREATE EXTENSION IF NOT EXISTS vector;   -- 已装
CREATE EXTENSION IF NOT EXISTS pg_trgm;  -- 已装

CREATE TABLE t_search_index (
  obj_type   text NOT NULL,            -- ITM/PROD/DOC/ECO/PRJ...
  obj_id     bigint NOT NULL,
  code       text,                     -- 编号（itemCode/prodCode/ecoCode）
  name       text,
  norm_text  text,                     -- DedupUtil.normalize(text)（去标点/大小写，保留 CJK）
  feat_ngram tsvector,                 -- 关键词/n-gram 可检索文本（含 CJK bigram 分词）
  simhash    bigint,                   -- SimHash(64bit, 词频加权)
  simhash_b4  smallint[] ,             -- 按 16bit 分块指纹（4 块），用于 Hamming 预筛选桶
  embedding  vector(512),              -- pgvector：bge-small-zh-v1.5（512 维，CLS）向量（语义层；维度由 V135 迁移）
  last_dirty timestamptz,
  PRIMARY KEY (obj_type, obj_id)
);
CREATE INDEX idx_simhash_b4 ON t_search_index USING GIN (simhash_b4);      -- 模糊哈希桶
CREATE INDEX idx_ngram ON t_search_index USING GIN (feat_ngram);           -- 关键词/trigram
CREATE INDEX idx_embedding ON t_search_index USING HNSW (embedding vector_cosine_ops); -- 向量 ANN
```

### 2.3 写入预处理（索引链路）
- **物化触发**：对象写入（item create/update、product、切换、doc 等）后，在 Service 内**同步/异步**调 `SearchIndexer.upsert(objType, objId)`——做 规范化 → 特征/ngram → SimHash → （若开语义）调嵌入生产者得 512 维向量 → 写 `t_search_index`。
- **低成本**：规范化/SimHash/ngram 是纯 CPU 哈希（微秒级）；向量化只有语义层才调用 sidecar（可缓存 + 幂等，仅当该行文本变化时重算）。
- **全量回填**：`V16__search-index.sql`（建表建索引；维度迁移 `V135__embedding-dim-512-bge-zh.sql`、文本哈希列 `V136__search-index-vector-hash.sql`）+ 启动时 `SearchIndexer.rebuild(objType)`（对存量对象批量物化），保证索引即时可用。
- **一致性**：小规模（当前 PLM）走**服务内写透**即可；规模上来后启用**已部署的 Debezium CDC（PG→Kafka）或写事件**异步同步 ES/重算（见 §5）。

### 2.4 查询如何走索引（不再是全量扫描）
- **精确键**：`norm_text` 或 `spec|uom|...` 组合上的 B-tree 等值 → 直接命中（EXACT）。
- **模糊哈希（近重复）**：用 `simhash_b4` 4 块桶，取与被查对象 Hamming 距离 ≤3 的候选（桶内桶间组合），再算真实 Hamming → 挑 ≥0.88。
- **关键词/n-gram**：`feat_ngram @@ to_tsquery/custom` 或 `norm_text ILIKE/trigram`（pg_trgm → `%q%` 走 GIN）→ `word_similarity` 排序。
- **语义向量**：`embedding <=> query_vec` cosine 距离，`ORDER BY embedding <-> ? LIMIT k`（HNSW ANN）。
- **混合**：候选集合并（SimHash 桶 ∪ ngram ∪ kNN）→ `DedupUtil` 评分收敛到 0..1 → verdict。

> **⚠ 未实现（批次46 后口径）**：本节上文的"SimHash 4 块桶（`simhash_b4`，16bit ×4）Hamming≤3 预筛"与 "`feat_ngram` tsvector 检索"**在实际 `V16__search-index.sql` 中并不存在**——V16 的真实列是 `fields jsonb / exact_key / norm_text / simhash / embedding / last_dirty`，索引只有三支：`norm_text` 的 trigram GIN（`idx_si_ngram`）、`exact_key` 的 B-tree（`idx_si_exact`）、`embedding` 的 HNSW cosine（`idx_si_emb`）；**没有 ngram tsvector 列、没有 `simhash_b4` 分块桶列**。
> **当前候选预筛实际走三路**（`DedupService.candidatePool`，各取 top-k=24 后并集去重）：① `exact_key` 等值命中；② `norm_text` 的 pg_trgm `word_similarity` 词法 top-k；③ `embedding <=> ?` 向量 cosine top-k。**SimHash 只作为评分项（权重 0.30），不参与预筛**；混合排名（RRF）仍属 Phase-2 未做项。

## ③ pgvector / 其它向量库：调研结论（已实测）

- **pgvector 已装**：`plm-pg` = `pgvector/pgvector:pg16`；`pg_extension` 含 `vector`(0.8.6)。可在 plm 库直接 `CREATE TABLE ... embedding vector(384)`、建 `HNSW (embedding vector_cosine_ops)`、跑 `<=> 余弦` ANN。**语义层 100% 用它**。
- **pg_trgm 已装**（1.6）：提供 `word_similarity( )`/`similarity( )` + GIN trigram 索引，覆盖"关键词/模糊串"层。
- **已有 ES 8.13.4（plm-es，healthy）**：BM25 全文 + `dense_vector` kNN。未来高吞吐全文引擎直接复用，**无需新装**。
- **因此：不需要任何其它向量库。** "还需要接其它向量库？" → **否**。若一定想用独立向量库（不推荐），本环境没有现成标配，需额外部署（已避免）。

## ④ jcode 已有本地嵌入框架（可复用，无需外部 API）

`crates/jcode-embedding`（Rust，jcode 工作区）：
- 运行时：`tract`（**纯 Rust、轻量、CPU 即可跑 ONNX**）+ `tokenizers`——即用户所指"小型的本地框架"。
- 模型：**all-MiniLM-L6-v2**（384 维，sentence-transformers），首次从 HuggingFace 下载 `model.onnx` + `tokenizer.json` 到本地目录（`download_model`），之后离线。
- API（可作 sidecar）：
  - `Embedder::load_from_dir(dir) -> Result<Self>`（无文件则自动下载）
  - `embed(&str) -> Result<Vec<f32>>`（384 维）
  - `embed_batch(&[&str]) -> Result<Vec<EmbeddingVec>>`
  - `CrossEncoder::load_from_dir(dir)` + `score(query, passage)` —— 二阶段相关性重排（可选、更强）
- 规模：MiniLM 小模型，CPU 单条毫秒~十毫秒，无需 GPU；容器可用。

> **桥接到 Java PLM**：jcode-embedding 是 Rust。建议以 `jcode-embedding` 为库建一个**极薄 Rust sidecar**（`GET /health` + `POST /embed {texts} → {vectors:[[f32;384]]}` + 可选 `/rerank`），供 PLM 后端 `SemanticVector` 实现调用。复用 jcode 现有框架、全本地、无外部服务依赖。（Java 侧另一条路：`onnxruntime-java` + 同一 MiniLM ONNX，但复用度低，不推荐为主径。）

### 4.1 Linux 部署可行性与效果评估（用户在方案确认时的追问）
- **能上 Linux**：jcode-embedding 是纯 Rust（`tract` 为**纯 Rust、无 Python/GPU 依赖**的 ONNX 运行时，静态/musl 可编译），产物为 `linux/amd64`（及 `aarch64`）二进制；**当前 PLM 部署环境就是 WSL2（Linux VM）+ Linux 容器**，sidecar 以 Linux 容器（`rust:alpine` 或 `scratch`）+ 命名卷（缓存模型）即可跑，CPU 即可。与 jcode 本体跨平台无关，可独立构建该 sidecar。
- **效果（模型选型是重点）**：
  - `all-MiniLM-L6-v2` 语义相似度**英文强、中文偏弱**；PLM 若以中文物料/规格为主，**纯向量层召回不如英文理想**。但查重是**分级混合**：精确键 + SimHash + 关键词/n-gram（这些**语言无关**，已覆盖绝大多数"同名/同规格/近写"重复），**向量层只作语义召回增强**，不是唯一判定——故整体效果对半结构化 PLM 文案足够。
  - **中文增强（推荐，Swappable）**：`SemanticVector` 接口保持可替换——如需更强中文语义，可用中文/多语 miniLM 类模型（如 **bge-small-zh**/paraphrase-multilingual-MiniLM，WordPiece 同款 tokenizer，tract 可跑；注意维度可能 384/512，需与 `t_search_index.embedding vector(dim)` 匹配）。
  - **采纳前最小质量验证（符合选型判据）**：建议在实施前跑一个**小 PoC**——取真实 PLM 物料/产品文本，用该嵌入算 top-k 相似，与"规则已确认的重复/非重复"对照，测 top-k 精度/召回；达到阈值才固化模型，不达标则换中文模型或仅保留非向量层（向量层降级）。**此 PoC 不涉及第三方部署**，可随时做。
- **结论**：Linux 可部署；效果以"语言无关层为主 + 向量层增强"整体可靠；中文偏强需求时经 `SemanticVector` 换模型。

> **POC 实测（B46，`b45-embed-poc.py`，37 条真实 PLM 文本）=384 维**：
> - 4 个同名"呼吸机 R3"产品 → **cos=1.000**（完美判重）；"增强型(0101)" vs 基础款 → **0.882**（正确分离，≠重复）。
> - 但**异类结构部件**两两基线 **0.82–0.90**（MiniLM 中文塌缩、区分度低）——若仅以向量阈值判重会大量误报。
> - **落地**：向量层**权重降为 0.15**（`score=0.45J+0.30SH+0.25FO+0.15vec`，精确键=1.0），以语言无关层为主；向量仅作**语义召回增强**。可再经 `SemanticVector`/`EmbeddingClient` 换中文模型（bge-small-zh）提升区分度。

## ⑤ 重构方案：把查重重构为"检索索引"复用为全文检索引擎

### 5.1 核心洞察
"查重"（给定对象/文本 → 找相似对象）与"全文检索"（给定查询 → 排名相关对象）**共享同一套底层**：分词/n-gram、SimHash/pgvector 向量、倒排/ANN 索引。**差异只在查询入口与排序目标**。所以抽一层**检索索引基础设施**，查重是它的一个 facade。

### 5.2 目标分层
```
       [SearchService（统一查询门面）]
        /            |            \
   FTS(全文)    DEDUP(查重)     TRACE(轨迹)
   query→rank   obj→similar    audit/debug
        \            |            /
   [SearchIndexPort（索引读/写驱动接口）]
        |               |
   Backends: postgres/pgvector+pg_trgm   |   elasticsearch(plm-es, 高吞吐/BM25)
               (事务内、同步、单库)        |   (异步、CDC, 更大规模)
              [SearchIndexer]物化写        |    [Debezium CDC / 事件写]
```

### 5.3 组件与改动点
| 层 | 现状 | 重构为 |
|---|---|---|
| `DedupUtil`(算法) | 已存在 | → 提取为 `com.plm.platform.search.TextUtil/SimHash/Ngram`（静态，纯函数） |
| `DedupService` | **读 `t_search_index`**（批次46 已重构落地）：`exact_key`/pg_trgm/向量三路候选预筛 + 评分 | → 维持索引化口径（不再有内存 `sources()` 全量在线评分）；保留 `SemanticVector`（现接 jcode embedding sidecar/pgvector 向量） |
| `SearchIndexer` | 无 | 新增：`upsert(objType,objId)` + `rebuild(objType)`，物化索引行；由各域 Service 在写后调用 |
| `SearchService` | 无 | 新增：`query(q, filters)`（FTS）+ `similar(objId)`（查重）+ `clusters()`；门面 |
| `_platform/dedup` REST | 已有 | 保留为 DEDUP facade；新增 `_platform/search`（全文） |
| 后端驱动 | 内存 | `PostgresSearchBackend`（pgvector+pg_trgm，默认） + `EsSearchBackend`（可选，CDC 同步） |
| 索引存储 | 无 | `t_search_index` + V16 迁移（+V135 维度、V136 vector_hash）+ 回填 |

### 5.4 查重→全文复用的映射（同一索引两用）
| 能力 | 查重用 | 全文检索用 | 底层 |
|---|---|---|---|
| 关键词 | 找同名/同规格 | BM25 排名 | pg_trgm / ES BM25 |
| n-gram/CJK | 模糊串相似 | 子串/词距 | pg_trgm GIN / ES analyzer |
| SimHash | 近重复 | （可选）探索近似 | simhash_b4 桶 |
| 向量 | 语义近似 | 语义召回 | pgvector HNSW / ES dense_vector |
| 混合 | 0..1 verdict | RRF 融合排名 | 候选并集 → 评分 |

> 结论：**查重 = "以对象为 query 的检索"**；重构后 `DedupService` 走 `SearchIndexPort.similar()`，全文检索走 `SearchIndexPort.query()`，二者共用索引与后端。满足"查重复用为未来全文检索引擎"。

### 5.5 分期建议
- ****Phase 1（MVP，本方案落地）**：pgvector+pg_trgm 单库索引 + `SearchIndexer` 物化 + `/ _platform/search` 全文 + 查重切到索引；嵌入用 jcode-embedding sidecar 提供语义层。**不需要新第三方**。
- **Phase 2（规模/多域）**：引入 ES 8.13（已装）+ Debezium CDC 同步；`SearchIndexPort` 加 `EsSearchBackend`；混合排名（RRF）；跨域（物料+文档+变更+项目）统一检索、语义查重。
- **Phase 3**：CrossEncoder 二阶段重排、（可选）多语/自定义词典、权限过滤下钻。

## ⑦ 模型选型与实测（批次36 新增；判据可复算）

**选中：`bge-small-zh-v1.5`（512 维，CLS 池化）**；对照：`paraphrase-multilingual-MiniLM-L12-v2`（384 维，mean）。

| 指标 | MiniLM-多语(384/mean) | bge-small-zh(512/cls) |
| --- | --- | --- |
| **改写查询检索排名**（5 条同义改写，域内） | 1 / **5** / **4** / 1 / 1 | **1 / 1 / 1 / 1 / 1** |
| 近重复下界（同一对象格式变体，3 对） | min 0.9947 | min 0.9886（仍 ≥0.98 ⇒ 判重不退化） |

结论与口径：
1. 排名指标 5/5 vs 3/5 ⇒ 语义召回实测量更优；近重复下界仍 ≥0.98 ⇒ 判重标尺不退化。
2. 向量层权重维持 **0.15**（doc10 §2.5 的刻意设计：绝对阈值标尺不随基础设施状态漂移）；本表"异类基线偏高"恰好说明**不能**把向量当唯一判据。
3. 换模型的可操作性：`MODEL_DIR`/`POOLING` 都是启动参数，`/health` 自述模型身份与维度；维度变化走一次迁移（如 `V135`）+ 重建索引。

## ⑧ 风险与技术债
- **嵌入模型跨语言/跨域**：已换中文模型（见 ⑦）；异构域（REQ 长文本占语料 59.5%）会稀释跨域检索的语义近邻——**跨域 RRF 的域间竞争是已知待调项**（见下条），换模型不解决它。
- **跨域 RRF 的域间不对称（批次36 实测发现，未改）**：`Q=气体流速检测元件` 在域内（ITM）排名 1，但跨全部域检索时被 1922 条需求（均长 299 字符 vs 物料 28 字符）挤到 top-5 之外；`氧气含量探头` 域内第 1、跨域第 3。**属排序权重问题，不属能力缺失**；可选的改法是"按域归一化/域内配额"或"域感知加权"，属产品行为变更，需先确认再做。
- **`SemanticVector` 契约**：现有 `DedupService.SemanticVector.cos(a,b)` 与 sidecar 的 batch 语义对齐（一次取整批向量再算 cosine，避免逐对调用）。
- **SIMHASH 桶**：`simhash_b4` 以 16bit 分块能覆盖 Hamming≤3 的预筛，但候选误报需真实 Hamming 复核（评分已含）。
- **索引与源数据一致性**：服务内写透在 PLM 规模够用；写透失败需有 `rebuild` 兜底（幂等、全量）。
- **ES 与 pgvector 双写**：Phase2 双后端时避免重复维护，以 CDC/事件为单一写入流。
