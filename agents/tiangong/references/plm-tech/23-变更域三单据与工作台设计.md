## 0. 一句话结论

**ECR / ECO / ECN 是三个对象、一条链**——申请（ECR）→ 变更单（ECO）→ 通知（ECN）——**不是同一个对象的三种状态**。
界面上由**同一个工作台**承载：**"一页三对象、一线三单据"**（左栏切对象，右栏跟着换字段与动作；三张单据背靠背排成一条线）。

| 说法 | 为什么这么表达 |
| --- | --- |
| "三个对象" | 三张表、三套编号、三套状态机、三类责任主体（§2/§3）；混成一个对象会把"基数"（一申请可拆多单）与"权责"（初评人 ≠ 五维签署人 ≠ 外部接收方）一起抹掉 |
| "一条链" | 业务上前者决定后者的去留：ECR 回答"要不要改"，ECO 回答"怎么改、谁能批"，ECN 回答"改了要通知谁、谁确认收到" |
| "一页三对象" | 界面上**不**为了"模型正确"把用户赶去三个菜单：切换在同一位置、同一手势，跳转（ECR→新建 ECO、ECO→已转变更单、ECN→来源变更单）**原地完成**，并写进 URL 便于复制与追问 |
| "一线三单据" | 三张单据不是并列的台账，而是**一条接力线**；因此列表列与动作都必须回答"我这一棒交给谁"（ECR 列表要显示 `ecoCode`，ECN 列表要显示 `ecoCode`） |

## 1. 三表对照（事实基线）

| 维度 | **ECR** 变更申请 | **ECO** 变更单（核心） | **ECN** 变更通知 |
| --- | --- | --- | --- |
| 表 | `t_ecr` | `t_eco` | `t_ecn` |
| 编号列 / 发号 | `ecr_code`（`ECR` 前缀，业务码唯一） | `eco_code`（`ECO` 前缀，业务码唯一） | `ecn_code`（`ECN` 前缀，业务码唯一） |
| 状态机（与 `flows/*-flow.yaml` 逐字对齐） | `OPEN 已发起` → `TRIAGED 已初评` → `TO_ECO 转变更单` → `CLOSED 已关闭`；`OPEN`/`TRIAGED` 可 `CANCELLED 已取消`（**rework 边：必须填理由**） | `DRAFT 草稿` → `EVALUATING 五维评估` → `CCB_REVIEW CCB评审` → `APPROVED 已批准` → `IMPLEMENTING 实施中` → `VERIFYING 验证中` → `CLOSING 关闭中` → `CLOSED 已关闭`；`EVALUATING` 可退回 `DRAFT`、`CCB_REVIEW` 可 `CANCELLED`（否决） | `PENDING 待下发` → `SENT 已下发` → `ACKNOWLEDGED 已回执` → `CLOSED 已关闭` |
| 可编辑状态（读面 `editableStatuses`） | `[OPEN, TRIAGED]` | `[DRAFT]` | `[PENDING]` |
| 字段重心 | **来源与问题**：`source`（`CAPA/PCN/IMPROVE/COST/REG/COMPLAINT`）、`urgency`（普通/加急/紧急）、`problem_desc`、初评三件套 `triage_by/triage_on/triage_concl` | **怎么改与谁批**：五维评估 JSONB（`eval_tech/reg/risk/vv/mfg`）、`change_class`（`MINOR/MAJOR/REG/EMERGENCY`）、库存与生效方式（`stock_disposition/effectivity_type/effective_date/sn_breakpoint`）、`ccb_result/ccb_on`、`approval_no`（REG 类 BR-05） | **通知了谁、谁收到**：`targets`（`ERP/MES/SUPPLIER/CS`）、回执行 `t_ecn_receipt(target, ack_by, ack_on)` |
| 责任主体 | **初评人**（`triage_by`）——"要不要改、改哪些、走哪条通道"由他判定 | **五维签署人**（技术/法规/风险/V&V/制造各签一维，维度-角色绑定）+ **CCB 决议人** | **外部接收方回执**（ERP/MES/供应商/客服在各自回执行上留痕） |
| 关系列 | —（链的**起点**） | `ecr_id`（**可空**，逻辑指向 `t_ecr`） | `eco_id`（**NOT NULL**，逻辑指向 `t_eco`） |
| 是否对外 | 否（内部申请） | 否（内部决策与执行） | **是**——**唯一对外单据**（发给 ERP/MES/供应商/客服） |
| 谁产生它 | 人（任何工程角色按域级权限点 `ecr.create`）+ **系统**（CBB 升版自动起草，22 号文 §5.3） | **只能由人**（`POST /ecos` 或工作台从 ECR「转变更单」） | 人，且**仅当来源 ECO 处于 `CLOSING`** 时（后端强制） |

> 状态机一节**照抄** `ipd/plm-app/backend/src/main/resources/flows/{ecr,eco,ecn}-flow.yaml`（三文件逐条核对，含 `label` 中文与 `rework` 标记）；
> 读面 `GET /_platform/flows/{ecr,eco,ecn}` 与界面画按钮都以它为准（**界面不硬编码边集**）。

## 2. 为什么不能合成一个对象（5 条判据）

用户的疑问本身是一个合理的建模直觉：三者确实是同一条流程的三个阶段。但"阶段"与"对象"的分界由下面 5 条代码级事实决定——

| # | 判据 | 事实（可核） | 若合成一个对象会怎样 |
| --- | --- | --- | --- |
| **① 基数不同（1:N）** | `t_eco.ecr_id` **可空且未限条数** ⇒ **一条 ECR 可拆多条 ECO**（也可先建单后补挂） | 实测走查 R25a2：同一 `ecrId` 下 `t_eco` 计数 = **2**，两张单并存 | 状态列只能表达一个"当前状态"，**第二张单无处安放**；"一申请分两批改（先改图纸、后改工艺）"这种真实场景被迫拆成两条申请 |
| **② 可以无前驱** | `createEco` 只在 `ecrId` 非空时回写 ECR；`prefillFromCbbImpact` 首行 `if (ecrId == null) return 0` ⇒ **无 ECR 也能直接开 ECO** | 实测 R25b1/R25b2：`POST /ecos {title}` 返回 `ecrId: null`，库里 `ecr_id IS NULL` | "第二种状态必须由上一种转换而来"这个**状态机的前提不成立**——合成后要允许"从空中开始"，那是伪装成状态机的对象图 |
| **③ 后继必挂前驱（不对称）** | `t_ecn.eco_id` **NOT NULL**，且 `createEcn` 强制来源 ECO 处于 `CLOSING` ⇒ ECN 不可独立存在 | 代码：`if (!"CLOSING".equals(e.getStatus())) throw ... 仅关闭阶段可生成 ECN` | 同一条状态链里出现"一边可空、一边必填"的不对称约束 ⇒ 约束只能写在业务代码里，模型本身说不清 |
| **④ 责任主体不同（三套签署）** | ECR=初评人（`triage_by/triage_on/triage_concl`）；ECO=**五维**签署人 + CCB 决议人（`ccb_result/ccb_on`，且维度-角色绑定见 REQ-2026-1083）；ECN=**外部**接收方回执 | 三套签署数据结构完全不同（单字段 / 五维 JSONB + 决议 / 回执行表） | 一个对象要容纳"三种完全不同的签署语义"，只能靠 JSONB 堆叠 ⇒ 签不动、审不清、追不到（正是 22 号文缺陷档案第 ④ 条"备注不是关系"的同族） |
| **⑤ 对外边界不同** | ECN 是**唯一对外单据**（发给 ERP/MES/供应商/客服，回执来自**组织外部**）；ECR/ECO 全在内部 | `targets` 值域 `ERP/MES/SUPPLIER/CS`；`t_ecn_receipt.target` + `ack_by/ack_on` | 把对外单据合进内部对象 ⇒ 外部回执会与内部评审混在同一状态链上，**WORM/审计边界与权限边界同时被污染** |

**另一条工程判据（不是业务判据，但同样硬）**：三张表各有独立的 `status` CHECK 约束与 flow 定义（`ecr-flow.yaml` / `eco-flow.yaml` / `ecn-flow.yaml`），
且已被 18 号文"词表单源"、10 号文"边级角色门"两套规格引用。合成一个对象意味着**推翻三套已上线的读面契约**（`GET /_platform/flows/*`、`MetadataService` 的 `editableStatuses` 分派、Lookup/Resolver 类型表），
代价远高于收益，而收益（少一个页签）在工作台上根本不需要——§3 已用"一页三对象"把它拿到。

## 3. 入口形态裁定（D-18）与落地

### 3.1 为什么是"同一个工作台承载"，而不是三个菜单

三个对象在业务上是**一条接力线**（§0），操作者常常要在一次排查里横跨三者（"这条申请转成了哪张单？那张单的通知发出去了吗？"）。
若按对象分三个菜单，用户每问一次就得重新导航、重新检索、重新定位——而**定位成本**正是本项目反复出现的问题形态（08 号规格 §6.3.1 列表范式与 §6.8 空态纪律的动机同一）。

### 3.2 落地形态（`frontend/src/pages/ChangeDetailPage.tsx`）

| 落地项 | 形态 | 为什么 |
| --- | --- | --- |
| 对象切换 | 左栏切换到 `ECR 变更申请` / `ECO 变更单` / `ECN 变更通知`（每项带一句 hint 说明"这一栏管什么"） | 切对象**不换心算模型**：同一位置、同一手势 |
| URL 深链 | `/changes?obj=ECR&code=<编号>`（`obj` ∈ `ECR/ECO/ECN`，`code` 是**业务编号**） | ① CBB 版本历史里"这次升版起草了哪条 ECR"必须能点进来；② ECR 与 ECO 的 **id 是两套主键**，只用 `/changes/<id>` 会把用户送到一条无关的 ECO 上（本批修掉的正是这类"id 张冠李戴"，22 号文 §10.1 #8）；故用**业务编号**（人类可读、跨环境稳定） |
| 深链落位纪律 | 深链进入一律**清空全部筛选**（目标行必须能被看到）；状态值域**不跨对象保留**（`TRIAGED` 是 ECR 的状态、不是 ECO 的） | 保留跨对象筛选 = 用户切过去看到一张空表，还以为"数据没了" |
| ECR 列表 + 初评 | 独立列表（服务端分页/检索/状态/时间）+ 初评结论内联填写 + 按 flow 定义的流转按钮 | 此前**没有列表入口**（§4） |
| 「转变更单(ECO)」 | ECR 详情里的显式按钮，**只在已初评（≥ `TRIAGED`）时出现** | 见 §3.3 |
| ECO「关联 ECR」 | 由只读字段升级为**可编辑检索选择面板**（`SearchPick`）；保存走 `PUT /ecos/{id} {ecrId}`，挂上即把该 ECR 置 `TO_ECO`；已 `TO_ECO`/`CLOSED`/`CANCELLED` 的 ECR 二次挂载被拒（`ECR_NOT_LINKABLE`） | 让"已经存在的变更单"接到它本该属于的那张申请上——库里那批 `OPEN` 的 ECR 就是这么被晾着的 |
| ECN 独立列表 + 回执 | 独立列表（分页对象）+ 回执登记（`POST /ecns/{id}/ack {target, ackBy}`）+ 流转（下发/全部回执/关闭）；回执收齐自动 `ACKNOWLEDGED`；关闭 ECN **反向把来源 ECO 置 `CLOSED`** | 此前 ECN 只活在 ECO 详情的页签里，**连"确认回执"按钮都没有** ⇒ 回执闭环永远走不到 `ACKNOWLEDGED` |
| 动作反馈的跨对象提示 | 关闭 ECN 的提示写明"**来源变更单也被置为 CLOSED**" | "一个动作改了另一个对象的状态"若不提示，用户会以为看错了（同族纪律：状态变更必须留下可核对的回执文案） |

### 3.3 为什么「转变更单」必须由人点（系统不替业务决定）

**这是本设计最刻意保留的一处"人工环节"**，理由是 ECR→ECO 之间的三分类本身就是业务判定：

| 三分类 | 问题 | 谁回答 |
| --- | --- | --- |
| **要不要改** | 这个问题值得动设计/物料/文档吗？还是记录在案、观察、或按现状处理即可 | 初评人（`triage_concl` 写入） |
| **改哪些** | 影响面里哪些是真的受影响、哪些只是形式相关（22 号文 §5.3 已把影响面准备成结构化清单，正是为了让这个判定有据可依） | 初评人 + 变更负责人 |
| **走哪条通道** | 走常规变更 / 紧急变更 / 注册相关变更（`change_class` ∈ `MINOR/MAJOR/REG/EMERGENCY`），走哪条评估与批准路径 | 变更负责人 + CCB |

因此系统只做**准备**：起草 ECR 时把影响面备好（结构化，不是散文），建 ECO 时落成 `t_eco_affected` 行（22 号文 §5.3）。
**不做**：收到 ECR 就自动开单（那等于把上述三项判定全部预设为"要改、按系统猜的范围改、走常规通道"——一个错误预设会直接生成本该被否决的变更，且**无人签字**）。

工作台把这条判定做成**可见的动作**：按钮只在 `≥ TRIAGED` 时出现（没初评就没有判定可依据），文案明确"是否变成变更单由初评决定"。
这与 22 号文对 CBB 侧的表述完全一致：**边界（刻意不做的事）：不自动创建 ECO、不自动改 BOM。**

## 4. 本批修掉的缺陷（变更域部分）

> 用户复审 CBB 页面提了 6 个问题，其中 4 个落在变更域。逐一列出"现象 → 根因 → 收口"。

| # | 现象（实测） | 根因 | 本批收口 |
| --- | --- | --- | --- |
| ① | **CBB 升版起草的 ECR 无人处理**：`t_ecr` 中 `problem_desc LIKE '%CBB 升版%'` 共 **18 条**，其中 **13 条停在 `OPEN` 且 `eco_cnt=0`** | 主框架里 **ECR 没有任何列表入口**：前端全仓对 `/ecrs` **只有 `POST`（发起）**、无列表；`/changes` 只查 `/ecos`；`ChangeDetailPage.createEco()` 是**死代码**；ECO 新建路径**从不带 `ecrId`**（面板字段里没有 `ecrId`）⇒ 界面无法把 ECO 关联到 ECR，**ECR→ECO 交接链整条断裂** | 一页三对象 + ECR 列表 + 「转变更单(ECO)」（§3.2）；ECO「关联 ECR」可编辑 + `PUT /ecos/{id} {ecrId}`；判据 R25 |
| ② | **`UpdateEcrReq` 是死 DTO**：`record UpdateEcrReq(String problemDesc, String triageConcl)` 全仓只有定义、**没有端点** ⇒ 申请正文写错了只能作废重开（而 ECR 一作废，CBB 升版回链的 `drafted_ecr_code` 就指向一张废单） | 只建了 DTO 忘了端点；这类"半个功能"不会报错，只会让用户在界面上找不到入口 | 新增 `PUT /api/v1/ecrs/{id}`（权限点 `ecr.update`，仅 `OPEN`/`TRIAGED` 可改，否则 400 `ECR_LOCKED`）；判据 R24c/R24e |
| ③ | **`getEcr` 潜伏的错误取数**：原实现 `ecoRepo.findById(e.getId())`——**拿 ECR 的 id 当 ECO 的主键**查；正确语义是"找 `ecr_id = 本 ECR` 的 ECO" | 实测当前 id 区间 `eco 160..182` / `ecr 103..120` **未碰撞（0 命中）** ⇒ 一直没显形；一旦碰撞，ECR 详情会回显**无关的** ECO 编号（**张冠李戴比空白更坏**：用户会照着错的单子去追变更） | 改为按 `ecr_id` 查（单条与批量 `DISTINCT ON (ecr_id) ... ORDER BY ecr_id, id DESC` 同口径，取最新一张）；判据 R24a |
| ④ | **`updated_at` 从不推进**：`EcrEntity`/`EcoEntity` 原是 `insertable=false, updatable=false`，且本库**没有 `updated_at` 触发器**（既定口径"更新列由应用层维护"）⇒ 一条今天刚初评的 ECR 在列表里仍显示建单日；`t_ecn` 连这一列都没有 | "最近更新"列与"按更新起止筛选"从一建成就**冻住**——两处都在说谎，且**越晚发现越贵**（历史值无法回溯，只能按 `created_at` 回填） | 实体 `@PrePersist/@PreUpdate` 统一推进（与需求域 REQ-2026-2111 同口径）；`t_ecn.updated_at` 由 V141 补列、存量行按 `created_at` 回填（**不假装它们"刚被改过"**）；`riseCbbRev` 里绕过 JPA 写 `t_ecr` 的裸 SQL 也显式推进；判据 R26c |

### 4.1 一条"走查漏网"的诚实说明（假红教训的反面）

**原 API 走查 R9 抓不到 ③**——它的断言是：`t_cbb_rev.drafted_ecr_code` 非空 + `t_ecr` 里该编号存在 + 正文含 CBB 编号 + 影响面已挂在 ECR 上。
四条**全部在 DB 侧**，`GET /ecrs/{id}` 这一步**只用来核正文，不核读面字段** ⇒ "ECR 详情回显了哪张 ECO"这件事**没有任何断言覆盖**。
后果：**读面错误天然抓不到**（数据是对的，错的只是"怎么读"）——而这正是本批最该防的一类（用户看到的东西与库里的事实不一致）。
**本批的修法不是"下次注意"，而是把读面变成断言点**：R24a1 直接断言 `GET /ecrs/{id}.ecoCode` 等于按 `ecr_id` 关联到的最新 ECO，且 R24a2 断言它**不得**等于"按主键误取"的那条。

> **同族教训（写进本批的纪律）**：判据要覆盖**用户实际看到的那个面**。只从 DB 侧证明"数据对"，等于默认"读面一定是镜子"——
> 本库已经为这个默认付过代价（同族：`#123` 内部 id 回显、`ecoCode` 取错行）。
> 附带一条**假红教训**（不是产品问题，但同样值得留档）：走查脚本里"中文关键词未做百分号编码"直接拼进 URL 会让服务端收到乱码、报"检索无命中"；
> 判据输入因此只用 ASCII 编号片段，并在注释中写明"输入必须先自证可送达"。**判据自身错了，会以"产品缺陷"的样子消耗排查预算。**

## 5. 列表契约（三域一致）

### 5.1 三个列表的参数与返回形状

| 端点 | 查询参数 | 返回 |
| --- | --- | --- |
| `GET /api/v1/ecrs` | `status`、`keyword`、`updatedFrom`、`updatedTo`、`page`、`size`（`pageSize` 别名）、`pageSize`（默认 20，上限 100） | `Paged<EcrResp>`：`{items, total, page, pageSize, pageSizeCapped}`；每项含 `ecrCode/source/urgency/problemDesc/triageBy/triageOn/triageConcl/status/createdBy/**ecoCode**/**updatedAt**` |
| `GET /api/v1/ecos` | `status`、`keyword`、`updatedFrom`、`updatedTo`、`page`、`size`、`pageSize` | `Paged<EcoResp>`：含 `ecoCode/ecrId/title/changeClass/五维评估/ccbResult/approvalNo/status/createdBy/updatedAt/affected/tasks/ecns/sodFlags` |
| `GET /api/v1/ecns` | `ecoId`、`status`、`keyword`、`updatedFrom`、`updatedTo`、`page`、`size`、`pageSize` | `Paged<EcnResp>`：含 `ecnCode/ecoId/targets/status/receipts/**ecoCode**/**ecoTitle**/createdBy/createdAt/updatedAt` |

**本批的形状升级（ECN）**：`GET /ecns` 原为**裸数组**且只支持 `ecoId` 过滤 ⇒ 界面只能"一次拉全量再本地筛"（08 号规格 §6.2.1 明令禁止的反模式）。
现与 ECR/ECO 同形状：标准分页对象 + 五类参数。**详情面板内的"某 ECO 下的 ECN"仍走 `GET /ecos/{id}` 的内嵌字段**，前端调用面不变（避免为一个内部读面改两处）。

**跨对象取号的两个新字段（同一口径，单条与批量共用一个实现）**：

| 字段 | 语义 | 取值口径 |
| --- | --- | --- |
| `EcrResp.ecoCode` | 这条申请**转成了哪张变更单** | 按 `t_eco.ecr_id = 本 ECR` 取 `id DESC LIMIT 1`（**最新一张**）；列表用 `DISTINCT ON (ecr_id) ... ORDER BY ecr_id, id DESC` 一次 `IN` 查询，不做 N+1 |
| `EcnResp.ecoCode` / `ecoTitle` | 这张通知**从哪张变更单来** | 按 `t_ecn.eco_id` 批量取 `t_eco.eco_code/eco_title`（一次 `IN` 查询）；单条视图组装复用同一函数 |

**为什么这两列是"必须有"而不是"好看"**：`TO_ECO` 状态的 ECR 若看不到"转成了哪张单"，用户就只剩"自己去变更模块搜编号"一条路——
而那正是本批 §4-① 那 13 条孤儿 ECR 的形成机制之一（**"链断了"在界面上表现为"一片 TO_ECO 无从追起"**）。

### 5.2 为什么时间维度必须三域一致

08 号规格 §6.3.1 要求「**所有对象列表**支持按更新起止时间搜索」（闭区间整天，服务端 `updatedFrom/updatedTo`）。
变更域此前只有 ECO 支持，ECR/ECN 都不支持——**同一套规格在不同域不一致，等于"看起来有规格、实际没有"**（用户按一个页面的习惯去另一个页面就失手）。
故本批三域拉齐：

- ECR：`updatedFrom/updatedTo` 由 `EcrRepository.search` 施加（**前提**是该列真的会推进——§4-④，否则筛出来的"更新"是假的）；
- ECN：V141 补 `updated_at` 列 + 存量回填，参数与 ECR/ECO 同形状；
- 口径细节：`*From` 取当日 0 点（含当天）、`*To` 取**次日** 0 点做开区间（含当天整天）——`listCbbs` / `EcrController.fromEnd` / `EcnController` 三处同一算法。

> **这条纪律的一句话版本**：时间维度是"三件必须一起成立的事"——**列有人在推进**、**接口收参数**、**界面给入口**。缺任一件，
> 用户看到的都是"筛不出东西"，而三件的缺失**表现完全一样**（所以排查时必须逐件取证，不能凭现象猜）。

## 5.3 权限矩阵（本域）与"发起人能不能处理自己发起的事"

### 5.3.1 现状（V142 之后，逐点实测）

| 权限点 | 允许角色 | 它守的动作 |
| --- | --- | --- |
| `ecr.create` | pdt_manager / system_engineer / quality / ra / admin / **platform_owner** | 新建申请；**CBB 升版自动起草 ECR 走的就是它**（V140 起含 `platform_owner`） |
| `ecr.update` | admin / system_engineer / pdt_manager / quality / ra / **platform_owner**（V142） | 初评结论写回（`PUT /ecrs/{id}`，仅 `OPEN`/`TRIAGED`） |
| `ecr.transition` | pdt_manager / system_engineer / quality / ra / admin / **platform_owner**（V142） | 申请状态机（`TRIAGED`/`TO_ECO`/`CLOSED`/`CANCELLED`） |
| `eco.create` | pdt_manager / system_engineer / admin / **platform_owner**（V142） | 新建变更单；**工作台「转变更单」就是它** |
| `eco.update` | admin / system_engineer / pdt_manager / quality / ra | 变更单字段与**关联 ECR**（`PUT /ecos/{id}`） |
| `eco.transition` | pdt_manager / system_engineer / quality / ra / admin | 变更单状态机（含 ECN 生成、回执确认） |
| `eco.eval` / `eco.ccb` / `eco.apply` | 见 `PermissionService.RULES`（评估=五维角色面 + 管理面；CCB=决议面；apply=实施面） | 五维签署 / CCB 决议 / 变更执行 |
| ECN 动作 | **没有独立权限点**（复用 `eco.transition`） | 下发与回执 |

### 5.3.2 一条真实缺陷与它的口径（裁定 D1-A，2026-09-22）

**缺陷**：V140 为了让"CBB 升版自动起草 ECR"成立，把 `platform_owner` 加进了 `ecr.create`——但只加了这一处。
于是 **CBB 负责人能发起 ECR、却不能处理它**：界面上「初评结论/保存/完成初评/转变更单」都能点，点了只回
403「无权限执行 ecr.update（当前角色：platform_owner/viewer）」。实测旁证：库内 66 条 ECR 中 39 条由 CBB 升版起草，41 条长期停在 `OPEN`。

**口径（用户裁定方案 A）**：补齐 `ecr.update` + `ecr.transition` + `eco.create`（迁移 V142 + `PermissionService.RULES` 同批）。
理由一句话：**"谁能发起"与"谁能处理"必须由同一口径回答**——资产负责人对自己资产引发的变更，至少要走得到"转成变更单"这一步。

**边界（同样重要，别读成"全程可用"）**：`platform_owner` 现在能**发起 → 初评 → 转变更单**；
**变更单内部**（挂载/解绑 ECR、状态机、五维签署、CCB 决议、ECN 回执）仍属项目角色。
这是**裁定范围**，不是缺陷：变更单是跨专业决策对象，其执行面归 pdt_manager/system_engineer/quality/ra。
若业务要"资产负责人对自己资产引发的变更全程可用到底"，需要**再补 `eco.update/eco.transition/eval/ccb` 四个点**（一处迁移 + RULES 同步）——
本条已在验收报告里作为待确认项单列，**未擅自放宽**。

### 5.3.3 守它的判据

- 服务端：`b42` **R20e1~R20e4**（逐点角色集 + "追加而非覆盖"）+ **R20e5/R20e6**（运行期探测：`platform_owner` 打 `PUT /ecrs/999999`、`POST /ecos` 空标题，必须 **400「对象不存在/缺字段」而不是 403**——权限"配置存在"与"运行期真的放行"是两件事）；
- 界面：W35 **CK-D1/CK-D1b**（永久哨兵：一旦权限矩阵被改回"只给 create"，立刻变红）。

## 5.4 深链参数与"认证清理"的碰撞（本域踩到、已修）

**现象**：整页加载（F5 / 把链接发给同事）`/changes?obj=ECR&code=ECR-2026-0123` 后，URL 变成 `?obj=ECR`、面板空、无选中行（**SPA 内点击跳转正常**）。

**根因**：本域的业务深链参数名 `code` **与 OAuth 授权码参数同名**。认证层为了防"刷新重放一次性授权码"（批次39 的真实报障），
在**任何**落地路径上只要看到 `code/state/session_state/iss` 就抹掉（`main.tsx` 的握手参数清理块，现行 `main.tsx:325` —— 行号会随壳层改动漂移，**以 `HANDSHAKE_PARAMS` 的 grep 命中为准** + `auth/autoLogin.ts` 的 `HANDSHAKE_PARAMS`）⇒ 深链丢目标。

**修法（用户裁定方案 A，2026-09-22）**：与本仓自己的握手判据（`hasOidcCallback`：**code + state 同在场**才算回调）对齐——
`state`/`session_state`/`iss` 出现即抹；`code` **仅与 `state` 同在场**才算握手参数。
`postLoginPath`（登录后还原深链）同一判据，否则登录完成后还原的目标路径也会丢掉编号。
**安全性不降**：单独一个 `code`（无 `state`）本来就换不到 token（state 与 PKCE verifier 不匹配），留在地址栏不构成重放面。

**教训（写进约定）**：**业务参数名要避开协议保留字**。深链是跨模块契约（本域被 CBB 版本历史直接链接过来），
一个"看起来只是命名"的选择，实际决定了"刷新/分享是否可用"。判据：W35 **C7c**（整页加载深链必须落到那一条）+ **W32 32/0**（批次39 登录/回调/刷新重放八项回归）。

## 5.5 状态机守卫的 NULL 安全（设计好的 400 不许变成 500）

界面走查在**正常业务链**上撞到两处 500（不是边界用例，是用户自然会走到的路径）：

| 场景 | 期望 | 实际（修复前） | 根因 |
| --- | --- | --- | --- |
| `EVALUATING` 阶段五维一个都没签，点「评估完成→CCB」 | 400「五维评估未全部签署，不可进 CCB 评审」 | **500**「服务端处理该请求时失败」 | `allDimsSigned` 用 `List.of(五个可能为 NULL 的列)`——新单 `eval_*` 五列**无默认值（实测 schema 无 default）**，而 `List.of` **不接受 null 元素** ⇒ NPE |
| `CCB_REVIEW` 阶段决议尚未写入，先点状态机按钮 | 400「CCB 决议必须为通过或附条件，方可批准」 | **500** | `List.of("APPROVED","CONDITIONAL").contains(ccbResult)` ⇒ `null` 参数同样 NPE |

**修法**：五维判定改 `Stream.of(...)`（允许 null，配"null 即未签"的谓词）；
并新增 **null 安全**的 `in(v, ...)` 值域判定，把本域**全部 9 处** `List.of(...).contains(<标量>)` 统一到它
（含 CCB 决议**缺字段**与**非法值**两种：都必须是 400 并点名）。

**口径**："值缺失"与"值非法"在用户看来是同一种体验——**都必须 400 + 可行动文案**；
`List.of(...).contains(x)` 这种写法在这个位置上**永远不安全**（它把"字段没填"变成"服务端崩了"）。
判据：`b42` **R28-0/R28a~R28h**（拒绝必须 400 + 点名 + **无副作用**，且五维齐备后仍能进 CCB_REVIEW）。
