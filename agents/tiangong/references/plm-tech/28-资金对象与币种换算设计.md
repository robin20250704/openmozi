# 28 · 资金对象与币种换算设计

> 定位：为**所有涉及资金的条目**建立统一的金额载体（`Money`）——**金额数 + 币种 + 单位**，支持元/万元/百万元/亿换算、依据**汇率表**做跨币种计算，并接入敏感字段治理。
> 依据：用户裁定 **D-P6**（"所有涉及资金的条目都应该有币种。资金单建一个小对象：资金数、币种，支持单位（元、万元、百万元、亿）转换、根据汇率表跨币种资金计算等"）。
> 上游：`ipd/plm-app/backend/src/main/java/com/plm/common/Currencies.java`（**币种唯一权威来源**）、`.../platform/governance/FinanceFieldAccess.java`（密级判定唯一实现）、`.../domain/finance/FinModelService.java`（"只报不拦"范式 + `npvRecheck`）、`.../domain/item/ItemDtos.java:279-290`（`planCost`/`stdCost` 双口径）。
> 下游：`26 号文`（`t_prj_objective` 的 MONEY 维度）、`27 号文`（`t_pco` 的 BUDGET 类）、`t_item_rev.plan_cost`、`t_fin_model`、`t_offering_line`。
> 断言：待落地后登记。

## 0. 一句话结论

**金额在本系统里第一次成为一等类型**：`Money(amount, currency, unit)` 三元组 + `t_fx_rate` 汇率表 + `MoneyConverter` 换算服务，取代"金额是个裸 `NUMERIC` + 靠字段名猜单位"的现状。

**立此对象的三条硬证据**（全部来自实测，非推测）：

| 证据 | 出处 |
| --- | --- |
| 同一"目标成本"在三个对象上有三个数：项目 520 / 产品 40 / 任务书 905 | `V103:24-26` 迁移注释 |
| 同一销量有两个数：charter 1/1.5/2 万台 vs 计划首年 3 万 / 产能 5 万 | `V81:8` 迁移注释 |
| `t_project.attrs.budget` 在两个项目上是 `1800` 与 `200`，**量纲不同且无任何单位声明** | 2026-10 实测（`26 号文` §2.4） |

`V81` 早已写下病根："**实测跨对象口径冲突的根源之一就是单位未声明，缺单位时数字无法比较**"。`D-P6` 是对这个病根的正面治疗。

## 2. `Money` 值对象

### 2.1 Java 侧

```java
package com.plm.common;

/** 金额值对象：金额数 + 币种 + 展示单位。 */
public record Money(BigDecimal amount, String currency, MoneyUnit unit) {
    public Money {                                  // 紧凑构造器做不变量校验
        if (amount == null) throw new BizException("VALIDATION_ERROR", "金额不能为空");
        Currencies.validate("currency", currency);
        if (unit == null) unit = MoneyUnit.YUAN;
    }
    /** 归一到"元"的金额（换算只在这里发生一次）。 */
    public BigDecimal yuanAmount() { return amount.multiply(unit.factor()); }
}
```

```java
public enum MoneyUnit {
    YUAN("元", BigDecimal.ONE),
    WAN("万元", new BigDecimal("10000")),
    YI("百万元", new BigDecimal("1000000")),
    YI_YI("亿元", new BigDecimal("100000000"));
    // factor = 该单位含多少个"元"
}
```

**不变量**：`amount` 与 `currency` 永不为空；币种合法值**只从 `Currencies.ALL` 读**（该类注释明确："CURRENCIES 已在 `OfferingService` 与 `FinModelService` 各抄一份（同一集合第三次出现）——按裁定收敛为本共享类"，**不得再抄第四份**）。

### 2.2 DTO / JSON 形态

```jsonc
{ "amount": 1800, "currency": "CNY", "unit": "WAN" }
```

**解析口径**：三缺一即拒——
- `amount` 缺失 → 400 `VALIDATION_ERROR`（指名字段）
- `currency` 缺失 → **400**（★ 这是本设计的关键约束：以前允许缺省 `CNY`，`FinModelService.java:61` 就是 `in.currency()==null ? "CNY" : ...`；**`D-P6a` 要求资金条目必须有币种 ⇒ 取消该缺省**，迁移期见 §7）
- `unit` 缺失 → 视为 `YUAN`（**单位可缺省，币种不可缺省**——缺单位的坏处是"数不可比"，缺币种的坏处是"根本不是钱"）

## 3. 单位换算（`D-P6c`）

| 单位 | 码 | 因子（该单位 = 多少元） |
| --- | --- | --- |
| 元 | `YUAN` | 1 |
| 万元 | `WAN` | 10,000 |
| 百万元 | `YI` | 1,000,000 |
| 亿元 | `YI_YI` | 100,000,000 |

**换算只在两个地方发生**（`一处一事实`）：

```java
MoneyConverter.toYuan(Money)            // 归一
MoneyConverter.display(Money, unit)    // 展示换算
```

**计算纪律**：
- 金额比较/求和**必须先归一到元**再运算，**不在混合单位上直接相加**（`1800万元 + 200万元 ≠ 2000`）。
- 归一用 `BigDecimal`，**除法必须带 `RoundingMode`**（既有先例：`FinModelService.npvRecheck:164-166` 用 `RoundingMode.HALF_UP` + scale 8）。
- **不裸加总多币种**（既有铁律：`ItemDtos.java:284` 注释 "ref_price/currency 为参考信息，不进本报表（多币种安全：不裸加总多币种）"）。跨币种求和**必须**经 §4 折算。

## 4. 汇率表与跨币种计算（`D-P6d`）

### 4.1 `t_fx_rate`

```sql
CREATE TABLE t_fx_rate (
  id          BIGSERIAL PRIMARY KEY,
  base_ccy    TEXT NOT NULL CHECK (base_ccy IN ('CNY','USD','EUR','JPY','HKD')),
  quote_ccy   TEXT NOT NULL CHECK (quote_ccy IN ('CNY','USD','EUR','JPY','HKD')),
  rate        NUMERIC(20,10) NOT NULL CHECK (rate > 0),   -- 1 base = rate quote
  rate_date   DATE NOT NULL,
  source      TEXT NOT NULL DEFAULT 'MANUAL',              -- MANUAL / IMPORT（ERP 回写）
  created_by  TEXT NOT NULL, created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT uq_fx_rate UNIQUE (base_ccy, quote_ccy, rate_date),
  CONSTRAINT ck_fx_rate_pair CHECK (base_ccy <> quote_ccy)
);
CREATE INDEX idx_fx_rate_lookup ON t_fx_rate(base_ccy, quote_ccy, rate_date DESC);
```

**取数规则**：

```java
Optional<BigDecimal> rate(String base, String quote, LocalDate on)
```

| 规则 | 理由 |
| --- | --- |
| 取 `rate_date <= on` 的**最近一条** | "某日汇率"= 那天或之前最后可得 |
| 精确日无记录 ⇒ **如实报"取的是哪一天"** | 返回 `(rate, effectiveDate)`，响应必带 `fxAsOf`；**不静默用今天的** |
| 逆汇率**由正向推导**（`1/a`），不另存一行 | 避免两行漂移 |
| 无路径可换算 ⇒ **400 `FX_RATE_UNAVAILABLE`**，文案指名缺哪一对 | **绝不按 1:1 兜底**（那是在造数） |
| 中间币经第三币两跳（如 CNY→JPY→USD） | 允许，但**响应标注 `via`** |

### 4.2 换算服务

```java
Money convert(Money src, String targetCcy, LocalDate on)
// 返回 (换算值, 实际汇率, 汇率日, 是否经中间币)
```

**跨币种求和**：`sum(List<Money>, targetCcy, on)` —— 逐笔换算后相加，**返回每笔的折算明细**（照 `costCompare().costBasis.sources[]` "每个数字带出处"的既有范式）。

### 4.3 ★ 汇率取哪一天：**已裁定 = 评价当日**（`D-P15`，2026-10 用户裁定）

达成率计算里"目标 CNY / 实际 USD"用哪天的汇率，直接影响数字。候选：

| 方案 | 口径 | 取舍 |
| --- | --- | --- |
| (a) **评价当日** ★ | `t_prj_achievement.measured_on` 对应汇率 | **本轮采用** |
| (b) 目标基线批准日 | `objective_rev.approved_on` 对应汇率 | 更接近商业实质，但"承诺日汇率"要另取 |
| (c) 期间平均 | 评价期加权平均 | 需汇率序列完整，**本轮明确不做** |
| (d) 目标值声明的币种即基准 | 目标定 USD 就比 USD | 目标本身可能是本币，掩盖了币种问题 |

**裁定（`D-P15`）：先用 (a) 评价当日，不用评价期平均。** 理由是**可解释、无需额外数据**：评价当日本来就是"实际值被测到的那天"，用那天的汇率与"实际值"同源，读数字的人不需要再问一句"这个 0.87 是几号的钱"；(c) 需要一条**完整**的汇率序列才成立，而本轮汇率表靠人工维护、序列大概率有缺口 ⇒ 用它算出来的"平均值"是**看起来更精确的假精确**。

**本裁定的已知代价（如实登记，不假装没有）**：

| 代价 | 说明 | 缓解 |
| --- | --- | --- |
| 达成率会随汇率抖 | 同一目标、同一实际值，隔一个月重算可能得不同数 | 达成记录**冻结时把当时汇率一并固化**（§7 的 `fx_rate`/`fx_as_of`/`fx_via` 三列）⇒ 冻结后**永不重算**，抖动只发生在"未冻结的滚动刷新"期间 |
| 长周期目标更敏感 | `YEAR1_VOLUME` 等 365 天期目标受期间汇率影响更明显 | 同上；且这类目标本就 `eval_offset_days=365`，只在期末算一次 |
| 汇率不可得即失败 | 评价当日无汇率 ⇒ `FX_RATE_UNAVAILABLE` | **不兜底 1:1**（那是在造数）；错误文案指名缺哪一对 |

**留门**：若日后汇率序列由 ERP 每日回写（`t_fx_rate.source='IMPORT'`）且**连续无缺口**，可重新裁定为 (c)——届时改的是 `MoneyConverter` 里**一处**取数规则，不是达成率计算本身。**不得**在达成率服务里写第二份取数规则（V-186）。

## 5. 落库形态

**决策：资金在库里仍用 `NUMERIC` + `currency` 两列**（不建宽表、不用复合类型），理由：

| 方案 | 评价 |
| --- | --- |
| **两列 `NUMERIC` + `currency`（选定）** | 与仓内既有 `t_item_rev.currency` / `t_fin_model.currency` / `t_offering_line.currency` **同构**；SQL 可直接 `WHERE currency=?`、可 JOIN、可索引；迁移与查询成本最低 |
| 复合类型 / JSONB | 查询与约束都更难写，**且与既有三处不同构** ⇒ 制造"金额有两种存法"，比现在更糟 |
| 独立 `t_money` 表 | 一次读取要多一次 JOIN，而金额**总是内嵌在业务行里**、无独立生命周期 ⇒ 过度建模 |

**`Money` 是"接口层的一等值对象"**，不是"一张表"。库侧靠 `currency` 列的 CHECK + 应用侧靠 `Money` 构造器的不变量共同保证。

**约束纪律**：凡新增 `currency` 列，CHECK 的值列表**必须与 `Currencies.ALL` 逐字一致**（该类注释原文："数据库侧 CHECK（`t_offering_line_currency_ck` / `t_fin_model.currency CHECK` / `t_item_rev_currency_ck`）列出的值必须与 `ALL` 保持一致，改动时两侧同步"）⇒ **不得抄第五份**。

## 8. API 契约

| 端点 | 说明 |
| --- | --- |
| `GET /api/v1/fx/rates?base=&quote=&on=` | 取汇率，返回 `(rate, effectiveDate, via)`；无则 400 `FX_RATE_UNAVAILABLE` |
| `POST /api/v1/fx/rates` | 维护汇率（`fx.rate.write`），同对同日期为覆盖（`ON CONFLICT`） |
| `POST /api/v1/_platform/money/convert` | 通用换算：`{amount,currency,unit} → {targetCurrency, on}` |

**错误契约**（沿用 `18 号文` E 规范：码判类别、消息取细节、状态码承担语义）：

| 码 | HTTP | 触发 |
| --- | --- | --- |
| `VALIDATION_ERROR` | 400 | 金额缺失 / 币种非法（`Currencies.validate` 已统一到此码） |
| `VALIDATION_ERROR`（币种必填） | 400 | **缺 `currency`**（`D-P6a` 新增约束） |
| `FX_RATE_UNAVAILABLE` | 400 | 指定日无可用汇率路径 |
| `MONEY_MIXED_CURRENCY` | 400 | 跨币种直接相加（未先换算） |
