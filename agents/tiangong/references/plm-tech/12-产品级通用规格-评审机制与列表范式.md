# 12 · 产品级通用规格：评审机制与列表范式

> **来源**：项目管理模块（IPD 项目域，V46–V59c）实战沉淀 + 用户口径逐条确认（见 10-§6.2/§6.4、09-§1.10 缺陷档案）。

> **分层关系**：模块实例文档（08/09/10）描述"项目域当前怎么实现"；本文描述"产品要求所有域怎么实现"。语义冲突时以本文（含用户口径）为准，实现细节以模块文档为准。

## 2. 评审机制通用规格（G-REV）

### G-REV-1 评审容器（对象模型）

**规格**：评审是独立于业务对象的**决策容器**——清单（items）＋ 责任人（判定人/签署人/否决人）＋ 结论（conclusion）＋ 签署（signatures，WORM）＋ 否决（vetoes）＋ 遗留问题（open issues）。

- 评审容器可挂接任意业务域与门点：项目 DCP/TR、变更评审、文档评审、供应商评审……**挂接关系是配置**（`t_gate_map` 型映射表：gate ↔ 评审类型 ↔ 阶段端点 ↔ 阻断指向），不是代码分支。
- 生命周期：`未发起 → IN_REVIEW（评审中）→ DECIDED（已判定＝定论）`。**定论后容器 WORM 只读**；唯一合法演进 = 再次发起一次**新的**评审（旧评审留档不可改）。
- 评审不走流程 YAML（09-§1.9 权威口径）：FlowEngine 只管对象状态机；评审由评审服务显式编排，作为流程的**守卫输入**（G-REV-6）。

**验收断言**：
- A1 对已判定评审执行 judge/sign/veto/decide 全部 4xx（错误码见 G-REV-5.3），详情面板只读渲染；
- A2 新评审与旧评审记录互不影响（新评审不改写旧评审任何字段）。

### G-REV-2 评审责任人管理

**规格**：判定资格与指派遵循**三层资格模型 ＋ 按项派发 ＋ 双通道指派 ＋ 实例收敛**四件套。

**2.1 三层资格模型（自下而上汇总，自上而下校验）**：

| 层 | 内容 | 纪律 |
|---|---|---|
| 项级 | 每个检查项声明责任角色 `judge_role`（领域责任人：谁有资格判本项） | 必须是已定义角色（启动校验 `JUDGE_ROLE_UNKNOWN`） |
| 域级 | 域级权限点（如 `review.opinion`）**＝ 全部项级资格角色的并集 ∪ 治理角色 ∪ admin** | **域级 ⊇ 细粒度资格并集**——启动期自动校验（`DOMAIN_UNION_MISSING`，10-§6.3），违者启动即失败，杜绝"合格的人在域级被拦死"的静默缺陷（历史 4 次：V41/V49/V52/V54） |
| 实际判定权 | 本评审项级资格 ∪ 评审类型治理角色（DCP_JUDGES/TR_JUDGES 型）∪ admin 代判 | admin 代判显式留痕（`*.override` 审计）；无资格用户看到的是"无判定资格（须哪些角色）"，不是灰色不可点 |

**2.2 待办按项派发**：发起评审时**逐评审项**生成待办（一待办 ↔ 一评审项，携带 `item_no`），候选池 ＝ 资格角色 ∩ 启用用户（组织角色 ∪ 对象所属项目角色）。禁止按角色聚合派发（一个角色多项只有一条待办 → 无法把具体检查项指派到具体人，V50 改口径的原因）。

**2.3 双通道指派（认领 ＋ 指派）与改派**：

| 动作 | 语义 | 纪律 |
|---|---|---|
| 认领 | 有资格人员在待办池认领 → `claimed_by` | 候选池可见性＝「组织 ∪ 项目角色」口径，无需新权限代码 |
| 指派 | 发起人/PM/主席从**合格候选人清单**指定 → `assignee`（ASSIGNED） | **指派不绕开资质**：非合格用户 400 `ASSIGNEE_NOT_QUALIFIED`；候选清单接口支持 keyword 检索（login/姓名）并限量返回 |
| 改派 | 同一评审项可重复指派：覆盖 assignee、清 claimed_by、**不新增待办** | 已指派后"改派"入口不消失（用户实测缺陷：处理人只能等认领） |
| 取消指派 | 回到候选池"待认领" | 审计记录含 before 值 |

**2.4 指派权按对象实例收敛**：域级角色（如 `review.assign`）是全局的——仅域级放行会让"任一带该角色者指派任意对象的评审项"。对象级授权集 ＝ 本项目/对象成员 ∪ PM ∪ 创建人 ∪ 本评审参与人；不匹配 403 `FORBIDDEN_OBJECT`，admin 豁免。

**验收断言**：
- A1 项级资格角色（非治理角色）可判定本项（域级不被拦，回归 V52/V54 场景）；
- A2 指派非合格用户 400；改派不新增待办行；取消指派后原认领人不可再判（重新回到候选可见）；
- A3 非对象实例内的人员（同角色、别的项目）指派本对象评审项 403。

### G-REV-3 强制检查项评审（清单驱动）

**规格**：评审清单的检查项是结论形成的**强制输入**，不是参考信息。

**3.1 检查项结构**：编号 / 文案 / 强制标记（`is_mandatory`，UI `*`＋高亮）/ 责任角色（G-REV-2）/ 判定 `PASS|COND|FAIL` ＋ 条件意见。**COND 必填条件意见**（可选责任人/期限），落库并**自动生成遗留问题对象**（绑定后续门点）——"有条件通过"必须留下可追踪的欠账，而不是一句话备注。

**3.1b「谁」与「哪份文档」一律对象选择，不用自由文本（2026-11-12 批次65 / D65-3、D65-4，用户裁定）**

**由来**：评审输入里曾有两个自由文本框——证据包挂载的「文档编号」、项级意见的「责任人/证据引用」，
以及结论级条件意见的「责任人」。自由文本写入的是**没有校验过的字符串**：填错的人、编号写错的文档
在库里都成立，事后无法追溯"这条意见到底指给谁、依据是哪份受控文件"。

**三条纪律**：

1. **人员引用 = 人员对象选择**。用 `SearchPick objType='USR'`，值域是 **login**
   （`lookup.ts` 的 `LOOKUP_VALUE_FIELD` 唯一非数字键）⇒ 下游 `openIssueOwner` / `condition_owner`
   直接存 login，**不需要**新增人名字段或外键。候选范围＝**全部系统用户**（按 login/姓名检索）。
   ⚠ 不走 `/reviews/{id}/candidates`（那条要求 `itemNo` 必填，而条件意见是结论级、拿不到 `itemNo`；
   若一处走资格候选、一处走全量用户，同类字段出现两种口径，反而更糟）。
2. **文档引用 = 文档对象选择，可多选**。用 `SearchPick objType='DOC' multiple`。
   证据包底子本就是真对象（`t_review_evidence_doc` 外键 + 挂载时校验存在性），所以这是**纯控件替换**。
   候选范围**默认限定本项目**（证据包本就是为本次评审准备依据），**必须另给一个显式的「看全部文档」开关**——
   冷门项目一张文档都没有时，开关是唯一出路，不能让人以为功能坏了。
   注意契约不对称：`EvidencePackReq` 收的是**编号** `docNos`，而 SearchPick 的 DOC 值域是**数字 docId**，
   映射在前端做（**不给后端加 `docIds` 字段**：契约只增不改是既有纪律）。
3. **证据类引用收进证据包，项级不再单设自由文本引用框**。同一屏里并排出现"证据包"和"项级证据引用"
   两个语义相近的输入框时，用户无从判断该往哪填——证据的唯一入口是**评审级证据包**（可移除、留痕、可审计）。
   ⇒ 删除项级判定编辑行里的「证据引用」输入框。**后端 `JudgeReq.evidenceRef` 字段保留不动**
   （契约只增不改，脚本化调用方可能仍在传），只是 UI 不再提供该入口。
4. **证据表「文档编号」列 = 深链，新 tab 打开**（2026-11-13 批次66 需求①，用户口径
   「点击后在新tab页打开相关对象」）。证据行持有真 `docId`，用既有 `deepLinkOrNull('DOC', docId)`
   渲染成 `<a target="_blank" rel="noopener noreferrer">`（与项目页 `📎` 深链同构，见
   `lib/routes.ts` 的 ROUTE.DOC）；**不新建**任何链接机制，无 docId 的行保持纯文本。

**本批落点**（`frontend/src/components/ReviewWorkbench.tsx`）：

| 位置 | 原控件 | 现控件 |
| --- | --- | --- |
| 证据包挂载 | 「文档编号」自由文本（逗号分隔）＋「＋ 挂载证据」 | 文档对象多选（`DOC`/`multiple`）＋「看全部文档」开关 |
| 项级判定编辑行 | 「证据引用」自由文本 | **删除** |
| 项级判定编辑行 | 「责任人」自由文本 | 人员对象选择（`USR`） |
| 条件意见编辑行 | 「责任人」自由文本 | 人员对象选择（`USR`） |

**存在未判强制项 → 不得形成结论**（`MANDATORY_ITEMS_PENDING`）。**止损豁免**：TERMINATE/REDIRECT 类止损结论允许带未判项定论（业务上"叫停"不能被"还没判完"卡死）。开门判据同源：强制项必须全 PASS（COND ≠ 满足，09-§1.8.3）。

**3.3 判定 UI 三律**（08-§6.11.2）：①按钮显隐由 `canJudge` 驱动，无资格显示原因；②PASS 一步直提，COND/FAIL 展开行内结构化输入（禁弹窗）；③**前端按资格渲染，后端始终权威兜底**（前端放行 ≠ 后端放行）。

**3.4 发起前机器预审（干跑）**：发起评审前给出预检结果卡（证据＝系统实时投影，非人工上传）；**预检项必须按门点阶段收敛**——任何"全量/项目级"判据用于门点预审前，先回答"它在该门点阶段是否已有意义"（RTM 教训：项目级追溯检查在概念门点把全部账号的发起按钮搞灰）。预审未通过 → 禁用按钮**必须附逐条可行动原因**。

**3.4b 预审判据的两级表达：门 vs 仪表（批次64 立，源自诉求「评审点对交付物的要求只提醒、不强制」）**

预审的每一项必须显式声明自己是**门**还是**仪表**，且界面表达随声明走：

| 级别 | 语义 | 界面表达 |
| --- | --- | --- |
| **门（BLOCKING）** | **决策前提缺失**——门集模板未解析、无判定资格、强制项未判。缺了就**无法形成可信结论** | 未满足 ⇒ 按钮禁用 ＋ ⛔ 逐条可行动原因（既有形态） |
| **仪表（ADVISORY）** | **材料/证据是否齐备**。缺了**只影响这次结论的采信度**，不影响能不能开这次评审 | 未满足 ⇒ **按钮照常可点** ＋ 🟡 黄色警示条逐条列出（新增形态） |

**判据**：齐备度**不得**当门。把齐备度当门会堵死真实路径——用户想做这次评审，唯一出路是先绕过评审去补材料，而材料本身往往**正是这次评审要产出的东西**（自锁）。只有"决策前提"才是门。

本批落地：`DELIVERABLES`（项目交付物全部 APPROVED，BR-09/IBR-07）由 BLOCKING **降级为 ADVISORY**。`passed` 仍按实际状态如实计算并照常上报（**不洗白成通过**），只是不再参与 `PrecheckResult.passed` 的聚合（`PrecheckService:212-213` 的 `allMatch(ADVISORY || passed)` 已经这么算，`ReviewWorkbench:317` 的 `failedChecks` 也已按 severity 过滤）⇒ 改动面只有两处构造器 + 一处前端警示条。**其余判据一律不动。**

**3.5 清单继承审计**：流程改造迁移旧检查项（旧门 → 新决策点）时，必须做**机器可重跑的继承审计**（规范化文本比对，分类＝逐字继承/有意合并/丢失，断言"丢失＝0"），不得以人工记忆宣称"已继承"（V50/V51：57 项 → 55 逐字 ＋ 2 有意合并 ＋ 0 丢失）。

> **2026-09-11 补充（REQ-2026-0700，阶段门 G1..G7 作废后的归并落地）**：
> 除上表的文本审计外，本批把"归并"落成**两张可查询的表 + 一个来源外键**，使"原门项去哪了"成为数据事实而非文档承诺：

>
> **配套清单继承机制（REQ-2026-0702）**：评审清单支持**族模板 + 种类专属 delta 叠加**
> （`t_checklist_template.base_template_id`，实例化沿链"由具体到通用"合并、同 item_no 以更具体者为准）。
>
> **降级链的两条铁律**（同一模块两次踩坑后固化，两条都必须显式回答）：
> 1. **更宽的档必须排在更窄的档之后**。实测发现"软件族共用档"排在"种类专属档"之前，导致任何带 med_class 的项目
>    在族档就被截胡，种类专属清单**接了却永不生效**。这是继"通用档必须排最后"之后的第二例同类缺陷，
>    已在 `ChecklistTemplateService.resolve` 中固化为注释与顺序约束。
> 2. **命中多档时是并集，不是选一档**。带维度（类别/市场/种类）的档存的是**增量**项
>    （`CL-DCP_ES-III-ALL` 只有 M10、`CL-DCP_ES-ALL-CE` 只有 M11），基座项在通用档（`CL-DCP_ES-ALL-ALL` 的 M1..M9）。
>    旧口径"选第一个命中的档"把增量当全集 ⇒ III 类/CE 市场的项目**只剩 1 条增量项、基座全部丢失**。
>    阶段门退役后评审清单是唯一判据，丢项 = 丢判据，故改为"命中的档全部并入"（同 item_no 更具体者胜出）。
>
> **归并/映射类对象的校验必须是双向的**：`t_gate_check_migration` 曾出现"映射目标不存在"的**假映射**
> （3 条指向 DCP2 M20/M21/R20，而 DCP2 并无这些编号）——比"漏映射"更糟，因为它让"这要求还在"看起来有据可查。
> 校验必须同时做"每个来源都有目标"**和**"每个目标都真实存在"，后者才是能拦住假映射的那一半；
> 且凡按编号 join，先确认两侧编号体系一致（归并后重新编号是常态）。

**验收断言**：
- A1 强制项未判时 decide 400 `MANDATORY_ITEMS_PENDING`；TERMINATE/REDIRECT 豁免路径可定论；
- A2 COND 无条件意见 400 `COND_NOTE_REQUIRED`，补齐后自动出现遗留问题记录；
- A3 无资格用户判定 403（UI 同时显示原因），admin 代判出现在审计与"代判"徽标；
- A4 预审检查项在低阶段门点跳过不适用项且明细说明原因。

### G-REV-4 评审结论形成（两级意见）

**规格**：意见分两级，**范围不同、允许差异化**：

| 级 | 谁写 | 语义 | 载体 |
|---|---|---|---|
| 项级（专业评估） | 各检查项责任角色 | 领域专业判断，是结论的**输入** | 逐项 conclusion/note |
| 结论级（综合评估） | 主席角色（评审类型定义的唯一结论权人） | 对投资/技术/资源/风险的综合权衡，是结论的**内容** | 综合评议结论 ＋ 综合意见 ＋ 条件意见 |

- **两级可以不同**：项级全 PASS，主席仍可因组合风险给"有风险通过"——这不是矛盾，是综合评估的职责。
- **系统给候选、用户可改**：按项级结果生成候选结论（存在 FAIL → 止损/退回类；存在 COND → 有风险通过类；全 PASS → 通过类）与候选综合意见（项级专业意见汇总 ＋ 综合评估空段），前端预填并提供「采纳系统建议」（可改）——主席从零起草既慢又易抄项级，自动汇总又剥夺权衡，候选＋可改是平衡点。
- **理由必填性由决策矩阵驱动**：结论×角色×理由必填是配置（决策矩阵表），接口下发 `reasonRequired`，**前端据此渲染理由输入框**——杜绝"后端要理由、前端无输入框"的契约错配（400 死路，L-147）。
- 决策矩阵引用的角色码必须是已定义角色码（否则实际仅 admin 可决策，V46 教训）；启动校验 `ROLE_UNDEFINED`。

**验收断言**：
- A1 项级全 PASS 时可改选"有风险通过"且成功定论；
- A2 候选结论与项级结果一一对应规则成立（FAIL/COND/PASS 三类）；
- A3 对 `reasonRequired=true` 的结论，前端无理由提交 → 前端即拦截（不发无效请求），后端缺理由 400。

### G-REV-5 签署、否决与定论（WORM）

**规格（用户口径，产品级判词）**：

| 动作 | 谁 | 语义 | 时间窗 |
|---|---|---|---|
| **否决 VETO** | 评审类型定义的否决权角色（须与签署/结论权分离） | **阻止对象流程继续往下推进**，**不是**否定已形成的集体评议结论 | **仅签署前**；可由本人撤回（RELEASED 留痕）；理由必填 |
| **主席签署 SIGN** | 评审类型定义的签署权角色（每类型一个主席席位） | **代表评审集体形成合议结论并生效（定论）**的程序动作 | **每轮一次**：同一时刻只允许一条生效签署；不可覆盖、不可删除 |
| **作废签署 VOID**（2026-09-11 增补，REQ-2026-0518） | 原签署人本人 / 主席 / admin | 声明某条签署**不成立**（签错结论、理由写错、探测签）——**只更正签名归属与理由，不改变已形成的结论内容** | 签署已生效且该条仍 ACTIVE 时；理由必填；作废后允许**重新签署** |
| **结论** | 随签署同一原子操作选定 | 决议**内容**；只有**放行型结论集合**解锁流程推进 | 与签署绑定 |

**关键澄清**：
1. **签署 ≠ 通过**：签署是"决议生效"，结论才是"通过与否"——止损/退回结论同样经签署定论，对象不往前走。
2. **签署 ＝ 定论（WORM）**：签署后否决窗口关闭、结论不可改判；**修改决策 ＝ 再次发起一次新的决策评审**。界面须在定论后明示该指引。
3. **"不可重复" ≠ "不可更正"**（2026-09-11 增补）：WORM 要求的是**记录不可抹除、不可篡改、可追溯**，而不是"错误记录必须永久占据生效位"。故本轮把原判词"一次；不可重复、不可撤销"细化为：
   - **不可重复**：任一时刻只允许一条生效签署（重复签署仍 400 `SIGN_DUP`）；签署后否决窗口关闭、结论不可改判（原语义完全保留）。
   - **可更正**：误签经 **VOID** 通道作废——原签名行 `status→SUPERSEDED`，其 `actor/reason/sign_hash/created_on` **一字不改**，仅追加 `voided_by/voided_on` 与作废理由（事件 `REVIEW_SIGN_VOIDED` + 审计 `review.sign.void`）；随后可重新签署，新签名经 `superseded_by` 指回被取代的旧行，形成可查**作废链**。签名链键在重签轮次追加 `#R{n}`，使每轮签署各占 `t_sign_rec` 一行、各自衔接上一条哈希（防重放保护对同一轮依然有效）。
   - 边界：作废**不**修改 `t_review.conclusion/opinion/condition_*`（结论内容的更正仍只能"再次发起决策评审"），也**不**回退容器状态。
4. **否决的靶子是"推进"**：项级专业意见与综合意见继续有效留档，只是本决策点不放行。界面必须写明此语义（用户实测纠正过一次反向理解）。
5. **主路径原子**：默认主操作是「签署并形成结论」一步完成（签名哈希绑定 结论＋综合意见＋条件意见，SHA-256 型 WORM）；「仅签署」只是历史数据/会签兼容路径，界面默认不提供。
6. **守卫族（统一错误码，前端按码给可行动提示）**：`SIGNER_REQUIRED`（未签而定论）/ `VETO_PENDING`（存在未撤回否决）/ `SIGNED_NO_VETO`（签署后再否决）/ `VETO_REASON_REQUIRED` / `MANDATORY_ITEMS_PENDING`（G-REV-3.2）/ `COND_NOTE_REQUIRED` / `DECIDED`（对定论评审再写）/ `VOID_REASON_REQUIRED`（作废缺理由）/ `NO_ACTIVE_SIGNATURE`（无可作废的生效签署）。
7. **解锁语义**：仅放行型结论（如 DCP GO/GO_WITH_RISK）解锁阶段流转；阶段内门（TR 型）通过"FAIL 阻断其指向的门点预审"生效，不直接拦流转。

**验收断言**：
- A1 未撤回否决时签署 400 `VETO_PENDING`；撤回后可签；签署后再否决 400 `SIGNED_NO_VETO`；
- A2 签署记录哈希绑定结论＋意见（改库比对不匹配）；**同一轮**重复签署 400 `SIGN_DUP`；
- A2' （2026-09-11 增补）作废签署：无理由 400 `VOID_REASON_REQUIRED`；作废后原行 `sign_hash/reason/actor/created_on` 全部不变且 `status=SUPERSEDED`、`voided_by/voided_on` 落值；作废后可重签且该评审同时存在 2 条签署记录（1 SUPERSEDED + 1 ACTIVE）；已作废记录再次作废明确报错（不静默成功）；
- A3 非 GO/GO_WITH_RISK 结论定论后，阶段流转守卫仍阻断（`STAGE_GUARD_BLOCKED`）；
- A4 界面在否决行显示"否决的是推进而不是评议结论"、定论后显示"再次发起决策评审"指引（UI 断言）。

### G-REV-6 评审与流程引擎的边界

**规格**：评审是流程的**守卫输入**，不是流程节点。

## 3. 列表查询范式通用规格（G-LST）

> 依据：PRJ-2026-0238"创建后看不到、查不到"（09-§1.10 #8，V59c 修复）。三因叠加＝升序排序＋固定首页无翻页 UI＋创建后不回首页；搜索 API 正常但"创建即可见"不能靠用户搜索兜底。

### G-LST-1 默认排序：最新在前

**规格**：所有业务对象列表默认排序 **`createdAt DESC, id DESC`**。`id` 是稳定决胜键（同秒创建不抖动、翻页不漂移、深链可复算）。

- 判词：用户心智是"**刚创建/最近更新的对象在列表顶部**"，不是"按创建时间正序翻历史"。升序作为默认值即是缺陷。
- 例外：确有"最旧优先"业务诉求的列表，须**显式产品决策并注明理由**，不得作为默认值。

**已登记的例外（2026-09-17 批次26，用户裁定）**：

| 列表 | 默认排序 | 理由（用户原话） | 边界条件（缺一不可） |
|---|---|---|---|
| 投诉台账 `/postmortem` → `GET /complaints` | **`DEADLINE_ASC`**：未了结优先 → `reportable_deadline` 升序（NULLS LAST）→ `id DESC` | "**这个对象有它的外部合规强制性，上报时限优先级更高**" | ① **服务端默认仍是 `LATEST`**（例外只在调用方显式请求 `sort=DEADLINE_ASC` 时生效，既有调用方/判据零破坏）；② 界面必须提供**排序下拉**可切回「最新在前」（例外可撤销、可对照）；③ 例外须在本表登记（不接受"代码里悄悄改了默认值"）；④ 非法 `sort` 值 → 400 并列出可选值 |

→ 详细规格与验收断言见 `08-前端实现规格.md` §6.3.1.1；服务端实现 `PvService.complaints`；判据 `plm-b26-opt-api.cjs` A1/A2、`plm-b26-console.cjs` P3/P4。

### G-LST-2 服务端分页 ＋ 工具栏分页 UI（成对交付）

**规格**：
- 服务端：`page`（0 起）＋ `pageSize`（默认 100、上限 100）＋ 响应含 `total`；keyword / updatedFrom / updatedTo 过滤与分页同参共存。
- 前端：工具栏**必须**渲染分页 UI——「共 N 个对象 · 第 x/y 页」＋ 上一页/下一页（首末页禁用）。
- **纪律：分页参数存在但无 UI ＝ 半成品缺陷**（不是"以后再做"）：用户等价于永远只能看到第一页，且没有任何迹象表明还有更多数据。

### G-LST-3 新建/变更后可见性

**规格**：**提交成功 ⇒ 用户能在列表看到它**——这是交付判据，不靠搜索兜底。

- 创建成功 → 跳回第 1 页并加载（新对象＝第 1 行，G-LST-1 保证置顶）；
- 编辑成功 → 行就地刷新可见（不整表重拉）；
- 删除成功 → 保持页码；若当前页因此越界则回退一页。

### G-LST-4 搜索与深链

**规格**：
- 搜索：keyword 单号/名称模糊，**回车触发**（08-§6.2）；命中为空时给出"无匹配"反馈（不能静默）。
- 深链 `?open=<id>`（或单号直链定位）：**对象不在当前页窗口时，按 id 直取详情回退加载**；排序/分页策略变化**不得破坏深链**（V59c 追记：改 DESC 后老项目出窗口导致深链失效，已修）。

### G-LST-5 验收断言（每个业务对象列表照抄）

| # | 断言 |
|---|---|
| A1 | 创建对象 → 列表停在第 1 页且该对象是第 1 行（total ＝ 旧值＋1） |
| A2 | 「共 N · 第 x/y 页」数字正确；翻页可到达全部 N 条（抽查首页/末页） |
| A3 | 单号/名称 keyword 搜索命中唯一并可选中 |
| A4 | 深链 `open=<非首页对象 id>` → 详情正确打开 |
| A5 | 排序稳定性：同 createdAt 批次按 id DESC，两次加载顺序一致 |

## 附：G-API-1 横切契约口径（HTTP 状态码 / 错误码 / 分页 / 处理记录）

> 追加于 2026-09（批次 E 遗留项收口）。**只追加**，不改动上文任何既有条目；
> 目的是把"散落在各域实现里的横切口径"提升为一条产品级规格——新增域必须按本节接入，
> 评审时按本节判定"契约是否对齐"。

### G-API-1.1 HTTP 状态码

| 语义 | 状态码 | 错误码 | 说明 |
|---|---|---|---|
| 身份/权限不足（RBAC / ABAC / 判定矩阵 / 治理矩阵） | **403** | 保留具体码：`FORBIDDEN`、`FORBIDDEN_*`、`*_DENIED`（如 `JUDGE_ROLE_DENIED`、`GOV_DECISION_DENIED`）、`UNAUTHORIZED` | **统一为 403**：同一类"你无权做这件事"不得一半 400 一半 403（否则调用方只能硬编码码值分支）。判定规则见 `GlobalExceptionHandler.isAuthorizationDenial` |
| 输入/字段校验不通过（必填缺失、格式/范围/白名单、只读字段被写） | **400** | `VALIDATION_ERROR`，**message 必须指名字段**（如 `currency=XXX`、`name: 物料名称不能为空`） | 含框架层（`@Valid`、缺参）与域内字段守卫；`stdCost` 这类"PLM 只读字段被写"按输入错处理（显式拒绝，不静默忽略） |
| 业务规则/状态机违反（非法迁移、锁定态编辑、门未过、前置未满足） | **400** | `BIZ_ERROR` 或该规则专属码（`ITEM_LOCKED`、`REQ_LOCKED`、`PRECHECK_BLOCKED`、`SUPERSEDE_CYCLE` …） | **不得**并入 `VALIDATION_ERROR`：调用方须能区分"我传错了"与"业务上不允许" |
| 资源/路由不存在 | **404** | `NOT_FOUND` | 含未知路由（不得回落成 400 SERVER_ERROR） |

### G-API-1.2 列表分页契约

- `page` **0 基**（0 = 第一页）；
- `pageSize` 上限：`/_platform/lookup/**` = **50**，其余列表端点 = **100**；
- 超上限**不静默截断**：响应回实际生效的 `pageSize` 并置 `pageSizeCapped=true`；
- `size` 是 `pageSize` 的**别名**，显式提供时优先；
- 上限唯一权威常量：`com.plm.common.Paged.MAX_PAGE_SIZE`（lookup 域见 `LookupService.MAX_PAGE_SIZE`）；
  OpenAPI 文档由 `config/OpenApiConfig.java` 全局注入上述口径（`/v3/api-docs`）。

### G-API-1.3 处理记录（`GET /{domain}/{id}/history`）

返回 `[{ts, actor, action, diff}]`（按时间正序，来自 append-only 审计链 `t_audit_log`）：

- `diff` 为**变更载荷**对象：`{字段: {before, after}}`（也兼容 `{字段: 值}`）；
- 前端由 `components/HistorySection.tsx` 渲染为 `旧 → 新`，不再出现"只看得到谁改的、看不到改了什么"；
- 各域共用 `AuditService.findByObject`，**新增域不得另写一套历史端点**（否则载荷口径又会分叉）。

**验收锚点**：`plm-contract-paging-verify.cjs`（分页 + 校验码双向断言）、
`plm-perm-ipmt-rep-verify.cjs` C4（403 授权拒绝）、`plm-item-cost-verify.sh`（只读字段显式拒绝 + 留痕含 before/after）。
