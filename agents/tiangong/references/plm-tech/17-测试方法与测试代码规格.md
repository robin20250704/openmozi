# 17 · 产品级通用规格：测试方法与测试代码规格

> **本文回答一个问题**：「在这个产品上，测试该怎么写、怎么跑、怎么算通过」——把批次 1~27 里**真正付过代价**的测试经验
> 结晶成可判定条款（方法 M / 判据 A / 夹具 F / 代码规格 C / 效率 E），使新域、新批次、新人都能一次做对。
>
> **与既有文档的关系**（不重复、不覆盖）：
> - `13-工程门禁与数据对账机制`：**机制层**——分层 CI 入口、对账与例外基线、受控订正通道（"凭什么相信约束真的生效"）；
> - `14-交付完整性…通用 UI 纪律`：**交付层**——产物指纹门、交付判据 L1~L4、UI 走查三条纪律；
> - `16-性能保障规格`：**性能层**——SLO 汇总、性能原则与可判定要求、性能门禁；
> - **本文：测试层**——怎么写断言、怎么造夹具、测试代码长什么样、回归怎么跑得快而可信。
> - 本文所有条款均**不改变** 13/14/16 已定判据；冲突时以本文为准的只有"怎么写/怎么跑"，判据口径仍以各文档为准。

> 反例证据一律指向真实缺陷编号（`kb/negatives.md`）与文件，便于复查。

## 1. 测试体系总览：每层回答什么问题

| 层 | 回答的问题 | 入口 | 典型时长（批次27 实测） | 失败时的含义 |
| --- | --- | --- | --- | --- |
| **T1 静态** | 代码/类型/断言特征串/迁移编号是否自洽 | `plm-ci.sh` T1 | 21s | 编译不过、类型错、判据特征串失配、迁移编号冲突 |
| **T2 单测** | 逻辑与契约在**全新库**上是否成立 | `plm-ci.sh` T2（与 T3 并行） | 239s（222 项） | 逻辑错、SQL 错、改造不等价 |
| **T3 运行态** | **已部署**服务 + 真浏览器上，用户路径是否真的可用 | T3-1 批次 E / T3-2 批次 G / T3-3 走查 / T3-4 需求验收 / T3-5、T3-6 接口层 / **T3-7 性能冒烟** | 680s（12 个走查 395s） | 部署态缺陷（"本地能跑"不算） |
| **T4 巡检** | 数据与机制的**不变量**是否仍然成立（不针对某次改动） | `plm-ci.sh` T4-1~T4-9 | 68s | 存量腐化：审计链断裂、悬空引用、判据不可达、覆盖率缺口 |
| 交付后 | **目标用户**是否真的用得上 | 试点/走查 + 用户反馈 | — | 价值缺口（backlog 优先项） |

> **T-1 三层证据缺一不可**：构建态（能编译/单测过）→ 一致性（契约/约定/对账）→ **运行态（部署后的真实路径）**。
> "代码能跑"不构成交付；`构建成功` 与 `服务健康` 也不能替代"用户路径可用"。

## 2. 测试方法（T-M）

| # | 方法 | 要求（可判定） | 为什么（真实代价） |
| --- | --- | --- | --- |
| **T-M1** | **判据先行** | 动手改代码前，先把"什么算通过"写成可执行断言（规格里的验收断言）；断言不可执行 → 先补判据再开发 | 先写完再想判据 ⇒ 判据会被实现"带偏"（把已实现的行为当正确） |
| **T-M2** | **先红后绿** | 修缺陷必须先用一个**能复现的失败断言**抓住它，再改代码；改完该断言转绿并保留为回归 | 无复现断言的"修复"无法证明修好了（批次 26 曾出现"报过的问题又回来"） |
| **T-M3** | **反空转自检（selftest）** | 每个巡检/对账机制必须自带"注入必然失败"的自检路径，并断言注入**被报出**（`*_SELFTEST=PASS`） | 只输出 `PASS` 的检查可能是空转；T4-5/6/7/8/9 均以自检证明"能发现" |
| **T-M4** | **参照集反证** | 凡断言"过滤/筛选后不含某类行"，必须先证明**参照集里确有该类行**（否则判据恒真） | 过滤条件写错会得到"永远通过"的假绿 |
| **T-M5** | **等价性优先** | 性能/重构类改造必须断言"新旧路径输出**逐字段相等**"（批量 vs 逐条 vs 详情） | `ReviewListBatchEquivalenceTest` 当场抓出一处真实列名错误（`t_open_issue.review_id` 不存在） |
| **T-M6** | **成本断言** | 改造若声称"更省"，必须同时断言**成本指标**（扫描次数/读取行数/请求数），不能只断言结果相等 | 只断言相等 ⇒ 实现退化成"同样慢"也能通过 |
| **T-M7** | **真用户路径走查** | 关键路径必须用**真浏览器 + 真实身份（SSO）**跑通，禁止只用接口调用代替界面可用性 | "接口 200"掩盖过页面静默失败（批次 1~5 多起） |
| **T-M8** | **对账式测试** | 跨层事实（登记表 ↔ 库列 ↔ 代码读取点 ↔ 判据能力）用"对账"而非"抽样"验证：两侧全量比对 + 差异分类 + 零差异断言 | 抽样通过≠一致；T4 四类对账各抓到过真实缺口 |
| **T-M9** | **失败先分类** | 任何红/失败先分类：**环境类 / 代码类 / 数据类 / 未知**；同类连续 2 次换手段，第 3 次触发重审方案 | 混类重试会耗尽预算且掩盖真因（批次 9 静默重试近半） |
| **T-M10** | **分层定位** | 见到异常结果先分清四种状态：`没跑` / `没跑全` / `真红` / `跑全且绿`；不同状态结论完全不同 | 批次27 出现 `378s 看似优化成功` 实为"整层只在跑第一个套件" |

## 3. 判据纪律（T-A）：断言怎么写才算可信

| # | 条款 | 反例证据（真实发生） |
| --- | --- | --- |
| **T-A1** | **只认子套件自报的汇总行**（`PASS=n FAIL=n`）；退出码信号也必须计入 FAIL 计数 | 曾把"子套件整轮没跑"读成通过（`OK PASS=0 FAIL=0`） |
| **T-A2** | **未跑 ≠ 通过**：`MISSING` / `TIMEOUT` / `FAIL` 三者分别可见、分别计数 | 缺列会让"没跑"混进绿色 |
| **T-A3** | **崩溃 = 失败**：脚本异常退出也必须打印汇总行（不要静默消失） | 崩溃无输出 ⇒ 被读成 MISSING 甚至"没影响" |
| **T-A4** | **禁止把红改 skip**，禁止用 `2>/dev/null` 吞掉判据自身或前置错误 | 位置号 `ORDER BY 2` 报错被吞 ⇒ 分组统计"看起来没数据"（批次27，5 次） |
| **T-A5** | **断言必须盯被断言的对象本身**（`回显`≠`数据`；`页面有内容`≠`就是要测的内容`） | 走查曾以"URL 变了"当跳转成功 |
| **T-A6** | **前置显式化**：前置不成立必须**判失败**并说明（不得"跳过=通过"）；关键前置要**自证在位**。**数据依赖型断言写成双分支**：有数据 ⇒ 必须出现且形态正确；无数据 ⇒ 必须不出现（若"空即不渲染"是产品规则）；两支都要打印实际数据量，**取数失败（非 200/超时）判失败** | W7 脏行未注入却继续跑 ⇒ 验的是"没有脏行时的守卫"；W23 无条件要求"决策点待办"面板存在，而该面板数据来自探针残留、回收后必红（`N-2026-09-17-31`）；其探针初版缺 Bearer token 返回 401 却判"通过" |
| **T-A7** | **就绪用轮询等待**（条件成立即返回），禁止固定 `sleep` 当同步手段 | 固定 sleep 在负载下必出假红，在空载下必变慢 |
| **T-A8** | **交互后先确认目标就位再断言**；不稳定判据用**有限重试**收敛，不得靠放宽阈值 | 点行后立刻量详情 ⇒ 量到旧面板 |
| **T-A9** | **全局不变量在多探针共库时必须带时间窗口**：存量必须为 0 + 本次新增逐条打印 | 邻座探针的临时数据被当成本套件残留 |
| **T-A10** | **计数类判据给对照**：界面计数必须与**服务端 total** 对照（不是与"当前页条数"对照） | "共 N 条"若取本地数组长度，第 2 页起必错 |
| **T-A11** | **例外基线纪律**：例外必须**点名**放行（表+列+理由）；"基线里的项不再成立"也要判失败；**基线为空必须能跑** | 例外变永久豁免；`plm-ref-integrity.sh` 在基线被清空的**期望终态**上崩溃过 |
| **T-A12** | **判据可达性**：判据要求的能力必须真的可达（有路径/有账号/有数据）；不可达路径要能被自检报出 | 曾出现"判据要求签某维度，而该维度可签账号=0" |
| **T-A13** | **断言特征串自校验**：关键断言文本（needle）进 CI 校验，防止判据被改名/删除后静默失效 | `NEEDLE_CHECK PASS=28 FAIL=0`（T1-3） |
| **T-A14** | **计时/度量类判据只用单调、可归因的量**，且必须声明测量口径与环境（见 `16-性能保障规格` §8.5） | 并发窗口里测出的毫秒数不可同比 |
| **T-A15** | **错误出口契约唯一**：任何 4xx/5xx——**无论由 MVC 层还是 Servlet 过滤链产生**——都必须返回同一形状 `{code,message,ts}`；判据须**逐出口**验证（带凭据失败 / 不带凭据失败 / 非法媒体类型 / 未知路由），不得只验其中一个就宣布"错误契约已统一" | 批次28 实测：带 token 的 400 有结构化体，**不带 token 的 401 体为空**（认证失败发生在过滤链里，`@RestControllerAdvice` 够不着）⇒ 同一系统两种表示；调用方必须写两套解析，空体在自动化里还会被读成"服务端没响应" |
| **T-A16** | **状态码要承担语义**：客户端要据此做不同决策的情形必须给不同码（`415` 媒体类型不支持 / `405` 方法不支持 / `404` 路径寻址资源不存在 vs `400` 入参不合法）；把"改一下再试就能成"的失败一律压成 `400 SERVER_ERROR` 会诱导无意义重试 | 批次28 实测：`Content-Type: text/plain` 与**不带 Content-Type** 都返回 `400 SERVER_ERROR: Content-Type … is not supported`——调用方只会怀疑服务端，而真实处置是"改用 application/json" |
| **T-A17** | **写路径的请求级记忆必须同批失效**：任何"本请求内先读、后又写同一张表"的代码，写完**必须**失效该键（`RequestCache.invalidatePrefix`），且判据要在**同一请求内**复现"先读→写→再读"（前置读是必须的，否则用例是碰巧通过） | 批次28 REQ-2026-2050：批次27 的列表批量预取把 `t_review_signer` 记住了，合并签署插行后同请求再读命中**写前空表** ⇒ `400 SIGNER_REQUIRED` 并把签署行与留痕审计**一起回滚**；两步路径（两个请求）因此不受影响 ⇒ 只有"同请求内先读"的用例能测出来（`L-417`） |
| **T-A18** | **词表只有一个事实源**：枚举/受控值域的权威是 `t_attr_template.enum_values`，服务层与前端都**读**它；出现第二份清单（Java 常量 / TS 常量 / 文档表格）即判缺陷——判据要断言"新增登记值无需改代码即可写入"，以及"拒绝文案里的合法值清单来自元数据" | 批次28 REQ-2026-2049/2112/2115：`source_channel` 四值在 Java 里硬编码两处、`dfxDimension`/`verifyMethod` 在前端硬编码——登记新值后调用方按报错补值仍被拒，报错文案本身也是过期的 |

## 5. 测试代码规格（T-C）：文件长什么样才算合格

| # | 条款 | 规格（可判定） |
| --- | --- | --- |
| **T-C1** | **清单登记** | 每个运行态套件在 `ipd/deploy/wsl/plm-app/plm-suites.tsv` 登记一行（id / tier / kind / timeout_s / script / desc）；**禁止**在 CI 脚本里再写第二份清单 |
| **T-C2** | **汇总行** | 必须打印唯一可解析汇总行：`==== <MARKER> PASS=n FAIL=n ====`（`MARKER` 全局唯一）；CI 只认它 |
| **T-C3** | **超时** | 每个套件有显式超时（清单 `timeout_s`，由 `plm-run.sh` 用 `timeout` 包住）；**超时 ≠ 失败 ≠ 通过**，三者分别计数 |
| **T-C4** | **证据锚点** | 每条断言随行输出**判据用到的原始值**（如 `http=200 total=391 pages=4`），不要求人回看日志才能判断 |
| **T-C5** | **共享库复用** | 浏览器/API/断言/夹具一律用共享库 `plm-harness/plm-browser.cjs`、`plm-suite.cjs`；**禁止**每个套件自带一套浏览器管道 |
| **T-C6** | **调用必带超时** | 所有跨进程调用（CDP 消息、HTTP、`docker exec`）必须有单次超时；浏览器锁必须**自愈**（陈旧锁按 pid/锁龄清理） |
| **T-C7** | **SQL 调用纪律** | `psql` 一律 `-v ON_ERROR_STOP=1 -P pager=off -A` 并**显式指定字段分隔符**（统一用竖线分隔，便于 `cut`/`awk` 取值）；读单值用 `-t` 并 trim；**不得**用 `2>/dev/null` 掩盖 SQL 错误（除非是已确认的噪声并写明理由） |
| **T-C8** | **SQL 写法** | 拼接列的查询一律用**列别名**排序（禁用位置号 `ORDER BY 2`）；关键统计输出必须显式断言非空 |
| **T-C9** | **夹具取值** | 枚举/受约束字段的取值**先查库约束**（`pg_constraint` 的 CHECK 定义）再使用，不凭业务语感造值 |
| **T-C10** | **生成物复核** | 脚本生成的清单/README/报告按**不可信输入**复核字节：重点查 **0 字节文件**（=重定向建文件的指纹）与漏项；生成文本**不要用反引号做装饰**（双引号里会触发命令替换） |
| **T-C11** | **一次性脚本处置** | 归档不删除：`ipd/deploy/wsl/_one-off-archive/<日期>/`，保持相对路径 + `README.md` 记判据与恢复方法；彻底删除由用户决定 |
| **T-C12** | **可达性台账** | 维护"CI 可达（清单内）"与"零引用（可归档）"两类台账；判据 = 不在清单 + 全仓零外部引用（含文档）+ 无 PASS/FAIL 汇总行；**有汇总行但零引用** ⇒ 应登记进清单，而不是归档 |
| **T-C13** | **同一入口** | 本地与 CI 跑**同一个** bash 入口（`plm-ci.sh` / `plm-run.sh`），禁止两套编排；"本地过了"必须与"CI 过了"同义 |
| **T-C14** | **不吞 stdin** | 清单驱动/`while read` 循环里的子进程必须显式接 `< /dev/null`（否则子套件会把清单剩余行吃光，表现为"整层只剩第一个套件在跑"，且退出码 0） |

## 6. 效率工程（T-E）：本次回归 16:50 → 12:53 的做法

## 6bis. 回归时点与范围规格（T-R，批次29 建立）

> 用户 2026-09-18 裁定口径："回归时点，可能不需要每批次，每批次增量测试，相关性功能抽查回归；
> **一次任务若干批次全完成后，做一次回归即可**。"
> 本节把这个口径变成**可执行**的东西：只写在文档里的口径 ≠ 被执行的口径（L-387③ 的原话）。

### 6bis.1 三个时点，各自的"应跑范围"由什么决定

| 时点 | 何时 | 应跑范围 | 成本（基线） | 判据强度 |
| --- | --- | --- | --- | --- |
| **P1 批次内（增量）** | 开发/回炉过程中，每次改完 | `T1` 全跑 ＋ **本次改动域**的套件（`--domain`）＋ 与本批改动**共享机制**的域抽查 | 实测 1m17s（前端登录层改动，见 §6bis.7） | 与全量**同一条断言**，不降级 |
| **P2 域抽查** | 改动触及跨域机制时（记忆/缓存/审计/元数据/索引/流程引擎/权限） | 该机制的所有消费者域套件 | 1~3 分钟 | 同上 |
| **P3 收尾全量** | **一次任务的若干批次全部完成后**（或发布/合并前） | `T1 T2 T3 T4` **全部套件**，`CI_RESULT=PASS` 且 MISSING=0 | 见 §6 与 T-E1 | 同上 |

**硬约束（不可协商的三条）**：

1. **P3 是交付前提**：P1/P2 绿**不等于**交付；"一次任务全批次完成后跑一次全量"是**唯一**能声明"本任务交付"的时点。
   P1/P2 的结论只能写成"**改动域已验**"，不得写成"回归通过"（口径区分，同 T-M10 的四态）。
2. **批次内不许"因为跑得少就放宽断言"**：P1/P2 跑的是**同一条判据**（同一个套件、同一份断言），
   唯一被裁掉的是"**与本批无关的套件**"。禁止为了快而在批次内用"精简版断言"——那是**另一套判据**，不是同一件事的加速。
3. **越过 P3 的情形必须显式登记**：SLA 硬上限等极端情况下跳过 P3 交付 → 必须在交付摘要里写
   「未跑全量 + 未跑清单 + 风险」并报用户确认（"未跑 ≠ 通过"，这里适用同一纪律）。

### 6bis.2 范围不能靠人记：从 git diff 自动推导（T-R4）

- `plm-suites.tsv` 新增 **`domains` 列**（域标签，多值用 `,`）：套件 ↔ 受测域的**唯一权威映射**；
- `plm-ci.sh --changed <base>` / `plm-run.sh --domain <域[,域]>`：由改动路径 → 域 → 套件，
  **不靠人回忆"我这次动了哪些地方"**（人记的范围 = 必然漏，同 L-321/T-E3 的机制化思路）；
- 新增套件时 `domains` 未填 ⇒ **T1 静态层判红**（清单不完整本身就是缺陷，而不是"以后补"）。

### 6bis.3 并行提速：**逻辑不相交还不够，必须实测物理资源**（T-R5，批次29 实测修正）

T-E2 已确立"并行只按资源不相交"。批次29 把这条原则推到**套件间**，并**被实测打回来一次**——
这条修正比原来的设想重要，故完整记录。

**设想（当时看起来无懈可击）**：T3-3 十二套走查实测 `套件墙钟合计 393s ≈ 该层实际墙钟 395s`
（**零重叠、完全串行**），其中 8 套（前 8 名共 391s）**全程只走 HTTP API**、夹具各按自有前缀自建自清、
互不写对方数据 ⇒ "逻辑上不相交"，于是按每端口一个 Chrome（`PLM_CDP_PORT` + **端口专属锁**）并行。

**实测（同机同期，8 个套件；单跑基线 = 各套件耗时之和 324s，全绿）**：

| 并发窗口 | 槽墙钟 | 结果 | 单套件相对单跑 |
| --- | --- | --- | --- |
| 8（同时启动） | 195s | **FAIL=24、TIMEOUT=1**（3 套红） | 慢 2~6 倍 |
| 3（间隔 2.5s） | 215s | 1 套 FAIL(1) + 1 套拿不到锁（rc=5） | W21 慢 1.6 倍 |
| 2（间隔 5s） | **335s** | 2 套红（共 6 条 FAIL） | W21 慢 2.2 倍、W23 慢 2.4 倍 |
| **串行（基线）** | **324s** | **全绿** | 1.00（基准） |

**根因**：8 套**逻辑上确实不相交**，但**物理上争同一台机器的 CPU/内存**（16 核 / 15G；
同开 4 个 Chrome + React/AG Grid 首屏即压满）⇒ SPA 就绪变慢 ⇒ 走查里"轮询到条件成立"的等待**触顶**
⇒ **断言打在未就绪的 DOM 上 ⇒ 假红**。单跑复验（`W14` 在新端口上 `PASS=48 FAIL=0`、97.5s，与基线一致）
已排除"端口改造引入缺陷"这一解释。

**结论（写进口径，不只是写进日志）**：

1. **判"能不能并行"的唯一依据是实测**："资源不相交"必须落到**物理资源**（CPU/内存/单实例服务/浏览器），
   停在"逻辑上互不干扰"是**不充分的**。这是 T-E2 那条原则的边界条件。
2. **并行在重资源上收益可能为负，且代价是假红**。**假红比慢更贵**——门禁最贵的属性是"红了就是真红"；
   一次 3 套假红就足以让人开始怀疑整个门禁（"是不是机器的问题"），而门禁一旦被怀疑就失去意义。
3. 故：`plm-suites-par.tsv`（分组登记表，含"凭什么不打架"的 `why` 列）与 `plm-par-run.sh`（支持
   `--slots` 窗口 / `--stagger` 启动间隔）**保留**，但 **`plm-ci.sh` 默认不启用**（须显式 `CI_PAR_WALK=1`），
   且启用前提是**先实测单套件耗时 ≤ 单跑基线的 1.5 倍**（超过即视为不可接受）。
   **批次30 用户裁定：并行代码保留、默认关——维持本条不变。**
4. **并行不得掩盖失败**：驱动与运行器产出**格式完全相同**的 `SUITE|id|状态|PASS/FAIL|耗时ms` 行，
   "取不到汇总行 = MISSING、超时单列"，"套件数 + 断言总数"必须与串行基线逐项对得上（T-E4）；
   并行时**逐套件完整日志按文件保留**（`/tmp/plm-par-last/<id>.log`）——截尾打印在并行下更不够用（L-424）。

> 由此得到的下一层方向：T3-3 的 395s 里**绝大部分是套件内部的固定等待**（导航后 `await wait(3500~6500)` 等），
> 而非计算或传输。要把这一层真正压下来，得逐条把"固定 sleep"换成"**轮询到被断言的那个对象就绪**"，
> 而不是靠堆并发。这条列为下一批的专项（本批不动，避免把"提速"做进判据本身）。

### 6bis.4 计时必须常驻（T-R6）

"整轮 21m28s"这种单条读数**不足以支撑任何优化决策**（说不出贵在哪，也就无法判断省下的是不是时间）。
故计时进入常驻输出，而不是临时脚本：

| 读数 | 位置 | 回答什么 |
| --- | --- | --- |
| **逐套件耗时** | `plm-run.sh` 的 `SUITE\|id\|状态\|PASS/FAIL\|耗时ms` 第 5 列 | 谁贵 |
| **耗时 TOP** | 同上汇总段（前 8 名 + 套件墙钟合计） | 总时长由谁决定 |
| **逐层墙钟** | `plm-ci.sh` 末尾「逐层墙钟」表 | 哪一层值得动、并行重叠了多少 |

**读法纪律**：① 套件墙钟合计 **≈** 该层墙钟 ⇒ 完全串行（并行的收益上限就在这个差值里）；
② 两者差值大 ⇒ 已有并行，**不要再叠加并行度**；③ 改前改后必须**同机器同期**对比
（负载会变：同一套件在同日不同时段实测相差 ±50%，见 T-R7）。

### 6bis.5 死锁与不合理等待（T-R7，批次29 普查 → 批次30 全部处置完毕）

| 项 | 现场 | 处置（批次30 落地） |
| --- | --- | --- |
| **忙等自旋** | 5 套走查的 `acquireLock` 用 `while (Date.now() - t0 < 1000) {}` 占满事件循环 1 秒 | **已修**：8 套全部迁移到共享库 `plm-harness/plm-browser.cjs`（Atomics.wait 真睡眠）；本地副本全删（L-389① 收口：修在一处） |
| **每次等待起一个进程** | 3 套用 `powershell -NoProfile -Command Start-Sleep -Milliseconds 500` 做重试间隔 | **已修**：随迁移消失（共享锁等待为进程内 Atomics.wait，grep 已验证零残留 `Start-Sleep`） |
| **陈旧锁自愈只在 Windows 上部分成立** | `process.kill(pid,0)` 在 Windows 上对已退出的 PID 不抛 ESRCH ⇒ "持有者已死"路径不生效，只剩锁龄兜底 | **已修**：共享库 `pidAlive()`——kill(0) 未抛时用 `tasklist /FI "PID eq N"` 复核（结果缓存 3s）；锁随端口走（`plm-ui-verify-<port>.lock`）+ 20min 锁龄兜底保留 |
| **固定 sleep 与"轮询到条件"混用** | 走查里大量 `await wait(3500~6500)`，最贵一族是"导航后等固定毫秒" | **已修**：8 套共 40+ 处固定等待改为条件轮询（`gotoReady`/`until`/`untilH`），确无锚点的防抖等待保留并注明"纯计时器"；T3-3 层 395s → ~145s（逐套件对照见 `plm-regression-timing.md` 批次30 节） |

> 纪律：**"等得更久"不是修法，"等得对"才是**。固定 sleep 改轮询的判据是——锚点必须是**被断言的对象本身**
> （T-A 已定：不能拿输入框回显当"数据已刷新"的就绪信号）。批次30 补充：**锚点错有三种形态，都必须用"断言要读的字节"当锚**——
> ① 元素根本不存在（等一个永不到来的文本）；② 先出后到（工具栏计数先更新、网格行数据/空态块后换）；
> ③ 内容未换（页码=2 ≠ 首行已换，"单元格非空"≠"已是新数据"）。

### 6bis.6 走查管道唯一实现（T-R8，批次30 建立）

**契约**：真浏览器走查的浏览器管道——锁、Chrome 启动/复用、CDP 客户端（带 20s 超时）、轮询原语、登录、网络捕获——**唯一实现在 `plm-harness/plm-browser.cjs`**；套件文件只保留「断言」与「本域交互范式」。新增走查**禁止**再复制管道（复制 = 把批次23/24 的事故形态请回来）。这与 T-C5"共享库复用"的区别：T-C5 说"要用"，T-R8 说"**只有这一份，别处写的即缺陷**"。

| 能力 | 共享库 API | 替代了什么 |
| --- | --- | --- |
| 端口域互斥锁 + 陈旧锁自愈 | `acquireLock({port,timeoutMs})` / `releaseLock(port)` / `pidAlive()` | 8 份本地锁副本（忙等/powershell/Windows 失效自愈各不同） |
| Chrome 复用/启动 | `ensureChrome({port,startUrl})` | 各套件自己的 ensureChrome（profile/窗口尺寸各异） |
| CDP 会话 | `connect({port})` → `send/ev/wait/until/goto/untilH/settled/gotoReady` | 各套件的 WebSocket 客户端与 wait/ev/until |
| 导航就绪 | `gotoReady(url)` = frameNavigated → readyState → **网络静默**（悬置请求 >10s 回收） | 「navigate + 固定 sleep 3~8s」 |
| 登录 | `login(user)`（登出→Keycloak 真实登录；返回 = **plm_user 与 oidc access_token 都已落库**） | 各套件登录变体（含"已登录就跳过"的隐式依赖） |
| 网络捕获 | `s.net.requests/{url,method,auth}`、`s.net.responses/{url,status,cd,ar,cl}`、`s.pending` 诊断 | 各套件自挂 Network 事件 |
| 可观测性 | `PLM_HARNESS_DEBUG=1`：login 分步计时、gotoReady/settled 逐次耗时、悬置请求 URL | 出问题靠猜 |

> 批次30 实证的三条教训（详见 lessons L-425~L-427）：① 下载型导航与 AbortController 中止都**不会**发 `loadingFinished`
> （CDP 缺口）——在途计数必须带"响应头到达即出列 + 悬置回收"，否则每次 settled 烧满上限（实测 97s → 180s 的反优化）；
> ② "登录完成"的判据是 **plm_user 与 oidc token 都落库**——只看 plm_user 会让页内 fetch 助手把"无 Authorization"
> 的请求头**缓存**住，之后全程 401；③ 委派转写的字符串常量（页内 fetch 助手这类多行拼接）必须逐字节 diff 审查——
> 一个多余的 `}` 让整个助手静默变成 SyntaxError（`ev` 返回 undefined，断言全红且无报错）。

### 6bis.7 影响面粒度：**粗域会逼人绕过门禁**（T-R9，批次39 实测建立）

> 用户 2026-09-20 追问原话："**为什么一个微小的登录页面改动要跑半小时 CI 回归？**"
> 答案不是"门禁太重"，而是**入口用错 + 域粒度太粗**：那次跑的是 **P3 收尾全量**
> （T1＋T2 全量单测＋T3 全部 39 套件＋T4 巡检，实测墙钟 **728s**，其中 16 个前端走查串行占大头），
> 而这次的改动只落在"登录/会话"这一层。更糟的是：**旧口径里 `frontend/**` 只映射到粗域 `FE`**
> ⇒ 哪怕正确使用 P1 入口，也仍然要跑 **17 个套件（套件墙钟合计 212.6s）**，
> 其中 13 个与登录层毫无关系。**"相关性抽查"退化成"前端全抽查"，人就又开始绕过门禁**——
> 与 §6bis.5 的假红是同一条道理：门槛一旦显得不合理，纪律就会先死。

批次39 落地的四件事（每条都有实测支撑）：

| # | 改动 | 为什么这么做 | 实测效果 |
| --- | --- | --- | --- |
| 1 | **前端域细分**：`FE-AUTH`（`src/auth/**`、`main.tsx` 的鉴权入口、运行时开关）与 `FE-SHELL`（`main.tsx`、全局样式）；**命中子域的文件不再按粗域 FE 展开** | 让范围与**真实影响面**对齐；`FE` 仍是兜底粗域（未命中子域的 `frontend/**` 照旧全查，覆盖面不缩小） | 同一个改动：FE 17 套 → **FE-AUTH 4 套 + FE-SHELL 2 套** |

## 10. 派生索引一致性（T-I）：从"幽灵文档"到可复算的判据

**背景（批次27 缺陷 D3）**：清理测试数据后，PG 侧检索索引重建为 1731 行，而 ES 侧仍有 **3345** 条，
其中包含**已被删除的项目/产品**——`GET /_platform/search?q=…` 照样把它们返回给用户（搜得到、点进去 404）。
根因是 `SearchIndexer.rebuild()` **只 upsert 不删除**：派生数据的"重建"不收敛；且旧口径只在"索引为空"时才回填
⇒ 连重启也修不好（恰恰是最需要自愈的场景）。

| # | 条款 | 判定方式 |
| --- | --- | --- |
| **T-I1** | 派生数据（检索索引/投影/聚合/缓存）必须**可重建且重建收敛**：重建 = upsert 事实源现存 **+ 删除两侧已消失的**；**只做 upsert 的重建不算重建** | 代码 + 运行态：`POST /_platform/search/reindex` 返回 `{indexed, deletedPg, deletedEs, remaining}`；启动回填改走同一收敛路径 |
| **T-I2** | 收敛必须有**只读巡检判据**：逐域 `ES 计数 == t_search_index 计数`；ES 不可达即 FAIL（未取到 ≠ 通过） | `plm-index-consistency.cjs`（CI **T4-10**）+ 应用侧 `GET /_platform/search/index-consistency` |
| **T-I3** | 巡检必须**自带注入自检**：向 ES 注入一条无事实源的幽灵文档 → 判据必须报 FAIL → 清除注入项（自检不得留污染） | `node plm-index-consistency.cjs --selftest` → `INDEX_CONSISTENCY_SELFTEST=PASS` |
| **T-I4** | 巡检**只读**：不得"顺手修一下再报通过"（那是自证）；收敛责任在应用侧（启动回填 / 维护端点） | 脚本无写库路径；唯一写入是自检注入，并在同一次执行内清除 + 复核恢复一致 |
| **T-I6** | **"能发现"与"能清掉"必须分别有判据**：注入类判据只证明发现能力；清除能力必须另做**制造→再收敛**闭环（建行→索引→只删库行→再重建→文档消失且计数回基线） | `plm-convergence-verify.cjs`（CI **T3-10**）：`PERF_CONVERGENCE=PASS`，`deletedEs≥1` 可核 |
| **T-I7** | 枚举派生数据的全量键时，**禁用排序/深分页形态**（本环境 ES 拒绝按 `_id` 排序与聚合）；term 查询一律用**长写** `{"term":{"field":{"value":v}}}`（短写在本项目客户端被判 `parsing_exception`） | `EsClient.allObjectIds`（terms 聚合 `obj_id`）+ 统一 `objTypeTerm`；两个坑都登记 `N-2026-09-17-38` / `L-414` / `L-416` |
| **T-I5** | 移植规则：凡"两处保存同一事实"（PG 与 ES、快照与主表、缓存与源）都要有这种**逐域计数 + 自检注入**的对账项 | T4 层巡检项清单：数据不变量 / 库口径 / 逻辑引用 / 判据可达性 / 审计链 / **派生索引一致性** |
