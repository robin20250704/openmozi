# 02b · 表格前端业界实践调研与落地建议

> 定位：对 ADR-7「AG Grid + Univer + glide-data-grid」的**业界成熟做法**做一次对照调研，回答「同样功能业界是怎么做的、我们能少写多少代码」，并把结论逐一映射到 PLM Grid Adapter 的六个能力。
> 输入：`02-datagrid与电子表格方案.md`（架构/性能基准）、`docs/plm-design/05-技术架构设计.md` §6.2。
> 读者：实现 Grid Adapter 的 subagent —— 按本文档「落地要点」即可交付，不必再翻 AG Grid 官方手册。
> 调研日期：2026-09（基于 AG Grid Community 32.x / Univer 0.4.x / glide-data-grid 4.x）。

## 0. 一句话结论

表格前端业界没有「一个组件搞定一切」；成熟做法是**「网格渲染」与「业务判定」彻底分离**：网格只负责按需渲染 + 回传单元格变更，**列定义、可编辑性、单元格值、撤销/提交、粘贴、diff 全部由业务层（即 PLM Grid Adapter + 后端）驱动**。我们自研的封装层主要价值不在「封装 API」，而在「把业务规则收敛到六类可测函数」。

下面按「先选型、再逐能力给业界做法 + 落地要点」组织。

## 2. 编辑与数据绑定（业界第一坑，本项目已踩 L-079/L-075）

### 2.1 铁律：不要在 `onCellValueChanged` 里 `setRowData(全量)`

业界共识：编辑回调里拿到的是「单格变化」，只应**精确更新那一行**，绝不可全量替换 `rowData` 触发整表重渲（慢、且会打断正在进行的客户端编辑）。

- **正确** → `gridApi.applyTransaction({ update: [rowNode.data] })`（只重渲该行）。
- **错误** → `setState({ rowData: [...rowData] })`。

> 本项目教训 L-079：`axios.then(setState)` 传的是响应对象而非 `.data`，导致 `editableStatuses` 成非数组、面板恒锁。根因是「把 onChange 里拿到的值直接当整个状态」。

### 2.2 immutable 数据（Redux/Zustand）时用 `valueGetter`/`valueSetter`

若 store 用不可变更新，grid 不能直接改 `rowData`。业界做法：用 `valueSetter` 拦截写入、`valueGetter` 生成显示值，把「显示层」与「store 层」解耦：

```typescript
{
  field: 'qty',
  valueGetter: p => p.data.attrs.qty,        // 显示
  valueSetter: p => { dispatch(updateAttr({ id: p.data.id, attr: 'qty', value: p.newValue })); return true; },
}
```

### 2.3 `getRowId` 必须在所有网格提供

AG Grid 树/编辑/事务全靠 `getRowId` 区分行。缺它 `applyTransaction` 无法定位行，还会产生重复 key。

```typescript
<AgGridReact getRowId={p => p.data.logicalId} ... />
```

### 2.4 提交时机：编辑即暂存，保存才 flush

业界（Notion/Sheets/Linear）统一：**单元格编辑进「本地暂存栈」，不立即写库；用户点「保存」才批量提交**。这与本项目「乐观批量提交 + 撤销栈」（02 文档 §3.3）一致，且天然支持 Ctrl+Z 逐格撤销。

```typescript
const draft = useRef<Map<string, CellMutation>>(new Map());  // key = cell coord
onCellValueChanged: e => draft.current.set(coord(e), mut(e.value));
onSave:   () => commitBatch(draft.current)   // 单事务
onUndo:   () => { const last = pop(draft); gridApi.applyTransaction({ update: revert(last) }); }
```

## 3. SSRM + 编辑的坑

SSRM 下**没有整表 rowData**，编辑后刷新必须用**局部`applyTransaction`**或**`refreshServerSide`**，不能用 `setRowData`。

```typescript
// 编辑第 N 块的一行
api.refreshServerSide({ route: [], purge: false });      // 按当前块增量
// 或直接
api.applyTransaction({ update: [editedRow] });
```

> 官方要点：SSRM 的 `refreshServerSide({route, purge})` 只刷新指定区块；编辑单格用 transaction 即可，避免整个 serverSide 重拉。

- **sort/filter 交互**：SSRM 的排序/过滤全部转发给服务端 datasource，前端不缓存排序。
- **编辑回调里取 e.data** 仍是当行原始数据；改完记得 `valueSetter`/`applyTransaction` 双管齐下，否则 grid 显示与 store 不同步。

## 4. 单元格级可编辑性判定（Grid Adapter Layer 2 落地）

业界做法：AG Grid 的 `editable` 给**函数或按列布尔**即达，无需自己判断：

```typescript
const colDef = {
  field,
  editable: (p) => canEditCell(p.data, field, role, status, ctx),  // 复用 02 §2.3
  cellEditor: mapEditor(attr.data_type),
  cellRenderer: attr.is_key ? KeyCellRenderer : undefined,
};
```

要点：
- `editable` 函数按「当前行数据 + 列」判定，天然覆盖「已发布行灰锁」「ECO 实施中仅受影响对象可编辑」「机密属性脱敏」。
- 服务端为最终判定（BR-18/BR-01），前端锁定只是 UX；写接口仍做守卫。
- **不要**为不同行渲染不同列定义（会触发整表 rebuild）——`editable` 回调才是按行锁定的正确方式。

## 5. 元数据驱动列 buildColDefs（Layer 1 落地）

`02` 文档 §2.2 的 `buildColDefs` 已正确。业界补充三点：

1. **用 React 组件做 cellEditor/cellRenderer**（`type: 'reactComponent'`），不要返回 HTML 字符串——本项目 L-075 正是 raw-HTML cellRenderer 被转义。统一用 valueFormatter + cellStyle 表达样式。
2. **动态列变更 → 用 `columnApi.getColumnState()` 保留用户调整的列宽/顺序**，重新 setColumnDefs 不要丢用户态。
3. **列多时给 `flex`/`minWidth` + 横向滚动**；必要时 `suppressHorizontalScroll` 关闭 + 虚拟列。

## 6. Excel 粘贴管道（Layer 3 落地，能力 4）

业界三种做法，按成本排序：

| 方案 | 做法 | 成本 | 适用 |
|---|---|---|---|
| A | AG Grid **内建 clipboard**（默认支持 Ctrl+C/V） | 0 | 同构粘贴（结构一致的 TSV） |
| B | 接管 **剪贴板事件 + 自定义解析** | 中 | 需「列映射预览 / 拒绝原因 / 走服务端校验」 |
| C | **SheetJS** 解析 Excel 文件（.xlsx 上传） | 中高 | 从文件导入而非剪贴板 |

本项目需「映射预览 + 差异预览 + 服务端单通道校验」（02 §2.4），**选方案 B**：

```typescript
const onProcessCellFromClipboard = (params) => {
  // AG Grid 粘贴时会回调，返回 null 阻止默认
  const rows = parseClipboardTSV(params.clipboardData);
  queuePreview(rows);        // → 列映射预览对话框
  return null;               // 不立即写入，走预览→校验→确认→bulk-commit
};
```

**关键纪律（02 §2.4 不变）**：管道只做预览与解析，最终一律 `POST /bulk-commit` 走正规写入管道（规则/校验/状态守卫/审计全在服务端）。粘贴不是后门。

## 7. 乐观批量提交 + 错误回滚（写路径纪律）

> 来源：业界 skill `frontend-optimistic-mutations`（写路径五拍纪律）+ `subagent-orchestrator`（错误恢复协议）。
> **技术栈对齐**：本项目**不用** TanStack Query / RTK Query / SWR——数据在 **AG Grid 行模型 + 本地暂存栈（draft Map / DetailPanel.draft）**，提交走 axios。所以下方把业界纪律映射到「行模型」形态，**不照抄** `queryClient.setQueryData` 代码。若未来迁移 TanStack Query，§7.4 给出映射。

### 7.1 五拍写路径（不可变纪律）

业界把所有写操作收敛为**固定五拍**，少一拍就破坏正确性：

```
(1) cancel  → 取消在途读取，避免晚到的响应覆盖乐观态
(2) snapshot→ 快照所有受影响的行/对象（回滚的唯一合法来源）
(3) patch   → 立即改本地（UI 跟手）
(4) rollback→ 失败时按 (2) 快照原样回滚（绝非"重新推导"）
(5) settle  → 成功或失败都失效重查，让服务端字段（时间戳/总数/版本）复位权威
```

> 对应本项目：**save/commit 前** `applyTransaction`/`cancelQueries` 等价 ← (1)；**提交前记录每行原值** ← (2)；**失败** `applyTransaction` 回滚 + 标注错误行 ← (4)；**提交后** `refresh` 网格 ← (5)。

### 7.2 什么时候能乐观，什么时候不能（业界决策表）

| 场景 | 策略 |
|---|---|
| 高置信、低冲突写（切换状态、改数量、批量受控字段） | **乐观**——立即 patch，出错回滚 |
| 创建且返回服务端生成的 id/编号/总数 | **pending**，用服务端响应 `setQueryData` 入缓存；乐观行可选，成功后调和对账 |
| 破坏性/难回滚写（删除级联、派生重算、签名/发布） | **先确认**再乐观或 pending，绝不静默乐观 |
| 结果用户当前看不到（后台任务） | **pending + toast**，完成后失效重查，不做乐观 patch |

> 本项目打样：需求/项目「改状态」= 高置信写 → **乐观**；「创建需求/项目」= 返回服务端编号 REQ-2026-NNNN → **pending**（先用服务端返回的正式编号，不靠本地假编号，因为编号是受控发号）；「提交/发布签发」= **先确认**（触发签名/流转，不可静默）。

### 7.3 本地实现形态（无 TanStack，AG Grid 行模型）/ 现有代码对齐

> **实际落地代码**：`ipd/plm-app/frontend/src/plm-grid/commit.ts`（`batchWithOptimistic` / `saveWithOptimistic` / `makeIdempotencyKey` / `installIdempotency` / `buildMutation`）。下方示意与之一致。

**① 批量网格（RequirementsPage / ProjectsPage 的 grid）——乐观改行（`batchWithOptimistic`）**
```typescript
// 每个受影响行：快照(Map) + 乐观落地(applyRow) + 失败回滚(restoreRow) + 成功复位(onSettle)
await batchWithOptimistic<Requirement>({
  idempotencyKey: idemRef.current,               // intent-time 生成一次
  snapshotProvider: (key) => items.find(x => String(x.id) === key),
  mutations: [mut],                               // buildMutation 产出的 {_rowKey, field: value}
  mutate: async (ms, idem) => {
    const patch = pick(ms[0], ['title']);        // 仅提交改变字段
    const r = await api.put(`/requirements/${ms[0]._rowKey}`, patch, { idempotencyKey: idem } as any);
    return [r.data];
  },
  applyRow:   (key, patched) => setItems(prev => prev.map(x => String(x.id) === key ? (patched as any) : x)),  // (3) patch
  restoreRow: (key, snap)    => setItems(prev => prev.map(x => String(x.id) === key ? snap : x)),             // (4) 原样回滚
  onSettle:   () => { setSelected(null); load(); },   // (5) 复位服务端权威字段
});
```
> 五拍落地：`cancel`(opts.cancel) → `snapshotProvider`(2) → `applyRow`(3) → `mutate` 失败 catch 内 `restoreRow`(4) → `onSettle`(5)。
> 注意：①网格须配 `getRowId`（`<AgGridReact getRowId={p => String(p.data.id)} />`）；②`mutate` 须把 `idempotencyKey` 透传到请求 config（`{ idempotencyKey } as any`），`installIdempotency(api)` 拦截器自动落 `Idempotency-Key` 头。

**② 单对象面板（DetailPanel）——`saveWithOptimistic`（已落地）**
`DetailPanel.submit` 用 `saveWithOptimistic({ snapshot: record, changes, idempotencyKey: entryRef.current.key, mutate: async (chg)=>{await onSave(chg);}, apply, restore: (snap)=>setDraft({...snap}), onSettle: ()=>setDirty({}) })`。
五拍映射：`snapshot`(2)/`apply`(3)/catch `restore`(4)/`onSettle`(5)；`entryRef` 加 `entrySnapshot` 保底——对象身份（reqCode/prjCode+version）变化时重置快照+幂等键，失败恢复**不依赖**父级 `record`（§7.3 指出的缺失已补）。
> ⚠️ 关键契约：`onSave` 须「失败 rethrow」，否则 `mutate` 永不进 catch 拍、回滚失效 —— 首版页面 catch 吞错导致此坑（tsc 不捕获，需人工核对；见 L-081）。

### 7.4 幂等键（安全重试的关键）

- 键在**表单初始化/首次意图**时生成一次（`useMemo(() => crypto.randomUUID(), [])`），随每次重试**原样重放**；绝不能在 `mutationFn` 内生成（会每重试变一个 → 失去幂等）。
- 客户端把键放进请求头（如 `Idempotency-Key`）；服务端在窗口内命中重复键就**重放原响应**，不重复执行。
- 配 `disabled-while-pending` 防用户二次触发。

> 本项目已具备发号/唯一约束，bulk-commit 与签名接口用 Idempotency-Key 抬升到「幂等写」纪律。

### 7.5 重试策略

| 类别 | 策略 |
|---|---|
| 读 | 默认退避重试多次（幂等、安全） |
| **写（非幂等）** | **不自动重试**；仅当幂等键保证重放，或仅网络错误(HTTP 0)时重试 ≤1 次；**4xx 不重试** |
| 409/冲突 | **不重试**——浮现类型化错误 + 失效刷新，让用户基于新数据重决策 |

```typescript
// axios 写拦截：仅网络错误、限 1 次
api.interceptors.request.use(async (cfg) => { /* 幂等键注入 */ });
```

### 7.6 撤销/重做（Command 模式）

- AG Grid **无内建 undo**；用 Command 模式 + `applyTransaction` 反向回滚，与快照栈共用同一份 `snapshots`（§7.3）。`undo` → 弹回 `snapshots` 末项并更新网格。
- glide-data-grid 内建 undo——它的大数据场景直接用内建。
- 红线/粘贴预览复用同一 `snapshots` 结构（单元格坐标 + 原值）→ 见 §8。

### 7.7 若未来引入 TanStack Query（映射，非现状）

| 五拍 | TanStack Query | 本项目现状（无 TQ） |
|---|---|---|
| cancel | `await cancelQueries({queryKey})` | 无对应；依赖「提交完成后刷新」防晚到覆盖 |
| snapshot | `getQueryData` → context | `snapshots Map` / `entrySnapshot` |
| patch | `setQueryData`（detail+每个 list 页） | `applyTransaction` / `setDraft` |
| rollback | `onError` 恢复 context | `applyTransaction([snap])` |
| settle | `onSettled` 失效 detail+lists | `gridApi.refresh` |
| 幂等 | intent 时生成 key，mutationFn 转发 | 同左（axios 头） |

**cache coherence 警示**：同一对象出现在「详情面板 + 列表网格 + RTM」，乐观 patch 必须**同时**改这三处，否则徽章/状态互相矛盾。本项目无统一查询缓存层，需在 Adapter 层用**事件**通知各表面刷新（如 `plm:entity-changed`），见 03 文档信号。

## 8. 红线比对（能力 6 落地）

AG Grid 无内建 diff；业界通用做法：**两快照先做 key 级 diff 生成三集合（added/removed/modified），再用单元格 cellClass/cellStyle 染色**。

```typescript
function redline(a, b) {
  const onlyA = a.filter(x => !bKey.has(x.id)), onlyB = ...;
  const modified = rows where field diff;
  return { onlyA, onlyB, modified };
}
// 渲染：differentRows 上 wholeRowStyle 标红/绿，diffCells 上 cellStyle 标黄
```

要点：
- 行 key（`getRowId`）是 diff 前提。
- 只对用户可见列染色，隐藏内部属性；差异浮窗给「旧值 → 新值」。
- 1K 行 diff < 1s（SLO）需 O(n) key 化，避免 O(n²) 双循环。

## 9. 无障碍与键盘导航

- react-data-grid / Adobe React Spectrum DataGrid 是键盘导航 + a11y 标杆（Tab/Home/End/箭头、单元格级 focus、ARIA grid 语义）。
- AG Grid 基础可访问性够用；若某列表对 508/无障碍敏感（如检查单），可优先用 react-data-grid。
- 本项目 main.tsx 顶栏 + 三栏已用标准 focus 管理，补充：网格内 `suppressCellFocus:false` + `enableCellTextSelection` 可改善键盘选择。

## 10. 性能陷阱清单（踩坑对照）

| 陷阱 | 后果 | 解决 |
|---|---|---|
| `onCellValueChanged` 全量 setRowData | 卡顿/丢失编辑态 | `applyTransaction` 单行（§2.1） |
| raw-HTML cellRenderer | 被转义、XSS（L-075） | React 组件 + valueFormatter/cellStyle |
| `axios.then(setState)` 传响应对象 | 状态非数组、恒锁（L-079） | 解包 `.data` |
| 动态列 rebuild 丢用户态 | 列宽/顺序被重置 | `getColumnState()/applyColumnState()` |
| SSRM 用 setRowData | 无法定位/整表重拉 | `applyTransaction`/`refreshServerSide` |
| 缺 `getRowId` | 事务/树/编辑错位 | 所有网格必配 |
| diff 用 O(n²) | 1K 行 >1s | key 化 O(n) |
| 大 BOM 前端全量加载 | 内存溢出 | SSRM+懒加载+缓存上限（02 §3.1/3.2） |
| 编辑器内存泄漏 | 卡顿 | 编辑组件卸载时清定时器/订阅（AG Grid 建议） |

## 12. 建议：S1 即可低成本落地的 3 件事（不需要等 P2）

1. **给现有需求/项目网格补 `getRowId` + 编辑改 `applyTransaction` 单行更新**（消除潜在卡顿，对齐 §2）——改动小、收益直接。
2. **把 `buildColDefs` 抽成 `plm-grid/colDefs.ts` 纯函数**（输入 templates/role/status → ColDef[]），为 P2 元数据列铺路；纯函数好测。
3. **定义并注入 `canEditCell`（Layer 2）为纯函数**，当前 status 驱动可编辑即先接到它——后续加密级/流程上下文只是加 if。
4. **把「提交写入」抽成 `plm-grid/commit.ts`（五拍写路径）**：`withOptimisticWrite(grid, ops, {idempotencyKey, snapshots})`，让需求/项目/变更共用同一套乐观+回滚+重试纪律（§7.3），避免各页面各写一套。匹配 DetailPanel 的 `entrySnapshot` 增强。

这三件让 Grid Adapter 的「业务判定集中为可测函数」骨架先立起来，P2 只补 Univer/SSRM/粘贴/diff，不再动架构。
