# 15 · 交付物基线（应有清单）与实交付三态

> 状态：**已落地（2026-09-15 批次）** · 依据用户裁定 D-05（见 `.creature/tasks/plm-ruling-20260915/decisions.md`）
> 相关需求：REQ-2026-1252（判据空集假绿）、REQ-2026-1259（转段不实例化）、REQ-2026-0764（门点自环死锁，同型约束）

## 1. 这一层此前完全不存在

平台此前**只有"实有交付物"**（`t_deliverable`，人工/接口登记），从来没有"本阶段应该有哪几条"的
权威表述：不存在 `t_deliverable_template` 表、迁移里零交付物种子、无模板文件、`t_gate_map` 也没有交付物列。

两个已实证的后果：

| 需求 | 症状 |
| --- | --- |
| 1252 | `DELIVERABLES` 判据的分母是"项目自己现存的那几条"。**删掉一条 `required=true` 的交付物会让齐套率更高**——它同时从"实有"和"应当在"里消失。实测 DELETE 端点只拦非 PENDING，required 的 PENDING 行可直接删。 |
| 1259 | `ProjectService.transition` 全程不写 `t_deliverable`。项目 298 转进「开发」后开发交付物 0 条，判据仍绿。 |

## 2. 「应有」= 元数据配置（按项目阶段）

**表**：`t_deliverable_template`（V126）。一行 = 一条"某阶段应当产出的交付物"。
新增/调整基线 = **写一行配置**，不改代码、不发版（与 `t_checklist_template` 同一套"配置即数据"范式）。

关键列：

| 列 | 说明 |
| --- | --- |
| `phase` | 应产出阶段，值域 = `ProjectStages.ALL`（10 阶段） |
| `critical_path` | 关键路径（判据语气/排序；**本版不参与硬判**） |
| `med_class` / `market` / `product_kind` | 适用维度，**NULL = 通吃**（行侧留空 = 基座，与 `t_checklist_template` 同口径） |
| `provenance` | `PLM_MIGRATION`（系统里正在跑的口径）/ `IPD_KNOWLEDGE`（外部 IPD 知识层映射的候选口径） |
| `provenance_ref` | 依据指针（`迁移文件:行号` / `yaml:行号`），**逐条可核对** |
| `active` | 软删（撤下的条目保留可审计） |

### 解析口径（三条硬规则）

1. **阶段是并集，不是单档**：交付物是"**进入**本阶段之前就该产出的东西"，故取「本阶段及更早」。
   取通向的阶段会让 DCP0 要求"概念阶段交付物先批准"，而概念交付物本身依赖 DCP0 通过
   ⇒ **任何项目永久卡在立项**（REQ-2026-0764 的原始形态）。
2. **维度档也是并集**（由具体到通用逐档收集，不 break）：单档命中会让基座项**整片丢失**
   （`CL-DCP_ES-III-ALL` 只有 1 项而基座有 10 项的历史事故，REQ-2026-0700）。
3. **产品种类族匹配**：行侧 `product_kind='SW_STANDALONE'` 代表整个软件族
   （`SW_IN_DEVICE`/`SW_SAMD`/`SW_STANDALONE` 统一命中），避免同一批条目按三种种类各存一份、日后漂移。

## 3. 实交付三态

| 状态 | 判据 | 是否参与门线硬判 |
| --- | --- | --- |
| **已交付** `DELIVERED` | `t_deliverable` 中存在同名条目且 `status='APPROVED'` | 是（既有 `DELIVERABLES` 判据不变） |
| **豁免** `WAIVED` | 同名条目且 `waived_at IS NOT NULL` | 否（已裁定为不需要） |
| **未交付** `NOT_DELIVERED` | `应有 − 已交付 − 豁免`（**派生，不落库**） | 本版**否**（ADVISORY） |

- **豁免 ≠ `required_flag=FALSE`**。后者是"登记人认为不必需"；豁免是"**按基线它应当有，但本项目该阶段确认不需要**"，
  是对基线的一次显式裁定，故 `waive_reason` 必填（≥10 字）+ `waived_by`/`waived_at` + 审计 `deliverable.waive`。
- 豁免一个**尚未登记**的应有项时，先登记再豁免（登记即置豁免，不产生 PENDING 待办）。
- **未交付不落库**：三态若两处存储必然漂移。

## 4. 为什么本版是 ADVISORY（这是有意的，不是没做完）

差集一旦作为硬门：新阶段该产出的条目必然是 PENDING ⇒ **转段瞬间自锁**。
而 `DCP_ES` 是走出「开发」阶段的**唯一阶段门**（`t_gate_map` 里唯一的 `stage_from='开发'` 出口），
一旦锁上，**没有任何合法路径离开开发阶段** —— 与 REQ-2026-0764 的门点自环是同型死锁。

**硬门化的前置条件**：① 豁免通道可用（本批已交付）；② 基线内容本身经业务评审
（当前 82 条里相当比例来自 `ipd/knowledge`，见 `provenance`）。两者齐备后由用户显式决策。

> 代码里 `baselineDeltaCheck` 与 `/baseline-delta` 的注释都写明了这一点 —— **不要"顺手改成硬门"**。

## 5. 接口

| 端点 | 用途 |
| --- | --- |
| `GET /_platform/deliverable-templates?phase=&provenance=&activeOnly=` | 基线配置读端（管理员据此评审"应有清单"本身） |
| `GET /_platform/deliverable-templates/coverage` | 各阶段基线规模；`phasesWithoutBaseline` 非空即该阶段**没配** |
| `GET /projects/{id}/deliverables/baseline?stage=` | 项目在某阶段的适用基线（解析结果 + 档位 + 维度 + 警告） |
| `GET /projects/{id}/deliverables/baseline-delta?stage=` | **三态 + 双向差集**（`notDeliveredItems` / `extra`） |
| `POST /projects/{id}/deliverables/baseline/{baselineId}/waive` | 豁免（理由 ≥10 字） |
| 预检项 `DELIVERABLE_BASELINE` | 门线上的差集可见化（恒输出、ADVISORY） |

**双向差集是刻意的**：只看"应有而未产"永远发现不了"基线漏项"；`extra`
（已登记但不在应有清单）正是**发现基线缺项的入口**。

## 6. 空集必须可辨（本批反复出现的缺陷形态）

- 该阶段没有基线条目（没配）时，差集必然为空 —— 预检会显式自述**「未配置」**而不是报 OK。
- `coverage.phasesWithoutBaseline` 把"哪个阶段其实没配"直接列出。
- `/baseline` 与 `/baseline-delta` 都会回 `tiers`（本次命中了哪些档）与 `warnings`
  （维度未设/种类未登记 ⇒ 只解析基座行）。

> 依据：本项目 26/27/28 三个批次的复盘结论 —— **每一次"假绿"都出在判据的分母或作用域上，而不是判据本身**。

## 7. 已知边界（需业务侧确认，不阻塞本版）

1. **基线内容初稿的来源分布**：全部 82 条中，`phasesWithoutBaseline` 为空（10 个阶段都有条目），
   但 **维护/退市** 两阶段在 PLM 侧**几乎没有依据**（PLM 侧只有 `t_eol_plan` 表结构），
   条目来自 `ipd/knowledge`；**注册申报** 阶段在 `t_gate_map` 里**没有任何端点为该阶段**。
   三处均已标 `IPD_KNOWLEDGE` 并在 `provenance_ref` 里写明出处。
2. **两套阶段模型并存且不互通**：`ipd/knowledge/processes/*.yaml`（六阶段，由 `ipd/mcp/ipd-process` 消费）
   在 PLM 应用后端**零引用**。本基线按 PLM 的 10 阶段组织，来自知识层的条目其阶段归属是一次**语义映射**。
3. **`marketScope` 证据薄弱**：只有少数条目能给出迁移里的显式市场代号；其余 `(通用)` 的含义是
   "来源未限定市场"，**不是**"已确认全球适用"。若要按市场差异化，需要业务侧给一张「交付物 × 市场」矩阵。
4. **DHF/DMR 章节类条目**（DHF-01..14、DMR-01..06）当前以语义名称收录为独立条目（如"设计输入（DI）清单"）。
   若今后要与 DHF 齐套扫描共用一份数据，应改成"指向 DHF 章节码"的形式。

## 8. 关联对象类型（`obj_type`）：三个反复咬人的事实（2026-11-11 需求批次 63）

`obj_type` 是交付物**指向另一个业务对象**的锚点。表面是自由文本，实际有三层"隐形契约"。

### 8.1 唯一权威 = 解析器注册表，不是枚举、不是 DB 约束

- `t_deliverable.obj_type` 是 **TEXT，无 enum、无 CHECK**。
- 唯一权威是 `ResolverRegisterConfig` 里的注册清单（20 个类型），
  经 `GET /api/v1/_platform/resolve/types` 下发给界面作为下拉选项。
  ⇒ **凡代码里 `setObjType("XXX")` 而注册表没有 `XXX`**，就是"库里躺着一行界面上永远选不到的数据"。
- **实测活体分布（2026-11-11）**：`NULL`=53 / `DOC`=26 / `REQ`=5 / `DOC_REV`=4 / `RVW`=3 /
  **`REQ_BASELINE`=2** / `ITEM`=2 / `CHT`=2 / `CBB`=1 / `PRJ`=1。
  `DOC_REV` 与 `REQ_BASELINE` 都是**未注册**的实据。

### 8.2 `REQ_BASELINE` 半个落地：需求基线自动登记的交付物，编辑必 400

需求基线批准时，`RequirementBaselineService` 会**自动登记**一条交付物
（`objType="REQ_BASELINE"`、`objId=<基线编号>`，独立事务落库，属"基线一经批准就产出可追责的文档"）。
**问题不在登记，在于登记用的类型没有注册**：

- 界面上"关联对象类型"下拉里**没有它** ⇒ 用户改不动这条交付物；
- 而 `DeliverableEvidenceService.guessType()` 对 `RB` 前缀返回 `"RB"`（**不是** `REQ_BASELINE`），
  保存时与库里声明的 `REQ_BASELINE` 矛盾 ⇒ **`400 声明与编号矛盾`**，死路。

⇒ 本批补齐整条链（注册表登记 + 前端中文标签 + 检索域 + 深链 + `guessType` 映射）。
判据要点：**必须有一条"从库里读出这条交付物 → 原样保存 → 200"的回显断言**，
只测"新建能选到"会漏掉本缺陷（缺陷在**读改**路径上）。

### 8.3 交付物**阶段**：创建即声明 + 三态语义（null / 空串 / 非空）

- `t_deliverable.stage` 声明该交付物属于哪个阶段，**创建与编辑是同一个语义**。
  本批（批次 63）把它**前置到新增行**：交付物清单页顶部的新增行同一行放
  「名称 / 阶段声明 / 关联对象类型」，选中阶段后创建，接口读回即该阶段
  （判据：`R5c`；负向配对 `R5d`「下拉首项仍是未声明阶段」——空值仍可表达，
  不能把新增行强制塞一个默认值）。
- **`stage` 是三态，不是二态**（`DeliverableController` PUT 的真实契约）：

  | 请求里发的 | 语义 | 是否写库 |
  |---|---|---|
  | 字段**不出现** / `stage: null` | 「**这次没提交阶段字段**」＝ 保持原值 | 否 |
  | `stage: ""` | 「**显式清空阶段声明**」 | 写成空 |
  | `stage: "开发"` 等 | 设为该阶段 | 是 |

- ⚠ **前端必须发空串而不是 null**（`ProjectsPage.saveDeliverable` 已加注释钉住）：
  `req.stage() == null` 才是"没提交"的判据，所以发 `null` 等于「不传」——
  界面下拉里选了「未声明阶段」也**存不住**。这条在浏览器里实测过一次（走查脚本报
  "保存成功但没清掉"），是「接口看着通了、界面没做对」的典型。
- 该三态是**接口语义变更**（本批落地），不是 UI 试探：清空走 `PUT ... stage:""`，
  不新增端点、不新增列。已批准（`APPROVED`）的交付物仍是**锁定面**，写 stage 直接
  `DELIVERABLE_APPROVED_LOCKED`。

> **归口提醒**：「项目交付物台账」（`t_deliverable`）与「任务↔交付物绑定」（`t_task_deliverable`）
> 是**两张表、两套界面**，文档里不要混用"交付物"指代其一。

## 9. 基线与交付物清单**融合成一个页签**（2026-11-11 需求批次 64）

### 9.1 缺陷现场：基线页签是"纯读界面"，缺口摆出来却没有出口

批次 63 的 P2-1 依当时用户裁定「先补『查看交付物基线』两个读界面，waive 暂不做」，
于是「应有基线」页签落成为**只读对账表**：覆盖度条 + 未交付/豁免/基线外三张明细，
`data-testid` 齐全、判据自洽，**但一个写入口都没有**。

用户实际要做的动作是「**比照应有基线，逐一添加交付物**」，而系统只给了两条路：
① 盯着缺口表；② 切到另一个页签，在一张**空白**的清单上手打名称、**手选阶段**。
⇒ 缺口越显眼，重复劳动越多。**这不是"少一个按钮"，是读界面与写入口被分在了两个页签里。**

### 9.2 融合形态 = 合并页签（用户裁定 2026-11-11）

`交付物清单` + `应有基线` → **`交付物与基线`**，`TABS` 由 8 项减为 7 项（原 6/7 前移为 5/6）。

- **爆炸半径**：`tab === N` 在 `ProjectsPage` 内硬编码 7 处，逐条改；已核实
  **外部没有任何按页签下标的深链**（`/projects/:id/gates/:code` 落在门工作台另一个组件）⇒ 只影响本文件。
  这也是为什么选"合并"而不是"再加一个联动按钮"：联动只是把两个割裂的界面用一条跳转缝起来，
  逐项对照仍要在两屏之间来回，而"比对"与"登记"是同一个动作的两半。
- **改名波及既有验收脚本**：6 个脚本按**文本精确匹配**页签
  （`plm-b32-deliv-link-ui.cjs` / `plm-b32-eco-cht-e2e.cjs` / `plm-b34-ui-fixes.cjs` /
  `plm-b63-ui-fixes.cjs` / `plm-p21-r11-ui.cjs` / `ui-walkthrough.mjs`），
  以及 `pco-bundle-assert.sh` 对页签名清单的 grep。**页内 `data-testid` 一个都不改**，
  于是这些套件的**断言**继续有效，只需改"点哪个页签"。

### 9.3 页内排布 = 实绩在上、缺口在下

1. **实交付清单**（原页签的全部动作原样保留：提交/批准/驳回/编辑/删除、自批标记、未声明阶段补填）——
   它是**项目自身的实态记录**（主记录）。
2. **覆盖度条** —— 沿用既有实现，「没配 ≠ 齐套」的判据（§6、`phasesWithoutBaseline`）一个字不动。
3. **未交付明细** —— **写入口所在**。每行两个出口（9.4）。
4. **豁免明细 / 基线外明细** —— 次要信息，留在同页下半段。

顺序是**实现事实**（`tab === 2` 的两块在组件里就是这个先后），理由也在这里：
"先看本项目已经有什么，再看还差什么"是对账的自然阅读序；而且"缺口在上"并不影响
逐项添加——成员在缺口表上连续操作，点完一条少一条，视线不必上下往返。

### 9.4 行内两个出口：为什么"添加"要预填、"豁免"必须另给

| 出口 | 行为 | 理由 |
|---|---|---|
| `＋ 添加` | **开新建表单，按基线行预填名称与阶段**，用户确认后提交 | 一行直接落库会让填错无法当场纠正，而 `stage` 决定**门点检查范围**（§8.3）——填错的代价要到后面几道门才暴露。预填保证"逐项添加"仍然快，但不放弃人工确认。 |
| `豁免` | 必填理由（后端 ≥10 字 + 留痕 who/when/why） | **必须与"添加"分成两个出口**：本阶段确认不需要 ≠ 还没做。把"还没做"记成豁免，等于用行政手段把门线缺口洗掉。 |

添加走既有 `POST /projects/{id}/deliverables`，**不新增端点**；预填值只是初值、可改。
同阶段同名**允许**重复建（现有契约如此）——不引入静默去重，避免"看不见的被丢弃"。

### 9.5 如实登记的边界

- **缺口统计是"本阶段"口径**：基线按 `bl.base.phase` 单阶段解析，实交付跨全部阶段。
  页内措辞必须点明阶段名，否则用户会把"本阶段 42"读成"全项目 42"。
- **本批不提供"撤销豁免"**：`waive` 端点是 `UPDATE ... SET waived_at = now()`，只进不出；
  要撤销得新增一条解除路径，属另一次裁定，本批不猜。
