## 5. 详情面板模式（DetailPanel）

### 5.1 结构

```
dp-head（标题 + 全屏/取消/保存按钮）
dp-body（字段网格：84px label | 1fr input）
dp-extra（附加区块：RTM 追溯 / 流转按钮 / 处理记录 —— **展开态下独占整行**，见 §5.8）
```

### 5.2 字段 schema

```typescript
interface DetailField {
  code: string;
  label: string;
  // tel=只读展示；json=JSONB 结构化录入；kv=键值对编辑器；lookup=主对象检索选择面板；
  // jsonread=JSONB 结构化只读展示 + 内联「编辑」切回 JSON 文本（2026-09-17 用户需求②）；
  // multi=多选勾选块（enum 多值，2026-09-30 批次50 引入）；
  // folder=文件夹层级选择（2026-09-27 批次62 引入）；
  // dimtext=**按维度分键的多行描述**（2026-10-04 批次54：$APPEALS 买点描述）——见 §5.2.5
  kind: 'text' | 'longtext' | 'select' | 'number' | 'date' | 'tel' | 'json' | 'kv' | 'lookup' | 'jsonread'
      | 'multi' | 'folder' | 'dimtext';
  enum?: (string | { value: string; label: string })[];
  readonly?: boolean;
  placeholder?: string;
  jsonLabels?: Record<string, string>;   // kind='jsonread'：JSON 内部键名 → 中文标签（未命中直出键名，不猜语义）
  // kind='dimtext'：**按哪个字段的当前取值分键**（批次54 = `'appeals_dim'`）
  dimensionsCode?: string;
  // 下面三个是**元数据下发的受控标志**（`MetadataService.detailFields` 随字段一起下发），
  // 页面**只按标志选 kind，不自己猜**（"两条权威分叉"的入口就是页面里手写判断）：
  //   isMulti          ⇒ ENUM 且允许多值 ⇒ kind 必须是 'multi'（漏了会退化成单选，静默丢值）
  //   isDimensionKeyed ⇒ JSONB 按维度分键 ⇒ kind 必须是 'dimtext'
  //   enumLabels       ⇒ code→中文短名（**不塞进 enum_values**：那会让 `toEnumArray` 解析失败、
  //                     词表整个变 null ⇒ 勾选框一个都不渲染，见 15 号文 §4.3 实施更正）
  isMulti?: boolean;
  isDimensionKeyed?: boolean;
  enumLabels?: Record<string, string>;
}
```

#### 5.2.1 长文本行数（2026-09-17 · 需求①）

`kind:'longtext'`（含 JSON 编辑态）的 textarea **最少显示 8 行**，三处同时约束：

| 约束 | 位置 | 为什么不能只做一处 |
|---|---|---|
| `rows={8}` | `DetailPanel.LONG_TEXT_ROWS` | `rows` 只定"初始行数"，被父容器高度约束时会被压缩 |
| `min-height: calc(8 * 1.5em + 14px)` | `.dp-input.longtext` | 兜住压缩；实测渲染高度 168px（行高 19.5px ⇒ 恰好 8 行可见） |
| `resize: vertical` | 同上 | 长文仍可继续拉大（需求 `content` 实测最长 5961 字，8 行也只够"看得见开头"） |

**判据**：真浏览器量 `clientHeight/lineHeight ≥ 8`（`plm-b25-opt-ui.cjs` S1a/S1b/S1c），不看 `rows` 属性本身——属性写了而 CSS 压回去了，用户照样看不见。

#### 5.2.2 `jsonread`：JSONB 的结构化只读渲染（2026-09-17 · 需求②）

**背景**：任务书的 `marketAnalysis` / `finEstimate` / `riskTop` / `reuseConclusion` 在 DB 是 `jsonb` 自由结构（无键级 schema，元数据 `t_attr_template` 只登记到**字段级**），此前详情面板当裸 JSON 文本显示 ⇒ 嵌套两三层、数组里还是对象，人读不出来。用户裁定口径：**结构化只读展示为主 + 「编辑」按钮切回 JSON 编辑**。

| 元素 | 规格 |
|---|---|
| 渲染器 | `components/JsonView.tsx`（本字段与任务书页财务 tab 共用同一实现） |
| 标量 | 键值行（键左值右）；值 `white-space: pre-wrap` 不截断；空值显示 `—` |
| 嵌套对象 | 分组块（浅底 + 左边框 + 组标题），≥3 层折叠为 `<details>`（默认展开，避免"要点开才看得到"） |
| 对象数组 | **表格**（列 = 元素键并集，保序）；标量数组 → 逗号分隔单行 |
| 空对象/空数组 | 显式 `（空）` / `（未填写）`——**不渲染成空白**（否则分不清"没填"与"没显示"） |
| 键名标签 | 优先 `jsonLabels[键]`（元数据/实测登记），未登记**直出键名原文**——自由 JSONB 的键由业务方自写（中英混用、逐条不同），猜语义会把 A 字段的说明挂到 B 字段上 |
| 「编辑」 | 仅当 `!locked && !readonly` 时显示（**可编辑性仍跟随流程状态**，冻结态不出现） |
| 编辑态 | JSON textarea（≥8 行）；**非法 JSON 就地红字且「完成」禁用**，非法值不写入草稿（服务端会拒非法 JSON，若放进去则整单保存失败、连其它字段的修改一并回滚） |
| 留空 | = 清空该区（提交 `{}`），与既有保存语义一致 |

**键名标签来源（不新增端点）**：字段级标题取 `GET /_platform/metadata/detail-fields?objType=CHT`（实测登记 9 条，含 4 个 JSONB 字段：市场分析/财务预估/Top 风险/复用结论）；字段**内部**键的中文映射由前端常量 `JSON_KEY_LABEL` 承载，每条都来自运行库 `t_charter` 的**实际键名**（`市场规模/Y3目标`、`rd/note/targetCost`、`prob/risk/owner/impact/mitigation`）。

#### 5.2.5 `dimtext`：按维度分键的多行描述（2026-10-04 · 批次54 `$APPEALS` 买点描述）

**问题形态**：一个**多选**字段（`$APPEALS` 8 维价值点）+ 一个"每个勾选项各写一段说明"的 JSONB 字段。通用 JSON 编辑器会把它们混在一个框里，用户既看不出"这段属于哪个维度"，也没法只填当前关心的维度。

| 元素 | 规格 |
|---|---|
| 分键来源 | `f.dimensionsCode` 指向的字段的**当前取值**（面板草稿优先，回落记录值）——**只有被勾选的维度才渲染输入框** |
| 输入框 | 每个已勾选维度一个 `textarea`（`rows=2`），锚点 `data-testid="dimtext-<字段码>-<维度码>"` 落在 **textarea 本身**（挂包裹 div 上时"这个框能打字"只能靠猜） |
| 维度标题 | 优先 `enumLabels[维度码]`（`appeals_dim` 的中文短名），未登记回落到维度码原文 |
| 一条都没勾 | 渲染**一行指引**（不是空白：空白分不清"功能没做"与"还没勾"） |
| 取消勾选 | **不删**已写的文字（误点一次不该丢数据），且显式披露"另有 N 个维度的描述保留但未勾选"（`data-testid="dimtext-orphan-<字段码>"`） |
| 宽行 | 进 `WIDE_KINDS`（与 `multi` 同独占整行）——横向并排会把 8 个中文标签挤到两三行 |
| 可编辑性 | 跟随 `locked`/`readonly`（阶段锁：`is_post_analysis_only` 的字段在 PROPOSED 态**全组只读**，不得出现"能点但存不进去"的半通状态） |
| 取值 | 值为对象 `{维度码: 文本}`；**空串键在提交前剪掉**，非字符串值原样交给服务端报错（前端不得 `String.valueOf` 洗白） |

**为什么不用 `json`/`jsonread`**：这两种渲染的是"自由 JSONB"，维度键是**业务方自写**的（猜语义会把 A 字段的说明挂到 B 上）；`dimtext` 的键来自**另一个受控字段的词表**，键的语义是确定的 ⇒ 可以做标题、可以做联动、可以只渲染需要的行。

#### 5.2.3 列表时间筛选的反馈（2026-09-17 · 需求③）

**口径**：产品结构页「按时间查询」= **产品主数据更新时间**（`t_product.updated_at`，服务端 `updatedFrom/updatedTo`，`to` 取闭区间 `+1 天`）。上市时间不在本口径内。

**为什么这是缺陷**：接口本就正常（实测请求携带参数、200），但**页面零可见变化**（左树仍是旧产品、右详情仍停在旧产品、无条数、无空态）⇒ 用户判定为"没反应"。故规则是：

| 元素 | 规格 |
|---|---|
| 日期标签 | 「产品更新起始 / 截止」+ `title` 写明口径（不能让用户猜是哪个时间） |
| 命中条数 | `data-testid="time-hit"`：`按更新时间命中 N 个产品`；到单页上限 100 时提示缩小范围 |
| 命中 0 | 显式空态（`data-testid="time-empty"`）：写明时间区间与口径 + 说明"空列表=筛选结果为空（不是无权限）" + 指路「清空时间筛选」 |
| 选中联动 | 命中 0 时清空选中（右详情不得假装还选中某产品）；命中 >0 且未选中时自动选第一条 |
| 加载 vs 空结果 | `loadedOnce` 标志区分（`products.length===0` 同时代表"还在加载"与"真的为空"，不区分会把"没加载完"说成"空结果"——**假结论比不提示更糟**） |

#### 5.2.4 物料库「名称」列默认宽度（2026-09-17 · 需求⑤）

默认宽度 = **能显示 20 个汉字**，实测标定（不用"每字 N px"折算）：真实网格里以「名称」单元格字体量 20 汉字 = **229.5px**（13.5px/汉字）+ 单元格内边距 14px + 表头图标占位 12px ≈ 256px ⇒ 取 **260**。

同时把该列由 `flex: 2, minWidth: 180` 改为**固定 `width: 260`（保留 `minWidth: 200`）**：实测原配置下名称列被压到 **32px**（网格可视宽 790px，其余列固定宽合计远超之，flex 只在剩余空间里分配），所谓 minWidth 并未兜住；固定宽度才是"默认能显示 20 个汉字"的可判定口径。


### 5.3 编辑规则

- 所有可编辑字段**内联可编辑**（text/select/longtext），**无逐字段弹窗**。
- 单一「保存」按钮一次性提交变更（仅提交发生了改变的字段）。
- **「保存&新建」按钮**（`onSaveAndNew` prop，可选）：在「保存」右侧；提交当前变更后由父级新建条目并切入面板新建态（`● 新需求`）；**无改动时点击也执行新建**；面板锁定（流程中）时不渲染。
- **「上一条 / 下一条」导航链接**（`onPrev`/`onNext` props，可选）：超链接形式，与按钮 bottom 水平对齐（`.dp-foot` flex + `margin-left:auto` 靠右）；hover 显示快捷键 hint（`title="上一条需求（快捷键 Alt+↑）"`）；键盘 `Alt+↑`/`Alt+↓`（window keydown，输入控件聚焦时不拦截）；导航跳过未保存的新建行。
  - **实现位置（2026-09-14 S25）**：抽为共享 hook `hooks/useSiblingNav.ts`（`nav(dir)` + Alt+↑/↓ 绑定），**需求管理 / 文档中心 / 物料库三页共用同一实现**——此前只有需求页有内联副本，三页行为会各自漂移。`nav` 恒稳定（空依赖 + ref 读最新状态），可安全进入依赖数组而不重建监听器。
  - 选中项不在当前页时（如 `?open=` 深链直取的跨页对象）**不跳转**：找不到相邻位置时静默不动，避免跳到与选中项不相邻的行。
- **字段插槽 `fieldExtras?: Record<string, ReactNode>`**：紧跟指定字段下方渲染额外内容——需求页用于把 **AI 查重结果栏显示在"标题"字段正下方**（而非面板底部）。
- **方案内容字段（需求流"方案制定中"节点，2026-09-09）**：`{ code:'solution', label:'方案内容', kind:'longtext', placeholder }`——`placeholder` 取元数据 `t_attr_template.sample_value`（经 `GET /_platform/metadata/detail-fields?objType=REQ` 下发，**columns 不带 sampleValue**），即"录入模版由元数据扩展定义，改模版=改元数据一行、零发布"；该字段仅在 `editableStatuses` 含 `SOLUTION_DEFINING` 时可编辑。
- **推进前置条件的前端预判**：迁移边 `requires` 未满足（对象字段为空）→ 流转按钮 `disabled` + `title="请先填写<label>后再推进"`；后端 `400 FIELD_REQUIRED` 为权威兜底（预判失效时以提示区展示 message）。
- **深链定位优先（2026-09-09 修正）**：任何"跳转到某业务对象"的入口（待办行点击、全局搜索、通知）统一用 `?open=<id>`，并遵守两条规则——
  ① **跳转时清空"处理人=当前用户"等会排除目标的筛选**（否则目标对象不在结果集中，用户"跳过来却看不到"）；
  ② **列表加载后仍未命中时按 id 精确拉取该对象**（目标可能超出首屏分页，如新建对象排在末尾）并选中。
  即：**深链的语义是"必须看到该对象"，而不是"在默认筛选里碰运气"**。
- 可编辑性跟随流程状态：`status` 不在 `editableStatuses` 时整表单锁定。
- 全屏编辑：`.dp.expanded` 两列网格（`110px 1fr`），高度自适应，复用外层滚动。
  **`expanded` 是受控入参，必须与 `onExpandChange` 成对传**（批次53 补，见 `01-design-tokens-shell-layout.md` §3.6 G-UI-7-6 的受控契约表；
  只传回调会让面板 `expanded` 恒 false ⇒ 两列网格失效且点 ⤢ 出不了全屏；静态守卫 = 套件 **W45**）。

#### 5.3.1 AI 查重结果栏（REQ-0092 UI 改版）

**触发点同位扩展（2026-09-17 · 需求④：物料库新建物料）**：同一点位与同一控件的第二种用法——**草稿行（`_isNew`）录入期查重**。

| 维度 | 需求页（REQ-0092） | 物料库新建（2026-09-17） |
|---|---|---|
| 触发字段 | 标题 / 描述（防抖 800ms） | **名称 / 规格**（防抖 800ms；2026-09-17 批次26 收敛——原先还含 类别/单位/物料类型，这三个只参与评分、改了会让结果栏无故跳动） |
| 触发条件 | 标题非空 | **名称或规格任一 ≥2 字即查**（批次26 修：原先硬门槛 `name.length<2 → return`，实测"只录规格"时页面零反应，而"规格相同、名称没写"恰是一物多码的高发场景） |
| 接口 | `POST /_platform/dedup/compare {objType:'REQ', name:title, spec:content}` | 同端点 `{objType:'ITM', name, spec, uom, materialType, itemClass}`（uom/materialType/itemClass 只作为**评分输入**，不再是触发字段） |
| 挂载点 | `fieldExtras={{ title: dedupPanel }}` | `fieldExtras={{ spec: dedupPanel }}`——**结果栏紧跟「名称+规格」两行之后** |
| 字段顺序 | — | **名称 → 规格 → 类别 → 单位…**（批次26 把"规格"上移到"名称"正下方，使「名称+规格+查重结果」构成同一视觉簇） |
| 为什么必须走 `compare` | — | 草稿行**还没有 objId**，`candidates`（按对象查重）用不了；`compare` 的入参正好是"任意文本 + 物料字段" |
| 软提示 | 不阻断保存 | 不阻断创建（「创建」按钮保持可用） |
| 既有对象 | 变更标题即触发 | 仍走 `DedupPanel`（`candidates`），**不重复请求** |

**探针纪律**：查重候选受相似度闸门约束（doc 10 §2.6），用与库内物料**毫不相干**的名字会得到 0 条候选——这会把"查重正常但无候选"误判成"查重没工作"。断言必须用与库内真实物料高度重合的文本（`tools/opt-dedup-names.cjs` 用于挑选这类文本）。

标题变更（防抖 800ms）触发 `POST /_platform/dedup/compare` → 结果栏渲染在**标题字段正下方**：

| 元素 | 规格 |
|---|---|
| 栏头 | `▾/▸ 发现 N 条相似需求（AI 查重）`——**可点击折叠/展开**（收起只留标题行，默认展开） |
| 每行 | **相似度%**（≥0.9 红 / ≥0.75 琥珀 / 其余蓝）+ **需求编号**（下划线链接）+ **标题** + **描述摘要**（第二行小字，来自索引 `fields.summary`） |
| verdict 列 | **不显示**（"OK"对用户无意义；DUPLICATE/SUSPECT 语义用相似度颜色表达） |
| 点击编号 | **只读悬浮窗**（`.dedup-peek`，fixed 380px）：右缘=详情面板左缘-12px，**不遮盖详情面板**；显示编号/标题/类型/优先级/状态/描述（滚动）/验收准则；✕ 或点击窗外关闭；数据源 `GET /requirements/{objId}` |

**索引支撑**：需求 `content` 已入检索索引（`SearchIndexer` REQ case `fields.content` + `summary=reqType · content 截断 120 字`），查重评分含描述、结果行有摘要；改索引结构后需 `POST /_platform/search/reindex?objType=REQ` 重刷。

#### 5.3.2 新增对象由详情面板草稿态承载（2026-09-20 · 批次41 · 系统设置·用户管理）

**范式**：「＋ 新增」不再在工具栏摆一行输入框，而是让**右侧详情面板进入草稿态**（`record._isNew = true`）——面板标题变「● 新对象」、头部出现「草稿（未保存）」pill（`data-testid="dp-draft-pill"`）、底部按钮变「创建」（`data-testid="dp-submit"` + `data-dp-mode="create"`）。必填缺失时**面板内红色横幅提示且不落库**（用户域 = `usr-new-err` 块）。

**三个新扩展点（共用构件 `DetailPanel` 为此新增，G-UI-2"扩展构件而不是另起一套"）**：

| 扩展点 | 形态 | 用途 |
|---|---|---|
| `draftReady?: boolean` | Props | 草稿态可否提交的**显式判据**。默认判据是"标题/名称非空"（`draft.title \|\| draft.name \|\| record.title \|\| record.name`），覆盖需求/物料/文档等以 title\|name 为主键展示的域；**对象没有 title/name 时由父级显式给出**——用户对象以登录名为标识，用户域传 `draftReady = login 非空且 ≥3 位`（若不传，「创建」会因"没填标题"永远禁用——一个按不动的按钮比没有按钮更糟） |
| `draftHint?: string` | Props | 草稿未就绪时「创建」按钮的 hover 提示（与 `draftReady` 配对；不传则用通用文案"请先填写标题"）。用户域 = "请先填写登录名（至少 3 位）" |
| `DetailField.testId?: string` | 字段 schema | 把 `data-testid` **透传到该字段的控件元素**（input/select/textarea/只读 div），供验收走查做稳定锚点——按标签文案找控件是最脆的写法（改一次措辞就假红）。允许同一字段在不同场景用不同锚点：用户面板新建态 `nu-*`、编辑态 `ue-*`（既有走查 W30 断言的锚点不消失，只是控件从工具栏/自建卡片迁到统一面板） |

**提交按钮锚点（走查稳定锚点）**：`data-testid="dp-submit"` + `data-dp-mode`（`locked` / `create` / `save` 三态）——走查可断言"这个面板当前是只读 / 草稿创建 / 正常保存哪一种形态"，不必靠按钮文案。

**创建成功后的可见性（G-LST-3）**：草稿创建成功 → 回第 1 页、新对象即第 1 行（默认排序最新在前）；若当前检索/筛选条件会把新对象排除在外，必须**显式提示**（"已创建 X——但它不满足当前筛选条件，列表里看不到"），不得让用户对着列表以为没建成功。

**当前实例**：系统设置·用户管理 `/settings`（`SettingsPage.tsx` 用户管理页签）——`＋ 新增用户` → 详情面板草稿态，字段 = 登录名（仅新建可填，建号后是身份键）/姓/名/邮箱（凭据服务档案必填）/显示名/状态/角色（`kind:'multi'`）；处理记录（审计）与口令重置子卡仍在面板内。

#### 5.3.4 新建对象三件套：面板最大化 / 取消归宿态 / 保存&新建（2026-09-28 UI 走查整改 · 全站统一）

任何"列表 + 详情面板"页面的**新建入口**都必须同时具备以下三件，缺一件即缺陷（走查第二轮把 5 个域逐页补齐）：

|---|---|---|---|

#### 5.3.3 关联/归属字段按"是否可改"选形态；**有意不呈现**的字段必须留痕（2026-09-20 · 批次41 回炉）

**规则一（关联/归属字段的形态由"写路径支不支持"决定，不由"能不能看"决定）**：

| 场景 | 形态 | 实例 |
|---|---|---|
| 写路径支持的归属（新建**与**既有对象都可改） | `kind:'lookup'`（`SearchPick` 检索选择面板，G-UI-1），带 `testId` 锚点、`allowClear` 表达"清空归属" | 风险台账的「关联产品」(`risk-product-pick`) /「关联项目」(`risk-project-pick`)——用户原话"产品、项目都要可以通过相应的对象选择控件，选择/改选，而不是不可编辑"（回炉第二轮），随后又裁定"**已有**条目也要能改选"（第三轮 O-7） |
| 写路径**不支持**的关联字段 | `kind:'tel'` + `readonly`，值走 `useLookupLabels` 批量取号，显示「编号 · 名称」（未解析=`#id`、归属为空=「未关联」，二者不混） | 只读形态只用于"接口层确实不能写"的字段——**不是**用来回避实现 |

> **只读字段里的流程状态**：显示词必须来自**服务端域词表**，并在同一元素上保留原码
> （`readonlyLabel` 取词 + `data-raw-value`；网格列的同款约定与依赖数组陷阱见 `02-datagrid-aggrid.md` §4.12）。
> 批次55 实例：BOM 编辑器右栏「选中节点详情」的手写 `.kv` 行——「状态」值 = `useFlowStateLabel('item')`
> 的中文 + `data-raw-status` 原码（该行不是 `DetailPanel` 字段，但同守这条约定）。

**规则一附则（改归属要连带重算派生判定）**：若某派生字段依赖归属，改归属就必须在同一笔写里按**新归属**重算它，
否则"能力看起来存在、实际给了错的结论"。实例：风险的「剩余风险可接受性」取自产品主档的可接受准则阈值
（`t_product.risk_accept_threshold`），改产品 ⇒ 必须用**改后产品**的阈值重新判定并留痕（`RiskLedgerService.update`；
接口断言 `T3-17 C10b`），但**人手工填过的判定不被阈值覆盖**（人工优先，`C10d`）。

**规则一附则 2（PATCH 语义下"清空"必须显式表达）**：`null = 该字段不动` 的协议里，"清空"无法用"不传"表达——
必须给专门的标志（`clearProductId/clearProjectId`，与 `ItemDtos.clearCostFields` 同族）。若不给，
清空会被读成"没改"，用户以为改掉了、实际没改（**静默无效**比报错更坏）。同时"既给值又给清空"必须 **400**（不猜意图）。
前端侧：面板的 `✕` 清除 → 提交 `clearXxx: true`，而不是"省略该字段"。

**规则二（有意隐藏 ≠ 删字段）**：面板里**有意不呈现**某字段时，必须在字段数组处留注释说明三件事——
**为什么隐藏**、**边界（只隐藏界面，接口/库动不动）**、**如何一行恢复**；并配一条走查断言把"已隐藏"这件事本身钉住
（否则下一个人"顺手补回字段"就能静默推翻业务裁定，而所有套件仍然全绿）。

**实例（`REQ.sourceType`，2026-09-20 用户裁定）**：需求详情面板里「来源」(`sourceType`：市场/标准/风险/CAPA/临床/法规/内部自省)
与「来源通道（需求来源）」(`sourceChannel`：市场/客户/法规/竞品/内部)**并存会造成混淆**——枚举部分重名但语义不同，
同屏两个都叫"来源"的选择器让填的人靠猜、看的人无法判断权威。故**面板不呈现 `sourceType`**，统一以 `sourceChannel` 为"出处"；
**接口与数据库不动**（`sourceType` 照旧读写、元数据登记不变）。守它的走查：`W13`
（`U6b` 断言面板无 `sourceType` 锚点/控件且「来源通道」仍在；`U12` 断言接口仍返回 `sourceType` ⇒ 证明隐藏只发生在界面）。

### 5.4 处理记录（历史修改记录）

> **产品级口径（批次48 定稿；由来：用户反馈「需求处理记录里看不到流程流转时的处理意见」）**
> 每个对象的详情面板底部都有「处理记录」，它是**审计链在该对象上的人类可读视图**。
> 它必须回答三件事：**谁、什么时候、做了什么 + 说了什么**。少答第三件，就等于没有处理记录。

#### 5.4.1 UI 结构

详情面板最底部，`▶ 处理记录 (N)` 折叠区域：

#### 5.4.2 数据流

```
前端                              后端                          DB
useEffect[selected] ──→ GET /{domain}/{id}/history ──→ AuditService.findByObject()
  ↓ setHistory(r.data)                                    ↓ SELECT seq, ts, actor, action,
  ↓ 重渲染记录列表                                                   diff::text, prev_hash, hash
                                                          FROM t_audit_log
                                                          WHERE object_type=? AND object_id=?
                                                          ORDER BY seq
```

- **触发**：`useEffect(() => { ... }, [selected])`——选中行变化即拉取该对象的处理记录。
- **清空**：未选中或新建行（`_isNew`）时 `setHistory([])`。
- **排序**：按 `seq` 正序（审计链写入顺序 = 时间正序）；**收起态摘要取数组末尾**那条（最新）。
- **数据类型**：前端一律用统一构件的 `HistoryItem`（`{ts?, actor?, action?, diff?}`）。**禁止**在页面里把 history 声明成 `{ts,actor,action}`——那等于在类型层面声明"没有 diff"，处理意见永远渲染不出来（批次48 缺陷根因之一）。

#### 5.4.3 后端审计链（WORM + hash chain）

| 属性 | 规格 |
|---|---|
| 表 | `t_audit_log`（append-only，应用层只增不改） |
| 字段 | `seq`（自增序号）+ `actor` + `action` + `object_type` + `object_id`（**text**）+ `diff`（JSONB）+ `ts` + `prev_hash` + `hash` |
| hash chain | `hash = SHA-256(actor\|action\|objectType\|objectId\|canonical(diff)\|ts\|prevHash)`，每条承接上一条 hash |
| 时间规范 | 微秒级 UTC 即时串（`Z` 尾），`ts` 截断到微秒（DB timestamp 精度） |
| 篡改检测 | `AuditService.verify()` 重算全链 hash，任一不匹配 → `false` |
| 查询 API | `AuditService.findByObject(objectType, objectId)` → 含 `diff`（jsonb 解析为**对象**；解析失败保留原文，绝不因解析问题丢审计内容） |
| REST 端点 | `GET /api/v1/{domain}/{id}/history`（各域 Controller 委托 AuditService） |
| **`object_id` 是文本列** | 直连库写 SQL 时**必须带引号**（`object_id IN ('3570')`）；写成裸数字会 `text = integer` 报错，而调用处常 `2>/dev/null` ⇒ **读数静默变空**。对照：`t_flow_task.object_id` 是 **bigint**（裸数字才对）——同名字段、相反写法（批次48 实测踩到） |

#### 5.4.4 复用方式（**硬约束：处理记录只能有一份渲染实现**）

各域 Controller 添加一个 `history` 端点即可：

```java
@GetMapping("/{id}/history")
public List<Map<String,Object>> history(@PathVariable Long id) {
    return audit.findByObject("requirement", String.valueOf(id));
}
```

前端各域页面**必须**用统一构件，不得自建一套：

```tsx
import HistorySection, { HistoryItem } from '../components/HistorySection';
const [history, setHistory] = useState<HistoryItem[]>([]);
// stateLabel 来自 useFlow()：状态码 → 界面名（取不到回落原码）
<HistorySection history={history} stateLabel={stateLabel} />
```

- **违规样例（2026-09-22 实测）**：`RequirementsPage` 曾自建 `history.map(...)`，只画 `ts/actor/action`
  ⇒ 全平台**唯一**一处违约，也正是"看不到处理意见"的根因（接口一直在下发 `diff`）。
- **判据（可脚本化，T3-25 A 段已落地）**：
  `grep -n 'history.map(' frontend/src/pages/` 必须**无命中**；
  且不得出现 `useState<Array<{ ts?: string; actor?: string; action?: string }>>`（类型说谎）。
- **唯一例外**：域内**事件流水表**（风险规则的 `t_risk_rule_history`、PV 的 `t_pv_event` 等）不是审计链，
  数据源与语义都不同，可以自建渲染——但**必须**在代码注释里写明"为什么不是 HistorySection"
  （`PostMarketPage.tsx:141`、`RiskRulesPage.tsx` 是范本）。

#### 5.4.5 流转处理意见（**本节即本批立规的由来**）

| 项 | 规格 |
|---|---|
| 定义 | 流程流转时人写下的自由文本：普通推进的「交接说明」、回退的「回退原因」、作废的「作废依据」——**同一个字段**（`reason`），语义由边的类型区分 |
| 事实源 | **审计链 `diff.reason`**。需求域**不新增数据库列**（`t_requirement` 无 `status_reason`；文档域的 `t_doc_rev.status_reason` 是"当前版本行"的字段、不是历史流水，两者不可互推） |
| 写入入口 | 全部入口都必须带理由：单条流转 `POST /{domain}/{id}/transition`、批量推进 `POST /requirements/bulk-transition`（**逐条**落到各自需求的处理记录，不是只有一条 `BULK` 汇总）、作废 `DELETE /{domain}/{id}?reason=` |
| 必填口径 | 回退边（`rework: true`）与 `reason: true` 边**必填**（服务端 400 `REASON_REQUIRED` 等）；普通推进边**选填**（写不写都要能推进） |
| 可见性（硬要求） | ① 收起态摘要可见最近一条；② 展开后**逐字完整**可见；③ 键名显示为「处理意见」 |
| **不得截断** | 理由类字段（`reason`/`note`/`comment`/`conclusion`/`decomNote`/`voidCriteria`/`why`/`selfApproveReason`）完整显示；通用 80 字截断只用于**非语义字段**。实测需求域 `reason` 最长 **313 字**、仅流转面就有 33 条 >80 字——按 80 字截断会把"看不到"变成"看不全"，**同族缺陷，不算修好** |
| 反向口径 | 未填理由的流转**不得**产生一条空「处理意见」（`diff` 里没有 `reason` 键就不渲染该行） |

#### 5.4.6 `diff` 键名标签表与状态码映射

审计 `diff` 的键是**机器名**，直接展示对业务用户等于没写。统一构件内置标签表（`HistorySection.DIFF_LABELS`），
**未登记的键回落原键名**（前向兼容：别的批次新增键不会渲染成空白，也不会编译期报错；只是"不够好看"，不丢信息）。

| 类别 | 键 → 标签 |
|---|---|
| 流转（十域共同口径） | `from`+`to` → **合并为一行**「状态」`旧 → 新`；`reason` → 「处理意见」；`fromStatus`/`beforeStatus` → 「原状态」；`obsoleteAs` → 「作废身份」 |
| 变更明细 | `before`/`after` → 「旧值」/「新值」；`changed`/`added`/`removed`/`skipped` → 「变更/新增/移除/跳过条数」 |
| 意见与依据 | `note` → 「备注」；`comment` → 「意见」；`conclusion` → 「结论」；`why` → 「说明」；`decomNote` → 「分解说明」；`voidCriteria` → 「作废判据」；`selfApproveReason` → 「自批理由」；`evidenceRef` → 「证据引用」 |
| 业务键 | `reqCode`/`req_code` → 「需求编号」；`item_code` → 「物料编码」；`cbbCode` → 「CBB 编号」；`prjCode`/`project_code` → 「项目编号」；`eco_code` → 「变更单号」；`ecr_code` → 「变更申请号」；`doc_no` → 「文档编号」；`riskCode` → 「风险编号」 |
| 版本与身份 | `rev`/`version` → 「版本」；`actor` → 「当事人」；`login` → 「账号」；`role` → 「角色」；`stage` → 「阶段」；`milestone` → 「里程碑」；`signature` → 「签名」；`round` → 「治理轮次」 |

**状态码 → 界面名**：`from`/`to` 的取值经各域 `useFlow()` 的 `stateLabel(code)` 翻译。
**取不到就回落原状态码**——产品域的状态码本身就是中文（`"概念"`/`"作废"`），任何"假设一定是英文码"的实现都会把它翻没。

### 5.5 详情面板内联横幅（状态提醒 / 关系可达）

> 落地：V104「需求订正/取代」（`RequirementsPage` —— `supersededBy` 警示 + `supersedes` 信息条）。

**适用判据**：当"当前读到的这条记录**不一定是最新有效版本**"或"本条与另一条记录存在**取代/从属关系**"时，
必须在详情面板**顶部**（`extra` 之首，字段区之前）给出横幅，而不是把信息藏在字段里或处理记录里。

**两级语义（颜色即语义，不得混用）**：

| 级别 | 底色 / 边框 | 触发 | 必须包含 |
|---|---|---|---|
| 警示 ⚠ | `#fef2f2` / `#fca5a5` | 本条已被取代/订正、已失效、已被驳回 | ①**取代者对象号**（可点）②**一句"本条内容保持原样不可修改，请以订正条目为准"**③被取代条目自身状态 |
| 信息 ℹ | `#eff6ff` / `#93c5fd` | 本条是取代/订正者、本条派生自某条 | ①**被取代对象号**（可点）②被取代条目标题 |

**强约定**：

1. **横幅里的对象号必须是链接，且必须能到达**——`<a href="/{域}?open={id}">`（深链是页面的既有入口，
   跨页跳转用硬导航即可，不必引入路由依赖）。"死文本"是明确禁止项（同 §6.8 的 DCP0 列缺陷）。
2. **两个方向都要有**：被取代条目显示警示条，取代条目显示信息条。只做单向会出现"两条看起来都像有效的"，
   审核人无法判断该信哪条。
3. **横幅只读**：它是关系投影，不是编辑位。任何"解除取代关系"的诉求应走新建条目，不做原地清除。
4. 横幅文案必须**自解释**（说清"为什么不可修改 + 该看哪里"），不接受只有对象号的裸提示。

### 5.6 面板高度与动作行留白（2026-09-17 · 用户反馈"放大时按钮行离 预算/风险等级 留空太多"）

> 编号说明：本节原写作 §5.5，与**既有的 §5.5「详情面板内联横幅」**撞号（后者已被 doc 13/14 引用），
> 2026-09-17 批次26 改为 §5.6；文中提到的 `doc 08-§5.5` 一律指"内联横幅"那一节。

**根因（实测）**：`.dp-body{flex:1}`（`flex:1 1 0%`）在**内容矮于容器时把 body 撑满**，底部动作行被推到面板最下沿。
放大态是两列网格，字段内容约 286px 而容器约 521px ⇒ 实测「最后一行内容底边 → 按钮行顶边」= **175px**。

| 规则 | 值 | 为什么 |
|---|---|---|
| `.dp-body` 伸缩 | `flex: 0 1 auto`（**禁 `flex:1`**） | 内容高度决定 body 高度，动作行紧随内容；富余空白留在动作行**下方**（符合"动作在内容之后"） |
| `.dp-foot` 上边距 | `margin-top: 14px`（**不加 `auto`**） | `auto` 会把按钮推回最下沿，等于把刚修掉的留空造回来 |
| 卡片高度 | 由内容决定，`min-height` 只作下限（`.dp{460px}` / `.dp.expanded{min-height:70vh}`） | 面板允许**比卡片矮**：空白留在卡片内、动作行上移（本批未给卡片加高度约束，故无需改父级） |
| 字段行 | `.dp-row{margin-bottom:10px}`（不变） | 行距即"内容自然高度"的一部分，判据容差按它算（10px + 6px 余量） |

**验收口径（固定，勿改成"按钮行在可视范围内"）**：
① 「最后一行内容底边 → 动作行顶边」**≤ 40px**；② 动作行在文档流内、未被裁剪；
③ `body 实际高度 − 内容高度 ≤ 16px`（证明没有被拉伸）。
量值基线：**修前 175px → 修后 24px**（未放大态同口径 24px；需求/任务书/物料页 14px）。
实现见 `plm-b25-dp-gap.cjs`（CI **W22**）。

> **取证纪律**：量"面板相对容器"必须用 `panel.parentElement`，**不要用 `closest('.card')`**——
> 详情面板内部本来就嵌着 `.card`（项目页的"产品种类变更/关联需求"等区块），`closest` 会命中内层卡片，
> 量出来的差值会荒谬到 579px/691px，把**正确的布局判成红的**（本批实际踩过，见 L-395）。

### 5.7 手写表单的字段行：整行占位子元素必须 `flex-wrap`（2026-09-17 批次26 · 用户反馈"属性字段宽度接近 0、无法输入"）

**现场（真浏览器实测，`getBoundingClientRect`）**：上市后监督的投诉/CAPA/召回详情面板里，
带**提示语**的字段一律**宽 6~8px**（投诉「评估结论」6px、CAPA「根本原因」6px/「有效性结论」6px、
召回「召回完成率」8px/「有效性评估结论」6px/「变更记录 ID」8px），而不带提示语的同款字段 **1251px 正常**
——用户看到的就是"这几个属性框几乎看不见、输不进去"。

**根因**：字段行是 `<label style={{display:'flex'}}>`，三个子元素——标签 `width:96 flex:0 0 auto`、
控件 `flex:1 1 0%`、**提示语 `flex:1 1 100%`（整行占位）**。父级**没有 `flex-wrap:wrap`** 时三者挤在一行：
提示语按 100% 基准吃掉全部自由空间，而控件基准是 0 ⇒ 被压到 0 宽。**"整行占位"这个意图只有配合换行才成立。**

| 规则 | 要求 |
|---|---|
| 字段行容器 | `display:flex` **必须同时** `flexWrap:'wrap'`（子元素里只要有 `flex:1 1 100%` 一类整行占位元素） |
| 整行占位子元素 | 允许用 `flex:'1 1 100%'` + `marginLeft`（对齐标签宽度），但**不得**在无 wrap 的容器里使用 |
| 控件宽度 | 手写表单控件宽度以 `flex:1` + `minWidth:0` 表达；**禁止**依赖 `width` 缺失时的默认尺寸 |
| 判据 | 详情面板内**每个** `input/textarea/select`（复选框除外）实测宽度 ≥ **200px**；断言按"最小值"取（漏一个字段就是一批人输不进去） |

实现见 `PostMarketPage.EditForm`；判据 `plm-b26-console.cjs` P6a/P6b/P6c（CI **W23**）。

> **为什么这类缺陷值得单列一节**：它是**静默**的——代码里 `flex:1` 看起来完全正确，静态读码看不出问题；
> 页面上也不报错，只是那几个框"窄得像条线"。**只有量 rect 才会暴露**（同族：L-395 量错对象、L-396）。
> 排查口径固定为"**对照法**"：同一页里"有提示语 vs 无提示语"的同类字段宽度对照，一眼定位到差异来源。

### 5.8 附加区块（`extra`）在展开态独占整行（2026-09-23 批次53 · 用户反馈「左边很空、右边挤、纵向很长」）

**用户原话**：「需求详情面板展开显示时，法规条款引用输入控件在左边，很空；而右边需求的流程、
订正/取代需求、RTM追溯、流程处理按钮等，挤在右边，导致占据纵向空间很长，建议这几个控件自身独立占据一行，
不要跟 法规条款引用输入控件 挤在同一行」。

**根因（真浏览器几何实测，需求详情面板 `?open=3232`，修前）**：展开态 `.dp-body` 是两列网格
（`grid-template-columns: 639px 692px`），而 `extra` 作为**普通网格项**被自动排进**最后一行的右半栏**：

| 读数（修前） | 值 |
|---|---|
| 附加区块 | `x=918 w=692`（= 整行的 **51%**）· `y=1595…2023` |
| 「法规条款引用」行 | `x=257 w=639`（左栏）· `y=1595…2013` · **行高 418px**（自身内容仅 30px） |
| 两者纵向 band | **完全重叠**（同一行） |

⇒ 左侧一个 30px 的输入框在 418px 高的行里居中（"很空"）；右侧半栏里塞着流程条 + 订正取代 + RTM +
流转按钮 + 处理记录，只能一路换行（"纵向空间很长"）。

**规则**：`extra` 一律整宽——`DetailPanel` 把它包进 `.dp-extra`，`styles.css` 给一条
`.dp-extra { grid-column: 1 / -1; min-width: 0; }`。

| 读数 | 修前 | 修后 |
|---|---|---|
| 附加区块 | `x=918 w=692`（51%，右栏） | `x=257 w=1353`（**100%**，左缘与字段区对齐） |
| 「法规条款引用」行高 | **418px**（内容 30px ⇒ 空白 388px） | **30px**（贴合内容） |
| 四类控件宽度 | 各 692px（半栏） | 各 **1353px**（整行，各自独占一行） |
| 面板总高 | 1736px | 1790px（**+54px**） |

> **面板为什么反而高了 54px**（诚实读数）：修前那段纵向空间是"借来的"——字段行与附加区块**共用一行**，
> 行高取二者较大值（`max(30, 428) = 428`）；修后两者各自成行 ⇒ `30 + 行距 24 + 428 = 482`，净增 54px。
> 换来的收益不在总高，而在**每个控件拿到整行宽、左侧不再出现 388px 的空行**。
> 若后续还要压纵向，方向是"区块内部两列并排"（如流程条 ∥ RTM），但那是**改变本节的排布约定**，
> 需用户另行裁定（批次53 按用户原话"各自独立占据一行"实现，未擅自两列化）。

**纪律**：判据落在**唯一出口**（`DetailPanel` + `styles.css`），14 个详情面板同时受益；
页面**不得**自己给 `extra` 写内联 `gridColumn` —— 批次53 已把 CBB 资产库页
（`CbbLibraryPage.tsx`，此前内联 `gridColumn:'1 / -1'` 并注明"不改 styles.css"）上收删除，
同 `.dp-row.wide`（§3.6 / doc 14 G-UI-2b）的处置口径。

**验收口径（固定，勿改成"看起来不挤"）**：① 附加区块宽 ≥ 0.9× 字段区整行宽且左缘对齐（容差 2px）；
② 与**任何** `.dp-row` 纵向不相交（容差 2px）；③ 整体位于最后一个字段行之下；
④ 区块内流程条/RTM/流转动作/处理记录**各自独立成行**且各宽 ≥ 0.9× 整行宽；
⑤ 字段行不被高邻居撑高（行高 ≤ 1.6× 自身最高子元素）；⑥ 反例：字段区仍是两列。
实现见 `plm-b53-dp-extra-row-walkthrough.cjs`（CI **W44**）；量值基线：修前 `PASS=6 FAIL=5` → 修后 `PASS=11 FAIL=0`。

> **为什么必须量几何**：DOM 里附加区块一直存在、文本一直可读、接口一直 200——
> "元素存在""文案正确""套件绿"全都证明不了"它没有和字段挤在同一行"。**只有外接盒关系能钉死它。**

### 5.9 页面文案纪律：异常才显示（批次54，2026-09-27 · 用户裁定 D54-4）

**一句话**：页面正面只放**结论与数字**；口径解释、教学句、设计原则**默认不上屏**（要看才查的进 `title`）；
而**领域不变量要求披露的内容，改为"真有缺口才出现"，且出现时必须一行说清、异常时不得缺失**。

**由来（用户原话）**：「BOM管理和产品结构管理的界面，文字描述太多了……设计原则之类不用显示于界面上，
把冗余的文字去掉」；以及「异常才显示，正常态只留数字」。此前页面把"设计原则"（三条口径的差别、
视图长描述、"结构行按视图分开维护"的教学句）常驻铺开，真正的异常披露反而埋在其中，
两类文字混在一起后，**用户对整块文字一律不再读**——于是异常也被漏掉。本节就是把两者分开。

#### 5.9.1 三个档位（写文案时先归类，不要靠"感觉长短"判断）

| 档 | 内容 | 落点 | 例 |
| --- | --- | --- | --- |
| **① 结论与数字** | 本次算出来的结果：金额、条数、状态、命中数 | 正面常驻 | `BOM 汇总：¥1,234.00` · `明细 12 行` · `状态：设计` |
| **② 要看才查的口径** | 固定口径、字段含义、三家口径的差别、后端给的溯源说明 | **控件/标签的 `title`**（悬停可见），正面最多留一个短标签 | 「互替货源口径」下拉的 tooltip；「汇总口径」标签；「当前视图：EBOM」的 tooltip |
| **③ 要删的教学句** | 视图长描述、指南式句子、"请到某页维护"式指引、复述页面本身行为的解释 | **删**（不搬家到 tooltip） | 「结构行按视图分开维护：这里显示的是 EBOM；别的视图（PBOM/MBOM…）若有行，可切换上方视图核对」——视图下拉本身就把视图列全了，切换即核对 |

- **③ 的一条例外**：**可行动的一句提示保留**（如"放宽时间段或点上方「清空时间筛选」"）——
  它告诉用户**下一步点哪里**，不是解释系统怎么设计。判据：把这句话删掉，用户是否还知道该做什么？
  知道 ⇒ 是教学句（删）；不知道 ⇒ 是行动提示（留）。
- **措辞不因"异常才显示"而变模糊**：披露句压到一行仍要保留**判断所需的最小事实**
  （缺口条数、按 0 计、结论不成立），细节（清单、原因、处置）进 `title`。

#### 5.9.2 必须保留的披露清单（**异常时不得缺失**）

这四类不是"文案"，是**领域不变量要求平台说出来的事实**——正常态可以完全不出现，
**一旦成立就必须出现**，且不得因为"页面要清爽"被删掉：

| # | 披露 | 出现条件 | 不变量 | 正面一行必须含 |
| --- | --- | --- | --- | --- |
| 1 | **未解析位金额计 0** | 结构位用了互替组但还没有候选成员（未解析数 > 0） | 金额口径完整性 | 未解析位数 · 「按 0 计」 · 「总额偏低、不给超差结论」 |
| 2 | **币种缺口** | 有成本行没有币种（`currencyGap` 非空） | 汇总口径唯一（本币才参与汇总） | 无币种行数 · 合计金额 · 「单位不成立」 |
| 3 | **汇总不完整** | 有未维护计划成本的行（`complete=false` 且非互替位未解析） | 数据缺失下结论无意义 | 未维护行数 · 「不给'是否超目标成本'的结论」 |
| 4 | **目标成本基线非权威** | 目标成本基线多来源不一致或未确认权威出处 | 目标成本基线权威性 | 「口径冲突」/「基线非权威」·「不可作为投资决策依据」 |

- 第 1、3 条**互斥**（两者说的是两件事：一个是"位没有成员"，一个是"件没有成本"），
  同屏时各出现一行，不合并、不互相冒充。
- **正反两面都要验**：只验"异常时出现了"会漏掉"正常态乱显示"；
  只验"正常态没有"会漏掉"异常时也没出现"（后者正是本仓记过的"假绿"形态）。
- 每句**一行**：把长句拆成事实片段（`·` 分隔），可读的是数字；
  折叠进 `title` 的必须是"要看才查"的部分（清单、原因、处置路径），**不得**把判断所需的事实也折进去。

#### 5.9.3 面向用户的文案不得出现内部编号与开发术语（G-UI-4 的延伸）

页面（含 tooltip、按钮 title、提示条）里**不得**出现：需求/规则编号（`REQ-…` / `BR-0x` / `IBR-xx`）、
流程状态码裸值（`DRAFT` / `RELEASED` 一类，必须经状态码→界面名映射）、表名/列名（`t_bom.status`、`cbb_source`）、
错误码、端点路径。

- 这是既有规格 **G-UI-4「后端原文不得直出界面」**（doc 14）在本批的延伸：
  原来的判据只管"报错文案"，现在**同样管正面文案与 tooltip**。
- **口径**：界面说人话（`草稿`/`设计`/`已发布`），编号只在**手册与开发文档**里出现——
  用户手册可以在括号里标注内部编号（它的读者含实施/开发），页面不行。
- 已落地的形态：BOM 网格的「BOM状态」列文案与 `title` 都由**同一份映射**产出（不写裸枚举），
  同一映射也被列表与事实条复用（两态时本页三处各写一份，加第三态必漂移）。

#### 5.9.4 判据（可机器断言）

| 锚点 / 判据 | 断言方向（**双向**） |
| --- | --- |
| 披露块的 `data-testid`（如 `currency-gap` / `unresolved-sub-positions` / `cost-incomplete`） | 缺口成立 ⇔ 出现；**缺口不成立时必须不存在**（"正常态只留数字"） |
| 披露块文本行数 | 正面块 ≤ 1 行（`·` 分段不算换行）；细节在 `title` |
| 页面容器（先剥注释、限定页面范围）内文本 | 不含 `REQ-` / `BR-0` / `IBR-` / `t_bom` 等内部串；反向实例：把一条已知带枚举的文案临时注入，断言扫描能抓到它（防止扫描器恒绿） |
| 控件 `title` | 被删掉口径原文的控件必须**仍有** `title`（教学句可以删，"要看才查"不能丢） |

#### 5.9.5 服务端生成文案的边界：前端不"清洗"后端文本（2026-09-28 走查整改）

**规则**：§5.9.3 的"去编号"纪律**只管前端自写文案**；**服务端拼接下发的文本**（如需求「下一步应由谁处理」
的派发诊断、作废操作的 blockers、管道驾驶舱瓶颈议程、规则名称里的示范说明）若含内部编号
（`devProjectId=604` / `RCN-04` / `QUESTION 象限` 一类），**前端不得在前端侧做字符串清洗**——
清洗规则会与服务端文案一起漂移，今天是替换成功、明天是替错了地方。正确路径：

1. 走查发现 ⇒ 登记为**后端依赖项**（进整改报告的"遗留后端依赖"一节）；
2. 由后端在**生成处**改写（那里知道每个片段的语义）；
3. 前端只保证**自己写的**文字干净（§5.9.3 判据照跑）。

**本轮实例**（均登记为后端依赖）：需求 nextHandler 诊断串、作废 blockers、`PipelineDashboardPage` 议程文案
（前端只去掉了与其重复的标题行——重复铺标题是前端自己的错，议程正文归后端）。


### 5.10 字段分组（`sections`）：分组是域知识入参，桶逻辑唯一实现（2026-09，UI 优化两轮落地）

**能力**：`DetailPanel` 可选入参 `sections?: DetailSection[]`（`{ title, fields, collapsible?, defaultCollapsed? }`）。
非空 ⇒ 按分组渲染；不传 / 空数组 ⇒ **回落扁平渲染，行为逐字不变**（向后兼容，未接入页面不受影响）。

**架构口径**：哪几个字段算一组是**域知识**（需求域与任务书域不同），面板只管"分组怎么渲染"——
同 `dangerActions` 的处置口径：构件管通用形态，域知识由调用方注入。

**唯一实现出口**（`components/DetailPanel.tsx`，页面不得再复制桶逻辑）：

```ts
// 页面只写声明常量（文件顶部）+ 一行 useMemo
const X_DETAIL_SECTION_SPECS: DetailSectionSpec[] = [ ... ];
const detailSections = useMemo(
  () => buildDetailSections(X_DETAIL_SECTION_SPECS, detailFields, extDetailFields),
  [detailFields, extDetailFields],
);
// 调用点：fields 照旧传（回落兜底）+ sections={detailSections}
```

`buildDetailSections(specs, detailFields, extDetailFields = [])` 的**六条口径**：

1. 归属表 `code → 组下标`，同一 code 被两处声明时**首个声明胜出**（一个字段只出现在一组）；
2. **遍历 `detailFields` 本身**建桶 ⇒ 组内顺序天然等于原字段顺序（分组只改"显示在哪一块"，不改字段先后；
   走查时差异只有分组标题）；声明了但字段不存在（元数据退役）的 code 自动缺席，无需特判；
3. 重复 code 只入桶一次（`seen` 去重）——扩展字段与核心字段重号时不会渲染出两行 / 校验两次；
4. 空组不渲染（草稿态字段少时相关组自然消失，无需第二套分组声明）；
5. 未被认领的字段落末尾「**其他字段**」兜底组（正常为空）——防"新增固定字段忘了登记分组 ⇒ 字段凭空消失"；
6. 必填校验与提交收集取**各组并集**（面板内 `allFields`）⇒ 切分组不会造成"看得见却提交不上"的半通状态。

**声明规范**（`DetailSectionSpec`）：

| 字段 | 口径 |
| --- | --- |
| `title` | 分组标题 = 折叠态的稳定标识，**须唯一且稳定**（改标题 = 丢用户折叠偏好） |
| `codes` | 只写 `code`，**不复制** label/kind/required 等字段属性（第二份事实必漂移） |
| `dynamic` | 元数据驱动的"扩展属性"组：成员 = `extDetailFields` 中未被其它组认领的字段，不写死 code |
| `collapsible` / `defaultCollapsed` | 条目数不定的组（扩展属性）用 `collapsible:true, defaultCollapsed:true`：先看得到"有这一块"，再按需展开 |

**配套 CSS（styles.css，全模块自动生效）**：`.dp-section`（分组容器）/ `.dp-section-title`（组标题）/
`.dp-section-body`（字段网格，与扁平 `.dp-body` 同规则）；`.dp.expanded .dp-body` 全屏双列下分组体照常两列；
`extra` / explain 块整行规则见 §5.8（唯一出口在构件 `.dp-extra`）；`.dp-foot` 底部按钮区 sticky。

**分组只换容器、不换字段判据**：`wide` 自动判据（`longtext/json/jsonread/kv/multi` 独占整行）、`fieldExtras` 插槽、
`required` 标星、`postAnalysisOnly` 阶段锁定，分组分支与扁平分支走同一个 `renderFieldWithExtras` 出口——
分组前后这些行为逐字一致。
