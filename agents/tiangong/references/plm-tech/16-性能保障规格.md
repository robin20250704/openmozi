## 3. 性能保障一般性原则（P-1 ~ P-8）

**P-1 列表不背详情（N+1 禁令）。** 列表端点只返回列表所需的字段与一次聚合结果；任何"对列表每一项再取一次详情"的实现都算缺陷。
*证据*：`09-§1.10 缺陷#1`（项目清单内嵌门明细：每项目 93 次查询、1.69s/842KB → 瘦 summary 后 0.24s/33KB）；
批次27 实测 `ReviewService.list()` 对每条评审复用 `get(id)`：`/reviews?pageSize=20` 单次 **564ms、读 34.8 万行**、
`t_review_signer` 被扫 **263 次**，修复后 **32ms、2226 行**（详见 §7 基线）。

**P-2 请求级记忆优先于跨请求缓存。** 同一请求内重复出现的判定（权限/角色/成员/元数据）应在**请求作用域**内记忆一次；
跨请求缓存必须显式声明失效点与一致性时限（S-4/S-11）。请求级记忆的收益与风险都最小：与请求同生命周期，不产生过期事实。
*证据*：批次27 之前每次 `@PreAuthorize` 都查 `t_permission_rule`；`/items?pageSize=50` 单次对 `t_project_member` 发起 **179 次全表扫**。

**P-3 读放大必须可观测。** "接口慢"要能归因到"读了哪张表、扫了多少行"。行读取量（`seq_tup_read + idx_tup_fetch`）与机器负载无关，
是首选代理指标；墙钟毫秒在 CI 并发环境下不可靠（本批实测：同一接口在负载下 564ms、空载 32ms）。
> 测量纪律（本批踩坑换来的）：PG15+ 统计延迟落盘（~1s），`pg_stat_force_next_flush()` **只对执行它的会话**生效
> ⇒ 必须在**同一会话**里"先刷新再读"，且读取前后静置 ≥1.5s，否则会把读放大错记到相邻快照上（表现为同一接口 0 行/25 万行乱跳）。

**P-4 派生数据必须可重建、且重建必须收敛。** 检索索引、流水线快照、驾驶舱聚合都属派生数据：允许删除后重建，但**重建必须能清掉已删对象的残留**。
*证据*：批次27 清理后，PG 侧索引已重建（1731 行），而 ES 侧仍保留已删项目/产品的"幽灵文档"（3345 条 vs 1731 条），
搜索端点照样把它们返回给用户 —— 根因是 `SearchIndexer.rebuild()` 只 upsert、不删除。**这是本批发现的产品缺陷之一**（见 `negatives.md`）。

**P-5 分页与上限只有一个事实源。** 上限、默认值、别名、超限行为都必须落在 `Paged.MAX_PAGE_SIZE` 与 `G-API-1.2` 上（引用 §2）。
前端不得用"预加载一页当全量 + 本地过滤"绕过（`08-§9 陷阱 #25`）。

**P-6 性能是"每个用户路径"的属性，不是"某个接口"的属性。** 判据要挂在目标用户会走的路径上（列表页首屏、详情深链、选择器、台账导出），
而不是只测一条最热的 SQL。批次27 的取证脚本按"页面会打的接口"成组取样（工作台/需求/物料/文档/项目/评审/上市后），就是这条原则的落地。

**P-7 门禁必须"能拦住"。** 一条没有被 CI 执行的 SLO 等于没有（`13-工程门禁` 的既有立场）。本文新增 **T3-7 性能冒烟**（§5）把读放大做成每次回归都跑的断言。

**P-8 测试时长也是性能。** 回归耗时是可度量的产品资产：门禁跑得慢 ⇒ 批次变小、验证变浅、缺陷后移。故给出回归时长预算与并行纪律（S-10）。

## 4. 规格要求（可判定）

| # | 要求 | 判定方式 |
| --- | --- | --- |
| **S-1**（新增） | 每个列表/聚合端点须满足**单次调用行读取上限**；阈值记在该端点的冒烟项里，且不得高于"该端点合理读取量的 3 倍以上" | CI T3-7 `plm-perf-smoke.cjs`（`PASS=n FAIL=0`） |
| **S-2** | 分页契约符合 `G-API-1.2`：`page`/`pageSize`/`total`、超限不静默截断、`pageSizeCapped` 回显、上限常量唯一 | `plm-contract-paging-verify.cjs`（既有，T3 层） |
| **S-3** | 列表读路径**不得**逐项复用详情读模型；批量路径必须与逐条路径**逐字段等价**，并给出查询数下降的定量断言 | 单测：批次27 `ReviewListBatchEquivalenceTest`（等价性 + `t_review_signer` 扫描数 ≤1/3 + 全库读行数减半） |
| **S-4** | 请求级记忆只在请求线程内生效，写路径必须显式失效；（跨请求缓存一律声明作用域+失效点） | 单测 `27-2 请求级记忆生命周期`；写路径 `RequestCache.invalidate*` 调用点自查 |
| **S-5**（新增） | **性能回归门禁**：任何改动后，T3-7 必须全绿；端点行读取量或耗时被突破即视为性能缺陷 | CI T3-7 |
| **S-6** | 新增外键/逻辑引用列**必须**建索引并登记；未建索引的 FK-like 列不得上线 | `plm-ref-integrity.sh`（逻辑引用对账）+ DDL 评审；本批已给出 ~70 处待补索引清单（见 `tools/p27-stats.sql` 取证） |
| **S-7** | 慢查询口径：单次调用 > 1s 或行读取量超预算的端点，必须**登记**到本文 §7 并在该批次给出处置 | 巡检 + 每批性能冒烟输出 |
| **S-8** | 数据体量治理：删除测试数据必须"先备份 + dryrun（同事务回滚）+ 前后行数取证"；WORM 表不得删改（其指向已删对象的行属设计口径）；清理后必须重启服务以刷新进程内/侧车索引 | `p27-db-prune.sh`（dryrun 自证"前后逐表一致"）+ 清理后复核 |
| **S-9** | 前端禁用"预加载单页当全量 + 本地过滤"，主业务对象选择一律用 `SearchPick`；列表必须成对交付分页 UI | `08-§9 陷阱 #25`、`12-G-LST-2`；UI 走查 W15/W21 |
| **S-10**（新增） | **回归总时长 ≤ 15 分钟**（T1+T2+T3+T4 全量、干净窗口）；超预算必须给出压缩方案而不是延长预算 | CI 计时日志（`p27-ci-timing.sh`） |
| **S-11** | 任何缓存/索引的失效时限须显式声明；派生索引重建后必须与事实源数量一致（不允许"重建后仍有幽灵文档"） | `plm-index-consistency.cjs`（CI **T4-10**）：逐域 `ES == t_search_index` + 注入幽灵文档的自检；重建端点返回 `{indexed,deletedPg,deletedEs,remaining}` |
| **S-12**（新增） | **全部 SLO 的声明前提 = 50 并发用户（≈10 QPS 读 / 2 QPS 写）**；并发前提变更必须重测后再改声明 | 本文 §6.2 G-1；压测/冒烟报告的抬头必须写清并发度 |
| **S-13**（新增） | **数据增长三档触发线**：① 物料/需求/文档任一表 > 20 万行；② 被直接查询的表 > 500 万行；③ 审计/事件表 > 3000 万行（评估分区/归档）。命中任一档 ⇒ 重跑基准、复核查询计划与索引 | 巡检记录（每次清理后重记体量基线，见 §8 附录 B） |
| **S-14**（新增） | **可用性**：研发时段（8:00–20:00）单实例 99.5%/月；维护窗口 ≤30 分钟/次且提前公告；**ES 不可用检索降级到 PG、AI 不可用不阻断业务流程**；**数据不丢为硬要求** | 探活巡检 + 降级路径走查（`SearchService` 降级已实现） |
| **S-15**（新增） | **前端包体预算**：路由 chunk ≤ 60 kB（gzip ≤ 20 kB）；首屏主包 ≤ 400 kB（gzip ≤ 130 kB）；重型库（**AG Grid `grid-*` / ECharts `chart-*`** / Univer）必须独立 chunk 且按路由懒加载，不得进首屏 | `plm-frontend-budget.sh`（CI **T3-9**）；基线见 §8 附录 D |
| **S-16**（新增） | **批量操作上限（服务端校验，超限 400，不得静默截断）**：需求批量推进 ≤200 条；列表批量选择/粘贴 ≤500 行；CSV 导入 ≤2000 行；批量下载 ≤50 个对象 | 既有 `bulkTransition` 200 条校验为事实源；新批量端点照此表实现并加断言 |

### 7.1 本次定位到的四类性能缺陷

| # | 缺陷类型 | 现象（实测） | 机制（根因） | 修法 | 结果 |
| --- | --- | --- | --- | --- | --- |
| **D1** | **判定型读放大**：同一请求内反复解析同一事实 | 每个 `@PreAuthorize` 都查权限规则表；`/items?pageSize=50` 单次对 `t_project_member` **179 次全表扫、读 13.9 万行** | 判定函数是"纯查询"，没有请求级记忆；同一 (项目,用户) 在一次请求里被解析 N 次 | 引入**请求级记忆**（与登录上下文同生命周期）+ 规则表一次取全；写路径显式失效 | `/items` **16ms、4.5k 行/次**；`/me` 2ms |

| # | 步骤 | 判据（做到什么程度算完成） |
| --- | --- | --- |
| **O-1** | **先取证，不动手** | 拿到"哪个接口、每次读多少行、扫多少次、多少毫秒"，而不是"感觉慢"；口径见 §7.5 |
| **O-2** | **按机制归类** | 归入 D1~D4 之一（判定型读放大 / 列表背详情 / 派生不收敛 / 门禁缺失）；不同类别的修法完全不同 |
| **O-3** | **一次只改一类** | 同类改动一次提交；改完**立刻用同一口径复测**，避免"多项一起改，无法归因" |
| **O-4** | **等价性优先** | 改造前后输出**逐字段相等**（新写一个等价性测试并长期保留）——先证明"没改坏"，再谈"变快了" |
| **O-5** | **缓存必须声明作用域与失效点** | 请求级记忆：写在哪、活多久、谁能失效；跨请求缓存必须写清失效事件；**未声明失效策略的缓存视为缺陷** |
| **O-6** | **列表与详情读模型分离** | 列表只取列表需要的列与关联；"列表需要的字段"由界面契约决定，不由详情模型决定 |
| **O-7** | **索引缺口先登记再补** | 用"无 FK 但形如 `*_id` 的列 × 实际查询条件"做取证（本批盘点出 61 个登记列、识别出多处缺索引），补索引作为独立小改动验证 |
| **O-8** | **前端三查** | ① 是否把"预加载的一页"当全量、再在本地过滤（`12-G-UI/G-LST`）；② 是否有请求风暴（驾驶舱逐项目拉取 ≈111 次）；③ effect 依赖是否导致筛选重复请求 |
| **O-9** | **门禁同批落地** | 优化必须同时带来"能被拦住"的机制（T3-7），否则下次退化仍无人知 |

### 7.4 阈值怎么定（本次 T3-7 的标定法，可复用）

1. **取样**：清理 + 修复后的**空载窗口**实测各端点"行读取量/次"与毫秒；（本批数据见 §8 附录）
2. **阈值 = 实测 × 3 左右余量**，且**必须显著低于缺陷量级**（例：`/reviews` 实测 2.2k 行 ⇒ 预算 80k；缺陷量级 348k，中间留 4 倍以上差距）；
3. **判据只用单调量**：行读取量/扫描次数/请求数——它们随数据规模与缺陷规模单向变化；毫秒只做**宽松兜底**（避免在 CI 并发下假红）；
4. **带"地板"的复合指标禁止设倍数阈值**（本次教训：把"全库读取行数应减半"写成断言，在 490 行恒定地板下被压成 1.42× 而误红 ⇒ 改为方向断言 + 用扫描次数做确定性判据）；
5. **阈值变更须双写**：冒烟脚本 + 本文档 §4/§8 同步更新，禁止只改脚本。

### 7.5 度量纪律（本批最贵的一课）

| # | 纪律 | 不这么做会怎样 |
| --- | --- | --- |
| **M-1** | PG 统计是**延迟落盘**的；`pg_stat_force_next_flush()` **只对执行它的会话生效** ⇒ 刷新与读取必须**同一条命令**（同一会话） | 跨会话刷新无效：同一接口读数一会儿 0 行、一会儿 25 万行，归因全乱 |

| **M-5** | 记录口径：**谁在测、测什么、几次取均值、窗口是否干净** | 三个月后没人能复现你的数字 |
