## 0. 文档目的与一句话结论

**一句话结论**：现有工作台 `/` 只是「跨域待办的一块公告板」——它按 `objectType` 把待办切成九宫格，**没有主语、没有筛选、没有分页、点一下就跳走**。本文把它改成**一个以「我」为主语的页面**：`我的看板 / 我的任务 / 我的流程 / 我关注的`，其中**任务与流程的五视图只换查询维度、不建新表**，只有「我下达」补一列、「我关注」建一张表。

**本文回答四个问题**：

1. 为什么现状不满足"面向人的作业"（**§1**，全部带证据）
2. 目标形态是什么（**§3~§6**）
3. 每个视图的**精确口径**是什么、数据从哪来（**§3/§4/§5**，可直接实现）
4. 操作步骤怎么最简化（**§2**）

**效力**：本文与 `12/13/14/16/17/18/19` 号产品级规格冲突时，**产品级规格优先**（例如分页纪律以 `12` 号文 G-LST-2 为准，本文不复述数值）；交互细节以 `08-前端实现规格.md` 及其 `frontend/` 子文件为准。

## 1. 为什么现状不满足（问题取证）

### 1.1 三条实测证据

| # | 现象 | 证据（文件:行） | 后果 |
| --- | --- | --- | --- |
| P-1 | 待办**一次全量渲染**：无分页、无筛选、无排序切换 | 前端 `frontend/src/pages/WorkbenchPage.tsx:50` 调 `GET /_platform/tasks/my`；后端 `platform/flow/FlowTaskService.java:750` 的 SQL `ORDER BY t.due_date NULLS LAST, t.id` **无 LIMIT**；`PlatformController.java:214` 该端点**无任何查询参数** | 手册实测读数「需求待办 **76 项**」挤在一个卡片里（`.creature/tasks/plm-user-guide-refresh/findings-D.md:32`）。用户原话：「密密麻麻的待处理对象清单」 |
| P-2 | 行点击 = **同页跳走**，工作台上下文丢失 | `WorkbenchPage.tsx:69-72` `go(t) → nav(linkOf(t))`；`nav` 是 `react-router` 的 `useNavigate()` | 处理完一个对象后回到工作台，页签/筛选/滚动位置全丢。用户原话：「每次跳转过去离开工作台了，查看其它对象又要打开工作台」 |
| P-3 | 轻量动作**只覆盖一个域** | `WorkbenchPage.tsx:208` 渲染「推进」按钮的条件是 `t.objectType === 'REQ'`；同文件 `:134-135` 注释明写「其它域 transition 端点形态不同未接入」 | 非需求域待办**只能跳转处理**——为点一下"批准"而离开工作台 |

### 1.2 P-2 不只是体验问题，是**违反已立规格**

`docs/plm-tech/frontend/01-design-tokens-shell-layout.md` §3.6 **G-UI-7-2** 已经把「工作台待办行跳转」列入适用入口，要求：

> 该引用必须是**真链接**（`<a href>`，不是 `onClick` 伪装的按钮）且 `target="_blank"` + `rel="noopener noreferrer"`；点开后**当前页 URL、选中对象、未保存草稿一字不变**。

而 `frontend/src/components/ObjLink.tsx` **就是按这条立的构件**——其文件头注释里保留了用户原话「**避免冲掉了当前正在处理的对象**」（该构件同批次落地于 `G-UI-7` 的接入清单、2026-09-23 批次52）。

**结论：构件已建好、规格已立好，工作台没用上。** 本次改造含一条**补齐已立规格**的动作，不是发明新交互。

### 1.3 归因

三个现象同一个根因：**工作台被设计成"待办清单的展示页"，而不是"一个人干活的地方"**。展示页的优化目标是最短路径看到全部数据（所以全量渲染）；干活的地方的优化目标是**不打断当前任务**（所以要保留上下文、就地完成轻量动作）。P-1 与 P-2 是同一个取舍的两面。

## 2. 目标形态：人为主体、三区分层、上下文不丢

### 2.1 页面结构（**2026-10-08 按用户第 1~5 条重排**）

```
工作台 /
├─ 页头：工作台                       [我的任务] [我的流程] [我的关注]   ← 右上角三个分区按钮（分区=页内互斥内容）
├─ 我的看板    常驻可折叠一行（磁贴 + 图表）
├─ 分区①我的任务   计划任务(B1)与"我"相关的项：未完成 | 我是主责 | 我是参与 | 已完成 | 全部
├─ 分区②我的流程   流程待办（flow task）：待办 | 已完成 | 我发起 | 我参与 | 全部  [+ 所有流程（仅管理员）]
└─ 分区③我的关注   收藏对象 + 关注进展（含未读标记）
```

**本页不再有**：① 页头角色徽章（用户第 1 条）；② 「待我审批 N 项」整节统计（用户第 2 条，与看板重叠）；③ 分区页签行（原 `.wb-zone-tabs`，用户第 3 条：功能上移到右上角按钮）。

**分区的性质**：右上角三个按钮是**互斥分区切换**（同一版面只渲染一个分区），`?tab=tasks|processes|favorites` 写 URL（深链/回退可用），并按 `localStorage['plm_wb_view:<user>']` 记忆；**深链进入时不恢复记忆**。

**「全部/所有」不占首页版面**：页头给 `▸` 直达入口，页签内也有。理由：参考形态要求「在此标签页中集中展示」，但把"全部"做成常驻版面会把首页重新拉长，与 §2.3 的目标相反。

### 2.2 页头与页签

| 元素 | 规格 |
| --- | --- |
| 页头 | 标题「工作台」；**不显示用户角色徽章**（2026-10-08 用户第 1 条裁定：角色信息已在各业务页与审批环节出现，工作台页头不再重复；徽章组件与 `.wb-role-badges` 样式仍在仓内备用） |
| 页头右侧 | 分区按钮 `我的任务 / 我的流程 / 我的关注`（用户第 3 条：由页内分区页签上移而来；`全部任务/全部流程/我关注的` 分别**改名为**我的任务/我的流程/我的关注） |
| 副标题 | 已删除（原「我的待办 · 跨域汇聚 · 点击行跳转对应模块处理」与 §2.1 的分区语义已不符） |
| 页签 | 复用既有 `.tabs/.tab/.tab.active` 类（`styles.css` 已定义，工作台此前未用） |
| 页签状态 | **写 URL query**（`?tab=tasks&view=todo`），使刷新与深链回退可用（G-LST-4 深链口径） |
| 记忆 | 上次所在页签按用户持久化 `localStorage['plm_wb_view:<user>']`；**深链进入时不恢复**（同 §6.8「`?open=` 进入时不恢复持久化」既有纪律） |

### 2.3 消除"密密麻麻"：五条手段

1. **服务端分页 + 筛选**（对应 P-1）：`page`（0 基）/ `pageSize`（默认与上限以 `Paged.MAX_PAGE_SIZE` 为唯一事实源）/ `total`，参数 `objectType` / `projectId` / `overdue` / `keyword`。
2. **默认排序按"该干的先后"**：`逾期在前 → due_date 升序 NULL 最后 → created_on 升序`。现状 `ORDER BY due_date NULLS LAST, id` **缺"逾期优先"**。
3. **紧凑/详表双视图**：默认**紧凑**（一行一任务：动作 pill + 编号 + 标题 + 时限 + 归属）；详表走 AG Grid，列由元数据下发。紧凑态是"扫一眼知道该干什么"，详表态是"要横向比对"。选择持久化。
4. **域分组降级为筛选项**：按 `objectType` 切九宫格正是"密密麻麻"的结构性来源——域维度改由 §6 的分布图表达，版面留给"该干的先后"。
5. **筛选条件持久化**：`localStorage['plm_wb_filters:<user>']`，重新进入恢复上次视角（依据 `05-interactions-part2a.md` §6.13 默认值策略：有使用者选择的地方 → 记住）。

### 2.4 上下文不丢：三条机制（对应 P-2/P-3）

| 机制 | 做法 | 依据 |
| --- | --- | --- |
| **看对象不丢上下文** | 任务行/流程行的对象引用**一律改用 `ObjLink`**（新标签页真链接）。处理完关掉标签页，工作台**原样还在** | **G-UI-7-2**；`ObjLink.tsx` 现成 |
| **干活不用跳走** | 轻量动作**留在行内**：认领 / 释放 / 指派 / **推进**。「推进」由"仅 REQ"扩到各域——接各域既有 `POST /{域}/{id}/transition`，**不新增写路径** | `04-interactions-part1.md` §6.7 既有原则「面板呈现待办清单 + 轻量动作行内完成」 |
| **看细节不必离开** | 行点击**就地展开「行详情条」**：所属项目 · 当前处理人 · 来源 · 流转记录摘要（复用 `HistorySection`）· 该对象上我的其它任务；条内再给 `ObjLink` 去完整页面 | `HistorySection`（G-UI-3 统一构件）、`flow-stages` 端点 |

> **边界（重要）**：**"不离开工作台"针对的是"看和推进"，不是"改内容"。** 本设计**不做**内嵌抽屉/右侧面板复刻业务页——那等于把 25 个页面各写一遍，维护成本远超收益，且与 §6.7 既有交互原则「涉及内容编辑的操作仍跳转业务页（详情面板统一保存）」直接冲突。内容编辑一律走业务页 `DetailPanel`。

- 「完成任务」按钮**只在**"我是主责/创建者"且该任务当前状态存在**合法流转边**时出现（判定复用 `task-flow.yaml`，**不放松**）；无合法边时按钮禁用并写明原因。
- 「加进展评论」对 创建者 / 主责 / 参与者 开放；评论即 `POST /tasks/{id}/comments`（`body` + 可选 `parentId`），**只增不改不删**（该域**没有**删除评论端点）。

- 「我的任务」空态**必须写明口径**（"按主责 ∪ 参与人 统计；当前没有与你相关的未完成任务"），避免被当成故障。

## 3. 我的任务：五视图

> ⚠ **本轮（2026-10-08）归属变更**：本节描述的是**流程待办（`t_flow_task`）**的五视图，其口径**全部有效**，但它现在挂在**「我的流程」**分区下。

### 3.3 三条易错口径（**必须实现为判据**）

**R1 · 系统归档不算"我办过"**
`archiveStale()` 会把"对象已越过 `from_state`"与"`created_on` 早于 90 天"的任务置 `CANCELLED` 并写 `done_by='system:stale'` / `'system:archived'`（`FlowTaskService.java:640-668`，`STALE_ARCHIVE_DAYS=90`）。
⇒ **`done_by LIKE 'system:%'` 的行一律排除在「已办」「我参与」之外**（我没办过它）。

**R2 · 归档必须有交代**（`04-interactions-part1.md` §6.7：「"消失"必须有交代，不允许无声丢弃」）
被 R1 排除的项**不能静默消失**。每个视图底部渲染交代行，数据源 `GET /_platform/tasks/archived-summary`（既有）：
`已自动归档 N 项（对象已处理或超 90 天未处理，仅统计近 30 天）`

**R3 · 「我下达」的存量交代**（用户裁定 **D-C2：加列但不回填**）
V163 只加**可空**列、**不回填**审计链。存量行 `assigned_by IS NULL` ⇒ **在「我下达」中不可见**。视图顶部**必须**渲染：
`历史指派未留派发人（本能力上线前派发的任务不计入）`

**禁止**：把 NULL 归给当前用户、或用空值行伪造。理由同 R2——"消失"必须被解释。

## 4. 我的流程：流程待办（行）+ 按业务对象聚合（管理员子页签）

> ⚠ **本轮（2026-10-08）归属变更**：现在叫「我的流程」的分区**主体是流程待办的行列表**（原 §3 的五视图 + 行内 `当前状态` / `下一步` 两列）；**本节的对象级聚合表降级为该分区下「所有流程（仅管理员）」子页签**（§4.3 授权不变）。

### 4.1 为什么必须"按对象聚合"而不是"按任务"

**事实：系统里不存在流程实例表。** `flow_instance` / `t_flow` 在迁移与 Java 全库**零命中**；「流程」是 `backend/src/main/resources/flows/*.yaml` 的 **20 个静态定义**（`FlowEngine` 启动加载）；「流程实例」= **业务对象表的状态列**（`V38:1-2` 注释明写"状态机仍是唯一事实源"）。

**基数关系**：一个 `(object_type, object_id)` × 一个当前 `from_state` → **1..N 条任务**（该状态每条带 `task:` 配置的出边各生成一条）；迁移完成时该 `(from,to)` 置 `DONE`、**同 `from_state` 其余并行任务置 `CANCELLED`**，再为新状态生成下一批（`FlowTaskService.java:44-49, 152-161`）。

⇒ 「我发起的流程」这类**单据视角**无法用任务行表达（同一单据会散成多行、且并行任务互相看起来像重复）。
⇒ **采用用户裁定 D-Q4：按 `(object_type, object_id, flow_id)` 分组，一对象一行**，行内展开该对象的任务与流转记录。

### 4.2 五视图口径

| 页签 | 判据 |
| --- | --- |
| **待办的流程** | 我名下有待办任务（§3.2「待办」口径）的对象，按对象去重 |
| **我参与的流程** | §3.2「我参与」的对象，按对象去重 |
| **我发起的流程** | 该对象 `created_by = me`（**域覆盖见 §8.2**；未登记创建人列的域**不参与**，由界面显式标注，不得算成「你没发起过」） |
| **已完成的流程** | **我在该对象上有 `DONE` 任务**（`status='DONE' ∧ done_by=me`，排除 `system:*`）、且该对象当前**无进行中任务**，按对象去重 |
| **全部** | 以上并集 |
| **所有流程**（**仅管理员**） | 系统内全部流程（见 §4.3） |

> **【2026-09-25 实现收口，本行为改口径】** 「已完成」原表述为「该对象流程已到**终态**（终态词表从库内元数据读）且我在该对象上有 `DONE` 任务」。**实现改为**：只判「我在该对象上有 `DONE` 任务 ∧ 该对象无进行中任务」，**不读终态词表**。
> **为什么改（不是偷懒，是判据更稳）**：
> 1. **终态词表没有统一权威**：终态是**每域各一套**（需求 `APPROVED`/`REJECTED`、ECO `CLOSED`、文档 `RELEASED`…），"从库内元数据读终态"在本库**没有这样一个字段**（`project-profile.md` 要求不硬编码是对的，但不存在的东西读不出来）——硬凑一份跨域终态表就等于**新增一处会漂移的口径**。
> 2. **用户的问题不同**：该页签要回答的是"**我经手的哪些单子已经办完了**"，而"对象是否终态"是**对象**的状态问题。用"我在它上面没有未完成任务了"表达同一件事，且**与 §3 的任务视图同源**（`done_by`/`status`），不会出现"任务说办完了、终态表说没完"的两套说法。
> 3. **可判定性**：「无进行中任务」是**可实测**的；「是否终态」依赖一份不存在的词表 ⇒ 判据必须选**能成立的**那个。
> ⚠ **遗留边界（如实登记）**：因此本页签**包含**「我办完了我这一步、但整单还在别人手里流转」的对象（它在我这里已完成、在整体上未终结）。这与"我关注的活"视角一致，但**与"整单已终结"的读法不同** —— 若业务上确需后者，需先立"跨域终态登记表"（属**新规格**，不在本批）。界面文案按**实现**写，不承诺后端不成立的语义。

### 4.3 「所有流程」的授权（裁定 D-C5）

**后端强制**，复用既有权限点，**不新造授权面**：

```java
@PreAuthorize("@permissionService.can('_admin','read')")
```

先例：`PlatformController.java:154/176` 的两处 `_admin read` 只读端点、`AdminController` 全族。

**非管理员**：UI 不渲染该页签 **且** 后端 403。**UI 隐藏不得作为唯一防线**（否则是可绕过的装饰门；同族纪律见 `conventions.md`）。
