#### 6.14.5 已知边界（写清楚，避免被读成"已具备"）

1. **两个域的导出端点都不做域级权限判定**：OIDC 下未登录仍 401，但任意已登录用户可导出全量清单，
   与本域读权限（如 `requirement.read`）无关联。这是既有形态，本批**刻意保持一致**，
   但属**开放安全项**——需要一次统一裁定"列表/导出是否统一受域读权限管辖"。
2. **同步内存路径**：整份文件进页面内存，边界 = 服务端 50000 行上限。若将来有"整车 BOM 级"导出，
   正确做法是服务端先落可签票产物 + 原生导航，**而不是**把上限调大（§6.12）。
3. **不做 CSV 公式注入改写**：单元格原样写出。加前导单引号虽常见，但会让导出物**不能原样导回**
   （物料的导出/导入是一对）。数据来源是已认证用户的业务录入 + 导入通道有逐行校验。

### 6.15 对象切换器：一页多对象的工作视图（批次45B，2026-09-22）

**一句话**：当一个业务域里出现**第二个平级的业务对象**时，用它自己的页签切换，而不是塞进同一个列表里
靠筛选区分，也不是新开一个互不相干的页面。

**范式来源**：变更域 ECR / ECO / ECN（§6.12 的工作台）已经在用同一套交互——顶部一组 `.tab`，
点一下换的是**数据源与字段集**，URL 也跟着换。需求域新增「需求基线」对象（§6.16）时沿用同一范式。

| 要求 | 规格 | 为什么 |
| --- | --- | --- |
| 切换器形态 | `.tabs` 容器 + `role="tablist"` + 每项 `role="tab"` / `aria-selected` | 与变更域同形；`ui-walkthrough` 有一条"页面 ≥6 个 `.tab`"的全站断言，本页出现 tab **符合规范** |
| 两个视图**互达** | 每个视图都要有切换器（不能"进了基线页就出不来"），两个方向都要能点 | 单侧入口会让用户以为自己是"二级页" |
| URL 跟着换 | 各自独立路由（`/requirements` ↔ `/req-baselines`），支持深链 | 可分享、可收藏、刷新不丢 |
| 锚点 | `reqwt-tab-REQ` / `reqwt-tab-BASELINE` 固定不变 | 走查靠它定位；改名等于让所有历史套件失效 |
| **不要"统一"成一种** | `.tab` 用于**对象**切换；**同一对象的多子对象**切换用 `.dual`（`ChangeDetailPage` 刻意不用 `.tab`） | 两处口径不同是**有意的**：混用会让"我在哪个对象上"这件事从界面消失 |

**反例（本批实测踩过的形态）**：只在需求页放一条"去基线页"的链接——用户点进去后切不回来，
且地址栏变化让"返回"行为变得不可预测。

#### 6.15.1 B4 增补：锚点命名规则、侧栏单入口、作用域深链（2026-09-26）

| 要求 | 规格 | 为什么 |
| --- | --- | --- |
| **锚点命名规则** | `data-testid="<域>wt-tab-<X>"`（实例：`reqwt-tab-REQ` / `reqwt-tab-BASELINE`、`taskwt-tab-TASK` / `taskwt-tab-GANTT`） | 走查靠它定位；规则固定为「域前缀 + `wt-tab-` + 视角码」后，**新域不必再商量命名**，历史套件也不会因起名不同而失效 |
| **侧栏只保留一个入口** | 第二个视角**不进侧栏**，入口挂在**主视角**上（甘特是"计划任务"的第二个视角，不单列侧栏项） | 侧栏是"**域**"的清单，不是"视图"的清单；两个入口会让用户当成两个域，进而问"这两个有什么区别" |
| **作用域深链** | 两个视角**共用**同一个 `?projectId=<id>`，切 tab 时**带上**，不新增第二套作用域参数 | 作用域是"看哪一份数据"的唯一事实；两套参数必然漂移（一侧带上、另一侧漏带 ⇒ 切过去看到**别的项目**的数据，而界面不报错） |
| **反例（B4 实测）** | ①两个视角各自维护一份作用域状态 ⇒ 切过去看到别的项目；②只在一侧放入口 ⇒ 切不回来（与上文同族） | 两条都是"看起来能用、**结论错**"的形态 |

> 来源：B4 批次（2026-09-26）。

### 6.16 需求基线与基线偏离（批次45B，2026-09-22）

**一句话**：基线 = **一组需求版本的集合**（不是需求的别名，不是冻结标记）；偏离 = **当前需求 vs 基线快照**
的即时对比，**只做可见化**（裁定 D45-1：不强制走变更流程）。

#### 6.16.1 与"版本"的关系（最容易误解的一处，界面必须点明）

库里有两个"版本号"，含义不同：

| 名 | 含义 | 谁在用 |
| --- | --- | --- |
| `t_requirement.version` | **内容改动次数**（2026-09-22 起；此前含状态流转，**存量值不回改**，见 D45-14） | 详情面板"版本"、基线成员表的「最新版本」 |
| `t_req_version.rev` | 该需求的**第几张快照**（每需求独立，从 1 起） | 快照表内部；界面上不展示 |

界面要求：
1. 成员表同时给**「基线版本」与「最新版本」两列**——只给一个会让用户以为"基线跟着需求一起改了"；
2. 表下**逐字点明**版本语义与生效日期（D45-14 要求），否则用户会把历史值当缺陷报上来；
3. `transition()` **不得**推高 `version`（D45-5）：状态流转不是内容改动，混在一起会让"版本"失去意义
   （历史数据里有个需求流转到 `version=182`，就是旧语义造成的，见 `.creature/tasks/plm-req-batch45/findings.md`）。

#### 6.16.2 偏离面板（页面底部通栏，默认收起）

- **四色六组**：红 = 需要处理（内容已改 / 已作废 / 已改项目归属）；黄 = 需确认（版本变化明细 / 项目新增未纳入）；绿 = 未变。
- **计数不得相加**：红组「内容已改」与黄组「版本变化」是**同一批行的两个视角**；面板顶部给的是原始读数
  （基线成员 N 条 · 项目当前活跃需求 M 条），并在面板里明写"各色条数不要相加"。
- **需求编号是真链接**（`<Link to="/requirements/{id}">`，不是 `onClick` 伪装的按钮）：对账时要能中键/新标签页
  同时打开好几条（D45-9 的"新页面"）。
- **空组也要在**（显示"（0）· 无"）：分组缺失与"该组没有内容"是两件事，前者是缺陷。
- **默认收起**：它是"要看时才看"的对账表，不该占首屏版面。

#### 6.16.3 复用与不重复（本批的复用盘点）

| 复用了什么 | 来自 | 说明 |
| --- | --- | --- |
| `DetailPanel` | 全站统一详情面板 | **必须传 `editableStatuses` 与 `status`**，否则字段全只读而界面不解释（§5.3） |
| `SearchPick`（对象选择控件） | §6.2.1 | 草稿态"纳入需求"用它，**不允许**裸 `select` 或自由文本框 |
| `ExportPanel` + `TabularExport` | §6.14（批次45A） | 需求列表新增「需求基线」列后，**导出自动同源**（同一份 `currentQuery()`、同一份列表服务）；本批只加了一列，没有动导出通道 |
| `useFlow` + YAML 流程 | §6.5 | 基线自己的 `req-baseline-flow.yaml`（4 状态 6 边）；流转按钮由**服务端算好的 `transitions`** 下发，前端不硬编码 |
| AG Grid + 统一详情面板 | §4 | 基线清单/成员表都是只读网格（双击不进内联编辑） |

#### 6.16.4 走查与验收锚点（走查脚本据此定位，改名等于作废历史套件）

| 锚点 | 位置 |
| --- | --- |
| `reqwt-tab-REQ` / `reqwt-tab-BASELINE` | 对象切换器两个页签 |
| `req-baseline-filter`（需求页工具栏） | 按基线筛需求（D45-10） |

| `bl-transition-<TO>` / `bl-obsolete-reason` | 流转按钮（按角色下发）与作废必填理由 |
| `bl-dev-toggle` / `bl-deviation-panel` / `dev-group-<组名>` / `dev-link-<REQCODE>` / `dev-add-<REQCODE>` | 偏离面板：开关、面板、分组、编号链接、纳入动作 |

**走查纪律（本批实测代价）**：
1. AG Grid 行**必须点行内 `.ag-cell`**，点 `.ag-row` 不触发 `onRowClicked`；
2. `pinned: 'left'` 的列渲染在**独立容器**里 ⇒ 按内容找行要**在整张网格里搜**，只看 `.ag-center-cols-container` 会匹配不到；
3. 偏离面板是**异步**拉的 ⇒ 断言前先等"计算中…"消失，否则会把"还没加载完"读成"分组缺失"；
4. 夹具（本批由 `tools/b45-baseline-fixture.py` 直插库造）必须**自证齐全**（例：两条成员各有一行快照），
   夹具不全的红是**仪器的红**，会被误读成产品缺陷。

### 6.17 扩展属性：元数据覆盖 + 面板/导出同源（批次49，2026-09-22）

> 由来（用户原话）：「导出 需求清单中要包含 需求详情面板中的各字段」「之前有元数据重复，这次让这些数据可视、可编辑，
> 要进行规整，废弃、没有意义的 attrs 就剃除，不要了。G1/G2 这些门点早就废弃了」。

**一句话**：凡是"值存在 `attrs`（JSONB）里"的扩展属性，**必须**在 `t_attr_template` 里有一行登记 ——
登记是它"能被看见"的唯一前提；**没登记的字段，面板不呈现、导出没有列，而且不会报错**。

#### 6.17.1 三层事实源（改任何一层都要问另外两层）

```
t_requirement.attrs  ──值──►  t_attr_template（元数据：标签/控件形态/值域/阶段约束/是否网格列）
                                      │
                    ┌─────────────────┴─────────────────┐
                    ▼                                   ▼
        详情面板 detailFields                   导出列 RequirementExportService.spec()
   = 固定字段 + detail-fields 下发字段       = 固定列 + detailFields + 网格列（去重）
```

**口径（一条，不许各写一套）**：**面板看得见的字段，导出必须有列**。实现上两边都读 `MetadataService.detailFields`
（面板经 `/_platform/metadata/detail-fields`，导出直接调服务），所以"加一个扩展字段"只需**改一行元数据**，
不需要动前端页面、也不需要动导出。

**去重口径（批次50 升级，2026-09-22）**：**按 `code` 或中文标签去重**，且 `promoted=TRUE` 的字段不下发。
为什么只按 `code` 不够：同一概念在本项目有**两套命名**（camelCase 是请求根级入口、snake_case 是 `attrs` 存储键），
面板原先用固定字段 `appealsDim`/`sourceChannel` 承载它们、元数据下发的却是 `appeals_dim`/`source_channel`
⇒ 按 code 比不出重复，**面板与导出里「价值维度（本需求改善的维度）」「来源通道（需求来源）」各出现两次**
（用户反馈"这些属性重复了"）。**标签就是用户在表头/表单上看到的东西，标签重名即重复**。
两条守卫分别落在：面板 `extDetailFields`（code 集合 + 标签集合）与导出 `spec()`（`hasLabel()`）。

#### 6.17.2 扩展属性登记的四个口径（批次49 实测定的）

| 列 | 取值 | 为什么 |
| --- | --- | --- |
| `is_grid_col` | **FALSE** | 共享网格已有 10 列，再挂十几列会把「标题/当前处理人/下一步应由谁处理」挤出屏幕；扩展字段走**详情面板 + 导出**通路（与批次44 父需求列同一取舍） |
| `is_post_analysis_only` | 按"是不是分析结论" | 批次49 登记 17 个：**13 个分析结论类**标 TRUE；**4 个客观归属类**标 FALSE。依据 = 批次44 裁定 D44-10。**批次51 退役后 REQ 域只剩 3 个扩展字段，且三个全是「分析后才可填」**：`source_channel`/`cost_est`/`regRef`（"随时可填"的扩展字段在 REQ 域已归零 ⇒ 阶段约束的"不锁"一侧改由**核心字段**（如「需求描述」）与**分析态夹具**承担，见 §6.17.7 与 W41 第 ④/⑩ 段） |
| `is_promoted` | FALSE（仍走 attrs）；**TRUE = 退役出产品面** | `TRUE` 表示"已是一等列、走根级读写"，故不再作为 attrs 详情字段下发（面板 `!c.promoted`、导出 `spec()` 两处同一谓词）。批次50 用它承载 `sourceType` 的退役，理由见 §6.17.6 |
| `is_internal_alias` | FALSE | `TRUE` 是**同义别名行**（如 `sourceChannel` vs `source_channel`）：两行都留库，但只有 canonical 下发（V143/D44-8）。**批次50 后 REQ 域只剩 1 行别名**（`sourceChannel`）——`appealsDim` 随字段退役一并删除 |

**面板侧的两个必做动作**（漏任一即"登记了也没用"）：
1. `record={{ ...selected, ...(selected.attrs || {}) }}` —— 把 attrs **摊平**到根级，否则面板按根级键取值取不到；
2. 保存时把**非核心字段名分流进 attrs**（`attrsDiff`），再整体 `PUT`。直接放根级提交会被后端**静默忽略**
   （200 + 值没存），用户读到的是"点了保存没反应"。核心字段名单以 `UpdateReqReq` 的根级字段为准。

#### 6.17.3 废弃属性的剃除（可恢复是前提）

| 步骤 | 要求 |
| --- | --- |
| ① 先取快照 | 剃除前把将被删的键值**全量导出**（批次49：`tools` 侧脚本写 `.creature/tasks/<批>/attrs-pruned-backup.json`，140 条键值 / 20KB）。审计链（WORM）只记"谁改过哪条需求"，**不含被删的值** ⇒ 快照是唯一还原依据 |
| ② 只在确有该键的行上更新 | `WHERE attrs ?| ARRAY[...]` —— 否则会把 2000+ 行的 `updated_at` 无谓推进，污染"最近更新"与增量导出 |
| ③ 成对自证 | ① 剃除键清零；② **保留侧键值一条没少**（按迁移前实测基线逐键对数：`value_score` 59 / `source_channel` 201 / `appeals_dim` 78）；③ 不得误删（保留侧总数为 0 即抛异常） |
| ④ 迁移**不写审计** | 审计链由应用层写入（hash chain），迁移直写会断链（V36）；本次剃除属**数据规整**，不产生业务变更留痕 —— 这一点必须在迁移头注里写明，否则后来者会以为"没留痕就是漏了" |

**已退役概念不得登记成产品字段**：`spec`（值 `G1/G2/G3/G4…`）是**已退役的旧阶段门**编号
（平台早已换成 DCP0-DCP3/TR1-TR6，`t_gate_map.old_gate_code` + `v_gate_legacy` 只是兼容视图，
旧门端点一律返回 `STAGE_GATE_RETIRED`）。把它登记回界面 = 复活废弃概念。
**反向守卫**：W28/W36 断言"界面与门词表里不得再出现 G1..G7"——这两条**不许删**（它们才是现行口径的探针）。

#### 6.17.4 巡检（只报告，不判红）

`ipd/deploy/wsl/plm-app/plm-attr-coverage.sh`（CI 层 T4-12）：逐表取 `attrs` 的键集合，减去该 `obj_type`
的登记键，打印**未登记清单**。口径与理由：

- **为什么只报告**：未登记键里混着两类完全不同的东西 —— "漏登记的产品字段" 与 "本就不该出现的治理标记/
  误建键/导入残留"。机器分不清，判红会逼着后来者**把内部标记也登记成产品字段**。
- **为什么不会空转**：`--selftest` 注入一个"必定未登记"的键，断言检测器能报出来
  （报不出即 `ATTR_COVERAGE_SELFTEST=FAIL`：不可信的报告比没有报告更危险）。
- 实测（2026-09-22，批次49 登记后）：需求域**未登记 = 0**。
- 实测（2026-09-22，批次50 退役后）：需求域未登记键 = **11 个**，且**全部是刚退役的字段**
  （`value_score`/`urgency`/`appeals_dim`/`rcRef`/`riskRef`/`hazard_ids`/`risk_before`/`risk_after`/`control_layer`/`fmea_ref`
  共 224 条键值仍在库里）。这是**刻意的可见状态**：字段退役、数据保留，报表如实列出"有值但已不是产品字段"，
  既没有偷偷删数据、也没有把数据伪装成不存在。要彻底清掉需另立裁定（且必须先落快照，见 §6.17.3）。
- 平台其余域仍有 150 个未登记键（ITM 71 / DOC 55 / PRJ 14 / PROD 8 / ECO 2）——同一形态的历史欠账，待产品裁定。

#### 6.17.5 走查锚点与判据（批次49 实测代价）

| 锚点 | 用途 |
| --- | --- |
| `.dp .dp-row[data-field="<code>"]` | 扩展字段行（`data-stage-locked` 表阶段约束、控件 `disabled` 表只读） |
| `[data-testid="req-export-open"]` / `[data-testid="req-export-panel"]` | 导出入口与面板（回归用） |

**判据纪律**（每条都对应一次实测假红）：
1. **值要读 DOM property `value`，不是 `innerText`** —— 文本框/下拉的当前值不在 innerText 里（首版按 innerText
   断言"显示真实值 ⇒ 7"⇒ 两条假红：值明明在，只是读取位置错了）；
2. **"能看见"与"能改"、"改了会不会存进去"是三件事**：必须真改一个值 → 真点保存 → 读**服务端** `attrs` 确认；
3. **必须断言"同一次保存没冲掉别的扩展字段"**：attrs 是整体 JSONB，最容易"写一个丢一批"；
4. **阶段约束要两条方向相反的断言**：标记为分析后字段的**必须锁**、未标记的**必须不锁**（只断一条会漏掉"一刀切锁死"）；
5. 旧门点字段（如「所属门点」）**不得**出现在面板（反向断言，防废弃概念回潮）。

#### 6.17.6 字段「退役」：三种状态与各自的机器形态（批次50，2026-09-22）

> 由来（用户原话）：「价值维度（本需求改善的维度）、来源、价值评分、紧急度 <-- 这些属性重复了，要删除。
> 详情面板和导出中都不需要这些字段」「风险相关的内容是关联出来的吗？如果是关联的对象，保持对象引用即可，
> 不需要展开为具体字段」「记得同步修改 需求导出时保留的字段」。
> 裁定：**D50-1** 保留 `source_channel`、踢掉重复的 `sourceChannel`、摘除 `sourceType`；**D50-2 = B** 风险类 7 个全摘、只留「法规条款引用」。

**产品口径**：字段退役 ≠ 删数据。本批**只摘产品面**（详情面板 + 导出 + 元数据登记），
`attrs` 里的值、接口字段、库列一律不动（沿用 2026-09-20 那条边界"只隐藏界面呈现"）。

| 退役方式 | 机器形态 | 适用 | 批次50 实例 |
| --- | --- | --- | --- |
| **登记行删除** | `DELETE FROM t_attr_template …` ⇒ 面板与导出**同时**消失（两处都读同一份 `detailFields`） | 该键**不是**任何写路径的词表权威 | `appeals_dim`/`appealsDim`、`value_score`、`urgency`、`rcRef`、`riskRef`、`hazard_ids`、`risk_before`、`risk_after`、`control_layer`、`fmea_ref` |
| **标记 `is_promoted=TRUE`**（不删行） | 面板 `!promoted` 与导出 `spec()` 的同一谓词把它摘出产品面，**行与词表仍在** | 该字段是**一等列**，或它的登记行同时是**校验词表权威** | `sourceType`：根级列 1356 行有值，且 `MetadataService.validateAttr`（创建）与 `RequirementService.validateEnumFields`（更新）都按这行的 `enum_values` 校验 ⇒ 删行会让根级字段**静默失去校验**，还会让 CI T4-2 的"越界 source_type"检查退化成永远为 0 的**空转绿** |
| **保留 canonical、别名停发** | `is_internal_alias=TRUE` 只隐藏别名行 | 同一概念两套命名，旧客户端仍写 camelCase | `source_channel`（下发）/ `sourceChannel`（不下发，D44-8 停发不下线） |

**导出侧必须同步改的三处**（用户明确点了这条）：① 固定列里删掉 `sourceType`/`sourceChannel`/`appealsDim`
（`RequirementExportService.FIXED`）——否则固定列与元数据动态列**同名重复**；② `spec()` 加"同标签不再生成第二列"
与"`promoted` 不下发"两条守卫；③ `cellValue` 里随固定列一起删掉三个已无调用者的 `case`（留着是"看起来还在用"的死代码）。
「来源通道（需求来源）」现在由**元数据动态列**（`source_channel`，值走 `attrs` 的 default 分支）承载，表头里**恰好一列**。

**退役前必须问的三个问题**（漏掉任何一个都会留下静默缺陷）：
1. **这行是不是某个校验/检查的词表权威？**（`grep -rn "<attr_code>" backend/src` + CI 脚本）——是 ⇒ 只能标记、不能删行（`sourceType` 即此）；
2. **值域会不会随行一起消失？**（`RequirementService.FALLBACK_JSON` 是否覆盖该键）——`appeals_dim` 有兜底八值 ⇒ 可删；
   兜底动作要用**行为判据**验（送一个越界值仍须 400），不能只看"行没了"；
3. **界面回归是谁在守？**——批次49 的 `sourceType` 就是"面板已裁定隐藏、又被元数据合并带回"；
   故退役后要加**反向断言**（`data-field` 逐键 0 命中 + 面板无同名标签），只删代码不加断言 = 下次再回来没人知道。

#### 6.17.7 「必录」类校验的执行点必须在"动作发生的时刻"，不能挂在"任意一次内容保存"上（批次50，D50-3）

**实测缺陷**（本批暴露）：`source_channel`（来源通道）的必录校验挂在"任何 attrs 写操作"上，
而该字段在发起阶段（PROPOSED）被标为「分析后才可填」⇒ **界面锁着不给填、后端却要求必须填**：

- 新建需求时只要填了**任何**扩展字段（例如「责任人」「产品线」），整次保存被 400 拒绝"缺少来源 source_channel"；
- 存量需求同理（全库 **2025** 条没填该字段，其中发起/分析态 11 条）。

**为什么会漏掉**：批次49 的走查夹具为了让请求成功**主动**补了 `source_channel`——
前提里的"顺手值"恰好把这一大类用户挡在了盲区外（教训 L-609）。

**裁定与落地（D50-3 = A）**：校验点从"任意 attrs 写"移到**分发**（B7「分发三路」的入口 `POST /requirements/{id}/dispatch`）：
写入路径**只校验格式**（填了就必须在登记词表内），**必须填**在分发那一刻校验；错误文案点名
`source_channel` 并给出可选值与字段位置。

**为什么没有同时挂到「进入分析态（→ANALYZED）」**（这一处必须写清，否则后来者会以为是漏了）：
同一份元数据把该字段标成"分析后才可填" ⇒ 若"进分析态"要求它存在、而"分析前"又不给填，就是**死锁**
（实测至少 9 条发起态需求缺该字段）。要挂那一处，必须先让它在发起阶段可填——**属另一次裁定（D50-5 待定）**。

**一般规则**：必录门的位置要与"用户什么时候才可能填"的界面事实**对得上**。
判据要**成对**：① 该动作之前**不该拦**（否则正常用户被拦）；② 该动作处**必须拦**（否则必录名存实亡）；
③ 补录之后必须放行（否则"拦住"退化成"这条路永远走不通"）。三条缺一，都会把一次修复变成另一次事故。

#### 6.17.8 扩展属性不得承载"分析结论的抄录"（批次50，D50-4 裁定）

**规则**：风险分析结论（危害源编号、风险前后等级、控制层级、控制措施、FMEA 引用等）**不得**再以 attrs 字段形式
写进需求；需求侧需要风险信息时，走**对象关联**（追溯链 `RISK_CTRL` → `RSK` 业务风险台账，平台已有该对象与词表）。

**依据**：实测那批字段是**外部文档的抄录**（值形如「S3×P4=12(黄)」「#2,#12」「施建军§4.3-3」，`HAZ-*`/`RC-*`
在库里没有任何载体），而 `t_req_trace` 里指向风险对象的关联 **0 条** ⇒ 抄录既不可追溯、也不可校验。
用户裁定"先不做对象化开发，只把规则写进规格"⇒ 本批只落规则，不新增字段、不做数据迁移
（存量 15 条需求的抄录值已随字段退役移出产品面，`attrs` 原值保留）。

#### 6.17.9 第二轮退役：跨域同名键只动目标域；"主档抄录型"字段一律不入需求（批次51，D51-1）

> 由来（用户原话）：「DFT测试分类、医疗器械管理类别、责任人、所处阶段、产品线几个字段也非需求对象所需，
> 请从界面和数据模型中去除」。裁定 **D51-1 = A**：**只删字段定义（元数据登记行），保留 `attrs` 存量值**。

**一天内第二次删字段，暴露了一条新纪律：同名键在别的域是合法字段。**
`t_attr_template` 是**按 `(obj_type, attr_code)`** 组织的，同名键跨域合法：

| 被退役的键（REQ 域） | 同名键在别的域的身份 |
| --- | --- |
| `medClass` | **PRJ**「管理类别」、**PROD**「管理类别」（都是网格列） |
| `owner` | **BOM**「责任人」（网格列） |
| `phase` | **RSK**「阶段」（网格列） |
| `productLine` | **RDM**「产品线」（网格列） |

一个"按 `attr_code` 删"的写法会**一次性干掉 5 个域的网格列**，而且**不报错**——面板少一列，用户下次打开才发现。
故退役的三条硬要求：**① `DELETE` 必须带 `obj_type`；② 自证里逐条断言"别的域那 N 行仍在"；
③ 判据要能点名缺失的是哪个 `域.字段`**（只断言一个总数，会把"A 域少了 2 行、B 域多了 2 行"读成通过）。

**"主档抄录型"字段的口径（本批确立）**：需求上的「医疗器械管理类别」「产品线」属**从项目/产品主档抄过来**的信息
（实测 `attrs.medClass` 16 行全是 `II`，与所属项目主档一致）。这类字段的处置不是"退役完事"，而是：
**需要时由界面从所属项目/产品带出（读主档），不得在需求上再登记可编辑字段**——否则同一事实两处可改，
迟早出现"需求说 II、项目说 III"的静默矛盾（与 V152 的 $APPEALS 重复同族）。
用户体验上这一点是可接受的：需求页顶栏本来就在显示**所属项目**的管理类别（读 `projects.find(...)`，不是需求字段）。

**退役前的四条审计（本批 5 个字段全部过检，逐条留证）**：
① 后端 `domain/requirement/**` 引用数 = **0**；② 无 `FALLBACK_JSON` 兜底 ⇒ 删行**不会**废掉任何值域校验
（与批次50 的 `sourceType` 不同，那个必须留行标记）；③ 流程 `requires:` 引用数 = **0** ⇒ 不卡流转；
④ 前端引用 = 0（需求页那处 `cur.medClass` 读的是选中**项目**的主档，见上）。
