# 21 · 治理台与权限治理设计（敏感字段名单 / 代理授权 / 决策矩阵 / 权限模型）

> **定位**：把「治理台」从**骨架页**发展为**可交付的治理功能**，并把两条长期只有口头口径的能力

> 权限模型（判定语义）+ 授权机制（授予/生效/回收/留痕）+ 页面与契约 + 判据。
> **依据**：`08-前端实现规格.md`（§6.1 禁弹窗、§6.2.1 SearchPick 对象选择、§6.10 治理类页面范式、§9 陷阱 28 脱敏只读）、
> `19-产品级通用规格-安全规格.md`（INV-1~6、§5 变更纪律、§7 新域接入检查表）、
> `docs/plm-design/ipd-extension/06-IPD权限模型设计.md`（§4 决策矩阵、§5 敏感数据权限、§6 授权代理与临时授权、§8 权限审计与复核）、

> 现状代码：`GovernancePage.tsx`（骨架）、`GovernanceController`（3 个端点）、`GovernanceService`（决策矩阵判定 + 主席/否决判定）、
> `V34__perm-governance.sql`（`t_gov_decision_rule`/`t_field_grant`/`t_delegate_grant`/`t_permission_rule`）、

### 1.3 差距清单（本设计要闭合的）

| # | 差距 | 后果 |
| --- | --- | --- |
| GAP-1 | 名单只能加不能减/不能看到期/不能看"这个人为什么能看" | 安全上不可审计；离职/转岗后权限残留（`06 §8` 要求"机密名单有效性核查"） |
| GAP-2 | 代理无管理面：到期未回收、范围无词表、被代理人不知情 | 越权风险 + 不可否认性受损（ISO 13485 电子签名） |
| GAP-3 | 决策矩阵改一次要写迁移 | 治理动作变成开发动作（发布依赖），响应慢且无审计粒度 |
| GAP-4 | 特权操作对象为自由文本 | 打错一个字母 = 给不存在的用户/字段授权（静默无效），或给错对象授权（静默越权） |
| GAP-5 | 三类授权（角色/名单/代理）的**判定顺序与冲突语义**没有成文口径 | 同一个人被"角色允许 + 名单拒绝 + 代理允许"时结果不可预测 ⇒ 事故时会各说各话 |
| GAP-6 | 无"影响面预览"与"变更冲击"视图 | 改矩阵/发名单前无法回答"这会放开谁" |

## 2. 权限模型（G0：判定语义）

### 2.1 主体与授权来源（四层，判定顺序固定）

```
判定（domain, action, 对象实例）→
 ① 基线角色      t_user_role（组织角色/项目角色，含 effective/expire 窗口） + t_permission_rule（域×动作→角色）
 ② 功能角色      obj_type 级能力（read/write/transition/approve，t_role_function）
 ③ 名单/例外     敏感字段名单 t_field_grant（**只加不减**，D2）
 ④ 代理          t_delegate_grant（**在有效期内把被代理人的授权平移给代理人**，含否决/门点裁定，D3）
 ⑤ ACL/ABAC      t_role_abac（属性条件：project/org/product/owner…，allow/deny）
```

**判定语义（必须逐条成文，这是 GAP-5 的闭合）**：

| 规则 | 口径 | 理由 |
| --- | --- | --- |
| R1 **deny 优先** | 任一来源**显式 deny** ⇒ 最终拒绝（不因其它来源 allow 而放行） | 最小授权；与 `19 INV-1` 默认拒绝一致 |
| R2 名单是**叠加**（D2） | 名单只**增加**可见性/可操作性；**不**替换也不削弱基线角色 | 回收简单（删行即回到基线）；不会因为名单缺失造成"角色给了反而看不到"的怪象 |
| R3 代理是**平移**而非放大 | 代理人获得的权限 = **被代理人当前权限 ∩ 代理范围**；被代理人失去权限，代理人也失去 | 代理不是"提权通道"；离职/停用立即失效 |
| R4 代理**不得越界到被代理人也没有的权限** | 例如被代理人自己都不是 `IPMT` 成员，则不产生任何 DCP 裁定权 | 防"借代理自我提权" |
| R5 已"批准/签署"的对象**不受事后授权变更影响** | 授权变更只影响**新动作**；历史签署的有效性由签名哈希 + 双留痕独立支撑（`design-principles-plm.md`："历史不动"） | 审计一致性 |
| R6 到期即失效（无宽限） | `until_at <= now()` 的行**不参与**判定，且进入"待回收"视图（可见） | 静默失效是不可接受的；**失效必须可见** |
| R7 判定必须**可解释** | 任一 allow/deny 结果都能回答"是哪一层给的"（`X-PLM-DECISION-SOURCE` 注释见 §7.4 的解释端点） | 事故定位与判据自证 |

### 2.2 SoD（职责分离，沿用现状并显式化）

| 分离对 | 口径 | 现状 |
| --- | --- | --- |
| 配角色/用户 ≠ 改系统设置 | 两个权限点（`_admin.user_role.assign` vs `_admin.manage`） | 已实现（批次先例） |
| **授予名单 ≠ 受益于名单** | 授予人**不得**给自己授予（除非其角色本就在基线名单内）；授予人对自己相关的授予要**显式标注** | 本设计新增断言（§3.6 A3） |
| **代理 ≠ 自我批准** | 不得代理**自己**（`delegator == delegatee` 拒绝） | 本设计新增 |
| 门点裁定者的独立性 | 参加评审会的人（含代理）不得是"被评审对象的作者"（沿用 `12` 评审机制的口径） | 已有口径，本设计在代理路径上**同样施加** |

### 2.3 判定公式（扩展 `06 §2` 的版本）

```
final(domain, action, obj, field?) =
   if any_source_deny                     → DENY
   else if base_role_allow
        or functional_role_allow
        or field_grant_allow(field)          # 仅字段级，D2 叠加
        or delegate_allow(domain, action)    # D3：限时 + 已确认 + 范围内
        or abac_allow(attrs)                 → ALLOW
   else                                     → DENY（默认拒绝）
```

> 与现状的关系：`GovernanceService`/`PermissionService` 已实现 ①②⑤ 与决策矩阵判定；
> 本设计**不重写**判定引擎，而是**补齐 ③④ 的判定入口**（`PermissionService` 增加两个来源 + 解释能力），
> 并把新权限点/新来源登记进 `PermissionConsistencyCheck`（§9 B3）。

## 3. G1 敏感字段名单（谁能看机密字段）

### 3.1 密级与字段分类（登记制，单一事实源）

| 概念 | 口径 | 落点 |
| --- | --- | --- |
| **密级** | `PUBLIC` / `INTERNAL` / `CONFIDENTIAL`（机密）/ `SECRET`（秘密） | 字段元数据（`t_attr_template.field_class` 扩展或独立登记表，§8） |
| **字段键** | `obj_type + attr_code`（如 `CHARTER.fin_estimate`）——**唯一**，不允许字符串拼接式自由键 | 登记表主键 |
| **默认可见性** | 由**密级**决定：`PUBLIC/INTERNAL` 对拥有该对象读权限者可见；`CONFIDENTIAL/SECRET` **名单外一律脱敏** | 判定在**序列化出口**统一施加（现状 `CharterService.maskWith` 的做法，扩展为通用出口） |
| **脱敏形态** | 值替换为 `"***"` + **同响应恒有** `xxxMasked: true/false`（禁止"用值的真假判断是否脱敏"） | 现状已收口（`finEstimateMasked` 恒有值）；**新字段必须同口径** |
| **脱敏字段的可用性** | 脱敏值**只读禁用**，前端回写即数据破坏（`08 §9` 陷阱 28） | 前端按 `xxxMasked` 渲染，不按值形状 |

### 3.2 名单的语义（D2：例外叠加）

- **基线**：功能角色/密级决定"这个角色的用户能不能看这类字段"；
- **名单**：在基线**之外**追加可见者（例如：某个非财务角色的 PMO 成员需要看某项目财务区）；
- **不削弱**：名单**不能**用来"禁止"某人（禁止走角色/ACL 的 deny，或直接不给角色）；
- **回收**：删除名单行即可（无需重建角色），**且回收立即生效**（判定实时查表，无长缓存）。

> 为什么不允许"名单削弱基线"：那会让"把某人从名单里删掉"变成一次隐式提权（回到了角色基线），
> 语义上危险；且会破坏 `06 §5` 的"密级 + 角色"双层结构。

### 3.3 授予粒度与有效期

| 维度 | 取值 | 说明 |
| --- | --- | --- |
| 受益主体 | **用户**（login）/ **角色**（role code）——两种 | 现状只有用户；角色级授予用于"整类角色临时可见"（更少行、更好回收） |
| 对象范围 | **全局** / **按项目**（`project_id`）/ **按产品线**（`product_line`） | 现状是全局（过宽）；范围化是"最小授权"的必要条件 |
| 字段范围 | 单个字段键 / 字段组（如 `CHARTER.finance.*`） | 组粒度便于"整块财务区" |
| 有效期 | `until_at`（必填，最长 **180 天**；到期自动失效并进"待回收"） | 现状无有效期 ⇒ 永久授权（GAP-1 的主因） |
| 理由 | `reason`（必填，≥8 字） | 审计链需要"为什么给" |
| 授予人/复核人 | `granted_by` / `reviewed_by`（D6 未选双人复核 ⇒ 默认同一人、`reviewed_by` 留空；接口位保留） | 未来开启双人复核不改 schema |

### 3.4 授予流程（取消自由文本 — GAP-4 的闭合）

```
治理台 › 页签「敏感字段名单」
┌ 左：名单表（AgGrid：主体 | 类型(用户/角色) | 范围 | 字段 | 到期 | 授予人 | 状态） ┐
│   搜索/筛选：主体、字段、范围、状态（生效/即将到期/已过期/已回收）             │
│ ┌ 右：授予详情卡 ────────────────────────────────────────────────┐            │
│ │ 主体      [SearchPick: 用户（USR）/ 角色（ROLE）] ← **受控选择** │            │
│ │ 范围      [全局 ▾] / 项目 [SearchPick: 项目] / 产品线 [▾]        │            │
│ │ 字段      [SearchPick: 敏感字段（来自登记表，含密级）]            │            │
│ │ 有效期    [日期]  ⓘ 最长 180 天                                  │            │
│ │ 理由      [多行输入，≥8 字]                                      │            │
│ │ ── 影响面预览（保存前必看）─────────────────────────────────── │            │
│ │  将新增可见者：3 人（robin / zhangming / pmo_li）                │            │
│ │  其中已因角色可见：1 人（robin）⇒ 实际新增 2 人                   │            │
│ │  [保存授予]  [回收]（已存在行时）                                 │            │
│ └─────────────────────────────────────────────────────────────────┘            │
└─────────────────────────────────────────────────────────────────────────┘
```

**对象选择器口径**：全部改用 `SearchPick`（`08 §6.2.1`）——用户来自 `GET /_admin/users`（受控集合）、
角色来自 `GET /_admin/roles`、项目/产品线来自既有域选择器、**字段**来自**敏感字段登记表**（§3.1，只列出 `CONFIDENTIAL/SECRET` 字段）。
**任何特权操作都不接受自由文本键**（D-1 缺陷的直接修复）。

### 3.5 影响面预览（GAP-6 的闭合）

保存前给出**三段数字**（服务端计算，不靠前端推断）：
① 目标字段当前可见者数量；② 本次授予**实际新增**的可见者数量（扣除已可见者）；③ 到期后自动回落到多少。
> 预览不是装饰：它是"授予操作可判定"的组成部分——断言 A6 要求**预览数字与保存后的实际差集一致**。

### 3.6 判据（断言）

| ID | 断言 | 反例 |
| --- | --- | --- |
| A1 | 名单外用户读机密字段 → 值 `***` 且 `xxxMasked=true`；名单内用户读 → 真值且 `xxxMasked=false` | 反例：名单内用户被脱敏（授了没用） |
| A2 | 名单**只读禁用**：脱敏态字段在前端不可编辑，回写不产生请求（`08 §9` 陷阱 28） | 反例：回写成 `{}` ⇒ 数据破坏判红 |
| A3 | 授予人**不得给自己**授予（除非其本就在基线名单内）→ 403/400 | 反例：自我授予成功 ⇒ 判红（SoD） |
| A4 | 到期即失效：`until_at` 过后同一用户读 → 脱敏；且出现在「待回收/已过期」列表 | 反例：过期仍可见 ⇒ 判红 |
| A5 | 回收立即生效（删行后同一请求即脱敏） | 反例：需重启才生效 ⇒ 缓存设计判红 |
| A6 | 影响面预览数字 == 保存后实际新增可见者集合的差集（同一时点） | 反例：预览 2 实际 5 ⇒ 判红（预览不可信 = 比没有更糟） |
| A7 | 未知字段键/未知用户/未知角色 → **400 且不落库**（受控集合校验，正反成对） | 反例：自由文本写入不存在对象 ⇒ 静默无效的授权 |

## 4. G2 代理授权（谁能代谁做什么）

### 4.1 范围词表（scope，**受控枚举**，不允许自由字符串）

| scope | 含义 | 现状/落地 |
| --- | --- | --- |
| `REVIEW_ATTEND` | 代为参加评审会（`T_REVIEW_ATTENDEE.attend_type=AGENT`） | 已设计（`06 §6`） |
| `REVIEW_SIGN` | 代为签署评审意见 | 已有 `on_behalf_of` 落库 |
| `REVIEW_VETO` | **代为行使否决权** | D3 允许（条件见 §4.3） |
| `GATE_DECIDE` | **代为做出门点裁定**（DCP/TR 结论） | D3 允许（条件见 §4.3） |
| `TASK_DELEGATE` | 代办工作台待办任务 | 待实现（与 `10-流程角色与任务分派设计` 对齐） |
| `APPROVE_ECO` / `APPROVE_DOC` | 代为审批变更/文档 | 按域扩展（词表登记在 `t_gov_delegate_scope`，§8） |

> 词表必须是**表**而不是代码常量：新增域需要加 scope 时走数据（+ 校验 + 审计），但**枚举受控**（不在表内的值一律 400）。

### 4.2 代理的生命周期

```
提出（被代理人或被代理人上级）→ 被代理人确认（D3 硬要求）→ 生效（生效期内）→ 使用（带双留痕）→ 到期/回收 → 归档
```

| 状态 | 说明 | 可见性 |
| --- | --- | --- |
| `PENDING_CONFIRM` | 已提交，等**被代理人确认** | 被代理人登录后面板提示；治理台列表可见 |
| `ACTIVE` | 已确认且未到期 | 生效；使用中 |
| `EXPIRED` | 超过 `until_at`（**最长 14 天**，D3） | 自动失效；进「待回收」 |
| `REVOKED` | 主动回收（被代理人/管理员/合规） | 立即失效；保留历史 |
| `REJECTED` | 被代理人拒绝 | 不生效 |

**确认机制（D3 的落地）**：被代理人在「我的信息」面板或治理台看到待确认项，点击**确认**（一次）后 `ACTIVE`；
确认动作本身入审计（`gov.delegate.confirm`），**不可由他人代点**（防"自己给自己确认"）。

### 4.3 覆盖否决/门点裁定的附加条件（D3）

代理 `REVIEW_VETO` / `GATE_DECIDE` 时，**全部**满足才生效：

| # | 条件 | 判据 |
| --- | --- | --- |
| C1 | 代理关系为 `ACTIVE` 且未到期 | §4.2 状态 |
| C2 | **被代理人确认过** | `confirmed_at` 非空 |
| C3 | 代理人自身**未被排除**（例如：不是被评审对象作者；项目角色仍在有效期） | 沿用 `12` 评审独立性口径 |
| C4 | 该动作**允许被代理**（`t_gov_delegate_scope.allow_delegate=true`；个别动作可设 `false`） | 词表列 |
| C5 | 双留痕完整：`actor=代理人`、`on_behalf_of=被代理人`、`reason` 非空 | 落库 + 审计 |
| C6 | 同一 (被代理人, scope, 时间窗) **不重复**代理给多人（避免"多代理同事代签"） | 唯一约束（§8） |

**红线（不得代理）**：① 代理**自己**；② 代理范围**超出**被代理人现有权限（R4）；③ 用代理路径**修改代理关系本身**（自举提权）。

### 4.4 使用点（与现有实现的连接）

| 使用点 | 现状 | 本设计要求 |
| --- | --- | --- |
| 评审签署 `POST /reviews/{id}/sign` | `SignReq(onBehalfOf, reason)` 已落 `t_review_signer.on_behalf_of` | 签署前**校验代理关系有效**（无效 → 403 + 明确原因「代理授权已过期/未确认」），并在响应中回显生效的代理关系 id |
| 评审决定/否决 `decide`/`veto` | `DecideReq/VetoReq(onBehalfOf)` | 同上；`REVIEW_VETO`/`GATE_DECIDE` 需 §4.3 六条 |
| 电子签名 `SignatureService` | `t_sign_rec.on_behalf_of` 已有 | 签名哈希覆盖 `on_behalf_of`（防事后替换"谁的名义"）——**实现期核对现状是否已包含**；不含则列入实现任务 |
| 工作台待办（`TASK_DELEGATE`） | 未实现 | 随 `10-流程角色与任务分派设计` 的下一阶段 |
| 项目角色临时授权（`t_user_role.effective/expire`） | 已有机制 | **与代理区分**：角色窗口是"权限本身有期限"，代理是"代为行使"；两者可叠加，判定按 R3 取交集 |

### 4.5 判据（断言）

| ID | 断言 | 反例 |
| --- | --- | --- |
| B1 | 未确认的代理**不可用**：`PENDING_CONFIRM` 状态下代为签署 → 403 且**不落签署记录** | 反例：能用 ⇒ 判红（D3 被绕过） |
| B2 | 过期即失效（14 天上限 + `until_at` 过后）→ 403；治理台「已过期」列表可见 | 反例：过期仍可用 ⇒ 判红 |
| B3 | 双留痕：签署记录**同时**含 `actor=代理人` 与 `on_behalf_of=被代理人`；审计链同 | 反例：只记代理人 ⇒ 不可否认性不成立，判红 |
| B4 | 不得代理自己（400）；不得重复代理（唯一约束冲突 → 409 + 文案） | — |
| B5 | 代理不放大权限：被代理人无 `GATE_DECIDE` 资格时，代理人通过代理**也**不能裁定（403） | 反例：能裁定 ⇒ 判红（R4） |
| B6 | 被代理人权限被回收后，代理人**同刻**失效（同一事务/下一次判定） | 反例：代理仍可 ⇒ 判红（R3） |
| B7 | 代理关系变更本身不可被代理（自举提权防护）：代理路径调用代理管理端点 → 403 | — |

## 5. G3 决策权限矩阵可编辑（D4）

### 5.1 现状与目标

现状：`t_gov_decision_rule`（`gate_type × decision → allowed_roles[]` + `veto_reason_required`）8 条种子，
页面**只读**，改一次要写迁移（GAP-3）。

目标：治理台可编辑，但**不给"随手改安全红线"的便利**——五条约束：

| # | 约束 | 判据 |
| --- | --- | --- |
| M1 | **默认只读**，点「编辑」进入编辑态（同 `08 §6.10` 的角色详情范式） | 打开页面为只读；有"编辑"按钮 |
| M2 | **二次确认**：保存前显示 diff（`旧角色集 → 新角色集`）+ 影响面（涉及哪些流程边/门点实例） | 无 diff 不允许提交 |
| M3 | **审计**：每次变更一条 `gov.decision-rule.update`（含旧值/新值/操作者/理由） | 审计可查、可回溯 |
| M4 | **生效期**：`effective_from`（默认立即）+ 保存即写 | U1（§11）待裁；默认立即生效 |
| M5 | **一致性校验联动**：保存后立即跑 `PermissionConsistencyCheck` 的相关规则（域级 ⊇ 细粒度并集、判定角色可得性）；违规**拒绝保存**并给出违规码 | 反例：保存出"域级缺角色"的矩阵 ⇒ 拒绝 |

### 5.2 编辑范围（受控）

| 可编辑项 | 口径 |
| --- | --- |
| `allowed_roles` | 只能从**已定义角色**里选（`SearchPick`/勾选列表，禁止自由文本） |
| `veto_reason_required` | 可切换（boolean）；切到 `false` 需理由（≥8 字） |
| 新增行 (gate_type, decision) | 允许（必须选已存在的门类型 + 决策枚举） |
| 删除行 | 允许，但**删除后该 (门类型, 决策) 变默认拒绝** ⇒ 二次确认里必须显式提示"删除即无人可批" |

**不可编辑**：门类型枚举、决策枚举（来自流程/域事实源，改了会与流程引擎不一致）、
super-admin 兜底（不存在这种行——`INV-2`：不允许"admin 万能"写进矩阵；`admin` 只在需要时按角色显式列出）。

### 5.3 判据（断言）

| ID | 断言 | 反例 |
| --- | --- | --- |
| C1 | 未加编辑权限时端点 403；有权限时 200（正反成对） | — |
| C2 | 非法角色码 → 400 且不落库；非法门类型/决策 → 400 | 反例：写进不存在的角色 ⇒ 静默无效 |
| C3 | 保存后**立即**按新矩阵判定（例如把 DCP/NO_GO 的 QA 去掉后，QA 否决 → 403） | 反例：需重启才生效 ⇒ 缓存判红 |
| C4 | 破坏一致性的变更被**拒绝**（域级并集缺失 / 判定角色未定义） | 反例：允许保存 ⇒ 判红 |
| C5 | 变更前后 diff 与审计记录一致 | — |

### 7.3 幂等与并发

- 授予/回收/确认/裁员：**幂等**（重复提交返回既有结果，不产生第二行；唯一约束兜底 → 409 + 文案）；
- 决策矩阵 PUT：**乐观并发**（请求带 `expectedRevision`；不一致 → 409 + 当前值），避免两人同时改覆盖对方。

### 7.4 审计事件（全部走既有审计链）

`gov.field-grant.create` / `.revoke`、`gov.delegate.create` / `.confirm` / `.reject` / `.revoke` / `.use`、
`gov.decision-rule.update`、`gov.review.freeze`（冻结长期未用授权）。
字段：操作者、对象、旧值/新值（矩阵）、理由、时间、结果；**不含任何脱敏字段的真值**。
