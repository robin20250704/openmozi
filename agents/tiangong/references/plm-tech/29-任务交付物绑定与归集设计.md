## 1. 交付物 = **直接引用的域对象**（V204，V202 立表前提被推翻）

### 1.1 用户裁定与它推翻的东西

> "任务的交付物，不要等价于项目的交付物。任务就是干活，任何做的事都是交付物。"
> "应该允许用户自由选择类型、检索各域对象关联上。"

V202 把绑定建成 `t_deliverable` 的外键，即"任务交付物 = 项目交付物台账里的一条"。这在**业务上是两件事**：

| | `t_deliverable`（项目交付物） | 任务交付物（V204） |
| --- | --- | --- |
| 归属 | 项目级主数据 | 某条任务的产出物 |
| 状态机 | `PENDING→SUBMITTED→APPROVED`（证据门 + 职责分离 + 独立权限点） | 无 —— 达标由用户标注 |
| 受谁管辖 | 交付物基线（V126）、齐套率、门线判定 | 无 |
| 谁能改 | 编制人 + 批准人 | 任务任一参与人 |

把前者当成后者的载体，会连带三个坏后果 —— 其中第一个就是用户实际遇到的缺陷：

1. **关联不上**。用户想关联"这条任务要交付的一份文档"时，若项目没登记过对应交付物，就根本绑不了。
   实测 dev 库：**有交付物的项目 27 个，有任务的项目只有 4 个**，可选面几乎必然为空。
   用户看到的现象正是"只能关联需求基线类型"（`REQ_BASELINE` 是库里 `obj_type` 分布里的一个值）。
2. **被迫改动项目合规口径**。想让它可用就得先登记交付物，而登记会拉低项目齐套率、进入基线差集的"基线外多出"项。
3. **凭空禁止正常作业**。V202 因此加了"必须与任务同项目"的守卫；但一条任务本来就会去动别处的通用物料、模板文档，
   那正是"干活"本身。这道限制没有业务依据，已随模型改动删除。

### 1.2 改法

`t_task_deliverable(task_id, obj_type, obj_id, obj_code, binding_type, source, done)`，
`UNIQUE(task_id, obj_type, obj_id)`。这正是平台既有的**统一对象寻址**口径
（`t_obj_link.ref_type/ref_code`、`t_deliverable.obj_type/obj_id`、逻辑 ID `PLM:REQ:REQ-2026-0001#A` 同源），
**不是**本功能自创的第三种写法。解析与深链一律走 `ResolverRegistry`。

V204 迁移先加列并从 `t_deliverable` **回填**（任何环境若已有行也不丢数据），再删旧列与旧外键。
`obj_id` 是逗号多值串的行**不**回填（它不是单对象，无法一一对应）——这种行宁可显式暴露为"待修正"，
也不静默取第一个码当它是唯一目标。

### 1.3 可绑定类型 = 检索基座 ∩ 已注册解析器

- **只取检索基座**（`LookupService`，23 类）：`TASK`/`FOLDER`/`ORG`/`USR` 搜得到但**没有解析器** ⇒
  没有可读名、没有深链，绑上去只剩一个裸业务码，点不开、也没法确认绑对了没有。
- **只取解析器**（`ResolverRegistry`，19 类）：`OFR`/`ECN`/`SEG` 能解析但搜不到 ⇒ 无法"自由选类型 + 检索"。

交集 = **16 类**，含用户点名的全部四类（物料 / 需求 / 文档 / BOM），每类都"搜得到 + 点得开"。
该清单由后端算出并下发（`GET /tasks/deliverable-obj-types`），**前端不维护第二份** ——
前端硬编码的必然结果是"下拉里能选、提交时被拒"（合法界面 + 错误结论）。

### 1.4 两种语义（`binding_type`），本版**都是软提示**

| 语义 | 含义 | 作用 |
| --- | --- | --- |
| `KIT` 齐套要求 | 这个对象是本任务的产出物之一 | 让"任务做完了什么"可追溯；**不**挡完成 |
| `CONTROL` 控制任务完成 | 这个对象未达标时，本任务**还不算齐** | 未达标时**提示**（不硬拦） |

- 硬提示落点：任务详情面板逐条点名 + 推进到 `DONE` 的**流转响应**里附带 `controlHint`
  （提示要出现在动作发生的当场 —— 事后翻详情才发现就晚了）。
- **本版不硬拦**（用户裁定）。硬拦需同时处理 `TaskAutoCloseJob`（DONE 后 2 周自动完成）与"进度 ≠ 状态"口径。
  升硬拦时改一个值域即可，语义位已留好。面板内显式写明"只提示、不阻断"——
  提前承诺"系统会拦"比不拦更坏。

### 1.5 达标：**用户人工判定**，系统不代判

`done` 取三态：`TRUE` 已达标 / `FALSE` 未达标 / `NULL` **未判定**。

**为什么不由系统判**（2026-10-03 全平台逐类型核查，结论记在 V204 迁移文件头）：

- 平台**不存在**跨域"完成态"字典。唯一名为 `TERMINAL` 的常量是 `TaskService.java:73` 的私有
  `{DONE, CANCELLED}`，而 `CANCELLED` 是"已放弃"、不是"完成"，且只覆盖任务域。
- 各域语义互不相同甚至矛盾：需求有 `APPROVED`/`CLOSED`/`IMPLEMENTED`/`VERIFIED` 四个都像"完成"；
  BOM 只有 `DRAFT`/`DESIGN`（**都不是**完成）；项目是中文生命周期阶段，`已终止` 是"离场"不是"达标"；
  产品线是**在营状态**；CBB 是**成熟度轴** `DEV→VERIFIED→RELEASED→MAINT→DECOM`。
- **6 类根本判不了**：`DOC` 与 `BPL` **主表没有状态列**（状态在版本行 `t_doc_rev`/`t_biz_plan_rev`，
  存在"取哪一版"的歧义）；而文档恰是用户点名的四类之一、也是现存交付物里引用最多的（26/97）。
- 造一本跨域完成态字典 = 新建一份与各域词表并行的**第二份事实源**（本仓明令禁止）；
  由系统代猜 = 假绿。

用户裁定："不同工作阶段有不同的完成标准。控制任务完成先由用户自己判断。"

**读面刻意不含状态字段**：`TaskDeliverable` 放一个 `status` 会诱导调用方拿它当完成判据。
要判断"做完了没"请走 `deepLink` 看对象本身。归集候选里的 `extra` 字段在界面上如实标成
**「次要信息」**而非「状态」（物料给的是物料分类、文档给的是文档类型、BOM 给的是父件标签）。

**未判定与未达标分开计数**：前者是"我还没标"，后者是"我标了、它没做完"。
压成一个"未达标 N 条"会让用户以为自己漏标 —— 而漏标恰好最需要提示。

### 1.6 智能归集：**预览 → 勾选 → 确认**，推荐本身不落库

用户裁定"系统自动推荐、人工确认" ⇒ 推荐端点**只读**，未经确认**不写任何数据**。

候选取自 `LookupService`（不是 `t_deliverable`）—— 既然交付物是域对象引用，候选就必须是域对象。
这同时白拿两样东西：已登记类型的表名/码列/名称列**唯一事实源**，以及 `TASK`/`FOLDER` 的行级可见性守卫。

| 判据 | 口径 | 不满足时 |
| --- | --- | --- |
| ① 目标交付件类型 | **本次请求的入参**（任一参与人输入），**不存任务字段** | 拦住并列出可选项 |
| ② 任务时间区间 | 候选 `updated_at` 落在 [计划开始 − 缓冲30, 计划完成] | 写进 `mismatches`，**不**过滤 |
| ③ 主责 == 对象当前处理人 | 同上 | 写进 `mismatches`，**不**过滤 |
| ④ 已关联的自动消重 | 在**候选池**里排除 | 不出现 |

**① 为什么必填**：跨 20 个域各取一页会得到近千条候选，而"该看哪个域"本就是用户要回答的问题。
让他选，也让"空结果"与"你没选类型"彻底分得开。

**③ 为什么不作过滤条件**（用户裁定"可以放宽处理人的约束"）：对象侧"当前处理人"只对有待办面的类型查得到，
且大量对象此刻处于**待认领**态。拿它当硬过滤，绝大多数候选会被静默滤掉，
而用户只看到"没推荐结果" —— 无法区分"确实没有"与"因为没人认领所以不给"。

**② 用引用对象的 `updated_at`**，不用交付物自己的 `created_at`：后者只说明"何时登记"，与执行痕迹无关。
任务**未排期**时不按时间过滤（否则未排期任务永远得到空推荐，且看不出是缺计划期）。
`LookupService` 对 USR/ORG/FOLDER **不下发** `updated_at`（这三类无时间列，排序用 `id`）——
强行把 `id` 当时间下发会让时间窗判据在一个看起来成立、实则无意义的值上运行。

**判据 C6 不变量**：`reasons` 为空的候选**不允许出现在返回里**。没有理由的推荐退化成一份列表。

## 2. objType 两套词表：后端映射层（不改全局）

### 2.1 事实

平台上**两套同名不同码**的对象类型词表，且都是**既有的、成文的**约定：

| 写法 | 事实源 | 消费方 |
| --- | --- | --- |
| `ITEM`（本号文称 REF） | `ResolverRegistry` 解析器注册表 | 深链、📎 引用、AI 强制引用、审计对账 |
| `ITM`（本号文称 FLOW） | `LookupService` / `FlowTaskService.OBJECT_META` | 检索选择面板、待办、`t_flow_task` |

两套里**只有物料一个类型不同名**，其余同名同码。前端已为这件事做过一次归一
（`lib/objRef.ts` 的 `canonicalRefType` / 本次导出的 `lookupTypeCode`），并因此踩过一次坑：
查重面板传 `ITM` 而白名单收 `ITEM`，导致每条相似物料静默退化成纯文本。**后端此前没有对应物**。

**本次实测踩到的三个坑**（都固化成了回归断言）：

1. 落库必须归一到 **REF 侧（`ITEM`）** —— 存 `ITM` 会让 fail-closed 守卫在**再次绑定**时直接拒绝
   （"第一次能绑、之后不能"），且列表里显示不出名称与深链。
2. 但调用 `LookupService` / `FlowTaskService` 时必须翻回 **FLOW 侧（`ITM`）** ——
   不翻的话 `ITEM` 会被 `LookupService` 以 `VALIDATION_ERROR` 拒掉，症状是"类型明明在下拉里、归集却报类型不支持"。
3. 前端把 `ITEM` 直接喂给 `SearchPick` ⇒ 它跳过契约端点去找 legacy 适配器、而 `ITEM` 没有适配器
   ⇒ **选择器一个候选都没有**，界面上却看不出原因。故经 `lookupTypeCode` 翻译。

### 2.2 本次只补映射层，不做全局统一

统一要动 **116 个文件**（后端 48 / 前端 16 / 走查脚本 52），还要迁 `t_flow_task` 存量行、重建检索与查重索引，
并推翻上面那条已成文约定。故新增 `com.plm.platform.resolver.ObjectTypeVocabulary`：
只登记**差异项**（`ITEM ⇄ ITM`），全量取值仍是两侧注册表的事实源（**不做第二份清单**）。
它还提供 `diagnose(...)` 自检：若哪天有人在待办侧也改成 `ITEM`，该方法会报出"映射层已变成恒等映射"。

**全局统一留作独立架构项**，不在本需求范围内。

## 3. 任务书「挂起 → 恢复评审」死锁（V201）

### 3.1 缺陷现场

任务书在 `DCP0_REVIEW` 点「挂起」进 `HOLD`；再点「恢复评审」恒定 400 `该任务书已有进行中的 DCP0 评审`，
且**永远出不来**（`HOLD` 只有一个出边 ⇒ 死锁，不是循环）。

### 3.2 三处根因叠加

1. `CharterService.transition` 用 `if ("DCP0_REVIEW".equals(to))` 判定"新建评审"，**从不看 `from`**
   ⇒ 「恢复」与「首次提交」走同一段代码；
2. 进入 `HOLD` 时**没有任何拆解**，在飞 `t_review` 原样留在 `IN_REVIEW`；
3. `t_review.status` 当时只有 `PLANNED/IN_REVIEW/DECIDED`，**没有"暂停"这个概念**。

1+2+3 的后果：`ReviewService.requestReview` 的唯一性守卫恒为真 ⇒ 恢复**在实现上不可能成功**。

> 讽刺之处：`charter-flow.yaml:41-53` 那段长注释诊断的正是这个形态（"给了路、路上有门"），
> 但只用它否决了**被提议的** `DCP0_REVIEW→PRE_REVIEW` 边；同一文件 `:54` 已有同构的「恢复评审」边
> （road）而 `ReviewService.java:218` 就是那道门（gate），未被识别。

### 3.3 处置：补"暂停"语义，不动守卫

守卫本身是对的（守的是"同门评审双轨"这一真实危害）。缺的是挂起期的评审状态。
V201 把 `t_review.status` 值域放宽出 `SUSPENDED`：

| 动作 | 行为 |
| --- | --- |
| `DCP0_REVIEW → HOLD` | 在飞 DCP0 评审置 `SUSPENDED`（**未作废、未定论**） |
| `HOLD → DCP0_REVIEW` | `SUSPENDED` 置回 `IN_REVIEW` 并**复用同一条**（不新建、不重新发号，清单与签署记录全保留） |

**为什么复用而不是新建**：评审本体是 DCP0 这次决策的载体。新建会让同一门出现两条编号、评委要重新认一次、
已签意见留在旧评审上而新评审是空的。

**HOLD 有两条来路**（因此 `resumeAfterCharterHold` 带兜底）：手工挂起走 `SUSPENDED` ⇒ 复用；
`REDIRECT` 结论导致的 HOLD 是在评审**已 DECIDED** 之后才翻状态，没有 `SUSPENDED` 行可复用 ⇒ 走新建，
且唯一性守卫不会拦（只认 `IN_REVIEW`）。

**存量回填**（同一迁移内）：已卡死在 `HOLD` 的任务书，其在飞评审仍报 `IN_REVIEW` ⇒ 时间线继续谎报"评审中"。
V201 按"任务书当前处于 `HOLD`"把它回填为 `SUSPENDED`——**任务书状态才是事实源，评审状态是派生**。
实测在 dev 环境修好 2 条卡死数据（`SUSPENDED=2`，"HOLD 且评审仍 IN_REVIEW" 归零）。

界面：`gateNodeLabels.ts` 登记 `SUSPENDED: '已挂起'`（不能沿用「评审中」——那正是要修的谎报；
也不能叫「已决策/已作废」，两者都在说评审有结局）；`statusPill.ts` 给 `muted`（暂停），与任务书自身的 `HOLD` 同色。

## 4. 投诉「不良事件 ⇒ 上报时限」漏校验

### 4.1 缺陷与后果

登记投诉时勾了「不良事件」却不填「上报时限」，**提交照样成功**：
`reportable_deadline` 是可空列（V90:41）、DTO 无任何校验注解、服务层唯一交叉校验是 `occurredOn <= receivedOn`。

后果不只是"少一个字段"：超期监管口径（汇总条「不良事件超期上报」、提醒列表）都带
`reportable_deadline IS NOT NULL`，于是**恰恰是违规的那一类在指标上彻底消失**，
排序 `NULLS LAST` 让它静默沉到台账最后一页。没有时限就无法判定超期，而超期上报是法规义务。

### 4.2 处置

- `PvService.assertReportableDeadline`：条件必填，错误码 `CMP_DEADLINE_REQUIRED`，文案点明"超期上报属违规"。
- **create 与 update 两条路径都拦**：只拦 create 会留下"登记后勾上不良事件、不补时限"的旁路
  （UPDATE 走 `COALESCE(?, 列)`，判据须是"入参优先、缺省回落库中现值"）。
  注：`reportable_deadline` **无法被清空**——`COALESCE(?, 列)` 里 null 的语义是"保持原值"，
  所以真正可达、且必须拦的旁路只有"把一行本来没有时限的投诉勾成不良事件"（用例即按此设计）。
- 前端两处表单补 guard（PV 域的既有范式：`setErr` 早拦 + 提示语注明后端码），权威判据仍在后端。
- **不建 CHECK 约束**：本仓约定业务级跨字段规则一律写在 service（V90 的 CHECK 只管枚举值域），
  且现存查询口径全跳过 NULL，库里很可能已有 `adverse_event=TRUE` 且 deadline 为 NULL 的历史行，加约束须先回填。

全部按仓库纪律（`05-技术架构设计.md` §15.3 反假绿第 2 条）成对给出**负向对照**：
既证违规被拒，也证合规照常放行——只测"被拒"无法发现过度拦截。

> ⚠ **两条构建纪律（本批都踩到）**：
> ① 多个 Maven 进程并发写同一个 `target/` 会**静默损坏** class 文件，表现为大批用例集体报
