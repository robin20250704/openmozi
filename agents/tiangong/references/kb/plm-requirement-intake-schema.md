# 需求受理信息模式（intake schema）

> 用途：把"用户口语"转成"可分析、可验收的需求"的**字段契约**。是本 creature 的**内容模式**核心之一。
> 纪律：**左侧是客服的活，右侧是分析人的活**——不越界（C-03）。

## 一、登记时写入 PLM 的字段（客观描述）

| 字段 | 必填 | 客服怎么写 | 依据 |
| --- | --- | --- | --- |
| `title` | 是 | `【<模块>】<现象短句>（<可辨识条件>）`，≤60 字，不含"优化/有问题"这类空词 | V-03 |
| `reqType` | 是 | 默认 `SR`（系统需求）；用户诉求偏使用体验用 `UR`；法规/风险/成本类分别 `REG`/`RC`/`COST` | `plm-module-map.md` |
| `content` | 是 | 四段式 + 证据 + 用户原话 + `【分析输入】` | V-04 |
| `projectId` | 是 | 默认 `87`（`PRJ-2026-0087 天工AI PLM 1.0`） | C-05 |
| `sourceType` | 建议 | PLM 自身问题用 `PLM_SELF`；标准/法规驱动用 `STANDARD`/`REGULATION` | 服务端词表 |
| `reqClassId` | 选 | 1 功能 / 2 性能 / 3 安全 / 4 可靠性 / 5 准入法规 / 6 可用性 / 7 可制造可供应 / 8 可测试性 / 9 成本 | `/requirement-classes` |
| `stdClause` | 选 | 涉及标准条款时写（如 `GB/T 21417.1 §x.x`） | 手册 §3 |
| `paramName` | 选 | 指标名（如 `export_latency`）**登记时可写**，用它表达"我们要量化什么" | `plm-contracts.md` C-03 |
| `paramValue`/`paramUom`/`verification` | ⛔ | **死锁区：登记时无论怎么填都被拒**（填 `paramValue` 要 `verifyMethod`，而 `verifyMethod` 被阶段锁拦住 ⇒ 阶段锁与可验证性校验互斥）。量化要求写进正文【量化期望】段，交分析人 ANALYZED 后补录 | 源码 `RequirementService.java:1136-1142`；工具本地硬拒 |
| `sourceChannel` | 选 | 服务端白名单豁免、登记时可写；默认不写（少一个写入面少一类 400） | `SOURCE_CHANNEL_STAGE_EXEMPT` |

## 二、只进正文、不进请求体的"分析输入"（后置结论）

| 字段 | 谁定 | 客服怎么处理 |
| --- | --- | --- |
| `priority` | 分析人 | 可在正文写"客服初判：影响面 X、频次 Y"作为**依据**，不写"优先级=HIGH"这种结论 |
| `dfxDimension` | 分析人 | 同上；只在现象明显指向某维度时提示（如"每次都要手工导数据"→ 可提示 `DFU`） |
| `verifyMethod` / `verification` | 分析人 | 客服只写"怎么算修好了"的**用户口径** |
| `appealsDim` | 分析人 | 客服只记录"用户觉得亏在哪"（价格/质量/时间/多样性/服务/渠道/品牌/关系） |
| `solution` | 方案人 | **完全不写** |

## 三、客服自己的受理记录（进 `.creature/tasks/` 与电容器，不进 PLM）

| 字段 | 说明 |
| --- | --- |
| `reporter` / `role` / `channel` / `reportedAt` | 谁、什么角色、从哪反馈、什么时候 |
| `repeatCount` | 同主题第几次反馈（**强度证据**，驱动洞察线聚类） |
| `triage` | 分诊结论：真缺陷 / 用法问题 / 权限问题 / 业务前置 / 已知偏差 |
| `dedupHits` | 查重命中的既有条目（编号 + 相似度），作为"为什么没有新建"的证据 |
| `evidence` | 证据清单（截图/日志/编号/URL）与其获取状态 |
| `unknowns` | 客服未能确认的点（**必须显式列出**，是分析人的第一批追问项） |
| `upgradeReason` | 若走升级讨论，写明为什么客服无权定性 |

## 四、清晰度质量门（四判据，逐条可判）

1. **现象可复现**：给了页面路径 + 操作序列 + 触发条件；不只写"有时候会这样"。
2. **影响可描述**：说清对谁、影响什么、是否造成实际损失；不含"不好用"这类无锚评价。
3. **期望可验收**：期望行为能被演示或观察判定（能写出"看到 X 就算成了"）。
4. **证据可指认**：至少有编号/URL/报错原文/截图路径之一；没有证据时**必须显式标注"无证据，待补"**。

> 四判据**全过** → 通过；**缺证据但其余齐** → 通过并在正文标注待补；**现象/影响说不清** → 无效，回炉结构化；**涉及跨模块争议或客服无权定性** → 升级讨论。
