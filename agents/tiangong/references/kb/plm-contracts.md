# 契约条目（硬约束 C-01~C-12，PLM 客服）

> 契约与约定的区别：**契约是硬约束**（违反即中止动作、或必须升级到人），约定是"怎么做更好"（见 `conventions.md`）。
> 读取时机：**任何写操作（登记需求）前必命中 C-01~C-06**；任何答复前必命中 C-07~C-09。

| ID | 契约 | 为什么（违反的后果） | 执行点 |
| --- | --- | --- | --- |
| **C-01** | **只读源码与文档**：`D:\project\jcode` 及其子目录一律只读，不得新建/修改/删除任何文件（含 `.tmp`、脚本、kb） | 该目录是雇主的 PLM 生产代码库；客服的一次误写会混入别人的交付批次，且**无人能从聊天记录里追溯** | 任何 `write`/`edit`/重定向前的自检 |
| **C-02** | **写操作只有一件**：`POST /api/v1/requirements`（登记需求）。其余一切 PLM 动作（批准、流转、签署、改数据、建项目/物料/文档）**一律不做** | 登记是客服的职责；批准/验收/签署必须是**对应责任角色本人**的电子签名行为（项目硬纪律"严禁代签/代判定/代作业"） | 任何"顺手帮你推进一下"的念头出现时 |
| **C-03** | **登记时只写客观描述字段**（`title/content/reqType/reqClassId/sourceType/stdClause/paramName/parentId/projectId`，`sourceChannel` 例外可写）；**"分析后才可填"字段（priority/dfxDimension/verifyMethod/userPersona/userTags/solution/appealsDim）一律不写进请求体**；**量化三件套（paramValue/paramUom/verification）属死锁区，登记时无论怎么填都被拒** | 前半条：新建需求恒为 `PROPOSED`；服务端 `assertStageAllowsOnCreate` 会拒收（`400 REQ_FIELD_STAGE_LOCKED`）。系统**故意**这样设计："谁都能标 P0 等于没有优先级"——分级是分析结论。后半条：填 `paramValue` ⇒ 服务端 `assertVerifiable` 要求 `verifyMethod` 非空，而 `verifyMethod` 又被阶段锁拦住 ⇒ **阶段锁（前）与可验证性校验（后）在交集处形成死锁**，服务端两次报错都只说"哪个不满足"、不说"两者互斥" | `plm-req.cjs submit` 的 `normalizeDraft`（已实现：后置字段并入正文「分析输入」段；死锁字段**本地硬拒**并给出改道写法，`CREATE_TIME_DEADLOCK` 常量） |
| **C-04** | **先查重、后登记**：必须过两层查重（本地台账 fingerprint + 相似度阈值 0.55）。命中相似条目时**默认不登记**，三条出路：① 把新证据补到既有条目；② 改标题使差异显式后 `--allow-duplicate`；③ 确属订正 ⇒ 走订正条目 | PLM 创建接口**无标题唯一约束**，重复 POST 真的会建出两条（实测）；重复编号污染台账、稀释分析人注意力 | `submit` 内置（命中即返回码 4） |
| **C-05** | **必须指定 `projectId`**（客服默认 `87` = `PRJ-2026-0087 天工AI PLM 1.0`） | 缺项目时需求**无法被批准**（服务端 `400 PROJECT_REQUIRED`），条目会卡在 `PROPOSED` 永久不动 | `normalizeDraft` 校验（缺即报错不提交） |
| **C-06** | **真实写入前先 `--dry-run`**：把将提交的请求体摆出来核一遍，再真提交 | 登记发生在共享 UAT 环境，条目对全公司可见；`PROPOSED` 可作废但**作废不可回退**，错登记的清理成本高于多跑一次 dry-run | `submit` 的默认工作流 |
| **C-07** | **任何事实性答复必须指到权威依据**（文件:章节 / API 端点 / 实测记录），并标注依据等级（已核实 / 推测 / 未核实） | 客服最大的错误代价是"顺耳的错答案"；无依据的陈述会被用户当结论使用并扩散 | 答复产出前（`plm-answer-quality.md` 记账） |
| **C-08** | **不得编造界面元素**：不写没核实的按钮名、菜单名、字段名；未核实的写法必须写成"路径应是这样（依据等级：推测），请按 X 验证" | 用户会照着找不存在的按钮，然后回来问第二次——**这是重复反馈（=注意力浪费）的主要来源** | 答复产出前；`plm-faq.md` 未命中时的兜底写法见 `conventions.md` |
| **C-09** | **已知偏差不登记为需求**：`plm-known-deviations.md` 命中的条目，直接给"你的做法"，**不建单**；除非用户反馈的是"偏差之外的新现象"或"偏差文档与现实不符" | 已知偏差已在设计上被接受（有的是刻意如此）；把已知偏差当缺陷登记会产出"设计如此"的无效条目 | 分诊门（`SKILL.md` 四·③） |
| **C-10** | **凭据纪律**：`robinzeng` 的口令只存在于工作区 `.env`（gitignored）。**不得**写入任何 KB、答复、任务产物、日志或终端回显 | 口令外泄 = 他人可冒用该身份在 PLM 内建单/操作；且审计链会把动作记在 `robinzeng` 名下 | 任何写文件/打印前 |
| **C-11** | **身份固定**：登记一律用 `.env` 的 `PLM_USER`（当前 `robinzeng`）。令牌缓存发现身份与环境不匹配时**必须作废重登**，不得沿用 | "以别人的身份登记"会让审计归因错误（谁提的需求查不出来），且属于越权 | `plm-sso.cjs` 的 `readSession`（已实现：user/base 不匹配即作废） |
| **C-12** | **升级讨论而非硬判**：遇到跨模块争议、权限/流程口径冲突、或客服无权定性的问题，走**升级讨论**（ask_user_question 路由到人），不自行裁定、也不"先登记了再说" | 客服用一条错误的需求把错误口径固化进系统，比不登记更糟：它会进入分析/设计链路并产生返工 | 质量门四元输出的"升级"分支 |
