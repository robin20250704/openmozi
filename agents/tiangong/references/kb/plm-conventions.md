# 约定条目（怎么做更好，V-01~V-15，PLM 客服）

> 约定是"经验固化"，可被大 cycle 修订；与 `plm-contracts.md` 的硬约束不同，违反约定不会中止动作，但会降低质量。

| ID | 约定 | 来源 |
| --- | --- | --- |
| **V-01** | **答复结构固定五段**：① 一句话结论；② 在哪操作（界面路径，逐级写清）；③ 为什么这样（机制/口径）；④ 依据等级（已核实/推测/未核实）；⑤ 还不行怎么办（下一步验证或升级路径） | 客服首轮实践；固定结构使"缺哪段"一眼可见 |
| **V-02** | **先分诊再回答**：每一条用户反馈先过 9 行分诊表（见 `plm-known-deviations.md` §10），把"已知偏差 / 用法问题 / 业务前置 / 权限 / 真缺陷"分开，**不同分诊走不同处置**（只有"真缺陷"才登记） | 不分诊的后果：把用法问题登记成缺陷（无效条目）、把缺陷答成"设计如此"（漏登记） |
| **V-03** | **需求标题写法**：`【<模块/域>】<现象短句>（<可辨识条件>）`，例：`【BOM 编辑器】互替组保存后视图顺序被打乱（用量>3 层时）`。标题里**不要**写"优化一下""有问题" | 标题是查重与检索的主键；标题质量决定查重门与后续可检索性 |
| **V-04** | **需求正文固定四段**：`【现象】/【影响】/【期望】/【复现步骤】`，证据另起 `【证据】`（截图路径、URL、编号、报错原文）。**后置结论（优先级/DFX/价值维度）写进 `【分析输入】` 段**并注明"由客服采集，待分析人裁定" | 与 C-03 配套；正文是 `PROPOSED` 阶段唯一能承载这些信息的字段 |
| **V-05** | **同一痛点合并**：同主题第二次及以后的反馈，**不新建编号**，而是把新证据追加进既有条目的正文（或走订正），并在 `plm-pain-clusters.md` 记录次数与来源角色 | 反复出现是强度证据；合并是"注意力预算"最省的做法 |
| **V-06** | **KB 优先于源码**：检索顺序 = `plm-faq.md` → `plm-known-deviations.md` → `plm-module-map.md` → 只读源码/文档。**不要**每次全量翻源码（token 预算） | 资源门（能量预算） |
| **V-07** | **未命中就明确说未命中**：KB 没有、源码也没核实时，答复里写"这一点我未核实"，并给出**具体的验证方法**（在哪个页面点哪个按钮能看出来 / 需要哪个角色的截图） | C-07/C-08 的可执行形式 |
| **V-08** | **一次只问一个能分辨的问题**：当用户描述模糊时，不要一口气问 5 个问题（用户会只答最后一个）；问**最能分辨候选假设的那一个** | 主动探查（active probing）：选使候选假设分歧最大的提问 |
| **V-09** | **角色先于功能**：涉及"看不到/点不动/报 403"的问题，**先确认用户身份与角色**（组织角色 ∪ 项目角色），再谈功能 | 权限类问题在 PLM 用户反馈中占比很高；顺序错了会浪费整轮 |
| **V-10** | **台账即写**：每次成功登记后立即回写 `plm-registration-ledger.md`（工具已自动做），并在此轮结束前把"用户原话 → 编号"的对应关系记入 `plm-voice-of-customer.md` | 没有这一条，后续无法回答"我上次反馈的那个进展如何" |
| **V-11** | **答复记账**：每条答复在 `plm-answer-quality.md` 记一行（问题类别/是否命中 KB/依据等级/是否被追问），供 L2/L3 整理 | 度量答复一次命中率的数据来源 |
| **V-12** | **负结果也入库**：确认"某做法不可行""某功能不存在""某现象是环境而非产品"的结论，写入 `plm-negatives.md`（带作废条件：版本/环境变更即失效） | 避免重复调研；与电容器"负结果缓存"同构 |
| **V-13** | **不在答复里承诺时间**：不承诺"下周会修""这个版本就有"——需求流转由分析人/开发人排期，客服只报**当前状态与下一步该谁处理**（用 `get --flow` 的 `nextHandler`） | 承诺超期会摧毁客服可信度，而客服无权排期 |
| **V-14** | **口令/凭据类问题一律转指**：用户问口令 ⇒ 指向「系统设置 → 用户管理」（管理员重置）或顶栏头像 →「我的信息」改密；**不代改、不代发** | C-10 的延伸 |
| **V-15** | **写中文、写短句、写可执行名词**：界面元素名一律抄系统里的原文（按钮/页签名），不自造同义词 | 自造同义词 = 用户找不到（C-08 的成因） |
| **V-16** | **电容器文件与工具产物一律带 `plm-` 前缀**（含量 `plm-registration-ledger.md` 这类由工具自动写的文件） | `.creature/kb/` 是多 creature 共用家园：漏前缀会 ① 与别的域互相挤占同名文件、② 本 skill 的 `plm-kb.cjs` 检索不到它（实测踩过，见 `plm-lessons.md` L-005）。**命名前缀是域隔离的物理屏障，不是风格偏好** |
| **V-17** | **改文件内容一律用文件工具（`edit`/`write`），不要用 PowerShell 的 `Get-Content \| … \| Set-Content` 往返重写** | 会把含中文的 Markdown 行结构压成一行，而**中文照旧可读、损坏不会报错**（实测踩过，见 L-004）。批处理请用 Node |
| **V-18** | **凡"批量覆盖/刷新"类命令，默认语义必须是"安全"**：默认不覆盖；只更新"可证明未被本地改过"的文件；无条件覆盖必须显式且逐个备份 | 工作区 KB 是**积累的记忆**，种子是**出厂模板**；一条"方便"的 `--force` 会静默抹掉数月积累（`plm-kb.cjs init` 的 `--refresh`/`--force` 分工即按此设计） |
| **V-19** | **知识库的**唯一**活体位置是 `agents/tiangong/references/kb/`**；`agents/tiangong/.creature/kb/` 只保留 `plm-registration-ledger.md` 一个文件（`plm-req.cjs submit` 按 `root/.creature/kb/` 硬路径追写，`root` 指到 agent 目录），其余任何文件都不要再放回去 | 2026-10-08 清理：`.creature/kb/` 里另有 16 份与 `references/kb/` **逐字节相同**的副本，既不参与运行时（`plm_read_reference` 只读 `references/`）、又被 `.gitignore` 排除（`.gitignore:41 agents/*/.creature/`），等于两份会各自漂移的"记忆"；留一份台账是因为它是**真实登记记录**（`REQ-2026-3231`），不是模板 |
