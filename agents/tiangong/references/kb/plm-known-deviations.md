## 1. 登录与鉴权

### D-01 运行态只允许 SSO，dev 身份入口停用
- **现象**：登录页不再出现「进入（dev）」；未登录访问任意页面/深链**自动跳转**统一认证用户名/密码页（无需点击）；自动跳转失败时停在兜底页并给 `登录（SSO）` 按钮。容器注入 `GET /plm-config.js` 返回 `{"devLogin": false}`。
- **影响**：早期文档/口口相传的"dev 入口"用法失效；依赖免登录身份的自动化脚本一律 401。
- **用户该怎么做**：直接用统一认证页登录；脚本/批量核对从**已登录会话**取凭据。
- **依据**：附录C 第 1 条（附录C:9-14）；01 章 §1（01:9-32）；17 章 C.4（17:249）。

### D-02 UAT 禁止密码授权取 token
- **现象**：UAT 上以账号口令直连取 token 报 `unauthorized_client`（客户端不允许 direct access grants）；dev 上同一脚本可用。
- **影响**：dev 上能跑的直连脚本（含 `_dryrun/tools/plm.mjs` 一类）在 UAT 不可用。
- **用户该怎么做**：UAT 验收**只走浏览器登录**；勿用账号口令直连 API。
- **依据**：附录C 第 2 条（附录C:16-21）；README「两个环境的关键差异」（README:35-38）。

### D-03 未显式配置鉴权模式时服务静默回落 dev 模式（所有角色门失效）
- **现象**：部署/重启时若未显式配置鉴权模式，服务静默回落到 dev 模式 ⇒ **人人都是同一套角色**，权限体系整体失效且**无任何报错**。
- **影响**：看起来"功能都能用"，实际全部门都开着；这是实施侧风险，**页面里修不了**。
- **用户该怎么做**：用**只读账号**登录自查——若"人人角色一样"，即鉴权模式配错，找实施。
- **依据**：10 章 §8（10:112-114）。

### D-04 建号缺邮箱/名/姓 → 建得出但登录被拒
- **现象**：新账号四项（登录名 ≥3 位，只允许字母/数字/`._-`；邮箱/名/姓）缺任一项，登录报 `Account is not fully set up`。
- **影响**：误以为"账号建好了但系统坏了"，或往身份源写合成数据。
- **用户该怎么做**：四项齐备再创建；缺项**先补齐再让人登录**，不要怀疑登录功能。
- **依据**：10 章 §5（10:79）；17 章 C.4（17:250）；README 账号节（README:42）。

### D-05 刷新/新标签页不会掉回登录页
- **现象**：刷新或新开标签页直接回到系统（会话在浏览器里，一次性参数立刻从地址栏清除）；只有连续自动跳转失败才显示「已暂停自动跳转以免反复来回」。
- **影响**：把"停止自动跳转"误读成"登录坏了"。
- **用户该怎么做**：点一次 `登录（SSO）`（自动跳转停了，手动入口不停）；提示"无法连接统一身份认证"多为凭据服务不可达，稍后重试或找管理员。
- **依据**：附录A Q16（附录A:92-94）。

## 2. 权限、角色与"看不到按钮"

### D-06 `GET /_platform/permission/rules` 受 `_admin.read` 保护 → 非管理员 403
- **现象**：普通成员请求该端点得 **403** `无权限执行 _admin.read（…）`。
- **影响**：普通成员**不能自助**读权限点矩阵，无法判断"我缺哪个角色"。
- **用户该怎么做**：走**治理台**（决策权限矩阵，只读）或请管理员/PMO 代查该点允许的角色集。
- **依据**：17 章 §B 第 2 步 ⚠（17:174-177）；10 章 §7（10:102）。

### D-07 两类 403 语义不同（角色不足 vs 对象超出授权范围）
- **现象**：① `无权限执行 <domain>.<action>（权限点：… 当前角色：…）` = 权限点不足；② `无权操作该对象（超出授权范围: <domain>.<action>）` = 对象级 ABAC 拒绝。
- **影响**：把对象级 403 当角色问题，会去申请一个**本来就已经有**的角色。
- **用户该怎么做**：① 看**角色配置**（`GET /_platform/permission/me` → `rules` → 治理台/管理员）；② 看**对象归属**项目/属主。
- **依据**：17 章 §3.1 表（17:188-196）；10 章 §6（10:85-94）。

### D-08 ABAC/ACL「只能收紧不能放宽」；"不配规则"≠"全放行"
- **现象**：规则按用户**全部角色取并集**求值，判定口径是"一条 allow 都没有 ⇒ 放行；有 allow 但全未命中 ⇒ 拒"。想表达"某角色不受限"不能靠不配规则——该用户一旦同时持有别人的受限规则就会被**静默误拒**（日志 `ABAC_LEAST_PRIVILEGE`，界面只看到 403）。
- **影响**：出现"莫名 403"且配置看起来"什么都没配"。
- **用户该怎么做**：要放行必须**显式配 `always`**（`always` 不是放宽 RBAC：RBAC 不过时根本走不到 ABAC）。改动影响全系统可见性，谨慎。
- **依据**：10 章 §4 ⚠（10:52-58）；附录A 术语（附录A:119）。

### D-09 角色编码不能由中文名称推导，且被流程引用后不可改
- **现象**：历史实现（及旧文档）试图用中文名推 `code` ⇒ 生成的 code 不符合格式、也**对不上流程边引用的角色码**，表现为"角色建了但流程还是跑不动"。
- **影响**：流程报"缺少角色/候选池为空/没人能签"，有人去翻流程定义绕一大圈。
- **用户该怎么做**：**先想好英文编码**（如 `pdt_mfg`）再填中文名；编码被流程引用后**不要改**；"流程跑不动"**第一查证点**是系统设置里的「角色 ↔ 流程匹配检查」卡（橙字 = 角色未定义）。
- **依据**：10 章 §2 ⚠ 与 §3 表（10:32-48）；17 章 A.11（17:126）。

### D-10 物料/文档/需求等"已发布禁改"，但报错码各不相同
- **现象**：`400 ITEM_LOCKED` / `REQ_LOCKED` / `CHARTER_LOCKED` / `DOC_LOCKED` / `当前状态不可编辑: …`（BR-01）。
- **影响**：用户以为是 bug 或权限不足。
- **用户该怎么做**：按对象分路——**物料**：ECO 登记为受影响对象后进 `CHANGING` 窗口（注意 `CHANGING` 下**也可能**报 `ITEM_LOCKED`）；**文档**：`DRAFT` 直接改，`APPROVED` 走「撤回重审」，`RELEASED` 走「＋ 新建版本（升版）」；**需求**：基线化后走 ECO（BR-10）；**任务书**：订正走 `POST /ipd/charters/{id}/corrections`（理由 ≥8 字，仅数据区字段）。
- **依据**：附录A Q8（附录A:67）；17 章 C.2（17:216）；08 章 §3.2（08:57-60）；05 章 §3.1。

## 3. 门线与评审（客服最常被问）

### D-11 交付物证据白名单不含 `RVW` / `MIL`
- **现象**：`objType` 只能取深链解析器注册的 19 种类型，**不含 `RVW`（评审）与 `MIL`（里程碑）**；指向它们报 `400 EVIDENCE_UNRESOLVED` 并列出可用类型。而平台自己的模板却预置了 `objType=RVW`。
- **影响**：**门评审类交付物在任何情况下都无法完成证据锚定**；评审类交付物只能靠名称里的门码被识别。
- **用户该怎么做**：证据一律锚定**受控业务对象**（`DOC`/`REQ`/`RSK`/`ECO`/`ITEM`…）；评审结果的证据用「评审本身的结论 + 遗留问题」承载；名称里保留门码（如 `[验证] TR4 评审记录`）。按 `SELF_GATE_REVIEW`/`OTHER_GATE_REVIEW` 作**不阻断项**处理。**不要反复试锚 `RVW`**。
- **依据**：附录C 第 4 条（附录C:37-42）；03 章 §6.3 ⚠（03:206）；17 章 C.2（17:220）。
- 源核对：`ipd/plm-app/backend/.../DeliverableEvidenceService.java:134` 抛 `EVIDENCE_UNRESOLVED`。

### D-12 交付物状态可被提交人自批（无"提交人 ≠ 批准人"强制）
- **现象**：`POST /projects/{id}/deliverables/{did}/status` **只有一道 `project.update` 权限门**，**无审批意见字段**；提交人自己批准不会被拦。
- **影响**：DMR/DHF 类职责分离在**数据上不必然成立**（实测曾出现"已批准交付物绝大多数是自批"）；审计看到的是"谁改了状态"。
- **用户该怎么做**：纪律要求**提交人 ≠ 批准人**；用门预检的 `DELIVERABLE_SELF_APPROVAL` 当**自查仪表**（报"编制人自批 N 条 / 本项目名册内有第二批准人可辨 / 无第二批准人"）。看到"自批"标记时**不要**当作他人批准的证明。
- **依据**：附录C 第 5 条（附录C:44-49）；03 章 §6.1 ⚠（03:185）、§8 第 5 行（03:241）。

### D-13 交付物阶段归属：存量条目可"卡门"且失败项看起来无关
- **现象**：阶段归属 = 显式 `stage` 优先，否则回落名称前缀（`[立项]`/`【立项】`/`（立项）`/`(立项)` 均可）。**新登记**两者必有其一（都没有 **400 拒绝**）；但 **V97 之前**登记的历史条目可能两者皆无（`STAGE_UNSET`），此类条目被**保守纳入每一道门的判定集**。
- **影响**：一条无前缀老条目会让 DCP0 与 TR1 **双双 `passed=false`**，失败项看起来与本次工作无关。
- **用户该怎么做**：登记一律 `[阶段] 名称`（建议同时传显式 `stage`）；接手老项目先扫一遍交付物名称；门被阻断时看预检 `DELIVERABLES.items[]` 的 `stage` 与 `reason`（`STAGE_UNSET` 即此类），按补前缀/补 `stage` 订正或按流程废弃。
- **依据**：附录C 第 6 条（附录C:51-56）；03 章 §6.2 ⚠（03:191-193）。

### D-14 门序无守卫（可乱序发起，事后拉红已定论的门）
- **现象**：门点之间**没有先后守卫**——TR3 可以晚于 DCP2 发起并**事后把 DCP2 拉红**；TR1/TR2 可以**从未发起**而系统不报错。
- **影响**：门线"看起来齐"不等于"按序走过"；事后补发的 TR 可能推翻已决策的 DCP。
- **用户该怎么做**：按阶段顺序推进，用「项目驾驶舱」的 `下一待决策` 与时间线核对**门序是否连续**；对"从没发起过"的门由 LPDT 在评审工作台补跑预检并留结论，**不要跳序决策**。发现乱序**按缺陷登记**，不要用改数据"摆平"。
- **依据**：附录C 第 7 条（附录C:58-63）；03 章 §8 第 2 行（03:238）。

### D-15 预检 `passed=true` 可能是"空通过"，`passed=false` 可能不阻断
- **现象**：`passed=true` 可能是"空通过 / N/A 未评估 / 未配置"（`detail` 会自述，如"N/A 空集自述"、"未配置：差集恒为空"）；`passed=false` 若 `severity=ADVISORY` 则**不阻断**。
- **影响**：把"没查"读成"查过且通过"；或看到一个红项就以为门被卡住。
- **用户该怎么做**：**读 `severity` 与 `detail`，不要只读 `passed`**；只有 `severity != ADVISORY` 且 `passed=false` 才是阻断原因；反向也要读自述，别把 N/A 当合格。
- **依据**：附录C 第 8 条（附录C:65-70）；03 章 §5.1（03:128-137）；17 章 C.3（17:232-233）。

### D-16 评审条件必须用结构化 `conditions[]`，只写 `conditionNote` 不生成可跟踪对象
- **现象**：条件若只写在 `conditionNote`（自由文本），**不会逐条物化**成可跟踪的遗留问题；只有 `conditions[]` 提交才逐条派生遗留问题并挂钩跟踪。
- **影响**：条件成为"散在备注里的一句话"，无责任人、无期限、无逐条闭环，下道门复查无从对账（`⚠N` 计数也会失真）。
- **用户该怎么做**：**用 `conditions[]` 逐条给条件**（描述/责任人/期限）；自由文本只作补充说明。
- **依据**：附录C 第 9 条（附录C:72-77）；03 章 §5.4 ⚠（03:161-165）；17 章 C.3（17:234）。

### D-17 `flow-overview` / 驾驶舱的 `blocked` 文案不指向真实失败项
- **现象**：被阶段守卫阻断的 DCP 节点 `blocked=true`、`blockReason` = `<门码> 尚未 GO/GO_WITH_RISK，阶段不可推进`——**只说结论缺失，不说缺什么材料**。
- **影响**：按文案去"补一个 GO"会走错方向（结论只能由评审工作台的判定 + 签署产生）。
- **用户该怎么做**：`blocked` 只用来**发现**阻塞；**原因一律看** `GET /api/v1/reviews/precheck?projectId=&gateCode=` 的 **BLOCKING** 失败项；`400 STAGE_GUARD_BLOCKED` 时同样先做对应 DCP 决策。
- **依据**：附录C 第 14 条（附录C:122-127）；16 章 §2.2 ⚠（16:63-66）；17 章 C.2（17:225）。

### D-18 驾驶舱：流程摘要拉取失败时显示告警占位，不可读成"无阻塞"
- **现象**：某项目流程摘要拉取失败 ⇒ 该项目行不显示门按钮，显示 `⚠ 流程总览加载失败（不代表无阻塞，请刷新重试）`，尾部读数 `—`。
- **影响**：把它读成"没有阻塞"；设计上**刻意不把"取不到"画成"无阻塞"**。
- **用户该怎么做**：点 `↻ 刷新` 重试；整页都失败时看筛选条右侧的 `msg` 文案，确认是网络/鉴权问题再排查。
- **依据**：16 章 §4 ⚠（16:111-114）；16 章 §6（16:134）。

### D-19 驾驶舱数据源是 `flow-summary`，与文档叙述的 `flow-overview` 不同（等价但抓不到请求）
- **现象**：文档写"数据源为 `GET /projects/{id}/flow-overview`"，而运行态 `/cockpit` 实际调**分页端点** `GET /projects/flow-summary`（每页 1 次请求）。
- **影响**：抓 `/cockpit` 网络请求找不到 `flow-overview` 调用点；两者语义等价，读数不会不一致。
- **用户该怎么做**：读板上的数字用 `flow-summary`；要看**阶段守卫**与门点完整明细（条件、签署、否决、判定人缺失）用 `GET /projects/{id}/flow-overview` 或直接开评审门工作台。
- **依据**：16 章 §3 ⚠「本批待裁定」（16:89-92）、数据来源表（16:81-84）。

### D-20 签署 = 定论；否决只在签署前有效
- **现象**：签署后结论**不可更改**，要改只能**再次发起一次新的决策评审**；存在**未撤回否决**时无法签署（`400 VETO_PENDING`）；已签署不能再否决（`400 SIGNED_NO_VETO`）；GO 类结论要求主席签署（非主席 400 `SIGNER_REQUIRED`）。
- **影响**：用户想"改一个字"却找不到编辑入口。
- **用户该怎么做**：签署前把结论与综合意见定好；改结论走"再次发起决策评审"；有否决先撤回或改判。
- **依据**：03 章 §5.3（03:150-159）；17 章 A.3 注（17:48）、C.2（17:221-223）。
- 源核对：`ReviewService.java:600`（SIGNER_REQUIRED）、`:606`/`:951`（VETO_PENDING）、`:985`（SIGNED_NO_VETO）。

### D-21 门结论不能用「流转」按钮或接口直接落地
- **现象**：门结论**只能由评审工作台的判定 + 签署产生**；用流转按钮/接口直接落地不成立。
- **影响**：有人试图"先把状态推过去"或"补一个 GO"，结果门仍然不开。
- **用户该怎么做**：走 项目管理 → 项目时间线 → 点门节点 → 预审干跑 → 逐项判定 → 签署。
- **依据**：17 章 A.1 硬约束（17:25）；附录C 第 14 条（附录C:125）。

### D-22 交付物状态只有三个值，其他值报 400
- **现象**：交付物状态只有 `PENDING` / `SUBMITTED` / `APPROVED`（其他值 400）；`APPROVED` 后锁定，只能看处理记录。批准/驳回未关联受控对象时理由必填（`EVIDENCE_REQUIRED`）。

## 4. 需求与追溯

### D-23 `TEST_CASE` 在系统内无实体 → RTM 无法建"需求→测试用例"链
- **现象**：界面保留了 `TEST_CASE` 目标类型，但**系统内没有测试用例对象**；指向它的追溯行会成为**脏追溯**（`TRACE_DIRTY`，仅告警不阻断，属历史欠账，实测存量 34 行 `TC-1` 全悬空）。**新写入会被直接拒**：`400 TRACE_TARGET_UNRESOLVABLE`。
- **影响**：RTM 无法建立"需求 → 测试用例"这一跳；追溯完整性只能证到"需求 → 设计/验证记录"。
- **用户该怎么做**：**替代路径**——① 验证证据锚定到受控**文档**（`DOC_REV`，如 V&V 计划/测试报告）；② 风险控制措施登记为**风险台账**条目并锚定（`RISK_CTRL`）；③ 需要矩阵时按文档/风险控制口径人工成册。**不要把 `TEST_CASE` 当可用对象去建**。
- **依据**：附录C 第 10 条（附录C:79-84）；02 章 §6 ⚠（02:167，注明"280 个 API 路径中不存在任何 TEST_CASE 实体"）；17 章 A.7（17:85）。
- 源核对：`RequirementService.java:241-242`（抛 `TRACE_TARGET_UNRESOLVABLE`）、`:974`；`RequirementTraceVocabulary.java:71`（`resolvable=false`）；`PrecheckService.java:266/290`（TRACE_DIRTY）。
- **补充（源）**：`PUT /requirements/{id}/traces` 是**整体替换**且**先 insert 后 delete**，body 与存量边重叠会 400 duplicate key；建议"先 GET 备份 → PUT 空 → PUT 全量"。**依据**：`docs/plm-reflection/raw-user-requests.jsonl`（子代理任务书原话，属 Tier B 转述）→ 现场验证前按**推测**对待。

### D-24 `ACCEPTED`（已验收）不能直接作废——但有「退回（误验收）」补救边
- **现象**：需求状态机 **9 态 / 16 边**（`GET /_platform/flows/requirement`）；`OBSOLETE` 边只从 `PROPOSED`/`ANALYZED`/`APPROVED`/`SOLUTION_DEFINING` 出发，**没有 `ACCEPTED → OBSOLETE`**；但 `ACCEPTED` 实测有 **2 条**出边：`→ CLOSED`、`→ VERIFIED`（`rework`，即「退回（误验收）」，**必须填原因**）。`OBSOLETE` **确实没有出口**且不可回退。
- **影响（已收窄）**：发现误验收**不必**改数据、不必新建订正条目，退回 `VERIFIED` 即可。**仍成立**：`VERIFIED` 同样不能作废 ⇒ 要彻底废弃仍须走**工程变更（ECO）**或**订正/新增替代条目**。
- **用户该怎么做**：入 `ACCEPTED` 前确认清楚；已误验收用「退回（误验收）」；作废前想清楚（作废不可回退，恢复只能新建条目并建追溯）。
- **依据**：附录C 第 11 条（附录C:86-106，含 2026-09-25 重写说明）；02 章 §5「两条看起来没有出口的状态」（02:134-143）、§8 边界提醒（02:208）。
- ⚠ **历史坑（务必避免复现）**：本条**此前被写成"无自助补救通道"**，导致"用户按手册以为无路可走，于是重复反馈同一问题"（附录C:91、02:110-112）。客服答复**必须以 16 边口径为准**。

### D-25 需求详情面板不显示「来源」（`sourceType`），但接口与库仍带着它

### D-26 需求元数据同义字段重复出现（`sourceChannel`/`source_channel`、`appeals_dim`/`appealsDim`）

## 5. 列表、筛选与"找不到对象"

### D-30 列表每页上限 100，超限被截断
- **现象**：`pageSize` 上限 100；超过部分**被静默截断**，响应体带 `pageSizeCapped=true`（界面显示「共 N 条 · 第 x/y 页（最新在前）」）。
- **影响**：第 101 条起在单页里看不到，被读成"没有这条数据"。
- **用户该怎么做**：看分页控件与 `pageSizeCapped`；找具体对象用**编号检索或深链**（`?open=<id>`），不要靠"翻完第一页"下结论。
- **依据**：附录C 第 13 条（附录C:115-120）；17 章 C.1（17:208）；01 章 §3.3（01:236）。
- 源核对：上限唯一常量 `Paged.MAX_PAGE_SIZE`（=100；lookup 域 `LookupService.MAX_PAGE_SIZE`=50）；**超限不得静默截断**是产品规则 —— `docs/plm-tech/16-性能保障规格.md:43`、`:130`、`:88`。

### D-31 筛选条件按用户记住 → "空列表"多半是筛选，不是没数据也没权限
- **现象**：下次进同一页会**恢复上次筛选**；空态会写出当前生效作用域并给 `清空全部筛选` 按钮，且明确"**空列表 = 筛选结果为空，不是无权限**"。
- **影响**：最常见的误判——「系统里没有数据 / 我刚建的对象丢了」。
- **用户该怎么做**：先看工具栏 `共 N 个` 与筛选条件；点 `清空全部筛选` + 把左侧分类树切回根节点「全部」；物料库还要看顶部 `📂 当前产品` 作用域。
- **依据**：README「先读这三条」第 2 条（README:17）；01 章 §3.3 ⚠（01:237-241）；附录A Q2（附录A:49）；17 章 C.1（17:206）。

### D-32 新建对象停留在草稿态（`new-<时间戳>` 未落库）
- **现象**：点 `＋ 新建…` 后面板进入草稿态，编号显示 `● 新xx`，**id 是本地临时值 `new-<时间戳>`，尚未落库**；草稿态按钮是 **`创建`** 而非「保存」；此时点流转会被拒（"请先「创建」后再流转"）。
- **影响**：以为"新建后没保存"；草稿行的 `new-…` 不能被别处引用。
- **用户该怎么做**：填齐必填项后点 **`创建`**，看到正式编号（如 `REQ-2026-0005`）才算落库。
- **依据**：01 章 §3.2 ⚠（01:221-231）、§5（01:296）；附录A Q3（附录A:52）；17 章 C.1（17:207）。

### D-33 排序与列举结果不稳定 →「列表里没有」不等于「不存在」
- **现象**：历史实测出现过：`GET /requirements` 全量列举的计数与按状态查询**互相矛盾**；某条新建条目在所有列举查询中**命中 0 条**，而**按 id 直取正常**。
- **影响**：以列表作为"对象是否存在"的判据会得出错误结论；批量核对可能出现"少一条"的假象。
- **用户该怎么做**：**按编号/深链直取复核**（`?open=<id>` 或 `GET /api/v1/requirements/{id}`）；结论与列表不一致时**以直取为准**，并把这次列举异常按流程**记录上报**。
- **依据**：附录C 第 12 条（附录C:108-113）；17 章 C.1（17:210）。

## 7. 界面交互与"点了没反应"

### D-38 全站禁止弹窗确认：破坏性动作点了就发请求

### D-39 按钮是灰的 / 点了没反应：先分清四种原因
- **现象**：① 必填项未填（如未选项目 → 导出的 `preflight` 提示"请先选择项目再导出"）；② 无该动作角色；③ 状态不允许（状态锁定整表单）；④「保存」显示 `无改动` 且不可点。

### D-40 界面弹出 Java 异常原文（错误文案未归一化）
- **现象**：如 `Failed to convert value…`、`java.lang…` 原文直接显示在界面上（前端 `lib/apiError.ts` 有 RAW 正则专门拦截这类原文）。
- **影响**：用户以为是自己输入错，反复重试同一动作。
- **用户该怎么做**：**记录并上报**（页面 + 时间 + 原文 + 复现步骤）——**不是你的输入错**，也不必反复重试。

- 源核对：`common/GlobalExceptionHandler.java:200-203`（对外不提参数名与 Java 类型，前端 RAW 正则拦截"Failed to convert value"/"java.lang"）、`:228`（去掉 Java 类型尾巴）。

### D-41 不存在的路径**历史上**返回 400 `SERVER_ERROR`（"看起来像故障、其实路径不存在"）
- **现象（源核对）**：`GET /api/v1/items/dedup-check` 这个端点**根本不存在**，但单段路径被 `ItemController` 的 `@GetMapping("/{id}")` 捕获，`"dedup-check"` → Long 转换失败，落到兜底出口被渲染成 **400 SERVER_ERROR**。同类假信号实测还出现在 `/documents/dhf-scan`、`/documents/dhf`、`/documents/dhf-coverage`。修复后：**路径变量**绑定失败 → **404 `ENDPOINT_NOT_FOUND`**（"接口路径不存在，请核对接口文档后再调用；重复请求同一路径不会成功"）。
- **影响**：调用方把它读成"服务端故障、可重试"，于是**永远重试一个不可能成功的路径**。
- **用户该怎么做**：看到 400 `SERVER_ERROR` 时**先确认端点是否存在**（查接口文档/OpenAPI），不要盲目重试；确认路径不存在就改路径。
- **依据（源）**：`common/GlobalExceptionHandler.java:181-223`（`NoResourceFoundException` → 404 `NOT_FOUND`；`MethodArgumentTypeMismatchException` 路径变量 → 404 `ENDPOINT_NOT_FOUND`）、`:193-198`（query 参数错**仍保持** 400，是有意不收口）。

## 8. 业务对象层面的"有意不提供"与"仍保留的限制"

### D-47 风险台账没有删除入口（有意不提供）
- **现象**：`/risks` **没有删除按钮，后端也没有删除端点**（`RiskLedgerController` 只暴露 GET/POST/PUT/transition/pms-calibrate/from-rule）。
- **影响**：登记错的条目**不能删掉重来**；想找"删除"的人会反复确认"是不是权限不够"——**不是权限问题**（ISO 14971 口径：风险记录是审计对象，不留"抹掉"通道）。
- **用户该怎么做**：登记错的条目按状态机走「关闭（可接受性已确认）→ `CLOSED`」（`CLOSED` 前若验证状态不是 `VERIFIED` 或剩余风险不可接受，理由必填）；已 `CLOSED` 的条目若生产后信息触发再评估，用「PMS 校准」或 `CLOSED → OPEN` 重置。
- **补充**：**「关联产品/关联项目」可以随时改选**（新建与已有条目都能改，也支持清空）——"归属填错了"**不再需要**关闭后重建；改完系统会用改后产品的可接受准则阈值重算「剩余风险可接受性」并留痕。
- **依据**：附录C 第 22 条（附录C:181-187）；14 章 §3 状态机。

### D-48 CBB 治理属性补录（V141 起）——名称/类型**不走补录**
- **现象**：CBB 入册曾经只有"名称 + 类型"两栏且**没有补录路径**（详情面板全只读），治理属性**永远补不上**（实测库里那批：无物料形态 44/44、无诞生项目 44/44、无 Owner 团队 44/44、无 TRL 27、无年审到期 23）。V141 起详情面板提供**治理补录**（`PUT /api/v1/ipd/cbbs/{id}`，权限点 `cbb.update`），并在 `DEV → VERIFIED` 加了**齐备门**（交付载体 / 责任人 / TRL，缺项点名）。
- **仍成立的限制**：**改名称 / 类型不走补录**（400 `CBB_GOV_UNKNOWN_FIELD`）——资产身份是审计对象，要改走**升版**或新建；**已退役（`DECOM`）的 CBB 主档冻结**，不再能补录，要重新启用请**新建**。
- **用户该怎么做**：补齐漏掉的信息走详情面板补录（**不升版、不起草变更单**）；改内容走「升版（起草变更申请 ECR）」；键名拼错会报错（不会"点了没反应"）；载体用"编号 + 版本"填（`CBB_ITEM_REF_NOT_FOUND` / `CBB_DOC_REF_NOT_FOUND`）。
- **依据**：附录C 第 19 条（附录C:157-163）；15 章 §3 三表（15:67-80）。
- **另**：**年审到期本版是人工查口径**——系统**不自动扫描/推送到期提醒**，靠人在资产库列表里按效期看（15:146-147；附录B §10，附录B:206）。

### D-49 CBB 发布/退役不走「流转」按钮（要签署 + 闸门）
- **现象**：直接调 `transition` 到 `RELEASED`/`DECOM` 会 400 并指出正确入口；`→DECOM` 无论从 `DEV`（作废）还是 `MAINT`（退役）来都走**同一个** `POST /ipd/cbbs/{id}/decom`，端点按**当前状态分流**（两条边要的东西不同）。
- **影响**："以为发布了其实没签"。
- **用户该怎么做**：发布用 `发布并签署`（`cbb.release` + 电子签署）；退役用 `签署并退役`（`cbb.decom` + 废弃通告 ≥10 字 + **使用方逐行处置** + 签署）；`DEV` 作废不设闸门（只要作废说明）。
- **依据**：15 章 §3 页面动作表与退役闸门三问（15:126-141）。

### D-50 产品包 BR-22b 的"已发布"校验**只覆盖物料行**（产品行不校验状态）
- **现象**：上架的"引用对象须已发布"校验只作用于**物料行**（服务/耗材/配件/备件）；**产品行**引用的是产品主档（`PROD`），其**生命周期状态不在上架校验范围内**（只校验对象存在性）。
- **影响**：产品行的产品主档还停在"概念/设计"阶段，**上架不会被拦**，可能卖出未到可售状态的产品。
- **用户该怎么做**：上架前**人工确认产品行的产品主档状态**（到「产品结构」`/structure` 查该产品当前阶段）；不要依赖上架校验替你守这一条。
- **依据**：附录C 第 18 条（附录C:150-155）；12 章 §4。

### D-51 变更域：ECR/ECN **仍保留两项限制**（不要读成"已经能做"）
- **现象（已交付部分）**：`/changes` 已升级为**一页三对象**工作台（左栏切 ECR/ECO/ECN，各有列表 + 详情 + 动作区），支持深链 `/changes?obj=ECR&code=<编号>`。**此前** ECR 全仓只有 `POST`、**没有列表入口**，导致 CBB 升版自动起草的 **18 条 ECR 中 13 条停在 `OPEN` 且从未被处理**——"不是没人管，是界面上根本看不到"。
- **仍保留的限制（两项）**：
  1. **ECR / ECN 没有项目作用域与 ABAC**——只有**域级权限点**（`ecr.*` / `eco.*`），即"持该权限的角色可处理本组织内全部变更单据"，**没有**"申请人只能看自己项目"这类对象级过滤。（触发条件：出现真实跨产品线隔离诉求时再做。）
  2. **ECN 没有真实的对外发送通道**——本期**只做状态与回执留痕**（`targets` 落库、回执逐目标登记、收齐自动"已回执"），**不会真的**把通知投递到 ERP/MES/供应商门户/客服系统。
- **用户该怎么做**：CBB 升版后要找它起草的 ECR，**别去"变更单"里找**（那是 ECO）——去 `/changes` →「变更申请 ECR」，或在 CBB 版本历史里点那个**可点的 ECR 编号**；把 ECN 的"下发"与"回执"当作**组织内的登记事实**，线下通道另按组织流程走。
- **依据**：附录C 第 24 条（附录C:200-208）；07 章（07:142）；15 章 §3（15:142-145）。
- 源核对（深链形态）：`frontend/src/lib/routes.ts:33-36`（ECR/ECN 只能按**业务编号**深链 `?obj=&code=`，无 `/changes/{id}` 形态）、`:28-31`（`/changes/:ecoId` 是 ECO 专有）。

### D-52 存在"界面无入口、仅接口可达"的受控动作（**不是功能缺失**）
- **现象**：部分受控动作在前端**没有按钮**，只能经接口执行，例如：
  - 交付物基线**豁免**：`POST /api/v1/projects/{id}/deliverables/baseline/{baselineId}/waive`；
  - 管道治理动作：`POST /api/v1/pipeline/terminate`、`/pipeline/eol-plan`、`/pipeline/eol-execute`、`/pipeline/dispose`（终止与退市类）。
- **影响**：界面上找不到入口，容易误判为"功能不存在"；实际能力存在但**必须走受控流程**（这些动作会改变治理状态，**有意**不做成顺手一点的按钮）。
- **用户该怎么做**：确需执行时由**有权角色**按流程经接口办理，并在评审/变更记录中留依据；**不要**为了"绕开界面缺失"改用其他路径。需要界面入口请按组织流程**登记需求**。
- **依据**：附录C 第 20 条（附录C:165-172）；15 章 §1（15:24）；07 章（07:144）。

### D-53 变更五维签署：`pdt_manager` 不在任何一维；无持角色账号 = 配置问题
- **现象**：五维（技术/设计、注册法规、风险、V&V 验证、制造/市场）**按维度绑角色**，`pdt_manager` **不在任何一维里**（有意收紧：PDT 经理通常就是编制人）；历史上 `mfg` 维发生过"可签账号=0 人"。
- **影响**：PDT 经理点"签署"被 403，误以为权限坏了；无账号则该维卡死。
- **用户该怎么做**：PDT 经理负责推进与决议，**签署交对应责任角色**；无账号是**配置问题**（找实施/管理员补角色），**不要自评硬签**。
- **依据**：附录A Q14（附录A:87）；07 章（07:87）；17 章 A.6 与 A.7（17:78、17:88）。

### D-54 变更域 ECR/ECO **没有边级角色门**（只有域级权限点）
- **现象**：`ECR` 与 `ECO` 两条流程**没有边级角色门**，只判域级权限点；"谁能取消/否决"靠**域级角色**。
- **影响**："取消/否决"按钮谁都能看到，实际能不能做取决于域级角色；有人当成状态机没写清或把 403 当缺陷。
- **用户该怎么做**：用 10 章 §6 三步自查 `/_platform/permission/rules` 里 `ecr.*` / `eco.*` / `eco.ccb` 的角色面。
- **依据**：07 章（07:162）。

## 9. 审计与签署纪律（客服必须守住的红线）

### D-55 受控发布自动作废旧版**不单独写 `document.transition` 审计**
- **现象**：文档受控发布会生成受控版并把**旧版自动作废（`OBSOLETE`）**——这条自动作废**不会单独写一条 `document.transition` 审计**。
- **影响**：只查流转审计看不到"旧版为什么被作废"，误以为被人手改。
- **用户该怎么做**：审计口径以**文档详情「处理记录」整体**为准，不要只看某条边审计。
- **依据**：附录A Q9（附录A:70）；附录C 第 12 条邻域（附录C:112 的"以直取为准"同族纪律）；08 章 §6（08:100）。

### D-56 治理台：决策权限矩阵**只读**；委托签署 7 天且**不转移责任**
- **现象**：治理台的「决策权限矩阵」是**只读**的（如 `DCP APPROVED ["ipmt_chair","admin"] false`）；**期限默认 7 天**，到期自动失效，**不是长期授权**；委托签署是**签署权的临时转移**，**不转移**被委托人对结论的责任归属（签名记录仍体现实际签署人与委托关系）。
- **影响**：矩阵里没有你要的角色 ⇒ **页面上无解**；误以为是长期授权；以为委托出去自己就不担责了。
- **用户该怎么做**：角色调整走 [10 章]「系统设置 → 组织角色/项目角色」；授权裁决前先在矩阵里查该决策的允许角色；**审计只看"实际签署人 + 委托关系"**。
- **依据**：15 章 §4 ⚠（15:178-182）；15 章 §7（15:224）；17 章 A.3（17:46）。

### D-57 代理授权的三条红线（不得代理）
- **现象（源/设计核对）**：代理**自己**（`delegator == delegatee`）被拒 400；代理范围**超出**被代理人现有权限被拒；**用代理路径修改代理关系本身**（自举提权）是红线；同一（被代理人, scope, 时间窗）**不重复**代理给多人（防"多代理同事代签"）。
- **影响**：把委托签署误用作"提权通道"或"代签捷径"。
- **用户该怎么做**：代理只用于**临时、限范围、不越权**的签署转移；不得用于替代他人作出实质决策。
- **依据**：`docs/plm-tech/21-治理台与权限治理设计.md:86`、`:228`、`:230`、`:249`（源/设计口径；界面表现需现场验证）。

### D-58 严禁代签/代判定/代作业；AI 只出初稿
- **现象**：这是贯穿全部域的最高纪律之一——**AI 不得代签、代判定、代作业**，签署与判定必须由**人在系统内**完成；AI 记录只能是草稿。
- **影响**：任何"帮我把结论签掉/帮他提交一下"的请求都不合规。
- **用户该怎么做**：客服/实施都**不得**代用户签署、判定或提交；只能指导用户本人操作。**不得**为开门把未来阶段交付物提前置 `APPROVED`（最常被误用的"绕过"）。
- **依据**：`plm-review-rules.md` **S-22**（plm-review-rules.md:217）、**F-23**；`requirements-taxonomy.md` 稳定偏好第 8 条（requirements-taxonomy.md:101）、§七安全段（requirements-taxonomy.md:135）；03 章 §6.4（03:210-211）。
- 源核对（治理侧）：`docs/plm-tech/21-治理台与权限治理设计.md:86/228/230/249`。

### D-59 审计链是 append-only hash 链，写路径串行化
- **现象（设计/规则口径）**：受控动作（文档创建/批准/发布、交付物状态变更、签署/作废/重签、权限变更）**一律写入审计链**；审计 **append-only（hash 链）**，`verify()` 可检出篡改，应用层只增不改（WORM）；写路径**串行化**避免并发写破坏不变量。
- **影响**：任何"手工改库让它对上"的做法都会被 `verify()` 检出，且**不可修复**。
- **用户该怎么做**：发现数据不对 → **登记需求**，不要直接改库/主数据；受控订正走"**追加订正记录**（含原值快照 + 必填理由）"，被订正条目**一个字节都不写**。
- **依据**：`plm-review-rules.md` **S-17**、**S-18**、**S-19**（plm-review-rules.md:212-214）；附录A 术语「受控订正」（附录A:109）；README §5（README:128）。

## 10. 是不是产品缺陷？——客服分诊判据

| 用户描述 | 判定 | 动作 |
|---|---|---|
| 命中本文任一条**「现象」** | **已知偏差 / 有意的限制** | 按该条「用户该怎么做」答复；**不登记缺陷**（若是"已修复仍复现"，如 D-43/D-45，则**登记缺陷**） |
| 界面文案与手册不一致，且本文未登记 | **手册/实现漂移** | 按统计纪律 1：**不要教用户忽略**；以**运行态 + 需求库**为准，并引导**登记需求**（附录C:218-219） |
| 报错码为 `400 <中文message>`，且 message 说明了缺什么 | **业务前置不满足**（不是缺陷） | 按 message 补齐（§D-27~D-29 是高频三种） |
| 报错码为 `403` 且文案带权限点与当前角色 | **角色面问题**（不是缺陷） | 按 §D-06/§D-07 分路自查；**不要重试** |
| 报错码为 `403 无权操作该对象（超出授权范围…）` | **对象级 ABAC 拒绝**（不是角色问题） | 查对象归属项目/属主（§D-07） |
| 界面弹出 **Java 异常原文** | **平台缺陷**（错误文案未归一化） | 记录并上报（§D-40） |
| 端点返回 **400 `SERVER_ERROR`** 但路径本身不存在 | **已经不再是缺陷**（修复后为 404 `ENDPOINT_NOT_FOUND`） | 核对端点；不要重试（§D-41） |
| 按钮点了没反应 / 界面找不到入口 | 先查 §D-42（导出/导入未挂动作）、§D-52（有意无入口） | 都不是缺陷；需要入口则**登记需求** |
| 数据不对但系统"看起来正常" | **绝不手改数据** | 登记需求 + 用本文给出的替代路径（§0 纪律 2） |

**登记需求的模板（照附录C 的反馈格式）**：`页面/路由` + `时间` + `界面文案（原文）` + `期望行为` + `复现步骤`（含账号角色、对象编号、操作序列）；截屏或复制报文原文最有用。标题注明【问题】/【建议】，来源按性质、优先级按影响，**先查重**。
**依据**：附录C「反馈与登记」§1-2（附录C:215-217）；附录A Q15（附录A:90）。
