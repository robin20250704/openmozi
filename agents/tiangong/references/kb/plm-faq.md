## A. 登录 / SSO / 会话（4 条）

### Q:1 我打开系统没有「进入（dev）」按钮，是不是登录功能坏了？
- **答复**：不是坏了。**运行态只允许统一身份认证（SSO）登录**，dev 身份入口已停用（容器注入的 `GET /plm-config.js` 返回 `{"devLogin": false}`）。**打开系统就直接是用户名/密码登录页，不需要点任何按钮**——未登录访问首页或任意深链都会**自动跳转**；只有在自动跳转没完成时才会停在**兜底登录页**（页面写明原因并给可点的 `登录（SSO）` 按钮）。**未带 Bearer 凭据的 API 请求一律 401，这是预期行为**。
- **权威依据**：附录C 第 1 条（`附录C-已知偏差与限制.md:9-14`）；01 章 §1（`01-快速入门.md:9-32`）；附录A Q1（`附录A-快捷键与FAQ.md:45-46`）；17 章 C.4（`17-角色工作闭环与排障.md:249`）。
- **依据等级**：**已核实**（手册实测 + 源码/容器配置口径）。
- **追问项**：① 完整 URL（含协议/端口）；② 页面上是否出现 `登录（SSO）` 按钮或"已暂停自动跳转以免反复来回"；③ 是否提示"无法连接统一身份认证"（若是 → 凭据服务不可达，找管理员）。**注意**：若客户是 UAT，证书为自签，浏览器会提示"不安全"，需按验收流程确认例外。

### Q:2 我登录后刷新页面 / 新开标签页，会不会掉回登录页？
- **答复**：**不会**。刷新或新开标签页会直接回到系统——登录会话存在浏览器里，登录过程带回的**一次性参数会被立刻从地址栏清掉**，不会因为"刷新"被重放。若**确实**看到兜底登录页，页面上会写明原因：连续自动跳转失败时显示「已暂停自动跳转以免反复来回」，此时**点一次 `登录（SSO）` 即可**（自动跳转停了，手动入口不会停）。
- **权威依据**：附录A Q16（`附录A-快捷键与FAQ.md:92-94`）。
- **依据等级**：**已核实**。
- **追问项**：① 是"停在登录页"还是"点完后又跳回来（循环）"（后者按缺陷登记）；② 是否提示"无法连接统一身份认证"；③ 浏览器/是否开了隐私模式或清了 Cookie。

### Q:3 新账号明明是管理员建好的，为什么登录被拒（`Account is not fully set up`）？
- **答复**：建号时**四项必须齐备**——**登录名（≥3 位，只允许字母/数字/`._-`）、邮箱、名、姓**；**缺任一项的账号即使建出来也登录不了**（凭据服务要求）。请管理员在**系统设置 → 用户管理**里补齐缺失的身份字段后再登录。**先补齐再让人登录，不要去怀疑登录功能。** 另外初始口令是**一次性临时口令**、**首次登录强制改密**；用户自己改密码走**顶栏头像 →「我的信息」抽屉 → 改密码**。
- **权威依据**：10 章 §5 ⚠（`10-系统设置与权限.md:79`）；17 章 A.12 与 C.4（`17:140`、`17:250`）；README 账号节（`README.md:42`）；01 章 §1（`01:38-40`）。
- **依据等级**：**已核实**。
- **追问项**：① 报错原文是否为 `Account is not fully set up`；② 该账号的**邮箱/名/姓**是否都填了（用户管理列表有「身份齐备」列）；③ 登录名是否 ≥3 位且只含字母/数字/`._-`；④ 是首次登录还是改过密码（首登强制改密）。

### Q:4 页面能打开但数据全是空的，接口报 401，是不是系统坏了？
- **答复**：多为**未登录或 SSO 会话过期**。**刷新页面**（会自动进统一认证页登录）即可。**未带 Bearer 凭据的 API 请求一律 401 是预期行为**。若客户用脚本/工具直连：**UAT 禁止"密码授权"取 token**（报 `unauthorized_client`），UAT 验收**只走浏览器登录**；需要批量核对时从**已登录会话**取凭据，不要用账号口令直连。
- **权威依据**：01 章 §1 浏览器/网络注意表（`01:46-49`）、§5 症状表（`01:293`）；附录C 第 2 条（`附录C:16-21`）；README 环境差异表 ⚠（`README.md:35-38`）；附录A Q7（`附录A:64`）。
- **依据等级**：**已核实**。
- **追问项**：① 哪个环境（dev `http://localhost:5174/` / UAT `https://120.25.103.162:8722/`）；② 是浏览器里操作还是脚本直连（脚本直连在 UAT 必然失败，属已知）；③ 401 出现在哪个请求路径。

## B. 权限与"看不到按钮"（4 条）

### Q:5 为什么我看不到 / 点不动某个按钮，一点就报 403？
- **答复**：多数是**角色面**问题，**不是系统坏了**。按三步自查（照做即可）：
  1. `GET /api/v1/_platform/permission/me` → 看**我的组织角色**；
  2. `GET /api/v1/_platform/permission/rules` → 看**每个权限点允许的角色集**（⚠ 该端点受 `_admin.read` 保护，**非管理员会 403** ⇒ 走**治理台**看决策权限矩阵，或请管理员/PMO **代查**；**不要重试**）；
  3. `GET /api/v1/projects/{id}/members` → 看**我在这个项目里的项目角色**。
  记住两条口径：**① 读不鉴权**（`GET` 列表与详情全员可见，只有**写/流转/判定/签署**才判权限）⇒ "看不到数据"基本**不是**权限问题，而是**筛选或分页**问题（见 Q:25）；**② 有效角色 = 组织角色 ∪ 该项目成员角色**，在 A 项目有 `prj_dev` 不代表在 B 项目有。
- **权威依据**：10 章 §6 三步（`10:85-94`）；17 章 §B（`17:147-186`）、§3.1（`17:188-196`）；附录A Q14（`附录A:86-87`）；附录C 第 3 条邻域（`附录C:218`）。
- **依据等级**：**已核实**（含"`permission/rules` 受 `_admin.read` 保护"这条 ⚠，见 `17:174-177`）。
- **追问项**：① 403 的**完整文案**（关键：是否带"权限点：`domain.action`；当前角色：…"）；② 操作对象**编号**与**它属于哪个项目**；③ 用户 login；④ 是"按钮不渲染"还是"点了才报错"（后者可能是**未做逐按钮权限裁剪**，如计划任务页，见 `TasksPage.tsx:14-16`）。

### Q:6 同样是 403，为什么有的让我去申请角色，有的说"超出授权范围"？
- **答复**：这是**两类完全不同的 403，排查点不同**：
  | 文案形态 | 含义 | 去看哪里 |
  |---|---|---|
  | `无权限执行 <domain>.<action>（权限点：… 当前角色：…）` | **权限点不足**（你没有那个角色） | **角色配置**：`permission/me` + `permission/rules` + 治理台矩阵 + 管理员 |
  | `无权操作该对象（超出授权范围: <domain>.<action>）` | **对象级 ABAC 拒绝**（不是缺角色） | **对象归属**：这个对象属于哪个项目/产品/属主 |
  **把对象级 403 当角色问题，会让你去申请一个本来就已经有的角色。** 另外判权限有固定顺序：**RBAC（功能权限点）→ ABAC（对象实例属性）→ 流程边角色门**，任一层不过都会拒。
- **权威依据**：17 章 §3.1 表（`17:188-196`）；10 章 §6（`10:94`）。
- **依据等级**：**已核实**。
- **追问项**：① 403 文案**原文**（区分的唯一依据）；② 对象编号 + 所属项目/产品；③ 用户 login。

### Q:7 ACL"我没配规则"，是不是就等于全放行？
- **答复**：**不是。** ABAC 规则集是"**按用户的全部角色取并集**"求值，判定口径是"**一条 allow 规则都没有 ⇒ 放行；有 allow 但全未命中 ⇒ 拒**"。所以想表达"某角色**不受限**"，**不能靠"不配规则"**——该用户一旦同时持有别人的受限规则，就会被**静默误拒**（日志里是 `ABAC_LEAST_PRIVILEGE` 告警，界面上只看到 403）。**要放行就显式配 `always`**（属性算子选 `always`，语义 = 该规则恒命中、不受对象属性约束）。注意 `always` **不是放宽 RBAC**：RBAC 不过时根本走不到 ABAC。另外 **`deny` 短路且优先**；ACL 影响**全系统对象可见性**，改动要谨慎。
- **权威依据**：10 章 §4 ⚠（`10:52-58`）、§9（`10:121`）；附录A 术语「ABAC / ACL」（`附录A:119`）；17 章 §B 注（`17:139`）。
- **依据等级**：**已核实**（手册标注为"治理要点，必须写"的 ⚠）。
- **追问项**：① 是"某用户莫名 403"还是"配置后仍被拒"；② 该用户**同时持有哪些角色**；③ 目标对象类型与 action；④ 是否已有同对象的 allow 规则（可用管理员看 `get` 日志里的 `ABAC_LEAST_PRIVILEGE`）。

### Q:8 我新建的角色，为什么流程还是跑不动 / 还是提示没人能签？
- **答复**：**第一查证点**是 **系统设置 → 「角色 ↔ 流程匹配检查」卡**。橙字 `⚠ M 个流程引用角色未定义：…` 就说明流程需要的角色**在系统里还没定义**（或**编码写错/被改**），按它给的指引**建角色、并用与流程边一致的 `code`**，问题就解决了。**关键纪律**：**禁止"名称推导编码"**——**先想好英文编码**（如 `pdt_mfg`）**再填中文名**；**编码一旦被流程引用就不要改**。另外：某个角色若显示 `未被任何流程边引用（可用于数据权限/功能角色映射）`，**这不是报错**，说明它只用于数据权限/功能角色映射。
- **权威依据**：10 章 §3 ⚠（`10:39-48`）、§2 ⚠（`10:32`）、§9（`10:120`）；17 章 A.11（`17:126`）、§B 第 2 步注（`17:177`）。
- **依据等级**：**已核实**。
- **追问项**：① 该卡是绿字还是橙字（**这是定性的唯一依据**）；② 报"缺角色/候选池为空"是在**哪条流程的哪个动作**；③ 角色 `code` 是英文还是中文（中文 code 是历史缺陷症状）；④ 是"流程跑不动"还是"门开不了"（**这两条是不同路径**：门线阻断看 03 章预检的 BLOCKING 项，候选池空看本卡，见 `附录A:76-78`）。

## C. 需求管理（9 条）

### Q:9 我要提一条需求，怎么建？
- **答复**：**需求管理** `/requirements` → 右上「**＋ 新建需求**」→ 右侧面板进入**草稿态**（编号显示 `● 新需求`，**此时 id 是本地临时值 `new-<时间戳>，尚未落库**）→ 填写字段（**标题等必填项填了按钮才启用**）→ 点 **`创建`**（**草稿态的按钮是「创建」，不是「保存」**）→ 成功提示 `已创建 REQ-2026-xxxx`，新需求进入**提案（`PROPOSED`）**状态。也可用 `保存&新建` 连续建。
- **权威依据**：02 章 §2（`02-需求管理.md:26-33`）；01 章 §3.2（`01:219-231`）；附录A A.2（`附录A:32`）、Q3（`附录A:52`）。
- **依据等级**：**已核实**。
- **追问项**：① 是否**已点过 `创建`**、是否看到正式编号 `REQ-2026-xxxx`（**看到 `new-…` 就说明还没落库**）；② 是否在草稿态点过流转（会被提示"请先「创建」后再流转"）；③ 报错文案（若必填项缺失会有提示）。

### Q:10 需求谁能批准？我点了批准但报错。
- **答复**：**边级角色门**如下（这是权限侧答案）：
  | 动作 | 允许角色 | 前置/约束 |
  |---|---|---|
  | 分析 | `requirement_analyst` / `pdt_manager` / `admin` | — |
  | **批准** | **`product_manager` / `admin`** | **必须已指定所属项目**，否则 `400 PROJECT_REQUIRED`；**批准即写电子签名** |
  | 方案制定 | `prj_sa` / `pdt_manager` / `admin` | — |
  | 确定方案 | `prj_sa` / `prj_dev` / `admin` | **须先填「方案内容」** |
  | 测试 | `prj_qa` / `admin` | — |
  | 验收 | `requirement_analyst` / `admin` | — |
  | 关闭 | `requirement_analyst` / `pdt_manager` / `admin` | — |
  **需求分析员不能批准**（批准要 `product_manager`）。
- **权威依据**：02 章 §5 边级角色门表（`02:114-126`）、§8 本角色要点（`02:199-208`）。
- **依据等级**：**已核实**。
- **追问项**：① 报的是 **403 还是 400**（403 = 角色问题；400 = 业务前置问题）；② 该用户 login 与实际持有的角色（按 Q:5 三步查）；③ 若报 `PROJECT_REQUIRED` → 见 Q:11。

### Q:11 点"批准"报 `PROJECT_REQUIRED`，什么意思？
- **答复**：**需求批准前必须先指定「所属项目」**——这是系统硬前置：未指定项目时批准会报 `400 PROJECT_REQUIRED`。**做法**：在需求详情面板把「**所属项目**」选上（用**检索选择面板**，点回显按钮选，**不要手输对象 ID**），再走 `ANALYZED → APPROVED`。批准**即写电子签名**。
- **权威依据**：17 章 C.2（`17:217`）；02 章 §3 字段表（`02:70`）、§5（`02:119`）、§7 典型场景（`02:184`）；端点 `POST /requirements/{id}/transition`。源码：`RequirementService.java:683`（抛出 `PROJECT_REQUIRED`）。
- **依据等级**：**已核实**（文档 + 源码双方一致）。
- **追问项**：① 报错码是否确为 `PROJECT_REQUIRED`；② 「所属项目」字段是否为空；③ 用户是该需求的分析员还是产品经理（角色对：批准只需 `product_manager`）。

### Q:12 填了量化参数值，为什么推不动（报 `VERIFICATION_REQUIRED`）？
- **答复**：**填了量化参数值 ⇒ 必须同时填「验证方法」与「验收准则」**（否则报 `400 VERIFICATION_REQUIRED`）。**三项成组填写**：量化参数名 + 量化参数值 + 参数单位（`paramUom` 一并给）+ **验证方法**（`TEST` / `ANALYSIS` / `INSPECTION` / `DEMO`，FDA 四类）+ **验收准则**（如何判定满足，可测量）。
- **权威依据**：17 章 C.2（`17:218`）；02 章 §3 字段表（`02:59-63`）；附录B §1（`附录B:20-23`、`附录B:28`）；02 章 §7 验收前自查（`02:190`）。源码：`RequirementService.java:1139`、`:1141`（分别对 `verifyMethod` 与 `verification` 抛 `VERIFICATION_REQUIRED`）。
- **依据等级**：**已核实**（文档 + 源码双方一致）。
- **追问项**：① 报错原文（确认是"验证方法"还是"验收准则"缺）；② 量化参数值/单位是否已填；③ 是否只想登记一条非量化需求（那就**不要填参数值**，三件套是成组触发）。

### Q:13 "确定方案"为什么点不动（报 `FIELD_REQUIRED`）？
- **答复**：推进前置字段缺失。典型：**「确定方案」（`SOLUTION_DEFINING → IMPLEMENTED`）前必须填「方案内容」**（`requires: solution`），否则报 `400 FIELD_REQUIRED`。**做法**：在详情面板填「方案内容」（JSONB，模板由元数据下发；**仅方案制定中可改**）后重试。**通用口径**：任何"能点但点了报 400"的情况，**先看返回的 message——系统会在消息里说明缺什么字段/缺哪个角色**。
- **权威依据**：17 章 C.2（`17:219`）；02 章 §3（`02:67`）、§5 边级角色门（`02:121`）；01 章 §4 通用（`01:285`）。源码：`RequirementService.java:728`。
- **依据等级**：**已核实**。
- **追问项**：① message 里点名的字段名；② 需求当前状态（是否确在 `SOLUTION_DEFINING`）；③ 用户角色（该边允许 `prj_sa`/`prj_dev`/`admin`）。

### Q:14 这条需求为什么改不了？字段都是灰的。

### Q:23 成本到底该录哪个字段？为什么成本对比老是"超差"？

## E. 门线与评审（5 条）

### Q:24 门为什么开不了？预检显示一堆红的。
- **答复**：**先分清"红"是不是阻断。** 门线唯一判据是 `GET /api/v1/reviews/precheck?projectId=<id>&gateCode=<门码>`，读法四条：
  1. **`severity` 分 `BLOCKING`（阻断）与 `ADVISORY`（只报出、不阻断）**——**`passed:false` 不等于门被断**，**只有 `BLOCKING` 的失败项**才决定能不能发起/推进；
  2. `DELIVERABLES.items[]` 是**本项目交付物清单快照（含全部阶段）**，**只有 `blocking=true` 的行才计入本门判定**；
  3. **`passed=true` 可能是"空通过 / N/A 未评估"**——`detail` 会自述（如" N/A 未评估"、"空集自述"、"未配置：差集恒为空"）⇒ **绿 ≠ 已核查**；
  4. **不要只看按钮亮不亮**——发起评审按钮的启用以后端预检为准，而 `flow-overview.canRequest` **曾与预检不同源**（会出现按钮亮着但一点就 400）。
  **口径**：**发起前先跑一次 precheck，读它的 `passed` 与 `BLOCKING` 失败项；把按钮状态当参考，不当依据。**
- **权威依据**：03 章 §5.1（`03:121-137`）；附录C 第 8 条（`附录C:65-70`）；17 章 C.3（`17:231-233`）；16 章 §2.2（`16:63-66`）。源码：`PrecheckService.java:1911`（`PRECHECK_BLOCKED`，消息含失败项明细）。
- **依据等级**：**已核实**。
- **追问项**：① 项目 id 与**门码**（如 `DCP1`/`TR3`）；② 预检报文中 `passed`、各项 `severity` 与 `detail`；③ 失败项 **code**（如 `DELIVERABLES`、`OPEN_ISSUES`、`RTM`、`DELIVERABLE_EVIDENCE`）；④ 是否已跑过 precheck（**没跑过不要凭界面颜色判**）。

### Q:25 卡片上说"尚未 GO/GO_WITH_RISK，阶段不可推进"，材料我都齐了啊？

### Q:26 评审签完发现自己写错了，能改吗？那个"否决"按钮还有吗？

### Q:27 我在任务书上，为什么项目没有自动建出来？

### Q:28 交付物要怎么登记？为什么一条老交付物让门死活开不了？
- **答复**：**登记两条硬契约**：① **名称必须带 `[阶段]` 前缀**（如 `[立项] 任务书Charter`；`[立项]`/`【立项】`/`（立项）`/`(立项)` 均可，也支持 `[概念]`/`[计划]` 等）**或显式传 `stage` 字段**——**两者都没有 ⇒ 登记直接 400 拒绝**；**建议两者都写**便于人工核对。② **证据锚定尽量一次性带全**（`objType` + `objId`）：支持多对象（逗号分隔，如 `REQ-2026-0413,REQ-2026-0414`）、支持版本写法（`编号:版本`，如 `DOC-2026-0212:1`、`M-2026-0190:A`）、**不支持区间写法**（`A ~ B` 会被**静默截为首尾**，**要逐个列出**）。
  **老交付物卡门的原因**：**V97 之前登记的历史条目**可能**既没有 `stage` 字段、名称也没有前缀**（`STAGE_UNSET`），这类条目**仍会被每一道门都纳入检查**（阶段过滤对它无效）⇒ **长期阻断**（实测：一条无前缀条目让 **DCP0 与 TR1 双双 `passed=false`**），而失败项看起来与本次工作无关。**做法**：登账时一律写 `[阶段] 名称`；接手老项目**先扫一遍交付物名称是否都带前缀**；门被阻断时看预检 `DELIVERABLES.items[]` 里的 `stage` 与 `reason`（`STAGE_UNSET` 即此类）。
  **状态与纪律**：交付物状态**只有 `PENDING`/`SUBMITTED`/`APPROVED` 三值**（其他值报 400）；`APPROVED` 后锁定；**批准/驳回未关联受控对象时理由必填**（`EVIDENCE_REQUIRED`）。**门线取数的正确姿势：只对 `[本阶段]` 的必交项负责**——**不要**为了让门变绿把**未来阶段**的交付物提前置 `APPROVED`（会污染证据链，也是**最常被误用的"绕过"**）。
- **权威依据**：03 章 §6.2 硬契约 ⚠（`03:187-193`）、§6.3 表（`03:195-206`）、§6.1 ⚠（`03:175-185`）、§6.4（`03:208-211`）；附录C 第 6 条（`附录C:51-56`）；17 章 A.1 硬约束（`17:25`）、C.2（`17:220`）。源码：`DeliverableController.java:460`（`EVIDENCE_REQUIRED`）、`DeliverableEvidenceService.java:134`（`EVIDENCE_UNRESOLVED`）。
- **依据等级**：**已核实**。
- **追问项**：① 项目 id 与门码；② 预检 `DELIVERABLES.items[]` 中失败行的 **`stage`、`reason`**（是否 `STAGE_UNSET`）；③ 该交付物**名称原文**（有无 `[阶段]` 前缀）；④ 证据锚定的 `objType`/`objId` 写法（是否用了区间 `~`、是否锚了 `RVW`）；⑤ 用户是否把未来阶段交付物提前置了 `APPROVED`。

### Q:29 我想把交付物证据指向这条评审记录（RVW），为什么一直报错？

## F. 列表 / 数据可见性（3 条）

### Q:30 列表是空的，是不是没数据 / 我没权限？
- **答复**：**八成是筛选条件在起作用，不是没数据、也不是没权限。** **筛选条件按用户记住**（下次进同一页面会**恢复上次的条件**）。**做法**：① 看工具栏 `共 N 个对象 · 第 x/y 页（最新在前）` 与当前筛选条件；② 点空态里的 **`清空全部筛选`**；③ 把左侧**分类树切回根节点「全部」**；④ 物料库还要看顶部 `📂 当前产品` 作用域（标题出现 `· 结构内物料` 时看到的**不是全部物料**）；⑤ 需求页还要注意「处理人」筛选。**空态已写明：空列表 = 筛选结果为空，不是无权限。** 另外两个常见原因：**每页上限 100**（超限被截断，响应带 `pageSizeCapped=true`）；**新建对象落在"最新在前"的第 1 页却仍被筛选挡住** ⇒ 用**编号检索或深链 `?open=<id>`** 直达。
- **权威依据**：README「先读这三条」第 2 条（`README.md:17`）；01 章 §3.3 ⚠（`01:233-241`）、§5（`01:295-296`）；附录A Q2（`附录A:49`）、Q4（`附录A:55`）；附录C 第 13 条（`附录C:115-120`）；17 章 C.1（`17:206-208`）；附录B §（分页上限）。
- **依据等级**：**已核实**。
- **追问项**：① 用户在**哪个页面**；② 工具栏的 `共 N 个` 与筛选条件截图/原文；③ 是否有左侧分类树/产品作用域（物料库）；④ 是"列表为空"还是"少数几条不见"（后者看分页与筛选）；⑤ 目标对象**编号**（可直接用 `?open=` 复核）。

### Q:31 我刚建的对象，列表里就是没有——是不是丢数据了？
- **答复**：先按序排查 **4 个原因**：① **还在草稿态**（没点 `创建`——草稿行编号显示 `● 新xx`、id 是本地临时值 **`new-<时间戳>`、尚未落库**）；② **每页上限 100 条**、列表**最新在前**——对象已落到第 1 页但**被筛选挡住**；③ **状态被默认过滤**（例如**产品作废后默认列表会过滤掉**；任务书**默认排除已作废**）；④ 历史实测出现过**列举结果内部矛盾**（全量列举计数与按状态查询互相矛盾、某条新建条目在所有列举查询中命中 0 条而**按 id 直取正常**）。
  **做法**：清筛选 + 切回树根「全部」+ 翻页看；**"列表里没有"不等于"不存在"——按编号/深链直取复核**（`?open=<id>` 或 `GET /api/v1/requirements/{id}`）；**结论与列表不一致时以直取为准**，并把这次列举异常**记录上报**。
- **权威依据**：01 章 §5（`01:296`）；附录A Q3（`附录A:52`）、Q4（`附录A:55`）；附录C 第 12 条（`附录C:108-113`）；17 章 C.1（`17:207-210`）。
- **依据等级**：**已核实**（含"列举结果不稳定"这条实测记录）。
- **追问项**：① 对象**编号**（有编号就能直取复核）；② 是否点过 `创建`、是否提示过 `已创建 XXX-2026-xxxx`；③ 当前筛选条件与页码；④ 是**只在这一页看不到**还是**按编号直取也 404**（后者才是真问题，按缺陷登记）。

### Q:32 表格数据量大了就卡，而且一页只给我 100 条，导出也受这个限制吗？
- **答复**：**分页与导出是两个口径**：
  - **分页**：`page`（0 起）+ `pageSize`，**默认 100、上限 100**；**超限不静默截断**——回显 `pageSizeCapped=true`（lookup 选择器域上限是 **50**）。上限的**唯一事实源**是后端常量 `Paged.MAX_PAGE_SIZE`。**前端不得用"预加载一页当全量 + 本地过滤"绕过**；对象选择一律用检索选择面板（`SearchPick`）。
  - **导出**：**导出 = 当前筛选命中的全部行，不受列表分页上限约束**（且会回显"最近导出"文件名，导出面板会逐条回显生效筛选）。
  - **批量操作上限（服务端校验，超限 400，不得静默截断）**：需求批量状态推进 **≤200 条/次**；列表批量选择/批量粘贴 **≤500 行/次**；CSV 导入 **≤2000 行/次**；批量下载 **≤50 个对象/次**（文档中心单包默认 **200 份**上限）。
  - **性能保障**：列定义与虚拟滚动、预加载反模式禁令是既有规格项；已实测优化过读放大的端点（如 `/reviews?pageSize=20` 从 **564ms/读 34.8 万行** 降到 **32ms/2.2k 行**；`/items?pageSize=50` 从 **138.7k 行/次** 降到 **16ms/4.5k 行**）。数据增长三档触发线：物料/需求/文档任一表 **> 20 万行**、被直接查询的表 **> 500 万行**、审计/事件表 **> 3000 万行**。
- **权威依据**：`docs\plm-tech\16-性能保障规格.md:43`（分页口径与常量）、`:130`（唯一事实源）、`:88`（S-2 分页契约）、`:95`（S-9 禁用预加载反模式）、`:99`（S-13 三档触发线）、`:101`（S-15 前端包体预算）、`:141`（G-5 批量上限表）、`:247-252`（批次27 实测基线）；附录C 第 13 条（`附录C:115-120`）；任务书/需求/计划任务页导出通道口径：`TasksPage.tsx:840`、`:856`、`:863`、`:938`。
- **依据等级**：**已核实**（规格文档 + 实测基线）。⚠ **但**：`pageSizeCapped` 的"静默截断"表述在附录C 与规格文档口径略有差异（附录C 第 13 条写"被**静默**截断（响应体带 `pageSizeCapped=true`）"，规格要求"**不静默截断**、须回显"）——**对客户统一答复：响应会带 `pageSizeCapped=true`，请以分页控件与编号检索为准**；如需以"静默截断"定性为缺陷，先按 Q:31 追问项确认环境版本。
- **追问项**：① 哪个列表（物料/需求/文档/评审/计划任务）；② 是"慢"还是"条数不对"；③ 慢的**具体操作**（首屏/翻页/筛选/导出/打开详情）与**大概耗时的量级**；④ 是否有浏览器控制台错误或请求耗时（客户端表现可能与后端读放大无关）；⑤ 是否用了"翻页替代检索"（先教用检索）。

## G. 快捷键 / 界面交互（2 条）

### Q:33 有没有快捷键？保存、上一条下一条怎么按？
- **答复**：（与 01 章 §3.5 一致）
  | 键 | 场景 | 作用 |
  |---|---|---|
  | `Tab` / `Shift+Tab` | 全局 | 在可聚焦元素间移动 |
  | `Enter` | 网格 | 进入单元格编辑；编辑后确认 |
  | `Enter` | 按钮 / 树节点 | 激活 |
  | `Enter` | 搜索框 | **立即触发搜索**（检索面板内为立即检索） |
  | `Esc` | 编辑中 | 取消编辑、恢复原值 |
  | `Esc` | 详情面板（有改动） | **放弃修改**（回到进入时的快照） |
  | `Esc` | 全屏 / 弹层 | 退出全屏 / 关闭检索面板 |
  | `Ctrl+S` / `Ctrl+Enter` | 详情面板 | **保存** |
  | `↑` `↓` | 树节点 / 网格行 | 移动选中，并**同步右侧详情面板** |
  | `↑` `↓` | 检索选择面板 | 在候选间移动 |
  | `Alt+↑` / `Alt+↓` | 详情面板 | **上一条 / 下一条**（需求、文档、物料等有相邻导航的页） |
  **焦点环是虚线蓝色**，鼠标与键盘操作都显示——用来确认"当前焦点在哪"。另：**对象引用一律用检索选择面板**（点 `编号 · 名称` 回显按钮 → 输入即检索、防抖约 **280ms**、回车立即 → `↑/↓` `Enter` `Esc` → 底部显示候选计数），**不要手输对象 ID**。
- **权威依据**：附录A A.1 表（`附录A-快捷键与FAQ.md:9-24`）；01 章 §3.5（`01:253-264`）、§3.4（`01:243-251`）；附录A A.2（`附录A:35`）。
- **依据等级**：**已核实**。
- **追问项**：① 在**哪个页面**（有些快捷键只在特定页生效，如 `Alt+↑/↓` 只在需求/文档/物料页）；② 是"按了没反应"还是"想知道怎么按"（前者提供页面 + 按键 + 期望，按缺陷登记）；③ 是否在**弹层/检索面板**内部（`Esc` 只关弹层）。

### Q:34 为什么"作废"点了就直接生效了，连个确认框都没有？我点错了。
- **答复**：**这是有意设计，不是缺陷**——**全站禁止弹窗确认**：破坏性动作**点了就发请求**，**没有 `确定/取消` 框**；不可逆动作需要在**详情面板内联填理由**（填错也来不及）。**做法**：点破坏性按钮前**先核对选中的行**；需要理由的动作**先把理由写好再点**。各域理由门槛不同（供参考）：文档作废 **≥8 字**、任务书作废 **≥8 字**、任务书订正 **≥8 字**、CBB 验证退回 **≥10 字**、CBB 升版"本版改了什么" **≥10 字**、CBB 退役通告 **≥10 字**、CCB 自评/自决理由 **≥10 字**、产品包…（按界面提示）。
- **权威依据**：01 章 §3.5 ⚠（`01:266`）；附录A A.2「破坏性动作」（`附录A:36`）；08 章（`08:182`）；07 章（`07:168`）；11 章（`11:80`）；15 章（`15:121`、`15:134`、`15:136`）；12 章（`12:71-74`）。
- **依据等级**：**已核实**。
- **追问项**：① 误操作的对象**类型 + 编号**（不同类型恢复路径不同）；② 该对象当前状态（有些可回退：需求 `ACCEPTED→VERIFIED`；有些不可逆：`OBSOLETE`/`DECOM`/已签署结论）；③ 操作时间与操作者；④ **不要**引导客户"改数据绕过"——按该对象的**状态机**或**受控订正**走。

## H. 审计纪律与缺陷登记（2 条）

### Q:35 你们（客服/实施）能不能帮我签一下 / 判定一下 / 帮我提交？
- **答复**：**不能，这是硬红线。** **严禁代签、代判定、代作业**——**AI 只能出初稿/建议，签署与判定必须由人在系统内完成**；AI 记录仅为草稿。相关配套口径：① **交付物提交与批准必须是不同账号**（纪律：提交人 ≠ 批准人；用门预检的 `DELIVERABLE_SELF_APPROVAL` 自查）；② **文档提交评审是作者动作**（只允许属主，admin 可破例；他人提交被拒并记审计 `document.transition.denied`）；③ **不得**为开门把**未来阶段**交付物提前置 `APPROVED`（这是最常被误用的"绕过"）；④ **受控订正**：生效/受控记录**只增不改**——要改就新建一条订正条目并声明它取代谁，被订正条目**一个字节都不写**；⑤ **审计链是 append-only（hash 链）**，`verify()` 可检出篡改，写路径串行化——**"手工改库让它对上"会被检出且不可修复**；⑥ **不得用其他路径绕过**（手改数据/绕过分页筛选/跳过评审门/挂不相关引用对象）——**绕过会污染受控证据链，事后无法与审计对账**。
- **权威依据**：`docs\plm-reflection\plm-review-rules.md` **S-22**（`plm-review-rules.md:217`）、**F-23**、**S-12**（`:202`）、**S-17/S-18/S-19**（`:212-214`）；`requirements-taxonomy.md` 稳定偏好第 8 条（`requirements-taxonomy.md:101`）、§七安全段（`:135`）；附录C「反馈与登记」§3（`附录C:218`）；03 章 §6.4（`03:210-211`）；附录A 术语「受控订正」（`附录A:109`）；README §5（`README.md:128`）；08 章（`08:74-77`）。代理红线另见 `docs\plm-tech\21-治理台与权限治理设计.md:86/228/230/249`。
- **依据等级**：**已核实**（规则表 + 手册 + 源码/设计三方一致）。
- **追问项**：① 客户具体诉求（"帮我签" vs "我不在时怎么办"）——**后者指向「委托签署」（治理台，默认 7 天到期自动失效，且是签署权临时转移、不转移责任归属）**；② 客户是否已持有该角色（按 Q:5 三步查）；③ 若客户是"缺人签"，那是**角色配置问题**（见 Q:8），不是代签的理由。

### Q:36 我发现一个 bug / 有个改进建议，要怎么提？
- **答复**：**在「需求管理」登记为需求**——**需求库就是系统自身的改进 backlog**。**要点**：① 标题注明 **【问题】/【建议】**；② **来源按性质**、**优先级按影响**；③ **登记前先查重**（见 Q:16）；④ **先记录事实（不要先下结论）**：`页面/路由` + `时间` + `界面文案（原文）` + `期望行为` + `复现步骤`（含账号角色、对象编号、操作序列）——**截屏或复制报文原文最有用**；⑤ **不要自行绕过**（见 Q:35）。另：**手册与实际界面/行为不符**时，记录「界面文案 + 路由 + 时间 + 期望」；**平台能力缺口/缺陷**按组织既有流程登记需求。⚠ **客服判定纪律**：**不要教用户"忽略"某个错数字**——凡界面与文档不一致，要么是**已修复**（答复时说明何时修），要么**按缺陷登记**（典型反例：G1–G7 门计数曾被当"登记"结案，用户第二次看到才修）。
- **权威依据**：附录A Q15（`附录A:90`）；附录C「反馈与登记」§1-4（`附录C:214-219`）；README §7 反馈渠道（`README.md:152`）；`plm-review-rules.md` **X-04**（`plm-review-rules.md:230`）、**X-02**（`:228`）；附录C 第 3 条「本条的教训」（`附录C:34-35`）。
- **依据等级**：**已核实**。
- **追问项**：① 上述 5 项事实是否齐备（**缺就不足以定性**）；② 是否**已查重**；③ 是**界面与文档不符**（手册类）还是**平台缺陷**（需求库类）——两者登记口径不同；④ 是否已尝试过本文登记的**替代路径**（若是"已知偏差有替代做法"，先给做法再问是否仍要登记）。
