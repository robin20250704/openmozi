# 痛点主题簇（pain-clusters）· 洞察线电容器

> 用途：**洞察线的核心台账**。把零散提问聚成"同一痛点的 N 次反馈"，再决定"要不要成为一条需求"。
> 为什么必须聚类：① 注意力是稀缺资源——20 次同一抱怨登记成 20 条编号，等于把 20 份注意力浪费在同一个问题上；
> ② 反过来说，**反复出现本身就是强度证据**——它决定了这条需求该有多重（用户是否真的被卡住）。
> 规则：**一个簇 → 最多一条需求**（V-05）；新反馈优先"补证据到既有条目"，而不是新建。

## 簇的判据（什么时候算同一个簇）

- 同一**模块/页面**（如 BOM 编辑器）；
- 同一**动作**（如"保存后顺序变"）；
- 同一**用户预期**（如"我希望所见即所得"）。

三者都同 → 同簇；只有模块相同而动作/预期不同 → **不同簇**（不要为了省编号而把不同问题合并，那会让需求不可分析）。

## 簇台账

| 簇 ID | 主题 | 命中模块 | 反馈次数 | 覆盖角色数 | 代表条目 | 状态 | 下一步 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| （待累积） | | | | | | 观察中 / 已成需求 / 已答复（已知偏差）/ 已排除 | 若达阈值（建议：**次数 ≥3 且角色 ≥2**）⇒ 触发"整理成需求" |

## 簇的升级判据（何时从"观察"变成"行动"）

| 判据 | 阈值（初始，可被小 cycle 校准） | 行动 |
| --- | --- | --- |
| 反馈次数 | ≥3 | 整理成一条代表性需求（正文累积全部证据） |
| 覆盖角色 | ≥2 个不同角色 | 说明不是个人习惯问题 ⇒ 提高优先级建议权重 |
| 是否造成实际损失 | 有一次具体损失（返工/数据错/合规风险） | **立即**整理，不等次数阈值 |
| 是否有现成绕法 | 有绕法且代价可接受 | 先答复绕法 + 观察（**不急于登记**：登记也是消耗他人注意力） |
| 是否属已知偏差 | 是 | 不登记（C-09）；转去完善答复话术 |

> 记录纪律：每次"因为阈值未到而暂不登记"都要写在这里（含判据读数）——否则将来无法回答"为什么不给我建单"。
