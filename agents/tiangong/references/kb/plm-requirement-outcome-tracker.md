# 需求落地追踪（requirement-outcome-tracker）· 判断-结果校准

> 用途：把"客服登记的判断"与"系统里的实际结果"配对，用来校准客服的判断力——这正是设计里的
> **价值函数持续校准**在客服场景的落地：不追踪结果的客服无法知道自己"什么时候判准了"。
> 数据来源：`plm-req.cjs track`（台账回读运行态）+ `get <reqCode> --flow`（当前阶段与下一步该谁处理）。
> 读取时机：回答"我上次提的那个进展如何"；L2 整理；L3 大 cycle 校准。

## 归因三分（回填纪律：**必须选一个**）

| 归因 | 含义 | 改进对象 |
| --- | --- | --- |
| **需求质量问题** | 现象说不清 / 影响说不明 / 期望不可验收 ⇒ 分析人无法推进或推进后返工 | 客服的采集与结构化（质量门判据、追问模板） |
| **系统实际如此** | 判为缺陷，实际是设计如此或已知偏差 ⇒ 客服分诊失误 | 分诊门与 `plm-known-deviations.md` 覆盖度 |
| **外部因素** | 排期/资源/优先级取舍、需求本身被判定不划算 | 客服预期管理（V-13：不承诺时间） |

> 归因错了会**污染校准**：把"我分诊错了"记成"开发不修"，会让客服停止登记真实缺陷；反之亦然。

## 度量（从本表计算）

- **需求被采纳率** = 推进到 `ANALYZED` 及以后的条目 / 登记总数。低 ⇒ 要么质量门太松（登记了不可分析的东西），要么分诊门太松（把已知偏差当缺陷）。
- **误判率** = 归因"系统实际如此"的条目 / 登记总数。高 ⇒ 分诊门需要收紧（先查 `plm-known-deviations.md`）。
- **闭环时长中位数** = 从 `PROPOSED` 到 `ACCEPTED`/`CLOSED` 的中位天数（客服只需知道，不承诺）。
