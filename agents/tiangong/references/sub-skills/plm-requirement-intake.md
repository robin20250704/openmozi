# 子技能②：痛点 → 需求结构化

> 上位机制见 `prompt.md` §四（需求线：采集 → 查重 → 质量门 → 登记）与 §二（事实纪律）。
> **实测口径（2026-09-27）**：登记字段受阶段约束——**优先级/DFX/验证方法/价值维度/用户画像/方案内容不可在登记时写入**（`400 REQ_FIELD_STAGE_LOCKED`），只能并入正文的「分析输入」段。与旧材料冲突时以 `prompt.md` §四为准。

## 一、采集三问 + 价值三问（澄清的最小完备集）

**采集三问（客观事实，用户一定答得出）**：
1. **现状**：你现在怎么做这件事？（逐步描述，从打开哪个页面开始）
2. **期望**：你希望它变成什么样？（用"我希望…就能…"句式，**不要接受"优化一下""友好一点"**）
3. **影响**：这件事给你造成什么具体损失？（多花了多少时间 / 卡住了哪一步 / 数据错在哪 / 谁受影响）

**价值三问（判断"值不值得占用一个编号"，答案进正文「分析输入」段）**：
1. **不做会怎样**：问题继续存在的后果（频率 × 严重度）；
2. **谁受益**：哪些角色/项目/批量场景（**"只有我这样"和"整条线都这样"是两个量级**）；
3. **怎么算做成了**：可验收的成功条件（"能导出当前筛选的 500 行"而不是"体验更好"）。

> **为什么价值和采集要分开问**：采集三问是**客服能确认的事实**（用户是唯一权威）；价值三问是**分析输入**（客服只提供素材，不下结论）。把两者混在一个问题里，用户会开始给方案，客服就越界替分析人做结论了。
> **一次 ≤2 问、带选项优先**（"是所有人在这个页面都看不到，还是只有你的账号？"比"权限情况如何"高效十倍）；问到即落 `tasks/plm-cs-<主题>/intake.md`，**新会话/压缩后先读再问**，不重复问已确认项。
> **需求粒度**：一条意见一个需求；多条意见**拆开提**，不合并成"大杂烩"——合并后无法验收也无法排优先级。唯一例外是**洞察聚类**（§六），那是同一痛点的 N 次重复，不是多条不同意见。

## 二、主动探查（active probing）：问"能使候选假设分歧最大"的问题

**机制来源**：门控是被动的互信息过滤；**探查是对偶的主动互信息设计**——当可以主动选择问题时，准则 = **最大化期望信息增益**，工程近似 = **选使候选假设之间分歧最大的那个问题**（哪个问题的不同答案，会指向完全不同的结论）。

**四步做法**：
1. **先列候选假设**（2~4 个，且**必须互斥**）——例："这个按钮点不动"可能是：① 缺角色；② 对象级 ABAC 拒绝；③ 状态不允许（整表单锁定）；④ 必填项未填；⑤ 真的是缺陷。
2. **为每个候选假设写出"如果它为真，世界会怎样"**（可观察的差异）——这一步是**判据的来源**，跳过它就只能凭感觉问。
3. **设计一个能一刀切开这些世界的问题**（**不问最"全面"的问题，问最有分辨力的问题**）。
4. **问完立刻收窄**（假设集从 5 个降到 2 个），必要时再问下一刀；**≤2 轮仍缺 ⇒ 用默认值 + 显式标注假设**，不要为了"问全"把用户拖住。

**8 组"模糊描述 → 分辨性提问"对照**（照抄可用）：

| 用户模糊描述 | 候选假设 | 分辨性提问（一刀切开） |
| --- | --- | --- |
| "这个按钮点不动 / 是灰的" | ① 缺角色 ② 状态锁定 ③ 必填项未填 ④ 该键本就未挂动作 | "**另一个同事在同一页面、同一对象上，按钮是亮的吗？**"（亮 ⇒ 排除③④，指向①）；再要 403 原文区分权限点 vs 对象级 |
| "我看不到某条数据" | ① 筛选/分页 ② 产品作用域 ③ 真的没有 ④ 权限（低概率，读不鉴权） | "**清空全部筛选、把左侧分类树切回「全部」之后，还在吗？工具栏显示「共 N 个」是多少？**"（N>0 而列表空 ⇒ 筛选；N=0 ⇒ 数据本身） |
| "我刚建的对象不见了" | ① 还在草稿态未落库 ② 被筛选挡住 ③ 列举结果不稳定 | "**面板上显示的是正式编号（如 `REQ-2026-xxxx`）还是 `● 新…`？**"（`new-<时间戳>` ⇒ 草稿态，**根本没落库**） |
| "我改不了这条需求" | ① 状态锁定 ② 基线化后须走 ECO ③ 缺字段 ④ 缺角色 | "**面板顶部有没有提示"已锁定"？当前状态码是什么？**"（锁定 ⇒ 走 ECO；报 `FIELD_REQUIRED` ⇒ 补字段） |
| "门开不了，材料我都齐了" | ① 真有 BLOCKING 项 ② 只是 ADVISORY 报出 ③ 文案误导（文案不指向真实失败项） ④ 历史交付物 `STAGE_UNSET` 卡门 | "**跑过 `precheck` 吗？把 `projectId` + 门码给我，我看 `severity=BLOCKING` 的失败项**"（没跑过硬判 ⇒ 一律先跑 precheck） |
| "系统好慢" | ① 后端读放大 ② 前端大数据量渲染 ③ 首屏/翻页/筛选/导出哪一步 ④ 用户在用"翻页替代检索" | "**慢的是哪一步：首屏、翻页、筛选、还是导出？大概几秒量级？**"（首屏 ⇒ 渲染/预加载；导出 ⇒ 数据量） |
| "这个功能没有 / 找不到入口" | ① 有意无界面（仅接口可达的受控动作） ② 路由改名/走错路径 ③ 确实没有 | "**你是在哪个页面找的？我确认一下运行态有没有这个入口**"（→ 核对 `plm-module-map.md` 的「没有独立入口的能力」节 + 深链落点限制） |
| "数据不对，跟实际不符" | ① 口径不同（成本三字段谁参与汇总 / 目标成本权威在项目侧 / 演示种子值） ② 真错 | "**你看的是哪个字段、哪个页面上的数字？期望值来自哪里？**"（口径类 ⇒ 给正确口径；真错 ⇒ 登记 + **绝不手改**） |

**探查的形态与红线**：
- **形态**：**对照式**（"别人/别的页面/别的对象是否也这样"——最快的分辨手段）｜**边界式**（"什么时候是好的"——定位触发条件）｜**原文式**（"把报错原文/截图发我"——把定性从猜测变成事实）。
- **红线**：探查是为了**分辨假设**，不是为了套话；**不诱导**（不要把答案放进问题里）；**不越权定性**（探查出来"这是权限问题"就引导用户自查，不要替管理员改角色）。

## 三、痛点澄清 → 需求要素映射表（口语 → 结构化）

| 用户口语（原话，不改写） | 映射到需求要素 | 写法要求 |
| --- | --- | --- |
| "每次都要点好几下才能…" / "这个按钮没反应" | **标题**（一句话诉求，用户视角） | 自解释、能检索：**写"哪里不对 + 期望什么"**，不要"系统有问题"；≥6 字（工具会拦） |
| "我在 XX 页面做 YY 的时候，点 ZZ 就报错/没反应" | **现象**（正文第 1 段） | 路由 + 操作序列 + 账号角色 + 界面文案**原文**；≥20 字（工具会拦） |
| "这样我每周要花两小时手工统计" / "卡在这里后面都做不了" | **影响**（正文第 2 段） | 谁受影响 + 具体损失（时间/错误/卡住的环节）+ 频率 |
| "要是能…就好了" / "能不能加个…" | **期望**（正文第 3 段） | 用户想要的结果；**不要替他写实现方案**（方案属分析人/开发） |
| "我试了三次都是这样" / "换了个账号也一样" | **复现步骤**（正文，含环境/角色/是否必现） | "必现/偶发""所有人都这样/只有我"是**决定性事实**，必须问出来 |
| 截图 / 报错原文 / 端点响应片段 / 对象编号 | **证据**（正文末尾 + 附件引用） | 报错原文最有用；大体积走文件引用（`.creature/tasks/plm-cs-<主题>/evidence/`） |
| "这个问题团队里好几个人都提过" / "已经第三次了" | **强度标注**（正文「分析输入」段 + `plm-pain-clusters.md`） | 写"N 次反馈，来源角色 X/Y/Z"——**这是分析人排优先级的关键素材** |
| "最好这个版本就改" / "下个迭代也行" | **优先级建议**（**正文「分析输入」段，不写请求体**） | 用 `HIGH/MEDIUM/LOW` + 理由；**标注"客服建议，待分析人裁定"** |
| "这属于 DFX 里的可制造性 / 主要看价格" | **DFX 维度 / 价值维度建议**（**正文「分析输入」段**） | `dfxDimension` = `DFM/DFR/DFT/DFU/SAFETY/ENV/COST/IP/COMPLIANCE`；`appealsDim` = `PRICE/QUALITY/TIME/VARIETY/SERVICE/CHANNEL/BRAND/RELATIONSHIP` |
| "你觉得该怎么修" | **不映射**（客服不设计解法） | 只写"期望的行为"，把"怎么实现"留给分析人与开发 |

**原话留痕纪律**：**整理的边界是"结构化"不是"改写"**——用户原话（尤其是"我们每周要花两小时"这类量化感受）**必须原样进 `plm-voice-of-customer.md`**，正文里可以做可分析的改写，但**诉求与期望以用户表达为准**，客服只补"可验证性"。

## 四、清晰度质量门四判据（可操作检查表）

| 判据 | 通过标准（逐项打勾） | 常见不过的表现 |
| --- | --- | --- |
| ① **现象可复现** | 有路由 + 操作序列 + 账号角色 + **界面文案原文**；且已注明**必现/偶发**、**所有人/仅我** | "有时候会出问题"；只有结论没有步骤；文案是转述而非原文 |
| ② **影响可描述** | 指明"谁 + 什么损失 + 频率"，最好可量化（每周 2 小时 / 卡住 N 个项目的门） | "影响效率""体验不好"（分析人无法据此排序） |
| ③ **期望可验收** | 写成"什么样的状态算做到了"，**可观察/可测量** | 写成了实现方案（"加一个按钮"）；或写了"优化一下" |
| ④ **证据可指认** | 至少一项可指认证据：报错原文 / 截图 / 端点响应 / 对象编号 / 既有条目编号 | "别人也这么说"（转述，无据）；截图未标注页面与时间 |

**四元输出（照 `prompt.md` §四 质量门）**：**通过**（进登记）｜**证否**（确实是已知偏差或用法问题 ⇒ **不登记**，回答客线给做法，并把结论入 `plm-negatives.md`）｜**无效**（不达标 ⇒ 回炉补证据，≤3 次；第 3 次**重审"该不该登记"**——反复补不齐通常意味着这不是一条需求，而是一次求助）｜**升级讨论**（跨模块、涉及**流程/权限争议**、或**客服无权定性**（如"这个字段到底该谁填"）⇒ 路由到人，**不硬判也不丢弃**）。

**红队自查（可选，用于高价值条目）**：让一个 subagent 扮演"最挑剔的分析人"，**只给它草稿、不给过程**，问它"**你会以什么理由打回这一条？**"——能显著降低"客服自己觉得清楚、分析人看不懂"的比例。“只给草稿”是判据的核心：给了过程它会替客服补全信息，就测不出草稿本身的清晰度。

## 五、三类不许登记的情形（与正确处置）

| 情形 | 判据 | 正确处置（**为什么**） |
| --- | --- | --- |
| **① 已知偏差 / 有意限制** | 命中 `plm-known-deviations.md` 的「现象」 | 给该条「用户该怎么做」→ **结案**。登记已知偏差 = 制造垃圾条目，并让分析人重复判定同一件事（**例外**：标"已修复"仍复现 ⇒ 按缺陷登记） |
| **② 用法问题 / 业务前置不满足** | 用户只是不知道怎么做；或 `400 <中文 message>` 已说明缺什么 | 教操作 / 按 message 补齐 → **结案**。**要区分"用户不懂"和"系统难用"**：若同一操作被 ≥3 人问过，那本身就是一条**体验需求**（走洞察聚类，不是逐条登记） |
| **③ 已有条目覆盖** | 查重命中（相似度 ≥ 0.55）且既有条目表达同一痛点 | **优先补证据到既有条目**（评论/追溯/补充复现信息）——同一痛点不要产生第二个编号；确属不同痛点 ⇒ 改标题使差异显式后加 `--allow-duplicate`；**订正**既有条目 ⇒ 走订正条目（`supersedesId`） |

**另需拦下的两种"不该进需求线"**：用户明确说"只是说说/不用改" ⇒ 只记 `plm-voice-of-customer.md`（并在会话摘要里说明"未提交"），**不登记**；纯个人偏好且无验收可能 ⇒ 记录到 `plm-preferences.md`，不占用编号。

**"不登记"不等于"丢弃"**：三类情形都要在 `plm-negatives.md` / `plm-pain-clusters.md` 留下条目与理由——**有价的否定结论也是产出**（下次同类提问可秒答，L3 也能据此校准分诊表）。

## 六、洞察聚类：N 次反馈 ⇒ 一条代表性需求

**为什么**：登记的粒度是"一条需求一个可验收的变化"。**20 次同一抱怨**若登记成 20 条 ⇒ backlog 被同一问题淹没、分析人无法排序、真实的长尾问题被挤掉。

**做法（四步）**：
1. **集簇判据**（三选一即同簇）：**同一模块/路由**｜**同一角色/同一作业环节**｜**同一现象句式**（同一报错码/同一按钮/同一字段）。
2. **写簇**（`plm-pain-clusters.md` + `pain-cluster-template.md`）：簇标题 = "模块 × 作业环节 × 现象"，记录**次数、来源角色、首次/最近时间、各自的证据指针**。
3. **出代表性条目**：挑**证据最全的那一次**当模板（它天然满足质量门四判据），标题写成**可被检索的形式**——把**模块名 + 关键动作 + 期望**都放进标题（例："需求管理：批量推进状态时无部分失败明细"），**不要**用"很多人反馈的一个问题"（这种标题查重查不出、分析人搜不到）。
4. **保留强度证据**：正文「分析输入」段写"**N 次反馈（角色 X/Y/Z，首次 A 日期，最近 B 日期），共 M 个证据指针**"——这是分析人判断优先级最缺的素材，也是**客服独有的贡献**（用户自己说不出"有多少人也遇到"）。

**簇的三种去向**：转成一条代表性需求（标"已选题"）｜**不登记但升级给洞察**（问题真实但不构成可验收需求，如"整体上手难"——积累到有具体切面再出条）｜**合并进既有条目**（查重命中）。

**簇的休眠与唤醒**：低频簇不删（半年后同类再出现时，那一句"这是第 N 次"就是最有说服力的证据）；**版本升级/模块重构后必须复核簇**——被改掉的痛点要标记"已随版本消失"，否则会把已解决的问题再提一遍。

## 七、与登记工具的衔接（draft.json 字段映射）

**生成 `draft.json`（只放登记时可写字段）**：
```json
{
  "title": "<哪里不对 + 期望什么，≥6 字>",
  "content": "<现象/影响/期望 三段式，≥20 字；末尾由工具自动追加「分析输入」段>",
  "reqType": "SR",
  "reqClassId": 6,
  "sourceType": "PLM_SELF",
  "projectId": 87,
  "priority": "HIGH",
  "dfxDimension": "DFU",
  "appealsDim": ["TIME"],
  "verifyMethod": "DEMO"
}
```
**关键规则（工具会自动执行，但客服必须理解为什么）**：
- **`priority` / `dfxDimension` / `verifyMethod` / `appealsDim` / `userPersona` / `userTags`** 写进 draft 后**不会进请求体**，而是被工具**并入正文的「分析输入 · 由客服采集，待分析人裁定」段**——因为它们是**分析结论**，`PROPOSED` 阶段写入必被 `400 REQ_FIELD_STAGE_LOCKED` 拒。
- 仍**要在 draft 里写它们**（而不是只在正文手写）：工具会做**词表校验**（填错词表当场报错，而不是把非法值写进正文交给分析人）。
- **`sourceChannel` 默认不写**（虽然服务端有 `SOURCE_CHANNEL_STAGE_EXEMPT` 豁免）——少一个写入面就少一类 400；确需登记来源通道时在草稿里**显式给**。
- **`sourceType` 与 `sourceChannel` 是两套词表**——给 PLM 自身提改进用 **`sourceType=PLM_SELF`**；把 `sourceChannel` 的五值（`CUSTOMER` 等）当 `sourceType` 用会立刻 `400 ATTR_INVALID`（实测踩过）。
- **`paramValue` / `paramUom` / `verification` 属死锁区，一律不要写**（工具**本地硬拒**）：填了 `paramValue` ⇒ 服务端要求 `verifyMethod` + `verification` 同时非空；而 `verifyMethod` 属"分析后才可填" ⇒ **带它被阶段锁拒、不带它被可验证性校验拒**——两头都堵，登记时无解。**正确做法**：指标名写 `paramName`（可写），量化口径写进正文【量化期望】段（目标值/单位/怎么算验收），交分析人 ANALYZED 后补录。
- **不确定的字段宁可留给分析人**：工具会把"未知/后置字段"从请求里剔除并告警。**登记时的目标不是"填满"，而是"准确"。**
- **草稿文件编码**：Windows 上用 `Set-Content -Encoding UTF8` 或 Excel 另存会带 **UTF-8 BOM**，工具已做剥离；若自行用别的写入方式，确保是**无 BOM 的 UTF-8 JSON**（BOM 会让 JSON 解析失败，而报错信息看起来像"JSON 写错了"，把人引向错方向）。
