# 子技能①：答客问与知识导航

> 上位机制见 `SKILL.md` §四（事实门/分诊门/时效门）。本文件是**答客线**的落地细节。
> **实测口径（2026-09-27）**：环境 UAT、身份固定 `.env` 的 `PLM_USER`（实测 `robinzeng`）、`password grant 已关闭`（只能真浏览器 SSO）。凡本文与旧材料冲突，以 `SKILL.md` §〇/§一 的事实为准。

## 一、答客线的第一动作永远是分诊

**为什么**：分诊决定"要不要登记需求"——分诊错一次，两头都错（把已知偏差当缺陷 ⇒ 制造垃圾条目；把新问题当已知偏差 ⇒ 用户的真实痛点永远不落地）。

**分诊流程（照做）**：

1. **抓现象原文**：不要接受"系统坏了"这种描述，先要到**界面文案原文 / 报错码 / 端点响应**。文案是分诊的唯一硬证据（例如两类 403 只差一句话，定性完全不同）。
2. **grep 命中 `plm-known-deviations.md` 的"现象"**：命中 ⇒ **已知偏差/有意限制** ⇒ 直接给该条「用户该怎么做」，**结案**。
   - **例外**：该条若标"已修复"，而现在**仍复现** ⇒ **按缺陷登记**（不要在"已修复"上结案——历史教训就是"登记被当成结案，用户第二次看到才修"）。
3. **未命中 ⇒ 走 §10 的 9 行分诊表逐行比对**：
   | 用户描述 | 判定 | 动作 |
   |---|---|---|
   | 命中已知偏差「现象」 | 已知偏差/有意限制 | 给做法，**不登记** |
   | 界面文案与手册不一致且未登记 | 手册-实现漂移 | 以运行态为准；引导**登记需求** |
   | `400 <中文 message>` 且 message 说明缺什么 | 业务前置不满足 | 按 message 补齐（**不是缺陷**） |
   | `403` 带"权限点：… 当前角色：…" | 角色面问题 | 走角色三步自查（§二）；**不重试** |
   | `403 无权操作该对象（超出授权范围…）` | 对象级 ABAC 拒绝 | 查**对象归属**项目/属主（**不是**缺角色） |
   | 界面弹出 Java 异常原文 | 平台缺陷（文案未归一化） | 记录并上报（页面+时间+原文+复现） |
   | 端点 400 `SERVER_ERROR` 而路径本身不存在 | 已不再是缺陷（修复后为 404 `ENDPOINT_NOT_FOUND`） | 核对端点；**不要重试** |
   | 按钮没反应 / 找不到入口 | 查"未挂动作"与"有意无入口"两类 | 都不是缺陷；需要入口则**登记需求** |
   | 数据不对但系统看起来正常 | 绝不手改数据 | **登记需求** + 给替代路径 |
4. **分诊结论落盘**：写进 `tasks/plm-cs-<主题>/`，并把新现象回填 `plm-known-deviations.md`（下次同类问题可秒答）。

**分诊的三条反直觉要点**：
- **`passed=false` 不一定阻断**（看 `severity`）；**`passed=true` 也不一定查过**（可能是"空通过/N/A 未评估"，看 `detail` 自述）——只读 `passed` 这个布尔值必然误判。
- **`blocked=true` / `blockReason` 只用来"发现"阻塞，不用来"解释"阻塞**——真实原因一律看 `GET /api/v1/reviews/precheck?projectId=&gateCode=` 的 `BLOCKING` 失败项。
- **按钮亮不亮不是依据**（`flow-overview.canRequest` 曾与预检不同源）——**发起前先跑 precheck**。

## 二、五步导航法（用法问题的标准路径）

**① 抽取用户实际身份与角色**（权限类问题多半是角色问题，不是系统问题）
- 问清：**登录名**、**在哪个项目里**、**想做什么动作**、**按了哪个按钮**、**报的什么**。
- 权威口径两条（背下来，能省一半来回）：**读不鉴权**（`GET` 列表与详情全员可见，只有**写/流转/判定/签署**才判权限）⇒ "看不到数据"基本**不是权限问题**而多半是筛选/分页；**有效角色 = 组织角色 ∪ 该项目成员角色**（在 A 项目有 `prj_dev` 不代表在 B 项目有）。
- 角色三步自查（**教用户照做，不要自己代查权限矩阵**）：
  1. `GET /api/v1/_platform/permission/me` → 我的组织角色；
  2. `GET /api/v1/_platform/permission/rules` → 每个权限点允许的角色集（⚠ 受 `_admin.read` 保护，**非管理员 403** ⇒ 走**治理台**的决策权限矩阵，或请管理员/PMO **代查**，**不要重试**）；
  3. `GET /api/v1/projects/{id}/members` → 我在这个项目里的项目角色。
- 判权限有固定顺序：**RBAC（功能权限点）→ ABAC（对象实例属性）→ 流程边角色门**，任一层不过都会拒——所以在不知道哪一层不过之前，任何"你去申请个角色吧"的建议都是猜。

**② 定位模块与路由**（`plm-module-map.md` §1）
- 先问"你在哪个页面、点的哪个入口"，再用"用户典型问什么"列反查入口；**用运行态的路由，不要用用户口述的名字**。
- 常见错位要先纠：**工作台 `/` 不是需求页**（需求管理在 `/requirements`）；**`/charters`、`/deliverables`、`/reviews` 三个路径不存在**（正确的是 `/charter`、项目详情页签、项目详情时间线）；**门评审入口在项目详情时间线点门节点**。
- 顺手把该入口的「常见坑」列读一遍——**大多数"按钮坏了"其实是该列已登记的行为**，直接答复比登记需求省一个编号。

**③ 在 KB 三库检索**（顺序固定，先 KB 后源码）
1. `plm-module-map.md`（模块/路由/端点/常见坑/角色边界/编号前缀）；
2. `plm-faq.md`（36 条四段式：答复/权威依据/依据等级/追问项）——**命中即答，直接抄权威依据**；
3. `plm-known-deviations.md`（59 条现象 + 该怎么做）。

**④ 命中即答**：按 §五模板给出答复；**抄依据，不要凭印象改写**（改写是"看起来一样、实际差一个词"的常见事故源）。
- 若 KB 条目标"**推测（需现场验证）**" ⇒ **不得当结论发出**：先按该条「追问项」问清，或明确标注"这是推测"+ 给出验证方法。
- 若 KB 条目带 ⚠/「未核实」（未核实清单 U-1…U-11、FAQ 附录 5 条） ⇒ 只答复**已核实部分**，缺口按"登记需求"处理。

**⑤ 未命中 ⇒ 查只读源码/文档 + 标依据等级 + 给下一步验证**
- 只读来源：`D:\project\jcode`（`docs\plm-user-guide\`、`docs\plm-tech\`、`docs\plm-reflection\`、`ipd\plm-app\`）——**只读！**
- 依据写法统一：`文件:行` / `端点` / `实测`；**没有依据一律标「未核实」**。
- **未核实也必须给出下一步**（去哪个端点取证、找谁代查、什么时候回）——**不回答**和**编答案**一样糟，但**编答案更糟**（用户会照着做，而且会替他传播）。
- 把这次"未命中"记入 `negatives.md` / `lessons.md`；**同类问题第 3 次出现 ⇒ 晋升为 FAQ 条目**（L2 整理）——KB 是靠提问长出来的，不是靠一次性编写。

## 三、六类问题的标准作业序（照做可少走弯路）

| 问题类 | 字段 | 作业序 |
| --- | --- | --- |
| **A 怎么操作** | 角色、目标、当前页面 | 定位模块路由 → 读「常见坑」 → 给逐步路径（用界面原文词汇） → 标注快捷键类小技巧（`Ctrl+S` 保存、`Esc` 放弃修改、`Alt+↑/↓` 上一条/下一条、对象引用一律用**检索选择面板**不要手输 ID） |
| **B 报错/推不动** | 报错**原文**、状态码、对象编号 | 分诊（`400` ⇒ 业务前置，看 message；`403` ⇒ 分两类；`500`/Java 原文 ⇒ 缺陷） → 给补齐动作 → **不重试未知端点** |
| **C 权限/按钮** | 403 原文、对象编号与归属、按钮渲染情况 | 三步自查（§二①） → 区分类别 → 指到治理台/管理员 → **不代查、不代改角色** |
| **D 门线/评审** | 项目 id、**门码**、precheck 报文 | 先跑 `precheck` 读 `severity`/`detail` → 给 `BLOCKING` 失败项及 code → 说明"结论只能由评审工作台判定 + 签署产生"（**不能靠流转按钮/接口补结论**） |
| **E 数据可见性** | 页面、工具栏 `共 N 个`、筛选条件、对象编号 | 清筛选 + 切回树根「全部」 + 看产品作用域 → 用**编号/深链直取**复核（"列表里没有" ≠ "不存在"） → 仍异常则**记录上报** |
| **F 数据不对** | 字段名、期望值来源、对象编号 | 先判**口径**（如成本三字段谁参与汇总、目标成本权威在项目侧、样例值是演示种子值） → 口径问题给正确口径；真错 ⇒ 登记需求 + **绝不手改数据** |

## 四、追问问什么（每类问题的通用追问项）

从 `plm-faq.md` 的四段式里提炼的通用模板——**缺任一项就不足以定性**，但**一次 ≤2 问、带选项优先**：

| 类别 | 必问项 |
| --- | --- |
| 通用根底 | **环境**（dev 还是 UAT——两者的"能否直连取 token""证书"完全不同）｜**登录名/角色**｜**完整 URL 或路由**｜**报错原文（截图/复制报文）**｜**操作序列** |
| 权限/按钮 | 403 **完整文案**（是否带"权限点：… 当前角色：…"）｜操作对象**编号**与**它属于哪个项目**｜是"按钮不渲染"还是"点了才报错"（后者可能是**未做逐按钮权限裁剪**） |
| 列表为空 | 哪个页面｜工具栏 `共 N 个` 与**当前筛选条件**｜是否有左侧分类树/产品作用域｜"列表为空"还是"少数几条不见"｜目标对象**编号**（可直接 `?open=<id>` 复核） |
| 门开不了 | 项目 id + **门码**（`DCP1`/`TR3`…）｜预检报文里的 `passed`/`severity`/`detail`｜失败项 **code**｜**是否已跑过 precheck**（没跑过不要凭界面颜色判） |
| 数据不对 | 对象**编号**｜期望值 vs 实际值｜**是否已点过 `创建`**（草稿态 id 是 `new-<时间戳>`，尚未落库）｜是否基线化/状态锁定 |
| 改不了 | 对象当前**状态**｜想改哪个字段｜报错码（`ITEM_LOCKED`/`REQ_LOCKED`/`CHARTER_LOCKED`/`DOC_LOCKED`/`当前状态不可编辑: …`） |
| 登录 | 环境与完整 URL｜停在登录页还是**点完又跳回来（循环）**｜是否提示"无法连接统一身份认证"｜是否隐私模式/清过 Cookie |
| 评审签署 | 想改的是**结论**还是条件/意见｜**是否已签署**（已签署只能再发起新评审）｜是否存在未撤回否决｜是否主席角色（`SIGNER_REQUIRED` 的根因） |
| 缺陷/建议登记 | 「页面/路由 + 时间 + 界面文案原文 + 期望行为 + 复现步骤」五项是否齐备｜是否**已查重**｜是"界面与文档不符"还是"平台缺陷"（登记口径不同） |

**追问纪律**：追问是为了**收窄候选假设**，不是为了凑齐表格——**每一问都要能改变结论**（见子技能②「主动探查」）。用户答不上来也给下一步（给判断方法），不要卡在"信息不全所以不答"。

## 五、答复模板（照抄结构）

```
【结论】一句话说清是什么/不是什么（例：不是系统坏了，是"来源通道"还没到可填阶段）。
【在哪操作】界面路径逐级写（例：需求管理 /requirements → 右上「＋ 新建需求」→ 选「所属项目」→ 点「创建」）。
【为什么】一句话讲机制（用户懂了就不会再问第二次）。
【依据等级】已核实（依据：02 章 §3 字段表 / 端点 …）｜推测（需现场验证：验证方法 = 在 dev 上实测一次 / 读 …）。
【如果还不行】下一步 + 我需要你补什么（报错原文/编号/截图），或"此处我无权代做，需由 XX 角色在系统内完成"。
```

**排版纪律**：结论放第一行（用户只读第一行的很多）；路径用**界面原文词汇**（"＋ 新建需求"而不是"新建按钮"）；控制长度——**一次答一问**；涉及破坏性动作（作废/删除/签署）时**先提醒"点了就直接生效、没有确认框"**（全站禁止弹窗确认是有意设计）。

## 六、答复后闭环（答复不是终点）

1. **记录一条答复**（`templates/answer-record-template.md` → `tasks/plm-cs-<主题>/answers/`）：问题原话 / 分诊结论 / 依据与**依据等级** / 答复全文 / 用户结果（是否解决、是否追问）。
2. **配对进 `plm-answer-quality.md`**：这是"推测被证实/被推翻"比例的**唯一数据源**——没有配对记录，L3 无法校准可信度门（也没法回答"我们到底有多少答复是猜的"）。
3. **用户否证了我** ⇒ **立即写 `lessons.md`**（症状→我的错误结论→真因→正确口径），并回改 KB 条目的依据等级；**不快**，但这是唯一能防止"同一个错误答第二遍"的机制。
4. **转成需求** ⇒ 把分诊结论与追问项一起交给子技能②（**不要重新问一遍用户**）。
5. **同类第 3 次** ⇒ 晋升 FAQ 条目；**同一操作被 ≥3 人问过** ⇒ 那本身就是一条体验需求（走洞察聚类，而不是逐条登记）。

## 七、三条禁令（每一条都由真实事故换来）

1. **不编按钮名 / 界面路径**——按钮文案变了、页面改了都是常态；**没核实过就写"在 XX 页找 XX 按钮"** ⇒ 用户找不到 ⇒ 信任一次就没了。没把握就给**检索方式**（按编号搜、`?open=<id>` 深链）而不是猜位置。
2. **不猜权限**——"你没权限"是最容易被滥用的解释。必须先看 403 **原文**（两类文案语义不同）、看**对象归属**（ABAC）再下结论；**不要把对象级 403 当角色问题**（会让用户去申请一个他本来就已经有的角色）。
3. **不把"已知偏差"说成"系统坏了"，也不把"新问题"说成"已知偏差"**——前者制造垃圾需求条目、动摇用户对系统的信心；后者让真实痛点永远不落地。分诊结论必须**指到具体条目/分诊表行**才算有依据。

**配套两条（同属红线）**：**不教用户绕过**（手改数据 / 跳过分页筛选 / 跳过评审门 / 挂不相关引用对象——绕过污染受控证据链，事后无法与审计对账）；**不代签、不代判定、不代作业**（AI 只出初稿，签署与判定必须由人在系统内完成；若用户是"缺人签"，那是**角色配置问题**，指向治理台委托签署或请管理员补角色，不是代签的理由）。
