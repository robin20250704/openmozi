# 接口清单标准树（interfaces）

> 表头固定为 `| ID | 名称 | 签名/路由 | 鉴权 | 幂等 | 错误码 | 性质 | 保证 | → 指针 |`。
> `性质` ∈ {`contract` 树是承诺 / `as-built` 树是描述 / `planned` 尚无实现}；
> `保证` ∈ {`def:同指针` / `def:<路径>#<符号>` / `assert:<路径>::<用例>` / `gen:<路径>` / `TODO`}。
> **写入纪律、冲突裁决、本树的缺口与债** ⇒ [`writers-guide.md`](writers-guide.md)。

## ① 这棵树回答什么问题

回答"**系统提供什么、怎么调、失败长什么样**"——具体是四类问题：

1. 我要调某个能力，**签名/路由/参数**是什么？（照着一行就能发起调用）
2. 这个接口**要不要凭据、能不能重复调**？
3. 调失败了会**拿到什么错误码**、对应什么含义？
4. 某个接口**哪份文档在讲它**、代码里的**权威声明在哪一行**？

**不回答**（属别的树，跨树只引用 ID）：业务规则与校验 → `business-rules`（如 `（见 R-012）`）；术语 / 实体 / 状态机定义 → `ontology`；目录用途与写者 → `inventory`。

### 本树有**两个主体**（2026-10-05 第三轮裁定时补说清）

| 主体 | 分片 | 真身在哪 | 为什么这样分工 |
| --- | --- | --- | --- |
| **jcode Harness API** | I-001~I-080 | **本树** | 协议面是手写 Rust，**没有生成器**、注解里读不出来 ⇒ 必须逐条声明，否则客户端只能读源码 |
| **PLM 应用 HTTP**（实测 530 个操作） | I-081~I-095 | **运行中的 OpenAPI** | 把 530 条抄进树 = 造第二份真身且必漂移；本片只声明 **spec 给不出或会说错** 的四类事实 |

> 这一节是补债：此前本树的 `role` 写「唯一声明」，而盘上 80 条**全是 Harness**——
> 于是「PLM 的接口要不要凭据、能不能重试、失败了拿什么错误码」在声明层**无处可查**。
> 最贵的一条是 **I-086**：生成的 spec 里 `security` **530 个操作全为空**，照它判断会得出"全部免认证"。
> 最容易被读错的一条是 **I-083**：它写的是**部署态只认 oidc**（`X-PLM-User` 不是身份，实测 401）。
> 代码里确有 `dev` 分支（服务"宿主直跑 `mvn spring-boot:run`"），但契约必须描述**对调用方有效的运行态**——
> 写成"dev/oidc 二选一"会让人以为可以拿 `X-PLM-User` 调接口。

## ③ 两条只看本页就够用的判据

1. **每条声明必须有非空指针**（最后一格 `→ 路径#符号`）。空指针 = 事实没有落处 = 不合格。
   指针列还兼任 `def:同指针` 的解析目标 ⇒ **它必须指向代码，不能指向散文**。
2. **`性质` 决定冲突时谁赢**：`as-built` ⇒ 代码是事实，代码改了要改树；`contract` ⇒ 树是承诺，代码不符是**代码缺陷**。
   所以"接口以代码为准"这句话**只对 `as-built` 成立**——当成通用规则就无法裁决，那正是"一句话两个权威"的来源。

其余 9 条（含「禁止造 `assert:`」「动过的分片整片补齐」等）在 [`writers-guide.md`](writers-guide.md)。
